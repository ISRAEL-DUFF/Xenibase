What Xenibase is

Xenibase is a Postgres platform that one company runs for many customers. A customer signs up, gets an organisation, and creates projects. A project is a Postgres database with a stable connection string. On the shared tier it is one database among hundreds in a shared cluster. On the dedicated tier it is a Postgres container of its own on a node, archived continuously with WAL-G, optionally with a standby on another node and read replicas. Around the databases sit backups and restores, branches, a SQL console and table editor, database webhooks and scheduled jobs, and since V4 a set of backend services that make a project usable straight from an app: a data API, project auth, file storage and realtime, served by xenibase-edge.

The product grew through five specifications, all at the repository root. V1 is the core: shared and dedicated tiers, the pooler, operations, backups and the operator UI. V2 added organisations, roles, API tokens, branches, webhooks and multi-tenant hardening. V3 and V3.1 added HA, the standby pooler, billing, the Free tier, regions and capacity automation. V4 and V4.1 added the backend services and the edge. docs/decisions.md records the choices made while building, milestone by milestone, and is the first place to look when the code and a spec disagree.

The binaries

Every directory in cmd/ is one command ( of them); five are released. The Makefile's build-go target builds them all with CGO_ENABLED=0, and release-check refuses a server or edge binary that links purego, so both stay static.

BinaryWhere it runsWhat it does
xenibase-serverThe control node, behind CaddyThe REST API and the embedded web UI, the operation workers, and about thirty background loops. It owns the metadata database (it runs the migrations at startup) and the pooler files. It also has offline modes: -gen-master-key, -rotate-master-key, admin and mail-preview.
xenibase-agentEvery node, including pooler hostsregister once with a one-time token, then run: an HTTPS service behind mutual TLS with a fixed set of commands (health, host metrics, dump, restore, copy, dedicated instances through Docker, pooler files and keepalived on pooler hosts). decrypt opens a backup with an exported key.
xenibase-edgeOne or more per regionThe backend services gateway at https://<ref>.<domain>. It is stateless: it follows xenibase-server's configuration feed, serves data, auth, storage and realtime, and reports usage back. Image transforms run in child processes (render-worker) with capped memory.
xenibase-statusAnother provider, on purposeThe public status page. It probes Xenibase from outside and takes signed heartbeats and incidents, so an outage cannot take down the page that announces it.
xenibaseDevelopers' machines and CIThe command-line tool: contexts, device login, and commands for organisations, projects, branches, SQL, backups and more, all through the public API with an API token.

The sixth, cmd/docsite, builds the documentation site from docs/ and fails on a broken link. It is a build tool, not a release binary.

What xenibase-server switches on

run in cmd/server/main.go builds each service in turn and hands them all to api.NewHandler. Much of it depends on configuration. Without XENIBASE_POOLER_CONFIG_DIR there is no pooler, and so no provisioning, backups, dedicated tier, branches, Free tier, backend services or webhooks; the server still serves accounts, organisations and billing.

Each service that does long work contributes operation kinds to one map, and a single jobs.Runner serves all of them:

Background loops are goroutines on a context that is cancelled only after the HTTP server has drained, so open Server-Sent Event streams end before shutdown waits on them and interrupted operations are requeued.

Risk

There is one edge secret for the whole platform, "the same everywhere" (backend services guide), and the feed returns every region's projects when the caller leaves region empty (EdgeConfig). A feed entry carries the project's edge login password and its request roles' passwords. So anyone holding the secret of any one edge node, including one created by capacity automation in a small region, can read the database logins of every project with backend services in every region. A per-edge or per-region secret, with the server fixing the region from the credential rather than the query, would contain a compromised edge to its region.

Where the outline moved a package

Three packages sit somewhere other than their names suggest. logical is not realtime: it moves a database between servers with logical replication, so it is on the HA and moves page. pgpstream encrypts backup objects as OpenPGP messages, so it is with backups. Realtime has no package of its own; it is part of edge (rthub.go, rtproto.go, rtbroadcast.go).

Spec and code differ

V1's technology table (V1 3.4) names the Docker Engine SDK for Go. The code has its own small client instead (internal/docker, covering images, volumes, containers and exec), so the module does not depend on Docker's SDK. The rest of the table holds.

Where the specs and the code disagree

These are the differences found in Part A. Each is explained where it matters.

  1. Database names are opaque (p_ and ten base32 letters), not V1's <slug>_<4 characters>. V2 §10.2 made the change; V1 projects keep their old name as a pooler alias. Life of a project
  2. The plaintext password is kept, sealed, in the create operation's parameters until it finishes, although V1 §5.3 says it is never stored reversibly (decision M1 #3). Life of a project
  3. A new shared project goes to the cluster with the fewest projects, not the one "with the most free capacity". Life of a project
  4. The smoke test through the poolers is skipped for a project with an IP allowlist. Life of a project
  5. The Docker Engine SDK is not used (above).
