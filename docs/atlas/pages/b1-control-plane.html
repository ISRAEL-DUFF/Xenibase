xenibase-server is one Go binary. It serves the REST API and the embedded web app, runs a pool of workers that execute operations from a table in the metadata database, writes the poolers' configuration, and runs a few dozen background loops. Nothing here is a separate service. Claims, schedules, migrations and pooler syncs all take Postgres locks, so two servers on one metadata database do not run the same operation or tick twice. follows one create through it. This page takes each part in turn.

How cmd/server starts

run does everything in a fixed order, and a failure before the listener opens stops the process:

  1. Read the environment (config.Load) and open the keyring from XENIBASE_MASTER_KEY plus any previous keys. -rotate-master-key re-encrypts every stored secret and exits here.
  2. Connect to the metadata database and run the migrations (). The server refuses a schema newer than it knows.
  3. Load the operator settings, build auth, mail and regions, then provisioning. setupProvisioning registers the shared cluster from XENIBASE_SHARED_ADMIN_URL if set, and returns nil when XENIBASE_POOLER_CONFIG_DIR is not set. Everything that needs projects (backups, dedicated instances, etcd, HA, the pooler hosts, tenancy) is built only when provisioning is.
  4. Each service contributes its operation kinds to one map, and one runner serves them all: jobs.NewRunner with XENIBASE_WORKERS slots (default 4).
  5. Build the HTTP handler and listen. Shutdown on SIGTERM drains HTTP for up to ShutdownTimeout (15 s), and stopping HTTP cancels the background context, which ends SSE streams and interrupts running operations.

Configuration is environment-only, read once. The one thing an operator edits at runtime that the provisioning path reads is the public database host, kept in the settings table and cached by settings.Store. Other services keep their own settings rows (mail, billing, capacity, costs, alerts, token expiry), with secrets inside sealed by the keyring.

The API and its guard

Routes are generated from api/openapi.yaml ( operations on paths) into a chi router. Every request under /api and /metrics first passes guard, which resolves the route pattern before routing so it can refuse early:

  1. Who. A bearer token becomes a token session, and the cookie is ignored. Otherwise the session cookie is looked up by its SHA-256.
  2. CSRF. A mutating request from a cookie session must carry the double-submit token, and its Origin, when sent, must name this host (checkCSRF). Program-to-program routes are listed in csrfExempt.
  3. A rule. The route must be in routeRules. A route with no rule is refused with 403, and TestEveryRouteDeclaresAnAction fails CI when the spec and the map disagree.
  4. Terms, then step-up. A browser session with new terms to accept gets terms_required, except on the few routes marked beforeTerms. Routes in reauthRequired (delete a project, turn on role management, transfer, refunds and others) need a password and code check in the last ten minutes. Tokens skip step-up and need the admin scope instead.
  5. Authorize. authorize finds the resource's organisation from the rule's scope, then asks authz.Can. A resource the caller may not know about answers 404, one they may see but not change answers 403. The resolved organisation, project and roles go into the request context for the handler.

Nested resources (/projects/{id}/replicas/{replica_id}, webhooks, jobs, saved queries) are found by the handler, which checks that the child belongs to the authorized project. The read replica handlers compare ProjectID after GetReadReplica, webhooks and saved queries query with project_id in the WHERE. That check is per handler, not structural, so every new nested route needs it.

Every mutating request, and a list of audited reads, writes one audit_log row after the handler returns (writeAudit), with the outcome taken from the status code and details the handler added.

Resolved

V1 says every mutating call writes an audit row (V1 7.5, and decision M2 #6). The row is still written after the handler returns, outside its transaction (the handlers call services that open their own), but an insert the database refuses is no longer only logged. auditlog.Writer keeps it in memory and retries it every 5 seconds, in order and with the request's time; up to 10,000 rows wait, and a row given up on (the buffer is full, or the server stops with the database still refusing) is logged in full. /metrics serves xenibase_audit_write_failures_total, _pending, _retried_total and _dropped_total from the process, so they work while the database is down. A crash still loses what is waiting (operations guide).

The operations queue

Every long action is a row in operations. A request inserts it, usually in the same transaction as the metadata change that needs it, and returns 202 with the operation. Workers claim it, run the kind's handler, and record the outcome. The dashboard follows it over Server-Sent Events.

The claim takes the oldest due row of a kind this worker knows, with SKIP LOCKED, so workers never block each other or take the same row:

A handler gets the operation and a StepLogger. Each log line is appended to the row only while this worker still holds it (locked_by, status = 'running'), and a line that matches no row returns ErrLeaseLost, so a handler that checks its log errors stops when it has lost the operation. The contract every handler signs:

Concurrency4Operations run at once per process (XENIBASE_WORKERS).

MaxAttempts, Timeout3, 30 minPer kind. Create: 3 and 45 min. Delete: 5. Import: 1 and 12 h.

After the handler returns, execute decides. If the heartbeat found the row taken, it writes nothing. Otherwise:

OnFail runs once, with its own two-minute budget, before the row is marked failed. Its error is logged and the operation fails either way. Succeed and fail both remove params.secrets, the sealed one-time password that create and rotate carry for their smoke test (decision M1 #3), and the API strips the same key from every operation it returns.

The stream (Streamer) sends log events numbered from one, status on changes and done at the end, and a client that reconnects with Last-Event-ID resumes after the last line it saw. The notifier holds one connection out of the pool for LISTEN, reconnects with backoff, and wakes every subscriber after a reconnect so nothing missed stays missed.

Risk: a restart can fail an operation that never ran its last attempt

On shutdown, an interrupted attempt is handed back with RetryOperation, which does not give the attempt back: attempts was incremented at the claim and stays. The next claim increments it again, and execute fails any operation whose count is past the limit before running the handler (attempts > maxAttempts), running its OnFail. So a deploy or restart during an operation's last attempt fails it with "gave up after N attempts". For the kinds with MaxAttempts: 1 any restart does: imports (12 h), restore tests, Supabase migrations, HA switchover, and moving a region's etcd (7 days), all of which then roll back or stop half-done. The upgrade guide says running operations are resumed by the new server. Decision M1 #10 counts crashes on purpose, to stop crash loops; a clean shutdown is not a crash. TestShutdownRequeues checks only the status. Fix: in the shutdown branch, requeue with attempts = attempts - 1 (a separate query), and assert the count in the test.

Risk: "gave up" rolls back work that finished

When a worker dies after the handler succeeded but before SucceedOperation commits (or that write fails: its error is only logged), the row is reclaimed. On the last attempt the next claim goes straight to fail without running the handler, so OnFail runs against completed work. rollbackCreate checks status = active and does nothing, but the operation reads failed. rollbackRotate restores the previous verifier, so the password the user was just shown stops working. Fix: on an over-limit claim, run the handler once more under its idempotence contract (it will find the work done) instead of failing blind, or record a "done" marker before the final write and check it.

Risk: the reclaim compares two clocks

locked_at is the database's now(), but the reclaim loop passes time.Now().Add(-LeaseTTL) from the worker's clock (reclaimLoop). A server whose clock runs more than 30 s ahead of the metadata database reclaims every running operation on every pass, and each is run again elsewhere while its first worker is still going. Fix: compute the cutoff in SQL, locked_at < now() - make_interval(secs => @ttl). The other lease weakness, a worker that cannot reach the metadata database and keeps running, is on .

One operation per project

Rotate, delete, settings changes, reclaim space, and most flows in other packages go through withIdleProject: lock the live project row FOR UPDATE, check its status is one the action allows, check ProjectHasActiveOperation, then enqueue in the same transaction. Two requests on one project serialize on the row lock, and the second sees the first's operation (decision M1 #7).

It is a convention, not a constraint. Nothing in the schema stops a second active operation, and some paths enqueue without the lock: RevokeCredentials queues drop_db_user directly, branch creation queues copy_branch_files, and the nightly scheduler checks "no operation in flight" in ProjectsDueForBackup without locking the project, so a backup and a delete requested in the same instant can both be queued. A kind that no running process registers stays queued forever and, through ProjectHasActiveOperation, blocks every exclusive action on its project.

Risk: a create whose rollback fails leaves an orphaned database and roles

rollbackCreate soft-deletes the project first, then calls teardown. OnFail runs once, and its error is only logged. If teardown fails, for example because the pooler sync fails with anything other than a reload error (it returns before dropping anything), or the shared cluster stops answering, the database, the owner role, the console and read-only roles stay on the shared cluster. The project row now has deleted_at set, so no delete can reach it, and for the shared tier nothing sweeps for databases or roles without a live project (the dedicated tier has ReapOrphans for instances). The roles keep their passwords: the owner can no longer log in through the pooler (no route), but a role on a shared cluster with a known verifier and CONNECT on a forgotten database is a standing liability, and the space is billed to no one. Fix: soft-delete only after a successful teardown, or queue a retrying drop_project_objects operation from OnFail; and add a sweep that compares pg_database/pg_roles on each shared instance with live projects.

Risk: a delete that fails after teardown cannot finish by itself

runDelete takes the final backup, tears down, drops automation, then soft-deletes. If an attempt fails or is interrupted after teardown (a DropAutomation or SoftDeleteProject error, a crash, a shutdown), the next attempt starts again with the final backup, of a database that no longer exists. Every remaining attempt fails, and failDelete leaves the project in error. Deleting again with the backup on fails the same way; only a delete with skip_final_backup finishes it. Fix: skip the final backup when the database (or dedicated instance) is already gone, or when this operation's log already has a successful final backup.

Personal logins

Each project member can have their own database login, <db>_u_<random> (IssueCredentials). A read/write login is a member of the owner role and switches to it on connect, so what it creates belongs to the project; a read-only one is a member of <db>_ro. Revoking deletes the metadata row, syncs the pooler, kills the login's pooled clients and drops the role, queueing drop_db_user when the instance does not answer.

The order in IssueCredentials is instance first, metadata second. If the metadata write fails after CREATE ROLE, the role stays on the instance with a password no one has, and teardown, which drops only the logins it finds in project_db_users, never removes it.

Dedicated projects: role management and connection ceilings

Release 4.2.4 lets a dedicated project's owner create roles, so an application whose migrations run CREATE ROLE works unchanged. SetManageRoles (organisation owners, after step-up) refuses the shared tier and Postgres before 16, writes projects.manage_roles, and gives the owner CREATEROLE (OwnerCreateRole). Postgres 16 limits CREATEROLE to roles the creator holds ADMIN on and never lets it grant SUPERUSER, REPLICATION or BYPASSRLS.

The poolers accept only logins Xenibase knows, so every 30 seconds SyncOwnedRoles reads the roles the owner administers, caps their connection limit at the project's, grants CONNECT, and records each syncable login and its verifier in project_owned_logins. A login is syncable when it is named <db>_… (each region's pooler auth file is one namespace), is not one of Xenibase's names, has no elevated attribute and has a SCRAM password. When the set changed it rewrites the rows in one transaction and syncs the poolers. Moves and major upgrades recreate the owner's roles on the target before the copy (restoreOwnedRoles).

A dedicated instance's max_connections now grows with memory instead of being 100 for every size, and is stored per instance (migration 00060). A project's connection limit can go up to the instance's ceiling less ten reserved slots, and ensureRole clamps it again on every run so a move to a smaller size cannot leave it too high. A restore's instance never gets fewer than its source, because a standby will not replay WAL from a server that allowed more.

Read replicas got per-replica standby settings (hot_standby_feedback, and one delay for both max_standby_*_delay settings). PATCH /projects/{id}/replicas/{replica_id} checks the replica belongs to the project, stores them, and on a streaming replica applies them with ALTER SYSTEM and a reload, recording when they were last confirmed (UpdateReplicaSettings).

Risk: role management is switched outside the project lock

SetManageRoles is not an operation and does not use withIdleProject. It writes the flag first and runs ALTER ROLE … CREATEROLE second, so if the instance refuses, metadata and instance disagree until something next runs ensureRole. And an apply_settings, move or restore that loaded the project before the switch runs ensureRole with the old flag and undoes it. Turning it off after a failed ALTER ROLE leaves the owner with CREATEROLE while the dashboard says off. Fix: run it through EnqueueExclusive as a small operation, or at least take the project row lock and alter the role before committing the flag.

The SQL console and query insights

Console sessions connect straight to the instance, not through the poolers, as <db>_console: a login with no privileges of its own, granted the owner role and <db>_ro WITH INHERIT FALSE, SET TRUE. Each submission opens a session, runs SET ROLE to the owner (or, for a read-only member, to <db>_ro), sets the statement and lock timeouts, and closes afterwards (connect). Read-only mode runs one statement inside BEGIN READ ONLY; SELECT 1, so the snapshot is taken and the transaction cannot be switched back to read-write. Results are capped at 1,000 rows and cells at 64 KiB. The audit row records that the console ran and the error code, never the SQL.

Risk: a read-only member can read as the owner

A read-only project member's console session is still logged in as <db>_console, which may SET ROLE to the owner. The statement they send can switch role and read in one go: SELECT set_config('role', '<owner>', true), query_to_xml('SELECT * FROM t', true, false, ''). Permission checks for the inner query run at its own start, as the owner. Checked against Postgres 16 with the same grants: rows hidden from <db>_ro by row-level security, and a table not granted to it, were both returned. Writes still fail, because the transaction is read-only. So a read_only member, or a read-scope token that the API sends down this path, reads everything the owner can, including tables an application protects with RLS (the owner bypasses RLS on its own tables). The table browser's raw filter runs in the same kind of session, and ValidateWhere checks its shape, not what it calls, so it is a second way in. Fix: give read-only sessions their own login, granted only <db>_ro, so there is no role to switch to; or grant the owner to the console login WITH SET FALSE for those sessions. Add the statement above to the isolation tests.

Query insights (insights) snapshot pg_stat_statements as the instance admin, keep each project's own rows as per-project deltas in query_stats and query_texts, and serve top queries, EXPLAIN, slow queries, index suggestions, bloat and locks. Tenants never query the view on a shared cluster, because the admin's copy is filtered by database before it is stored. Console sessions are tagged so their queries are not counted.

Operations in the API

GET /operations lists an organisation's operations, limited for members to the projects they belong to and for a project-restricted token to its projects (visibleProjects, which fails closed). ?platform=true lists platform work, for platform admins. GET /operations/{id} and its stream need project.view on the operation's project. The response carries the parameters, minus secrets, and the whole step log.

Risk (low): rotate operations keep both SCRAM verifiers

A rotate's parameters are verifier and previous_verifier, the owner's new and old SCRAM verifiers, in the clear. Only secrets is scrubbed, so they stay in the row forever and are returned to anyone with project.view, which includes read_only members. A verifier is not the password, but it lets its holder impersonate the server to a client and recover the client key from one observed login. Fix: put both verifiers under secrets, or read the previous one from projects in the rollback and keep only a hash in params.
