What a node is

A node is a machine that xenibase-server sends work to. Each runs xenibase-agent, which is the only thing on the machine the control plane talks to. The control plane never logs in over SSH and never runs a shell command it composed. It calls a fixed HTTPS API on the agent, and the agent turns each call into Docker API requests, pg_dump/pg_restore processes, or file writes.

A node row has a role, set when an operator adds it (CreateNode):

RoleWhat runs thereCan change to
shared, dedicated, bothPostgres: a shared cluster, dedicated instance containers, or both. Which of these new projects may be placed on.Each other (SetRole)
poolerThe two PgBouncers, keepalived, and the agent in pooler mode (pooler hosts)Nothing: remove it and add the machine again
edgexenibase-edge beside the agent, never a database (V4.1 §11)Nothing

A node also has a region (the home region when none is given) and an optional failure domain, which HA, etcd and pooler placement use to keep pairs apart.

How a node joins

  1. The operator adds the node. POST /api/v1/nodes (Admin → Nodes → Add node) inserts the row and returns a one-time registration token, xbreg_ and 24 random bytes. Only its SHA-256 is stored, with an expiry a day later (newToken). NewToken issues a fresh one for an existing node, replacing any earlier token.
  2. The agent registers. xenibase-agent register --server … --token …, or the first run when no state exists yet, which retries up to 30 times two seconds apart. agentsvc.Register makes a P-256 key and a certificate request (NewCSR) and posts it with the token and the address the server should dial (--advertise, default the hostname and port 7070) to POST /api/v1/agent/register. That route has no session. The token in the body authenticates, and the route is rate limited per IP (RegisterAgent). The agent checks the server's HTTPS certificate against the system roots or --server-ca.
  3. The server signs and pins. In one transaction, nodes.Register finds the node by the token's hash (unexpired, row locked), signs the CSR for that node, and records the certificate's SHA-256 fingerprint, the advertised host and port, and the agent version. The token is cleared in the same statement, so it works once.
  4. The agent saves its state: agent.key, agent.crt, the CA certificate and node.json, each 0600 in a 0700 directory (/var/lib/xenibase-agent). From then on run loads that state and listens.

The bootstrap token

The install bundle's own agent registers the local node without an operator. XENIBASE_AGENT_BOOTSTRAP_TOKEN (at least 24 characters) is given to both the server and that agent, and the agent sends it with --node local. The server compares it in constant time, and accepts it only for the bundle's local node (XENIBASE_SHARED_NODE_NAME, default local), only while that node has never had an agent and is not removed, and only once: the registration records agent_bootstrap_used in settings, under an advisory lock. Re-registering needs a token from the UI.

Resolved

The bootstrap token never expires, and it used to claim any node without a pinned certificate by name: a machine just added whose own agent had not registered yet (so a hostile agent could take its identity and receive its instance specs and their passwords), or a removed node, which CompleteNodeRegistration brought back as healthy. It is now bound to the local node, refused for a removed node, and single use (TestBootstrapToken, TestBootstrapTokenBound).

Machines Xenibase creates

Capacity automation (V3 §5.1) creates machines through cloud.Provider: Hetzner Cloud (hetzner.go), or manual, which has no API and returns ErrManual. The new server joins by itself with the same one-time token, carried in its cloud-init document (cloud.Bootstrap). That document installs Docker, turns off SSH passwords, sets ufw to deny incoming traffic except SSH and the private network, and starts the agent with the Docker socket mounted. On an edge node it also starts xenibase-edge and opens 8443. Every value that reaches a shell line is checked first by Validate: names, CIDRs and image references against patterns, and the token and edge secret refused if they hold spaces, quotes, $, backslashes or backticks. YAML strings are JSON-quoted.

Note

The cloud-init document is the server's user data, so the registration token and, on an edge node, its edge credential stay readable from the provider's metadata service by anything on that machine. The registration token is spent within minutes. An edge node's credential is not, but it unlocks only its own region's feed (see the edge).

The agent's identity and certificates

internal/agentca is a private CA that lives in the metadata database. LoadOrCreate creates it on first start under an advisory lock, so two servers starting together make one CA, and stores the private key sealed with the master key (associated data settings.agent_ca.key). It is P-256, valid for 20 years, and may sign only end-entity certificates (MaxPathLenZero). There are three kinds of certificate:

The CSR's own subject is ignored. The server writes the node's UUID into the certificate, so an agent cannot ask for another node's name. SignAgent checks the CSR's signature, which proves the agent holds the key.

Both directions of the handshake

The server always dials the agent; the agent never calls the server after registering. When the server dials, dial trusts only the agent CA, requires TLS 1.3, and then checks two more things the CA alone would not give:

The pin means a stolen copy of the CA key is not enough to stand in for a registered agent: the impostor would also need the node's own certificate. The subject check stops one node's genuine certificate being used at another node's address. Revocation is the pin: re-registering replaces the fingerprint, and RemoveNode (refused while any instance is live on the node) clears it. There is no CRL.

On the agent, agentsvc.TLSConfig requires a client certificate from the pinned CA, TLS 1.3, and the subject xenibase-server. Go's own check also requires the client-auth key usage. Agent certificates are server-auth only, so one agent cannot call another even though the same CA signed both. An overlay test written for this page confirmed both refusals: a client certificate named xenibase-server with server-auth usage fails with "incompatible key usage", and a client-auth certificate with another name fails the subject check.

Spec and code differ

The V1 spec (§3.3) says the server "issues each agent a client certificate at registration". Agents get server certificates. The client certificate is the server's, and every agent accepts any unexpired one the CA signed with that subject. There is no per-server identity: a copy of any server's client certificate commands every agent until it expires.

Resolved

The server's client certificate used to be issued once, in nodes.NewService, and kept for the life of the process, so a xenibase-server that ran for more than 30 days without a restart lost every agent at once. Every handshake now asks clientCerts.get (through tls.Config.GetClientCertificate), which reissues it when 7 days or less are left and keeps the current one if that fails. The alerts loop asks too, so it renews on an idle server, and the agent_client_cert alert fires when under 3 days are left. TestClientCertRenewed reaches an agent with a certificate issued 40 days ago.

What the control plane can make an agent do

The whole API is the mux in Service.Handler, with paths and bodies defined in internal/agentapi. nodes.Agent has one method per path.

PathWhat the agent does
GET /v1/health, GET /v1/host/metricsReports its version, node ID, tool versions and whether Docker answers. Reads load, memory, disk, CPU ticks and disk I/O from /proc and statfs.
POST /v1/dumppg_dump -Fc of a database, encrypted as it streams (Xenibase's own format, or OpenPGP to a project's own key), uploaded to S3. No temporary file. If pg_dump fails after the upload looks complete, the object is deleted.
POST /v1/restoreDownloads an object, decrypts it, pipes it into pg_restore: owned by the project's owner, single transaction, stop at the first error, unless the request allows errors (imports).
POST /v1/copypg_dump piped into pg_restore with nothing in between: imports from an outside database.
POST /v1/instances, GET/DELETE /v1/instances/{id}, …/start, …/stopCreates, idempotently, a Postgres container with its volume. With restore it first fills the volume from a WAL-G base backup and recovers, to a time if one is given. With recreate it swaps the container and keeps the volume (a minor-version upgrade). With patroni it runs the instance as an HA member. Reads, starts, stops and destroys containers.
POST …/walg/backup, GET …/walg/backupswal-g backup-push inside the container, then delete retain FULL n. Lists base backups.
PUT/GET/DELETE /v1/etcd, GET /v1/etcd/address, POST /v1/etcd/membersRuns, inspects or removes this node's etcd member, and lists, adds or removes cluster members through it (V3.1 §3.2).

Request bodies are capped at 1 MiB (64 MiB for a pooler bundle, which carries every login's verifier). Dumps, restores, copies and base backups share MaxJobs slots, two by default (acquire). A further request waits for a slot until its own context ends.

Why a command cannot become a shell

The agent takes values, never command lines, and each value reaches a process as an argument or an environment variable:

  • Connections reach pg_dump and pg_restore as PGHOST, PGUSER, PGPASSWORD and the rest (pgEnv), so passwords never appear in ps. Schema filters are single --schema=… arguments (dumpArgs), so a value starting with - cannot become a flag. Child processes get SIGKILL if the agent dies (Pdeathsig).
  • Instance IDs must be UUIDs (instanceID). Container and volume names are made from them.
  • Postgres settings become -c name=value arguments to postgres, with names limited to [a-z_][a-z0-9_.]* and values without NUL or newline (settingName). The settings come from the server's size profiles and replica settings, never from a customer.
  • The few shell scripts are constants. Their variable parts come in through the exec environment: the move rules, the recovery settings, the backup name (checked against ^(LATEST|base_…)$). The one file a script sources, the recovery source's WAL-G settings, is written by shellExports with every value single-quoted.
  • etcd membership takes a peer URL that must start with https:// and a numeric member ID, sent as JSON to etcd's gateway.
  • Docker is reached through docker.New: the Engine API over the Unix socket (or tcp://, unencrypted), at API version 1.43 or the daemon's minimum if that is higher. It has no SDK dependencies.

So what the control plane can do to a node is bounded by this API, not by what a shell could do. But that bound is wide. The agent runs as root with the Docker socket, and creates containers from whatever image and settings the server sends. Whoever holds the server's client certificate effectively has root on every node.

Resolved

An import's source address was not checked, which defeated IP allowlists: connectSource and the agent's /v1/copy connected to any host, from addresses every cluster's pg_hba.conf trusts, so a project's owner password got a full copy past its allowlist, and the path probed the private network. The source now goes through outbound.CheckSource: public addresses only unless the platform admin allow-listed the host for the organisation, and never loopback, link-local, a node's or instance's own address, XENIBASE_OUTBOUND_BLOCK or (with machines Xenibase creates) the cloud private network, allow-listed or not. pgsource.Config refuses a URL whose settings name another host (host=, several hosts, a socket directory) and pins the connection to the checked address: pgx resolves every name to it, and the agent's copy gets it as hostaddr. The import checks again just before the copy, and Supabase migrations take the same path.

How commands are authenticated and authorised

Authentication is the TLS handshake and nothing else: no token, no request signature, no per-request check. Authorisation is all or nothing. Once a client presents a valid xenibase-server certificate, every path is open, and the agent does not know which project or operation a call is for. Each request is decided in the control plane. The operation that calls the agent has already been authorised against the caller's organisation role (see Security), and the agent trusts the server's decision.

The server also refuses to send work to an agent it does not trust to understand it. agentFor checks the version the agent last reported against the server's (Compatible): the same major, and a minor no older than the server's. Development builds match anything. Health checks use dial without the version check, so an agent that needs upgrading still reports in.

Pooler hosts add a second listener: an unauthenticated HTTP API on a loopback address for keepalived's check script and notify calls (LocalHandler). ServeLocal refuses any address that is not loopback. Any local process can mark the host MASTER and so make xenibase-server move the floating IP to it.

Instances through Docker

instances.Create holds a per-instance lock and is idempotent. If the container exists it is started and waited for. Otherwise it pulls the image if missing. The image name is a template with {major}, default xenibase-postgres:{major}-walg3.0.9. It then creates the volume xenibase-<id>, optionally restores into it in a one-off container, and starts postgres with hard CPU and memory limits, shm sized from memory, SIGINT as the stop signal, and restart unless-stopped. It finally checks that the running major is the one asked for (postgres -V). PGDATA is always set inside the volume, because older images declare an anonymous volume that a recreate would lose.

Network logins are limited at initdb to XENIBASE_AGENT_DB_ALLOW, which defaults to every private range and 127.0.0.1 (defaultDBAllow), with SCRAM. On every start the agent appends, once, rules that let only xenibase_move_<hex> logins in from XENIBASE_AGENT_MOVE_ALLOW for logical-replication moves, and reloads (ensureMoveHBA). Instances are reached by container name on the agent's Docker network, or on a port published on the node's private address.

Note

A project's IP allowlist is enforced at the poolers, not here. Anything that can reach a node's private address with a project's password connects to its instance directly. On the dedicated tier that includes another customer's postgres_fdw, which is allowed there.

Resolved

dial used to build a new http.Transport for every agentFor call: a full TLS 1.3 handshake per call, and about twenty idle connections left open on each pooler host by the 3-second arbiter. It now keeps one client per node (agentClients), keyed by the agent's address and pinned fingerprint; a change to either replaces the client and closes its idle connections, so a re-registered agent's new pin applies at the next call. The configuration (agentTLS) reads the server's client certificate in GetClientCertificate at each handshake, so a cached transport doesn't freeze it. TestAgentConnectionsAreReused counts one connection for five calls.
