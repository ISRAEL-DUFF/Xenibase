Everything the control plane knows is in one Postgres database, separate from the clusters that hold customers' data: who the users and organisations are, where each project lives, the operations queue, backups, billing, the audit log and the settings. Customer rows never land here, apart from the query texts that query insights and the session reaper keep. Ids are random UUIDs (gen_random_uuid()), times are timestamptz, and money is integer minor units with a currency code.

Projects, instances and nodes

A nodes row is a machine with an agent; an instances row is a Postgres server on it, either the node's shared cluster (one per node) or a dedicated container; a projects row is one database on one instance. The project row is the one the rest of the system reads most:

How organisations are kept apart

There is no row-level security in the metadata database. The application connects as one role that owns every table, and tenancy is enforced by the API guard () and by the queries. Tables that belong to an organisation carry org_id, including child tables where it could be derived (project_members, project_db_users, saved_queries, reaped_sessions, usage_records, audit_log), so a query can scope itself without a join.

Queries live in internal/store/queries and sqlc turns them into typed Go in internal/store (sqlc.yaml; make generate, and CI fails on a diff). Each query either filters by org_id or says why it may not, in a comment the lint reads:

TestTenantQueriesAreScoped splits every query file on -- name:, and for each query that reads or writes a tenant table requires either an org_id predicate or a -- tenant: system - <reason> line of more than ten characters. A tenant table is any table the migrations leave with an org_id or project_id column (migratedColumns replays them; TestTenantTablesMatchTheSchema checks the result against a migrated database). A predicate is org_id compared with a parameter, a list or NULL in a WHERE, ON or HAVING clause, or org_id among an INSERT's columns.

Spec and code differ

V2 says every sqlc query on a tenant table takes org_id and filters by it, as defence in depth even when the handler has checked (V2 2.6). In the code the opt-out is the common case: about 600 of the 850 queries carry tenant: system, most of them "a project the request already authorized". For those the only check is the guard and the handler.

Resolved

The lint was weaker than it read: its list of tenant tables was fixed in the test and predated backend services (project_api_keys, project_jwt_keys, project_services, read_replicas, auth_*, instance_members and others were missing), and any occurrence of org_id passed, including SELECT org_id, SET org_id = … or a join. It now reads the tables from the migrations and requires a real predicate. That caught 25 queries, all of them platform or worker queries on instances, storage_targets, region_early_access, device_auth_requests and the user's own memberships; each now says why in its tenant: system line, and the platform storage-target queries pass on org_id IS NULL.

The schema ties a child's org_id to its project's. projects has UNIQUE (id, org_id), and the six tables that carry both (project_members, project_db_users, saved_queries, reaped_sessions, editor_preferences, dedicated_requests) have FOREIGN KEY (project_id, org_id) REFERENCES projects (id, org_id) ON UPDATE CASCADE (00068). Nothing checks that a project member belongs to the organisation; the handlers do. audit_log and usage_records keep the organisation of the time and have no key.

Resolved

Nothing used to tie a child's org_id to its project's, and orgs.Transfer moved members, logins and saved queries by hand, leaving reaped_sessions, editor_preferences and dedicated_requests under the old organisation. Now the transfer updates the project and the keys carry every child with it (saved-query favourites, which have no project_id, are moved explicitly), and a copy under another organisation is refused. 00068 puts right the rows earlier transfers left behind and adds the keys NOT VALID; 00069 validates them in a transaction of its own. TestTransferMovesEveryChild and TestProjectOrgKeysOnLiveData cover it.

Each log line rewrites the row (log = log || jsonb_build_array(…)), and finished operations are never deleted, so the table and its TOAST grow for the life of the install.

What is sealed, hashed, or in the clear

Secrets the control plane must read back are sealed with the master key: AES-256-GCM, a key id in the header so old keys keep working after a rotation, and associated data that names the column and row ("nodes.pg_admin_secret:" + id), so a sealed value copied into another row does not open (Keyring.Encrypt). Secrets it only needs to check are hashed.

Risk (high): rotating the master key skips most sealed columns

xenibase-server -rotate-master-key re-encrypts what rotate.collect lists: TOTP secrets, recovery codes, storage credentials, node and instance admin credentials, project signing keys, the operation password handoff, and five settings blobs. It does not list backup_keys.key_enc, instances.patroni_secret, webhooks.secret_enc, previous_secret_enc and headers_enc, scheduled_jobs.spec_enc, project_auth_config.providers_enc, auth_message_outbox.message_enc, device_auth_requests.sealed_token, or the etcd CA key in the etcd_ca setting. Its verify step checks only what it collected, so it reports success. The documented procedure then replaces the key in .env with the new one alone. From the next start every value above fails to open: per-project backup keys (so those projects' backups and WAL archives can no longer be decrypted or written), HA instances' Patroni and replication passwords, every webhook signature and stored header, every scheduled job, every project's auth SMTP settings and queued messages, and the etcd CA. Nothing warns until each feature is used. Fix: add every sealed column to collect, and add a test that finds every keyring.Encrypt call site's AAD prefix in rotate (or that seals one row of each kind, rotates, and opens them with the new key alone). Until then, keep the old key in XENIBASE_MASTER_KEY_PREVIOUS after a rotation.

The audit log and settings

audit_log has the actor (user or token, or the system), the organisation and project, the action, target, details, address, user agent and outcome. Migration 00009 makes it append-only with triggers that refuse UPDATE, DELETE and TRUNCATE:

Resolved

The migration used to say rows can never be changed "even by xenibase-server itself". The server connects as the role that ran the migrations and owns the table (in the Compose bundle, the metadata database's superuser), so it can ALTER TABLE audit_log DISABLE TRIGGER or drop it. The claim is corrected rather than the gap closed: the migration's comment and the security review now say the triggers stop mistakes and injection through the server's queries, not a compromised server, and TestAuditLogIsAppendOnly pins both halves. A separate migration owner and a runtime role with only SELECT, INSERT on audit_log was not done: there is one database URL, and the split would change every install's roles and its upgrade.

settings is a key/value table of JSON. Each service owns its keys (db_host, mail, billing, capacity, alerts, backup_key, agent_ca, etcd_ca and others), and secret fields inside are sealed blobs, as V1 §9 asks.

When the reaper ends a long statement it records the statement's text (truncated) in reaped_sessions. Statements carry literals, so this is customer data, and it is kept with no limit, after the project and even the organisation are deleted, because both are soft deletes and the table's cascade never fires. The same holds for step logs in operations. Fix: prune reaped_sessions (30 days, like slow queries) and drop it with the project; prune finished operations after a set time, keeping a summary row if the history matters.

How migrations run

Migrations are plain SQL files embedded in the binary and applied by goose when the server starts, before it serves anything (store.MigrateTo). A Postgres session advisory lock serializes servers that start together. Each file runs in its own transaction, so a failed migration leaves the previous version. A server refuses to start on a schema newer than the newest migration it carries (refuseNewerSchema), because running there could write rows that break constraints it does not know. Each file has a Down section, used only by tests that load data at an older version. Rolling back in production means restoring the metadata backup taken before the upgrade.

A few migrations change data as well as shape: 00010 turns operators into users and moves every V1 project into its owner's personal organisation, 00018 queues an apply_settings for every active shared project, and several add plan limits to quota_plans. sqlc expands SELECT * into named columns at generation time, so adding a column never breaks a running binary's queries.

The recent migrations are safe to run on a live install. They add columns with constant defaults (no table rewrite) and small indexes, and the tables they touch have one row per project, instance or region. Adding a column with a CHECK still scans the table under an exclusive lock, which is fine at these sizes.

Risk (low): some releases cannot run old and new side by side

The upgrade is "stop, migrate, start" in practice, and the guide does it that way for one server with Compose. But nothing stops an older server that is already running when a newer one migrates (the newer-schema check runs only at start), and some migrations remove what older binaries use: 00038 renames auth_email_outbox, 00052 drops payment_methods and a billing_accounts column, 00025 drops a column. An install with more than one control-plane server, or a rolling restart, then has the old server's queries fail until it is replaced. Fix: split removals into a later release (expand, then contract), or have each server check the schema version periodically and stop taking work when it is newer than its own.
