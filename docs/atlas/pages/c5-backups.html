Shared projects get a nightly pg_dump, encrypted on the node and streamed to S3. Dedicated projects archive WAL continuously with WAL-G and take a daily base backup, so they can be recovered to any second in their window. Both run as operations () carried out by the agent that holds the data (), so plaintext never passes through xenibase-server. Imports reuse the same machinery.

What a backup is

Each backup is a backups row (target, operation, wrapped file key or project key, size, SHA-256 of the encrypted object) and, except for base backups, one object. objectKey names it projects/<id>/<kind>/<time>-<hex>.dump.enc, or .dump.gpg under a project's own key, relative to the target's prefix.

Scheduling

backup.Service.Run ticks every minute on every server. Schedule:

  1. Returns at once without a default storage target or the platform backup key.
  2. Takes pg_try_advisory_xact_lock(hashtext('xenibase_backup_scheduler')), so several servers never queue twice.
  3. Lists due projects. The window opens at XENIBASE_BACKUP_HOUR UTC (default 2); each project is due at a stable offset into it, an FNV hash of its ID modulo XENIBASE_BACKUP_JITTER (default 2 h).
  4. Queues each through EnqueueIfIdleTx, which locks the project, rechecks it is active, and skips it if any operation is pending, so a backup never interleaves with a restore or delete. Shared projects get backup, dedicated ones base_backup.
  5. Queues a storage_switch for any dedicated project archiving somewhere other than where its backups now go, the metadata backup once per window, and the restore test once seven days have passed.

"Already done" is any backup or base_backup operation since the window opened, whatever its outcome: a nightly backup that fails its three attempts waits for the next night, and the alerts report it. Hourly, Run also deletes backups past their expires_at, fails rows whose operation ended while they were running (SweepStaleBackups) and deletes failed rows' leftover objects. Every five minutes it makes cross-region copies.

Taking a logical backup

runBackup first looks for a backup an earlier attempt of the same operation finished (BackupForOperation), so a retry never takes a second one. dumpTo then resolves the target and sealing (sealing: a fresh file key wrapped by the platform key, or the project key's OpenPGP public key), fails rows an earlier attempt left running, inserts a new row and calls the agent. doDump pipes pg_dump --format=custom through the encrypter and a SHA-256 into a multipart upload, without touching the disk. Last, retention runs over the project's logical backups; its failure is only a warning.

A failing pg_dump closes the upload's pipe with its error, so the multipart upload aborts; if it already looked complete, the agent deletes the object. An upload the bucket completes after the attempt gave up is caught by cleanFailed, which deletes failed rows' objects before every dump and hourly.

BackupNow queues the same operation (a base backup on a dedicated project). On a platform target it counts against backup_storage_mb and is refused past it; nightly backups still run.

Retention and expiry

Retention.Expired keeps the newest backup of each of the Daily most recent UTC days that have one, the newest of each of the next Weekly ISO weeks, and always the newest. Counting days that have a backup means failed nights never shorten the history. Policies are standard 7 + 4 (also the metadata backups), and the billed add-ons extended 30 + 12 and long 30 + 52 (V4.1 §4.2).

applyRetention runs only after a successful backup of the project. deleteObject removes the object, its cross-region copy, and the original a switch copied it from. Final and safety backups carry an expires_at instead, as do a deleted project's nightly and archive backups on platform storage, and deleting an organisation re-dates all of them to 30 days after (ExpireOrgFinalBackups).

Resolved

A deleted project's nightly backups used to stay for good: retention runs only in the project's next runBackup, which a deleted project never gets, its logical rows had no expires_at, and runDelete and the organisation sweep touched only the final backup, so up to 11 copies of the database (82 with the long add-on) stayed on platform storage, listed and restorable, against V2 §10.10 and the terms template. Now runDelete soft-deletes the project and, in the same transaction, gives its logical and archive rows on platform targets the final backup's expiry, or 30 days without one (ExpireDeletedProjectBackups); finishing an organisation's deletion re-dates them with its final backups. The hourly expiry now also takes copied originals, so deleteObject removes each object, its cross-region copy and the row. Backups in an organisation's own bucket are left alone. Migration 00075 dates those of projects already deleted, at least a week after the upgrade (TestDeleteExpiresEarlierBackups, TestExpiryRemovesDeletedProjectBackups, TestOrgDeletionExpiresBackups, TestDeletedProjectBackupsMigration).

Encryption and keys

Project key (32 bytes)backup_keys.key_enc sealed with the master key, and the file its admin may downloadThe project's .dump.gpg objects and WAL-G archive

GenerateKey refuses to replace the platform key, which would orphan every backup. ConfirmKey wants the whole key pasted back, compared in constant time. The control plane unwraps a file key and sends the agent only that.

The writer holds a full buffer back until more data arrives, so the final chunk is always the one Close writes, and the reader reads a chunk ahead to know which one must carry the final flag (Reader.Read). A cut at a chunk boundary fails on the flag. Each chunk is authenticated before its plaintext is passed on.

A project key lets an organisation restore with standard tools (V2 §6.3). pgpstream writes plain OpenPGP: SEIPD v1 with MDC, AES-256, no compression. Its integrity check comes at the end, so the agent's restore reports a decryption error even after pg_restore succeeded (doRestore), and the operation rolls back. The OpenPGP keys are never stored: deriveKey feeds 4 KiB of HKDF output as the random source to openpgp.NewEntity, with a fixed creation time, for PGPKey (WAL-G, from the platform key) and ProjectPGPKey. EnableProjectKey creates or rotates a project key (old backups keep theirs); ProjectKeyFile gives a README and the armored private key, behind re-authentication and the audit log.

Risk

Nothing pins the derived OpenPGP keys. The key is whatever go-crypto builds from the seeded reader. A version that reads its random source differently, or changes a default in the key packet, derives a different key from the same secret, and every WAL-G archive and .dump.gpg object becomes unreadable through Xenibase, unnoticed until a restore. TestPGPKeyDeterministicAndUsable only compares two derivations in one build. Fix: a golden test that derives from a fixed secret and checks the fingerprint against a constant.

Where backups go

PlacementFor picks the project's chosen target (a platform target or its organisation's own bucket), else its region's, else the platform default; a data-residency project only targets marked as in its region. SaveTarget saves a target only after a live write, read, list and delete, never at another live target's endpoint, bucket and prefix, and DeleteTarget refuses one in use, or holding backups unless the loss is accepted.

  • Cross-region copies (V3 §2.5): CopyRegionBackups copies logical backups on platform targets to the region's copy target under the same key, checking the SHA-256 while streaming and again by reading the copy back. Residency projects copy only within their region, and SetResidency deletes copies outside it.
  • Switching target (V2 §6.2): SwitchTarget is immediate on a shared project. A dedicated project gets a storage_switch that points WAL-G at a new prefix, restarts the instance and takes a base backup (reconfigureArchive). copy_existing copies logical backups as twin rows verified by checksum (copyBackup); delete_originals then removes the originals.
Resolved

Two targets at one location used to turn "copy, then delete the original" into "delete the only copy": only names were unique, so two rows could name the same endpoint, bucket and prefix (and backups and backups/ give the same keys, Target.Key). Copies keep the object key, so a switch between them with delete_originals overwrote each object with itself, passed the read-back, and deleteOriginal deleted it; turning residency on did the same through deleteCopy when a region's copy target was its primary. Now SaveTarget refuses, with a 409, a target whose Location (endpoint without case, default port or trailing slash; bucket; prefix as Key applies it) is another live target's, naming it only within the same organisation or the platform. For rows saved before, copyBackup and the cross-region copyObject refuse a destination at the source's location (a switch logs and skips such a backup), deleteOriginal deletes an original only once a verified copy is at another location, and deleteCopy leaves a "copy" at the primary's location alone (TestSaveTargetRefusesATakenLocation, TestCopyBetweenTargetsAtOnePlaceIsRefused, TestLocation).

Restores

POST /backups/{id}/restore needs BackupCreate on the backup's organisation. backup.Restore accepts any succeeded project backup; a base backup becomes a recovery to the moment it finished. RestoreInto has the agent pipe the decrypted object into pg_restore --no-owner --no-acl --role=<owner> --single-transaction --exit-on-error as the project's console login, never the superuser, because a dump's functions run during a restore (restoreArgs). Webhook triggers are reset from Xenibase's configuration with an empty outbox (V2 §9.3).

  • Into a new project (the default): a project in the source's organisation, region and residency, created as a restore operation; the source may already be deleted. runRestore recreates the database empty on a retry, restores and publishes. Failure rolls the project back.
  • In place: the project admin role, re-authentication and the project's exact name. The project moves to restoring; a safety backup is taken (once per operation), the pooler KILLs clients while new ones wait, the database is recreated and restored, members' grants are re-applied (SyncMemberRoles), and the route resumes.

GET /backups/{id}/download (ProjectExport, two at a time per organisation) streams a logical backup decrypted in xenibase-server as a plain pg_dump archive (Export).

Risk

A decryption that fails half-way can look like a complete file. Once DownloadBackup has written a byte, an error is only logged and the handler returns, so Go ends the chunked response cleanly and the client reports a good download of a truncated archive. The runbook's xenibase-agent decrypt … > metadata.dump has the same gap: it promises a damaged object "fails without writing a partial file", which holds only with --out (decrypt removes its own file), and the next line restores whatever was written. Fix: panic(http.ErrAbortHandler) on a mid-stream error, and use --out with && in the runbook.

The weekly restore test

runRestoreTest picks a random active, unarchived project with a succeeded logical backup, and verifyRestore restores its newest logical, final or safety backup into xenibase_restore_test_<hex> on the project's own instance, owned by its owner and restored as its console login. It counts every table (TableCounts) and drops the database. Weekly runs alternate between a point-in-time recovery and a logical backup, and the logical runs between a backup's primary object and its cross-region copy (nextRestoreTest); the scheduler passes over a turn with nothing to test. On the point-in-time turn, or when a platform admin runs one now for a dedicated project, runPITRTest picks a random running dedicated project with a base backup, and ScratchPITR recovers it to now as a point-in-time restore would (flush, newest base backup, WAL from the archive, promote), but into a smallest-profile container on the source's node, named by the operation's ID, that no project uses, no pooler routes to and that archives nothing; it then counts every table of the project's database there as the superuser, and destroys the container. It wants twice the instance's databases free on the node, plus 1 GiB. A failure raises the critical restore_test_failed alert.

Spec and code differ

V1 §6.5's weekly job restores "the latest backup of a random project"; the logical turns restore a logical, final or safety backup, and every other week a dedicated project's base backup and WAL instead, so a given project's backups are tested only when the draw picks it.

Resolved

A dedicated project's archive used to be able to break for months unnoticed: only the flush before a recovery read pg_stat_archiver, no alert covered archiving, and the restore test restored only logical backups, so a failing wal-push (rotated credentials, a full bucket) let WAL pile up in pg_wal while base backups still succeeded, and the first test was the customer's restore. Now the metrics collector samples each dedicated instance's archiver every minute, at the instance's address, which follows an HA leader (collectArchiver: failed attempts, the age of the last archived segment, and the segments waiting in archive_status with the oldest one's age, which is how "stale while there is something to archive" is told from an idle archive), and walArchiveConditions raises the critical wal_archive alert when failed attempts went up in the last 15 minutes or a completed segment has waited longer than that. The restore test recovers a dedicated project's archive every other week (above). Both turn the status page's Backups component to degraded (TestWALArchiveAlert, TestCollectArchiver, TestRestoreTestTurns, TestScheduleSkipsThePITRTurnWithoutADedicatedProject; the recovery itself in the integration suite's TestDedicatedProjectAndPITR).

WAL-G and point-in-time recovery

A dedicated instance runs with archive_command='wal-g wal-push %p' and archive_timeout=60; walg.Env supplies the prefix, credentials, zstd and the derived key. The daily base_backup (dedicated.BaseBackup) runs wal-g backup-push on the leader, then delete retain FULL n --confirm (instances.Backup), where n is 7 or the purchased 14 or 30 (RetainFull). It records a base row and, when WAL-G lists the new backup, forgets the rows it no longer lists:

Resolved

One failed listing used to forget every base backup: instances.Backups ran wal-g backup-list … 2>/dev/null || true and returned an empty list, without error, on empty output, so a transient S3 error on the listing after a backup emptied keep and every base row of the archive, the new one included, became deleted, restarting the window the UI shows and PlanPITR accepts at the next night's backup. Now parseBackupList makes a failed listing an error, with WAL-G's stderr, and only "No backups found" an empty archive; the agent's Backup also refuses to report a newest listed backup that started before its push. forgetUnlisted forgets nothing when the listing lacks the backup just taken (an older agent, or a store that lists late), and a listing that fails is a warning in the step log (TestParseBackupList, TestNewBackup, TestBaseBackupReconciliationNeedsTheNewBackup).

  1. Plan. PlanPITR takes the newest base backup finished at or before the target (at most a minute in the future).
  2. Flush. flushWAL commits a transaction with an XID, switches segment, and waits up to two minutes for it to be archived. Recovery to a time ends at the first commit after it and fails without one, so the forced commit guarantees one. A stuck archive answers 409 before anything is created.
  3. Create a new dedicated project on the source's node with its size, version, region and residency, as a restore in mode pitr (runPITR).
  4. Replay. A one-off container runs wal-g backup-fetch, then Postgres recovers with restore_command reading the source's archive (settings in a 0600 file), recovery_target_time and recovery_target_action=promote (instances.restore).
  5. Adopt. adoptRestore waits for promotion, resets the recovery settings, renames the source's database and owner to the new project's, drops the source's console login and resets webhooks.

The window runs from the oldest recorded base backup to now (PITRWindow). After a switch the previous archive stays restorable from its own prefix and key for the project's window (7, 14 or 30 days), until its base backups expire, and the last takes the prefix with it. See for WAL-G on a failover.

Resolved

A storage or key switch used to cut a 14- or 30-day window to 7 days: reconfigureArchive expired the retired archive's base backups after PITRWindow, a fixed 7 days, whatever pitr_days the project paid for, so from day 8 to day 30 after a switch (which enabling or rotating a project key triggers by itself) the project could recover only to the switch. Now they expire after retiredArchiveKept, the larger of 7 days and the instance's pitr_days (TestRetiredArchiveKeptForThePaidWindow). Archives retired before this keep the 7-day expiry they were given.

Imports and Supabase migrations

An import (V1 §6.8) copies schemas from someone else's Postgres into a new shared project. The source is the tenant's, so Xenibase must neither change it nor trust it.

  1. Preflight. preflight reports the version (refusing 19 and later), size, schemas, extensions against the shared allow-list, and grants and policies naming anon, authenticated or service_role. On a Supabase source the managed schemas (SupabaseManagedSchemas) are left unselected.
  2. Create. Import repeats the preflight and creates the project. The URL travels sealed with the master key in the operation's params.secrets, bound to a random reference (SealOpSecret), which the job runner removes when the operation succeeds or fails and the API never returns; the log and the API see a redacted URL.
  3. Prepare. prepareImportTarget creates what pg_dump -n leaves out: the allowed extensions in their source schema, NOLOGIN stand-ins for the Supabase roles, and auth.uid(), auth.role() and auth.jwt() when auth is not imported.
  4. Copy. The agent pipes pg_dump --no-owner --no-acl --schema=… into pg_restore --role=<owner> as the console login, continuing past failing objects and listing up to 40 (agentsvc.copy).
  5. Verify. verifyImport compares row counts and sequences in the chosen schemas. A missing table fails and rolls back; a differing count is a warning, as the source may be live (decisions M3 #14).

Every source connection goes through pgsource.Config, which refuses a URL naming any host but its authority (host=, several hosts, a socket directory) and pins Xenibase's connection and the agent's pg_dump to the address the guard approved:

The guard is outbound.CheckSource: public addresses unless the platform admin allow-listed the host for the organisation; never loopback, link-local, metadata, or a node's or instance's address; and for imports never XENIBASE_OUTBOUND_BLOCK or the cloud private network, allow-listed or not (SourceInternal). The operation checks and pins again when it starts. Xenibase's own sessions run SET default_transaction_read_only = on (ReadOnly), a SET because PgBouncer refuses unknown startup parameters; pg_dump reads in its own read-only snapshot. The Supabase helper (V4 §9, MigrateSupabase) then rewrites policies, copies auth.users with their bcrypt hashes and copies storage, through the same pgsource path, with the credentials sealed in each step's operation the same way.

Resolved

With more than one server, imports used to fail at random: the URL was only in the memory of the server that took the request, but any server may claim the operation, and elsewhere runImport failed permanently ("xenibase-server restarted?") and rolled back; with two servers about half of imports and Supabase steps ended so, and a retry after the first attempt always did. Now Import seals the URL with the master key (SealOpSecret, bound to the import's reference) and hands it to provision.Create's Secrets, which puts it in params.secrets beside the password; importSource opens it on whichever server runs the operation. A Supabase step's URL and S3 key travel the same way (sealSecrets, opened in migrationStart). The runner removes them when the operation succeeds or fails, and the API strips params.secrets; the redacted URL stays for display (TestImportSourceReachesAnyServer, TestSupabaseStepSecretsReachAnyServer, TestCreateKeepsExtraSecretsWithThePassword).

Risk

Verification reads every table in the source, not only the chosen schemas. verifyImport counts the whole source and filters afterwards, so a login that may read only the imported schema hits "permission denied" on another table and the import rolls back after an hours-long copy. pgverify.Compare has the same shape. Fix: filter by schema in TableCounts's catalogue query.

Risk

Supabase migrations get a weaker address check than imports. services.sourceGuard uses the general outbound service, built with no Internal ranges (main.go). A host allow-listed for an organisation, whose DNS the tenant controls, can then resolve into the cloud private network and reach platform services not registered as nodes, which an import refuses. Fix: give it the backup service's Internal list.

Spec and code differ

V1 §6.8 has the operator choose a tier for an import. ImportRequest has none: imports always create a shared project, to be promoted afterwards.

Metadata self-backups and disaster recovery

runMetadataBackup has any agent dump XENIBASE_METADATA_BACKUP_URL (default XENIBASE_DATABASE_URL, off to disable) to metadata/ on the default target, in the Xenibase format, nightly at the window's start (V1 §11.6). A failure is a critical alert. docs/disaster-recovery.md rebuilds a lost control node from three things kept off it (the .env with the master key, the backup key file, the bucket credentials): start the metadata database, decrypt the newest metadata/ object with xenibase-agent decrypt, pg_restore --clean it, start everything (the pooler configuration is rendered again), re-register agents whose state was lost, and restore lost databases into new projects. Project-key backups also restore with gpg, pg_restore and wal-g alone.

Note

The metadata is as old as its last dump: projects, targets and project keys created since are gone from it, though their objects remain in the bucket. A project key exists only sealed in the metadata and in a download its admin may never have made, so such a key, or every project key once the master key is lost, leaves its .dump.gpg backups unreadable; the platform key file does not open them.

Alerts

internal/alerts raises backup_failed (critical) when the latest backup, base backup or metadata backup failed, restore_test_failed (critical), wal_archive (critical) when a dedicated project's WAL archiving failed in the last 15 minutes or a completed segment has waited longer than that (WALArchiveSamples, from the collector's wal_archive_* metrics, which /metrics also serves), and backup_overdue (warning) for a project the scheduler backs up, older than 26 hours, with no backup in 26 hours (OverdueBackups). Any of them turns the public status page's Backups component to degraded (States).

Resolved

"Backup overdue" used to fire for projects the scheduler skips on purpose: OverdueBackups checked only status = 'active' and age, but the scheduler skips paused and archived projects (whose status stays active), branches without backups, and suspended or deleting organisations, so one sleeping Free project kept "Some backups are delayed or failing" on the public status page indefinitely. Now OverdueBackups applies ProjectsDueForBackup's filters: lifecycle = 'active', a branch only with branch_backups, an active organisation (TestBackupOverdueSkipsWhatTheSchedulerSkips). A project woken or reinstated after a day or more still fires until its next nightly backup, which is late in fact; without storage or the backup key the scheduler queues nothing, and every project fires.
