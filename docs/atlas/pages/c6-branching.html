A branch is a project that starts as a copy of another project, its parent, and can be refilled from it later. Typical uses are a database per pull request in CI, trying a migration, or debugging against real data (V2 §8). internal/branching holds the whole lifecycle. It reuses provisioning and restores from the control plane and backups, and adds very little of its own.

What a branch is

A branch is an ordinary row in projects with its own database, owner role, app password and pooler route. Seven columns, added by migration 00015, make it a branch:

ColumnMeaning
parent_project_idThe parent. Not null means "is a branch". A foreign key to projects(id) only, not to (id, org_id).
branch_sourcebackup or live: where it was filled from, and the default for a reset.
branch_schema_onlyWhether it holds the parent's schema without rows. Fixed at creation. A reset keeps it.
expires_at, expiry_notified_atWhen the sweep deletes it (null: never), and whether the 24-hour warning was sent.
branch_backupsWhether it takes nightly backups and a final backup on delete. Off by default.
sensitive_data"Contains sensitive data" (V2 §8.5). Shared with ordinary projects. A branch copies its parent's.

How a branch relates to its parent:

  • One level deep. Resolve refuses a parent that is itself a branch.
  • Same organisation, same region, always the shared tier, on the organisation's own shared cluster if it has one, even when the parent is dedicated. It runs the parent's Postgres major (Create reads the parent's instance).
  • Members are a snapshot. The transaction that inserts the branch copies the parent's project members and roles (CopyProjectMembers). Its creator becomes its admin, unless they are an organisation owner or admin, who are admins of every project anyway. Later changes to the parent's members do not reach the branch.
  • Its own credentials. The branch gets a new opaque database name, owner role and app password, shown once in the create response. A reset keeps all of them, and members' personal logins, so a DATABASE_URL in CI or a .env keeps working (TestBranchResetKeepsURL).
  • Not copied: webhooks and scheduled jobs. The xenibase schema that comes with the data is dropped or rebuilt by ResetWebhooks (see Life of a project).
  • Not promotable. Promotion refuses a branch (dedicated.Promote). Detach it first.

Creating a branch

POST /api/v1/projects/{id}/branches (CreateBranch), or xenibase branch create, whose --replace deletes a branch of the same name first and whose --env prints DATABASE_URL lines for CI.

  1. Resolve. Resolve checks the request against the parent and fills the defaults. The parent must be active. A live copy needs a parent that is not asleep (a sleeping Free project refuses connections). A backup copy needs a succeeded logical backup. The TTL defaults to 7 days and must be 1 hour to 30 days, or 0 for none.
  2. Quotas. The handler checks CheckCreateBranch with the parent's latest measured size, then operations in flight (see limits).
  3. Insert and queue. Create calls provision.Create with a BranchSpec. One transaction inserts the project, sets the branch columns, copies the members, adds the creator and enqueues branch_create. The parent and options go into the operation's params as {"branch": {...}}, next to the sealed password.
  4. Backend services. If the parent has them, PrepareBranch makes the branch's API row, ref and keys now, so the response can return them once (below).
  5. Fill. The worker runs runCreate: Prepare (role, database, hardening). On a second attempt, RecreateDatabase first, to start from an empty database. Then fill, then Publish (member logins, pooler route, smoke test, active), then EnableBranch.

fill first runs copyExtensions. It reads the parent's extensions, and creates those in public on the branch as the admin, because the restore runs as the owner, who may not. Extensions in a schema of their own come with the dump. Then it copies from one of two sources:

SourceHowCost to the parent
backup (default)The newest succeeded logical, final or safety backup (LatestSucceededBackup), restored by backup.RestoreInto on the branch's agent: decrypted as it streams, pg_restore as the console login with --role the owner.None. The data is as of that backup.
liveThe agent's /v1/copy: pg_dump of the parent as the instance admin, with --no-owner and --no-acl, piped into pg_restore as the owner on the branch (see agent commands).A full dump, now.

Schema only passes SchemaOnly to the dump or the restore. Its default is the parent's sensitive_data, and only the parent's project admin may take a full copy of a sensitive parent:

MayCopySensitive is the caller's effective role on the parent (the request was authorised there), so organisation owners and admins qualify. TestBranchQuotaOnPersonalPlan covers both refusals.

Reset

POST /api/v1/projects/{id}/reset on the branch (ResetBranch). Reset queues branch_reset through EnqueueExclusiveTx: the branch must be active or error with nothing else in flight (one operation per project), and it moves to restoring. The source is the request's, or the branch's own. A backup source needs a backup of the parent. Schema only is always the branch's own.

PgBouncer's KILL drops the branch's client and server connections, and new clients wait until RESUME instead of failing. RecreateDatabase drops the database WITH (FORCE) and makes it again with the same name and owner. The owner's SCRAM verifier lives on the role, which is not dropped, so the app password still works. SyncMemberRoles puts members' grants back. If both attempts fail, failReset resumes the route and leaves the branch in error, its data possibly partial. Another reset or a delete fixes it.

Risk

A reset re-reads the parent without asking whether the caller may still read it. The route checks project.branch on the branch only, and fill reads the parent by ID. Two ways this hands out data that was meant to be withdrawn. First, membership: removing someone from the parent (RemoveProjectMember) deletes only the parent's row, so a developer copied onto a branch, or its creator, can keep calling reset with "source": "live" and get a fresh dump of the parent's current data. Second, sensitivity: the full-data rule is checked only in Resolve. A full branch of a parent marked sensitive afterwards keeps refilling with every row, for any developer on the branch. Re-checking the caller's project.branch (and, for a full copy of a sensitive parent, the admin role) on the parent in Reset would close both.

Detach, expiry and backups

  • Detach (POST /api/v1/projects/{id}/detach, Detach) is one statement, DetachBranch: it clears the parent, the expiry, the warning and branch_backups. The project keeps its database, credentials, members and API. branch_source and branch_schema_only stay on the row as history.
  • Expiry moves with PATCH /api/v1/projects/{id}/settings (expires_at, or no_expiry), which needs project.settings, the admin role. SetExpiry accepts a time in the next 30 days and re-arms the warning. branch_backups goes through the same route (SetBackups).
  • The sweep, Sweep, deletes up to 100 expired branches per pass through the ordinary provision.Delete, with no final backup unless the branch takes backups. It then emails each creator once when less than 24 hours remain. Without SMTP the warning counts as sent. A conflict (another server got there first) is ignored, so several servers can sweep at once.
Spec and code differ

V2 §8.4 calls for "an hourly job". cmd/server runs the sweep every 10 minutes (branchSvc.Run), as docs/decisions.md (M13 #4) records, though the package and the comment above that line still say hourly.

Risk

Detach makes a standalone project without the checks a new project gets. Detach needs only project.branch, the developer role, and calls neither CheckCreateProject nor org.create_project. Branches don't count toward the projects quota (CountOrgProjects), and detaching frees the branch's slot, so create-then-detach repeats without limit. It gives an organisation as many permanent projects as it likes, and it lets a developer in an organisation whose members may not create projects own one as its admin. Restore-into-new-project, by contrast, checks CheckCreateProject. Detach also takes no lock and ignores the status, so a branch detached mid-reset is overwritten from its former parent once the reset continues. Running detach through EnqueueExclusive-style locking with CheckCreateProject would match the other paths.

Risk

The sweep deletes from a list it read earlier. ExpiredBranches runs once per pass, and provision.Delete locks the row but does not look at expires_at or parent_project_id again. A branch extended or detached between the query and its turn in the loop is deleted anyway, and without a final backup unless it took backups, because the sweep passes the skipFinalBackup it worked out from the row it read earlier. The window is short, a pass of up to 100 deletes, but it is exactly when a user acts to save a branch at the last minute. A check inside the delete transaction that the row is still an expired branch would close it.

Who may manage branches

One action covers branches: project.branch, developer and above, token scope write.

The delete row is how developers delete branches but not projects (V2 §2.3). A route rule may carry a branchAction, and the guard swaps it in when the project it resolved has a parent:

The resolved parent also widens restricted tokens. authz.Can lets a token restricted to a project act on that project's branches, so a CI token for the parent can create, use and delete them. Lists apply the same rule through tokenAllows. A detached branch is outside the token from then on. Roles still come from project_members of the branch itself, and scopes still apply. See Security for the guard as a whole.

Risk

A transfer breaks the rule that a branch and its parent share an organisation. orgs.Transfer refuses neither a parent with live branches nor a branch, and the foreign key on parent_project_id does not include org_id. Moving a branch to organisation B leaves it a branch of A's project. B's owners and admins, project admins of everything in B, can then reset it from live, and fill reads A's parent by ID with no organisation check, so they keep receiving A's current data. Moving a parent instead leaves its branches in A: ListBranches filters by the parent's organisation and no longer shows them, while CountLiveBranches does not filter and keeps B from deleting the parent. Only someone who owns both organisations can transfer, but the access lasts after that, for everyone in B. Refusing transfers of branches and of parents with branches, or checking the organisation in fill, would keep the rule.

Branches with backend services of their own

When the parent has backend services (V4.1 §9.5), the branch gets an API of its own, never the parent's, so neither's tokens work on the other. cmd/server sets branching.Service.API to the services service. The work is split in two because the keys must be in the create response but the API can only be turned on once the copy is in:

  1. PrepareBranch, in the request, in one transaction: the branch's services row and a new ref, the parent's settings (exposed schemas, public tables, CORS, auth configuration and templates) without their secrets (providers_enc: SMTP, SMS, OAuth, captcha and hook secrets), and a publishable and a secret key. A failure here is logged, and the branch is still made, without an API.
  2. EnableBranch, at the end of runCreate and of every reset: purgeSessions deletes the sessions, refresh tokens, flow states, one-time codes and MFA challenges that came with the data, so a parent's refresh token cannot be spent on the branch. Then the request roles, xb_* schemas and a new signing key. The parent's app users and their password hashes come with the data, so they sign in again on the branch with the same passwords.
  3. With copy_files on create only, EnableBranch queues copy_branch_files as a background operation. runCopyBranchFiles reads the object versions the branch's xb_storage.objects names, which came with the data copy, and copies each one from the parent's prefix to the branch's inside the store.

TestBranchServices covers the keys, the separate signing key, the dropped sessions and the file copy.

Risk

Any copy error counts as "not found in the parent", and the operation succeeds. storage.Client.Copy returns ErrNotFound for a missing object and a wrapped error for anything else. The loop does not tell them apart. Throttling, a network error, an object over S3's 5 GB single-copy limit, or the operation's context ending each skip a file. The job then reports success with a "not found" count, and its three attempts are never used. The branch's rows point at files it does not have. Counting only ErrNotFound as missing and returning other errors would let the retry finish the copy.

Risk

A reset brings the parent's file rows but not their files, and strands the branch's own. runReset calls EnableBranch with copyFiles false. The refilled xb_storage.objects names the parent's current versions, so files the parent added since the branch was created are missing on the branch. The objects already under the branch's prefix, copies and the branch's own uploads, are no longer named by any row. The garbage list that would delete them lived in the dropped database, so the storage sweep, which meters rows, neither bills nor removes them until the branch is deleted. Copying files again after a reset, when the branch was created with them, would fix both.

Risk

Resets skip the operations-in-flight limit. branch_reset is in operationKinds, so it counts against the limit, but ResetBranch never calls CheckOperation. A developer, or a CI token, can reset every branch at once: with a live source that is one full pg_dump of the parent per branch, all running together on the parent's instance, past the 3 or 5 the plan allows. Calling CheckOperation in ResetBranch as CreateBranch does would apply the limit.

Failure handling

What failsWhat happens
No backup to branch from409 at request time, telling the caller to branch from live. If the backup disappears before the worker runs, the create fails permanently and rolls back.
The parent is deleted before the fillfill fails permanently. A create rolls back. A reset leaves the branch in error.
The copy itself (pg_dump, pg_restore, an extension the shared tier lacks)A live copy's error is permanent. A backup restore's error is retried once, on an empty database. Then Rollback soft-deletes the branch and drops its route, database and role, handing them to drop_project_objects if that fails.
A live reset of a sleeping parentNot checked at request time, unlike create. The copy fails, and the branch ends in error.
A reset that gives upfailReset: RESUME, status error, data possibly partial. The sweep still expires it.
The server dies mid-resetThe attempt is retried: KILL again, recreate, refill. Clients wait at the pooler meanwhile.
PrepareBranch failsThe branch is made and the response has no API. EnableBranch finds no services row and leaves it alone.
The expiry email failsRetried next pass. With no SMTP it is marked sent.
The organisation is suspendedNothing expires until it is active again.
Risk

A failure after Publish retries against a live branch, and the rollback then does nothing. In runCreate, Publish marks the branch active and routes it before EnableBranch runs. If EnableBranch fails, the second attempt calls RecreateDatabase, which drops the routed database WITH (FORCE) without the pooler KILL it requires, under any client already connected. If that attempt fails too, rollbackCreate sees active and returns: the operation reads failed, the branch reads active, and the API keys in the create response never work. Running EnableBranch before Publish, or not recreating once the branch is active, would keep the two consistent.

Spec and code differ

A few smaller differences, most recorded in docs/decisions.md under M13. V2 §8.2 names a branch's database <parent-db>__<branch-slug>_<rand>; branches get opaque names like every project. §8.2 step 3 applies extensions after the restore; they are created first, because the owner cannot. §8.3 pauses the route; the code uses KILL, which also drops open connections. §11 lists a branch_delete operation; a branch is deleted by the ordinary delete. §2.3's role table lets developers create, reset and delete branches; they may also detach, which the spec leaves to no particular role.
