A dedicated project has a Postgres container of its own on a node, created by that node's agent and archiving WAL with WAL-G from its first segment. Everything here builds on that container: HA adds a second member under Patroni, a read replica adds a member that never leads, a resize recreates the container with new limits, and a move builds a container elsewhere and copies the database into it by logical replication. Every long step is an operation (the operations queue); the kinds and their attempts are in Kinds.

Placement and creation

Validate refuses a dedicated create while no default storage target or backup key exists, then places it with placeDedicated: among the region's healthy, active dedicated or both nodes where the size fits (the agent's reported CPUs, memory and disk, less what dedicated instances there are allocated), the one with the fewest dedicated instances. The size is a profile's, or for a restore, a detached replica or a node move the source's CPUs and memory as given (CreateParams.Size), which may match no profile. When nothing fits and capacity automation is on, it asks for a new machine and the create waits up to 25 minutes for it to join (waitForHost). A node chosen by hand gets the same checks.

Ensure is the instance half of the create flow (): it generates xenibase_admin (a point-in-time restore takes the source's, which is in the data), fixes where the archive goes, has the agent create the container, records its address, and revokes CONNECT on postgres and template1 from PUBLIC. The first base backup follows, always taken on the current leader; WAL-G keeps 7, or one per day of a longer PITR add-on (). A restart from the Instance panel is a Recreate, a fresh container from the node's current image on the same volume. Start, stop and restart are refused with HA on.

Resolved

The reaper used to destroy the target of a running move, promotion or major upgrade. These insert the target when they are queued, and the project points at the source until the cutover commits, so five minutes after queueing the target matched every condition: the sweep destroyed it mid-copy and deleted its archive, the retry recreated an empty container under a row that kept deleted_at, and a pass that listed the target just before a cutover and removed it just after left only the stopped source. Now the query skips an instance a queued or running operation names as its target_instance, and an upgrade preflight's scratch instance in its first hour; once the operation has failed and its rollback could not remove the target, the reaper takes it. ReapOrphans runs the same query again for each instance, by id, just before destroying it, and Ensure refuses an instance already marked deleted rather than start a container under it (TestListOrphanedInstancesSkipsAnOperationsTarget, TestEnsureRefusesARemovedInstance).

Resizing

PlanResize refuses a smaller disk and checks that the difference fits on every node holding a member. runResize writes the size onto the row and recreates. Without HA the poolers freeze the routes (Freeze: PAUSE on the transaction pooler, KILL on the session pooler) around one recreate, then replicas follow one at a time. With HA the standby and replicas go first, the project switches over, then the old primary is recreated, so writes pause only for the switchover. A disk change alone needs no restart. When the node cannot hold the new size, a project without HA or replicas is moved into an instance of the new size on another node; with them the resize is refused. failResize puts the old size back on the row and, without HA, recreates at it.

Resolved

A resized instance used to be impossible to restore or detach. A size that matches no profile is recorded as profile custom (profileName); a point-in-time restore and a replica detach copied that name into the new project, and Validate, looking it up in Profiles, refused with unknown profile "custom", on the path used in an incident. Now both pass the source's CPUs and memory as CreateParams.Size (SizeProfile), which Validate takes in place of a profile, names as the row will be, and checks for room on the node. A node move passes its size the same way, so a move's capacity check is now of the real size rather than of the small profile (TestDetachReplicaOfAResizedProject, TestValidateTakesAResizedSourcesSize).

The maintenance window

Agents report each instance's running release and its image's, checked hourly. Every 5 minutes MaintenanceSweep, inside the window (default Sunday 02:00 to 06:00 UTC), upgrades at most one instance that is behind, dedicated first, skipping any with a project not active or with an operation pending (InstanceBusy). MinorUpgrade freezes the poolers for every project on it, recreates, resumes, and records the pause. An HA instance is switched over instead (minorUpgradeHA), and only inside maintenance announced to it 72 hours ahead; the sweep drafts that announcement for the first window at least 96 hours away, for an admin to confirm.

Risk

A maintenance restart is not an operation, so nothing keeps other work off the instance. The sweep checks InstanceBusy once and never takes the project's exclusive lock. For an HA instance minorUpgradeHA recreates the standby and waits for it to stream (up to an hour), and meanwhile the owner can queue ha_disable, which removes the standby it is about to switch to, or a resize, which runs its own minorUpgradeHA on the same members. The loop also runs on every xenibase-server without a lock, so two servers can restart instances at once, or the same one twice. Run minor upgrades through EnqueueExclusive as operations, or take a per-instance advisory lock.

High availability

An HA project runs two Patroni members on nodes in different failure domains, with Patroni's state in its region's three-member etcd cluster. Patroni decides who leads; xenibase-server follows the leader and moves the pooler route.

The etcd cluster and its CA

Each region has its own cluster, so its failover depends only on its own machines (V3.1 §3.1). ha.Setup takes three distinct healthy nodes of one region in three failure domains, refuses while any etcd setup or replacement is pending anywhere, and has each agent run etcd:v3.6.5 as a new cluster with a random token. Health is refreshed every 30 seconds; Ready, checked before HA or a replica is added, wants three members with a majority healthy.

The etcd CA is separate from the agent CA, so neither's certificates pass for the other's. LoadCA creates it once under an advisory lock (P-256, 20 years, key sealed with the master key). Members get 5-year server-and-client certificates, and each HA instance a client certificate patroni:<instance>. Etcd checks client certificates on both ports but has no per-cluster authorisation: every Patroni scope sits under /xenibase/ and any certificate from the CA can write any key. Isolation between projects rests on tenants never getting a shell or superuser in a member container, whose environment holds the key.

Replace swaps a member: a dead one is removed first so the other two keep a quorum, a live one (a drained node) only after the new one joins. MoveToRegionEtcd moves a project whose state is still in the home region's cluster: it removes the standby, restarts the leader on the new cluster under a pooler pause, and builds a new standby, so the project has none until the end.

Patroni members

An HA instance stays one row that follows its leader: node_id, leader_member and the addresses are the leader's. Each member is a container keyed by its own ID in instance_members, and the first member's ID is the instance's (leaderKey). memberSpec is the plain spec plus a Patroni block: the scope, the region's etcd endpoints, the instance's etcd certificate, the replication and REST passwords and synchronous mode. Turning HA on and off

EnableHA needs a running instance, its region's etcd ready, and a node from standbyNode: healthy, dedicated-capable, in the region, holding no member, in another failure domain, with the fewest instances. Unlike placeDedicated it does not check that the size fits there. runHAEnable then creates xenibase_replicator and the Patroni secret, recreates the container under Patroni on the same data with the poolers frozen (about 4 seconds; on failure back to a plain container), starts the standby from the newest base backup (pg_basebackup as fallback), waits until it streams, and adds the SLA probe login. A standby that never joins is removed. Turning HA off removes the standby and leaves Patroni with one member, so turning it on again needs no restart. With HA on, node moves, demotion, major upgrades and stop or restart are refused.

The HA watcher: failover and routing

Patroni promotes the standby when the leader's 20-second lease expires and the standby is under 1 MB behind. The route is the server's job: RunHAWatcher polls every instance under Patroni once a second, and watchOne decides:

No running leader for two polls freezes the routes so clients queue. The current leader counts as gone as soon as its own API stops answering, about 15 seconds before the other member stops listing it. A new leader is written onto the row and the poolers synced (routeTo), a failover_events row records the outage, and the poolers resume. The old primary rejoins through pg_rewind. Writes come back 17 to 20 seconds after the primary's node dies in the tests. When etcd loses its quorum, failsafe mode keeps a primary that reaches every member serving, and no failover happens until the quorum returns; ensureFailsafe turns it on for clusters made before it was the default.

Spec and code differ

V3 §2.2 fences with "Patroni's watchdog plus the leader lease". Containers have no watchdog device, so Patroni runs with watchdog: off and the lease alone fences (decision M19 #6): a primary whose Patroni hangs while Postgres runs is stopped by nothing, and only the poolers' following the lease keeps traffic off it. The spec also puts etcd on the control node and moves archiving with Patroni callbacks; the code runs a cluster per region on tenant nodes and needs no callbacks, as Postgres archives only on a primary.

Risk

The watcher pauses a healthy project whenever the control plane loses sight of its primary. "No leader" includes the leader's REST API not answering xenibase-server within 2 seconds, twice (memberUp). A fault between the server and one node freezes every HA project led there, although Patroni, etcd and the poolers are fine, until the server sees the leader again or PgBouncer's wait timeout fails the clients. With two servers on one metadata database it is worse: the watcher has no lock and its paused flag and switchover mutex are per process, so one server's partial view pauses the poolers that only it will resume, and the other records a "failover" for the first's switchover. Pause only when Patroni agrees (the other members stop listing the leader too), and run the watcher on one server through an advisory lock.

Switchover and synchronous replication

switchOver holds the instance's watcher lock, picks the least-lagging streaming standby that is not a replica (with synchronous replication, the synchronous standby, waiting up to 30 seconds for one), freezes the poolers, calls Patroni's /switchover, waits for the candidate to lead, routes and resumes. The old primary stops cleanly first, so nothing is lost; about 2 seconds of pause. Synchronous replication patches synchronous_mode in Patroni's configuration; without it a failover can lose up to 1 MB of acknowledged commits.

The SLA probes

HA projects carry 99.9% monthly availability of the pooler endpoint. ensureProbe creates a login <db>_sla with only CONNECT and a limit of 5 connections. Every minute SLATick connects through each project's pooled URL and runs SELECT 1 within five seconds; with a status page it also pushes the targets to xenibase-status and pulls its per-minute results, both signed. A minute is unavailable when every vantage point that probed in it failed. Minutes while the project is not active or its organisation is suspended are excluded, as are minutes inside maintenance announced to the project 72 hours before them (ApplyMaintenanceExclusions, over the last six hours on every tick).

Spec and code differ

V3 §2.7 counts a minute unavailable "if the probe fails from two vantage points". The code needs only every vantage point that probed to fail, so without a status page one failed internal probe makes a minute unavailable (decision M19 #11).

Failure domains and regions

A failure domain is what fails with a node: a rack, a host, a power feed. Separated decides whether two nodes can fail together. A recorded domain wins and a node without one counts as alone; otherwise two Hetzner servers are apart only inside the same spread placement group, and a node with neither is its own domain. The rule binds an HA pair (standbyNode refuses), a region's etcd members (setup and replacement refuse) and a region's pooler pair (a warning); read replicas never take over, so they are exempt. Changing a domain moves nothing: faildomain.Check lists the groups that now break it, for a banner and a failure_domain alert.

A region groups nodes, a pooler pair with its own hostname (pooler hosts), a storage target and a copy target. Placement, standbys, promotions and demotions stay in the project's region. A hidden region's launch checks (Readiness) block opening it without a healthy node, with etcd that is not three members in three domains, or with a pair sharing a domain.

Read replicas

A read replica is a member tagged nofailover and nosync: it streams from whichever member leads, is never promoted and never holds up a commit. A project may have two. runCreateReplica first puts a plain instance under Patroni (the same restart as HA), then builds the member from the newest base backup on a healthy node holding no member, in the project's region or, without data residency, another. Every replica of an instance publishes on one port, 20000 + fnv32(instance) % 10000, because PgBouncer takes one port for a host list. Moves, demotions, major upgrades and the regional etcd move are refused while a project has replicas.

The pooler renders <db>_ro for such a project: the same logins, each server connection started with SET default_transaction_read_only = on, balanced across the replicas in rotation in the pooler's region, else all in rotation, else the primary (replicaHosts). Read-only is a session default the client can change, not a permission. On every watcher poll checkReplicas measures each replica's lag as how long ago the leader was first seen past the position the replica has not replayed, so a replica that stops replaying lags even while the leader is idle. Over 10 seconds, or not streaming, takes it out of rotation; under half that brings it back.

Per-replica standby settings

Each replica has its own hot_standby_feedback and one delay for both max_standby_streaming_delay and max_standby_archive_delay; the primary and standbys keep Postgres's defaults.

They reach the replica twice: in memberSpec's local parameters, so a recreated container starts with them, and through UpdateReplicaSettings, which stores them and, on a streaming replica, runs ALTER SYSTEM and a reload and reads back what the server runs with. The values can only be on, off or <n>s, checked before quoting. The watcher re-confirms them every 5 minutes (30 seconds after a failure), which also covers a replica rebuilt from a base backup with the primary's postgresql.auto.conf.

Detaching a replica

DetachReplica turns a streaming replica into a new dedicated project while the source runs on. The new instance takes the member's ID, so container and volume keep their names. ensureDetached deletes the member row, recreates the container as a plain instance with the source's superuser, promotes it with pg_promote, resets primary_conninfo, the slot and the standby settings, and renames the database and owner as a restore does. A failure removes the new project and the replica.

Moves

A node move (logical_move), a major upgrade (), a promotion and a demotion all copy through one engine. A node move to another region's node is a region move. Each holds the project in a non-active status, which keeps other operations off it, for two attempts. Move refuses HA, replicas, the same node, and a region the project's data residency or a hidden region's early access forbids. A shared project goes into the target node's shared cluster of the same major; a dedicated one gets a new instance of the same size.

The copy

runMove first checks where the project is: already on the target means the cutover committed and only finishMove is left. Otherwise a second attempt first unfreezes the source, in case the first froze it, and it creates a new target instance, and prepareTarget creates the database and every login with the same SCRAM verifiers (owner, members, integrator roles, roles the owner made, NOLOGIN stand-ins for roles grants name); a second attempt first clears the first's replication objects and recreates the database. copyForMove then:

  1. Preflight (Preflight): wal_level=logical, a free slot and WAL sender, a target major no older, no large objects or unlogged tables, the extensions available on the target. Any blocker falls back to dump and restore inside the freeze, recorded as fallback_reason.
  2. Schema: pg_dump --schema-only | pg_restore through the target node's agent, owners kept.
  3. Replication (Setup): REPLICA IDENTITY FULL on tables without a primary key, a marker table on both sides, an event trigger refusing tenants' DDL, a REPLICATION login xenibase_move_<op> (agents admit it only from XENIBASE_AGENT_MOVE_ALLOW), a publication FOR ALL TABLES, and a subscription with disable_on_error and, at the same major, binary.
  4. Catch up (WaitCaughtUp): every table copied, then under 1 MB behind for 30 seconds.
  5. Freeze (freeze): owner and member logins NOLOGIN, the poolers frozen, those roles' and the console's sessions ended.
  6. Cutover, within 30 seconds: the marker below, then each used sequence set to the source's value plus 1,000 steps, then exact row counts on up to 20 tables of at most 16 MB.

A dump-mode move copies with pg_dump | pg_restore inside the freeze and compares every table and sequence, so its pause grows with size. A logical move's does not: 115 ms at 1 GB and 135 ms at 3 GB under continuous commits, none lost (TestMoveUnderLoad).

Spec and code differ

Decision M18 #5 says missing extensions on the target block the move. In the code they are one more preflight blocker and every caller allows the dump fallback, so the move freezes writes, fails at CREATE EXTENSION and rolls back: a pause and a failed move instead of a refusal.

The switch, and how the URL stays the same

MoveCutOver points the project at the target. Nothing in a connection string names an instance (the pooler host, database name, role and password all stay), so once finishMove re-renders the route and resumes, the held clients carry on against the target. A region move changes the hostname to the new region's, and keeps the old region in forward_region with forward_until 30 days ahead; while that is in the future the pooler sync also renders the project into the old region's configuration (served), so the old hostname reaches the new instance until the first sync after it.

finishMove is idempotent and is also the rollback after the commit. It sets the project active, keeps the source for 48 hours (a shared copy read-only, a dedicated instance stopped) for DropRetired to remove, removes the replication objects on both sides in a deferred cleanupMove, and takes the target's first base backup, where its point-in-time window starts. Before the commit, failMove removes the replication objects, unfreezes the source, sets the project active, and destroys the new instance or drops the partial copy. If the source's logins cannot be given back, the poolers still resume and the target still goes, but the project keeps its status for the sweep below to finish.

Resolved

A retry after the freeze used to copy everything again with the source still frozen: only the rollback, after the last attempt, unfroze. A transient error between freeze and the cutover commit, or a crash, lost lease or deploy in that window, started attempt two with the logins NOLOGIN and the poolers paused, and in dump mode the project stayed unreachable for a second whole copy. Now runMove, runPromote and runDemote call thawRetry on any attempt after the first that finds the project not yet cut over: the logins get LOGIN back and the poolers resume, so the source serves while the attempt copies again, until its own freeze (TestRetryUnfreezesTheSource).

Resolved

A rollback that could not reach the source used to leave the project frozen and stuck. unfreeze opened a connection to the source first and, if that failed (often why the move failed), returned before resuming the poolers, and failMove before setting the project active; Runner.fail logged "rollback incomplete" and never retried, so the project stayed moving, NOLOGIN and paused until someone repaired it by hand. Promotion and demotion shared this. Now thaw resumes the poolers whether or not the logins could be given back, and the rollback still removes the target; only the project's status stays as it was, which keeps other operations off it, and the operation fails with the reason in its log. Every minute, beside the reaper, RepairStuckMoves takes each project in moving, promoting, demoting or upgrading with no queued or running operation, gives its logins LOGIN back, resumes its poolers and sets it active once its instance answers, and the alerts raise project_stuck for one still frozen after 10 minutes (TestFailedRollbackResumesAndIsRepaired).

Risk

Replication objects a rollback could not remove stay for ever. cleanupMove is best effort, logical.Cleanup skips the source when it cannot open it, and nothing else looks for xenibase_move_ objects. The orphaned slot has no consumer and no instance sets max_slot_wal_keep_size, so it keeps WAL until the disk fills, which on a shared cluster stops every tenant there; the event trigger keeps refusing the tenant's DDL. Sweep inactive xenibase_move_* slots, publications, triggers and logins with no running operation, and cap slot WAL.

Risk

A region move leaves the WAL archive in the old region. The target's archive is placed once, when it first runs, from the project as it is before the cutover, so regionTarget picks the old region's bucket, and the moved project's WAL and base backups stay there for the instance's life. Residency is not breached (residency projects cannot leave, and turning residency on is refused while the archive is elsewhere), but the archive outlives the move in a region the project left. Place the target's archive by its node's region, or queue a storage switch after a region move.

Promotion and demotion

Promotion (runPromote) moves a shared project, not a branch, onto a new dedicated instance in its region. The wizard's estimate is 5 seconds for a logical copy, or 5 seconds plus the size at 40 MiB/s for dump and restore. The target is the project as it will be: the same role, verifier and database name, dedicated limits, timeouts kept, the console read-only. CutOverProject switches instance, tier and settings in one statement, the shared copy is kept read-only for 48 hours, and the instance takes its first base backup.

Demotion refuses HA and replicas, and preflight runs seven checks: size against the shared storage limits, extensions outside the shared allow-list, roles beyond the project's own (integrator roles block), the allowance released, last week's peak connections (a warning), settings the copy drops (a warning), and a shared cluster of the same major in the region with room for the size plus 20%. They run at preflight, at queue time and again in runDemote. After the cutover finishDemotion takes a logical backup (point-in-time recovery ends) and stops the dedicated instance, destroyed 48 hours later; its WAL-G archive stays for the base backups still under it.

Spec and code differ

V1 §6.6 freezes with ALLOW_CONNECTIONS false and verifies every table's rows. The code uses NOLOGIN, which leaves pg_dump working (decision M5 #2), and a logical copy counts only small tables, trusting the marker (M18 #3). V3 §2.3 keeps every source read-only for 48 hours; a dedicated source is stopped instead.
