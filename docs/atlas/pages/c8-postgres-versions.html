Xenibase runs more than one Postgres major at a time. Each major has a place in its life, kept in one table, and each instance runs an image built for its major. Minor releases are a restart on the same data, done by a background sweep in a weekly window. A major upgrade is a move: the project's database is copied by logical replication into a new instance (or a shared cluster) of the newer major, and the route is switched.

Which majors are offered

Two things decide whether a major can be used. The server is configured with the majors it has images for, XENIBASE_PG_VERSIONS, default 17,18 (config). The pg_versions table says where each major is in its life (00046_pg_versions.sql). The first time the server looks, ensureVersions inserts every configured major as supported with ON CONFLICT DO NOTHING, so an operator's statuses are never overwritten. A major dropped from the setting keeps its row and is listed as not installed. Versions joins the two and counts the live projects on each.

The image is a template. The agent's XENIBASE_AGENT_PG_IMAGE defaults to xenibase-postgres:{major}-walg3.0.9, and ImageFor replaces {major} with the instance spec's PGVersion (18 when it is 0). One Dockerfile builds every major: PG_MAJOR picks a stage built from the official postgres image of that major's pinned minor release (PG17_RELEASE, PG18_RELEASE), and WAL-G (a pinned commit), Patroni (a pinned version) and hypopg are added on top. Two checks keep an instance on the major it asked for:

  • After start, checkMajor runs postgres -V in the container and refuses a different major. An image name without {major} serves one version only, and this is where that shows.
  • PGDATA is set per major inside the instance's named volume, /var/lib/postgresql/{major}/docker (pgdataFor). The 17 image declares /var/lib/postgresql/data as an anonymous volume, and data there was lost on a recreate (decision M18 #9).

The agent is built on postgres:18, so its pg_dump is 18. A newer major needs the agent image rebuilt before dumps of it work.

The lifecycle

A major is preview, supported, deprecated or retired. The table's check constraint requires a retires_at on a deprecated row. No job ever flips a deprecated major to retired: EffectiveStatus reports a deprecated major as retired once retires_at has passed, everywhere the status is read (decision V4.1-M5 #3).

The middle five columns are the five uses CheckVersion is called with: ForProject, ForPreviewProject, ForUpgrade, ForCluster and ForDerived. A major not in XENIBASE_PG_VERSIONS is refused for every use, whatever its row says.

ForCluster allows a preview major, for the projects trying it, and a retired one on purpose: a cluster for the projects still on it. ForDerived returns before the status is looked at: the source's data is on that major already.

Changing a status

A platform admin changes a major with PATCH /api/v1/admin/pg-versions/{major} (UpdatePgVersion, Admin → Platform → Postgres versions). One endpoint covers every transition, and pgversions.Change enforces the rules:

  • Preview only stays preview: no major goes back to it.
  • Supported from anything: promoting a preview, or taking a deprecation or retirement back.
  • Deprecated needs retires_at at least 180 days ahead (MinNotice). Deprecating again keeps deprecated_at and may move the date. Only a fresh deprecation sends the first notice.
  • Retired is refused while a live project runs on the major, unless its date has passed. Projects are never upgraded automatically: an upgrade can break an app.

Notices to organisations

On a deprecation, and again 90, 30 and 7 days before retirement (Reminders), the owners and admins of every organisation with a project on the major get one email listing those projects, each with a link to its Upgrade card. Sweep runs hourly (pgVersionSvc.Run(bgCtx, time.Hour) in cmd/server) and sends only the nearest step reached, so a server that was down past a step sends one mail, not several; before the first reminder it sends the deprecation notice to any organisation that has not had it. notifyOrg inserts a pg_version_notices row keyed on major, organisation and step in a transaction that stays open until the mail is sent, and skips the organisation when the insert finds a row already there. A second server's insert waits on the first's and then finds the row, so the sweep is safe to run on two servers at once, and a send that fails rolls the row back, so the next sweep tries again. Projects on a deprecated or retired major show a banner (VersionBanner), red once it is retired: "keeps running but is unsupported".

Resolved

A notice whose email failed used never to be resent: notify committed the pg_version_notices row before sending, so a mail server that was down for the deprecation or a reminder meant that organisation never heard of it. Now the row is committed only with a successful send (notifyOrg), still under the insert's row lock, so two servers still send once, and the sweep also retries the deprecation notice until the first reminder is due (TestNoticeIsResentAfterAFailedSend).

How new projects pick a major

provision.Create resolves the requested major with CheckVersion, as ForPreviewProject when the create form's preview box was ticked. A request without a major gets DefaultVersion: the newest installed supported major, else the newest installed deprecated one, else an error. A shared project then needs a running shared cluster of that major in its region (PickSharedInstance filters on pg_version), and otherwise fails with no_capacity. A dedicated project gets an instance of that major. Preview and retired majors are refused with a message saying what to choose instead. A deprecated major is still open: decision V4.1-M5 #2 keeps it so, to avoid surprising owners in the middle of a migration.

Every other way of making a project goes through the same Create with the source's major and Derived set, checked as ForDerived: a branch (branching.Create), a point-in-time recovery (backup.PITR) and a detached read replica. A project on a retired or preview major can do all three. Moves, promotions and demotions do not create a project and do not check the status.

Resolved

A project on a retired or preview major used to be unable to recover to a point in time, branch, or detach a replica: all three called provision.Create with the source's major as ForProject, which refuses retired and preview majors, so the owner of a retired-major project who dropped a table could not get it back from the WAL archive, and every preview project was in the same position from the day it was made. Now the three set CreateParams.Derived, and CheckVersion takes ForDerived: any major in XENIBASE_PG_VERSIONS, whatever its status. The comment on ForCluster now says what it allows. TestCheckVersionForDerived and TestCreateDerivedOnARetiredMajor cover it.

Minor releases

A minor release (18.1 to 18.2) changes binaries only, so an upgrade is a restart of the same volume on a newer image. The operator rebuilds or pulls the image tags on each node (make pg-image, install.sh, or docker pull; docs/upgrade.md). Nothing in Xenibase pulls a newer image: the agent pulls a tag only when it is missing.

  1. Releases are read. Every five minutes MaintenanceSweep first calls CheckReleases for running instances not checked in the last hour. The agent's info reads PG_VERSION from two images: the one the container was created from (pg_release, only while it runs) and the one its tag names now (pg_release_available). An instance whose container is not running is left as it was recorded. Clusters the server was configured with, which have no agent, are skipped.
  2. Inside the window (DefaultWindow: Sunday 02:00 to 06:00 UTC, one platform-wide setting), InstancesBehind lists instances whose two releases differ, dedicated before shared, leaving out any whose last upgrade to that release failed. NewerRelease keeps those where the tag is a later minor of the same major.
  3. One instance per sweep. An instance with a project that is not active or has an operation queued or running is skipped (InstanceBusy). An HA instance waits for maintenance announced to its project at least 72 hours before (announced), unless XENIBASE_MAINTENANCE_REQUIRE_ANNOUNCEMENT=false. proposeMaintenance drafts that announcement for the first window at least the draft lead away. The first instance that passes gets a minor_upgrade operation (EnqueueMinorUpgrade), exclusive with its projects' other operations, and the sweep returns; nothing more is queued while it is queued or running. One server sweeps at a time, under an advisory lock (LockedMaintenanceSweep).
  4. The restart (minorUpgrade, run by the operation). The minor_upgrades row is recorded when it is queued; it freezes every project database on the instance at the poolers (Freeze: PAUSE on the transaction pooler, falling back to KILL after 10 seconds; KILL on the session pooler). It calls Recreate and then RESUME. Read replicas of an instance without HA follow one at a time, each out of rotation meanwhile (recreateReplicas).
  5. HA instances are switched over, not restarted (minorUpgradeHA): each standby and read replica is recreated and waited for, the leader is switched over to a standby, and the old leader is recreated as a standby. Writes pause only for the switchover.

On the agent, a recreate stops the container (60 seconds, then a kill), renames it aside (xenibase-<id>-previous), and creates a new one from the tag on the same volume. The old one is removed only once the new one is ready; otherwise putBack removes the new one and starts the old one again:

A shared cluster is upgraded the same way, after every dedicated instance, with all its projects frozen together. The bundle's own cluster from compose.yaml has no agent and is left to the operator. An admin can also upgrade one instance at once, outside the window and past the announcement gate (MinorUpgradeNow, POST /api/v1/admin/instances/{instance_id}/minor-upgrade).

Resolved

A failed minor upgrade used to leave the instance down, and the sweep then forgot it. The agent removed the old container before creating the new one, so a new release that could not be created, started or made ready left nothing running under a row that still said running; the sweep retried the same instance every 5 minutes, freezing its projects each time, with no other instance upgraded meanwhile; and once CheckReleases ran again a missing container reported no release and a crash-looping one the new release, so the outage looked like a finished upgrade. Now the agent keeps the old container, stopped and renamed, until the new one is ready and puts it back otherwise, even when the server's request was cancelled; a create that finds only the set-aside container (an agent stopped part-way) renames it back. info reports a release only for a running container, and CheckReleases records nothing for one that is not. On the server, Recreate records the restored container's address, or says the instance is down; the failure is kept in minor_upgrades, InstancesBehind leaves out an instance whose last upgrade to its image's release failed, so the sweep moves on to the next one, and a minor_upgrade_failed alert fires until an upgrade of it succeeds. A newer release or Upgrade now tries it again. The instance is not marked error: the old container normally runs again, and an empty shared cluster in error would be reaped. TestRecreatePutsTheOldContainerBack, TestCreatePutsBackAContainerARecreateLeft, TestInfoReportsNoReleaseWhenStopped, TestInstancesBehindSkipsAFailedUpgrade and TestMinorUpgradeFailedCondition cover it.

Resolved

The minor-upgrade sweep used to take no lock and keep no state that survived a crash. Two servers picked the same first instance and restarted it twice, the first one's RESUME letting clients in while the second had it down, and a server that stopped between Freeze and Resume left PgBouncer paused with nothing to resume it. Now the sweep holds a session advisory lock on a connection of its own, and each upgrade is a minor_upgrade operation, exclusive with the projects' other operations: a crash hands it to another worker, whose attempt resumes the poolers first, and its OnFail (failMinorUpgrade) resumes them and finishes the run. A minor_upgrades row left unfinished with no operation to finish it (a run from before this change, or an OnFail cut short) is finished by the next sweep after resuming its instance's poolers. Upgrade now (MinorUpgradeNow) queues the same operation and waits for it. See for the tests.

Resolved

The image tag used not to pin the Postgres release: FROM ${REGISTRY}postgres:${PG_MAJOR} took whatever minor the official tag held when a node built or pulled it, so xenibase-postgres:18-walg3.0.9 named different releases on different nodes, any recreate outside the window landed on whatever the tag held there, and the previous release, no longer tagged, could not be pointed back at after a regression. Now the Dockerfile builds each major from a pinned release (ARG PG17_RELEASE=17.11, PG18_RELEASE=18.6, overridable), and build.sh, which make pg-image and install.sh run, tags it both xenibase-postgres:18-walg3.0.9 (the agent's {major} template, unchanged, so upgrades keep working) and with the release it holds, xenibase-postgres:18.6-walg3.0.9, so the release a rebuild replaces stays on the node and the major tag can be pointed back at it. The server still does not choose a release per instance: every instance of a major on a node runs what its major tag names. TestInstanceImagePinsTheRelease checks the Dockerfile and the script.

Spec and code differ

V3 §2.4 asks for "a weekly maintenance window per region". There is one window for the platform, stored under the maintenance_window setting and read in UTC. Decision M18 #11 deferred per-region windows to M25 (regions), and they have not arrived.

Major upgrades of dedicated projects

A major upgrade is not pg_upgrade. It is a move (decision M18 #10): a new instance of the target major, of the same size, on the project's own node, filled by logical replication while the old one keeps serving, then a cutover of a few seconds. pg_upgrade would need both majors' binaries in one container and a longer outage. Members with the ProjectPromote permission run it from the project's settings (POST /api/v1/projects/{id}/upgrade/preflight, then …/upgrade), and the deprecation emails link there.

The preflight

UpgradePreflight changes nothing and returns a list of checks, each ok, warning or blocked:

CheckBlocks when
targetHA is on, or the project has read replicas (both must be removed first and set up again after), or a shared project has no shared cluster of the target major in its region open to its organisation, or a dedicated project's node is not active or has no room for a second instance of its size.
versionThe target is not supported (ForUpgrade), or is not newer than the current major.
extensionsThe target cannot create an extension the project uses (logical.Preflight).
replicationNever. A warning when logical replication is not possible (large objects, unlogged tables, no free slot or WAL sender): the copy is then a pg_dump piped into pg_restore during the freeze, and writes pause for its whole length, estimated at 40 MB/s plus 5 seconds.
deprecatedNever. A warning for each name the new major removed that appears in a function body, view or per-database setting (Removals, matched by whole word).
schemaThe schema does not restore on the target major.

The schema check is a real restore. For a dedicated project, scratchTrial starts a temporary instance of the target major on the project's node: 0.5 CPU, 512 MB, profile scratch, no WAL-G. schemaTrial then creates a short-lived non-superuser login and database there, creates the project's extensions as the superuser, and restores a schema-only, owner-less dump as that login with errors allowed. Each error becomes a blocked line. The temporary instance is destroyed and marked deleted when the check ends, success or not, and if that destroy fails the orphan reaper removes it once it is an hour old (it leaves a younger one alone, since the check may still be using it). A shared project's check runs the same restore in a scratch database on the target cluster. Upgrade runs the whole preflight again and refuses if anything is blocked.

The upgrade

  1. Queued. In the transaction that sets the project to upgrading and queues a major_upgrade operation (EnqueueExclusiveTx), Upgrade inserts the target instance row: same node, the source's CPU, memory, volume and pitr_days, max_connections at least the source's, its own WAL-G prefix. It refuses if the project moved since the check, or if the node no longer has room for a second instance of that size.
  2. The target starts. The operation runs runMove, the node move's handler (Kinds: two attempts, 48 hours), which calls Ensure for the new instance.
  3. Roles are restored before any data (prepareTarget): the database and owner with the same SCRAM verifier (Prepare), member logins and the read-only role (SyncMemberRoles), integrator roles with the owner's admin option (restoreIntegratorRoles), the roles the owner created with role management, with attributes, password and memberships (restoreOwnedRoles), and NOLOGIN stand-ins for any other role that a grant, policy or owner in the database names (placeholderRoles). So existing passwords keep working on the new major.
  4. The copy (copyForMove). The schema goes first (copyKeepingOwners). Then a publication FOR ALL TABLES and a subscription copy the rows, not in binary mode, since the majors differ. Schema changes are paused on the project until the move finishes. The source keeps serving reads and writes.
  5. The freeze and cutover. When the subscription has caught up, freeze makes the owner and member logins NOLOGIN, pauses the poolers and ends remaining sessions. logical.Cutover waits up to 30 seconds for the last commits, copies sequences with a margin of 1,000 and compares sampled tables. One transaction then points the project at the new instance and records the old one in retired_databases for 48 hours (RetainSource). The old base backups get an expiry instead of being deleted.
  6. Finishing (finishMove, idempotent). It syncs and resumes the poolers, sets the project active, removes the replication objects (a slot left behind would keep WAL forever), stops the old instance (retireSource), and takes the first base backup on the new one. Clients reconnect to the same URL.

Downtime is the freeze: the decisions record 115 ms for a 1 GB move and 135 ms for 3 GB under continuous writes (M18 #12). In dump mode it is the whole copy. Rollback covers only the time before the cutover: failMove removes the replication objects, makes the source's logins LOGIN again, resumes the poolers, sets the project active and destroys the new instance. A source that cannot be reached still gets its poolers resumed, and the project stays upgrading until RepairStuckMoves gives its logins back. After the cutover the only failure handling is to run the finishing steps again.

Resolved

The orphan reaper used to destroy an upgrade's target after five minutes. ListOrphanedInstances took any dedicated instance older than 5 minutes that no live project pointed at for a failed create's leftover, and a major upgrade's target is inserted when the operation is queued but pointed at only at the cutover. So any upgrade whose queue wait, schema copy and initial sync took more than five minutes lost its target and its WAL-G prefix part-way and rolled back, and a pass that listed the target just before a cutover would have destroyed the live instance. Node moves, promotions and resizes that move had the same problem. Now the query skips an instance a queued or running operation names as its target_instance and a scratch instance in its first hour, and ReapOrphans checks each instance again just before destroying it (TestListOrphanedInstancesSkipsAnOperationsTarget).

Resolved

Recovering to a time before a major upgrade used to fail. PITRWindow and BaseBackupBefore offer the old instance's base backups, since they select by project, but backup.PITR created the new project with the current instance's major, so a 17 base backup was started in a Postgres 18 container, which refuses the data ("database files are incompatible with server"). Now PlanPITR names the instance that took the base backup as the source (backupInstance: archives live under instances/<id>/, so the backup's prefix names it, running or kept stopped), which also gives the restore that instance's superuser, the one in its data; and PITR takes the major from it (SourceMajor), checked as ForDerived so its status does not matter. An owner whose app breaks on the new major restores to before the upgrade on the old one (TestPITRStartsTheBaseBackupsMajor).

Risk

Nothing points a project back at its retained instance. The old instance is kept stopped for 48 hours, but no API, UI or command starts it again as the project's. Doing that without losing data needs the writes made since the cutover copied back, and the move machinery cannot: it copies into an empty target from scratch, and nothing records a replication position on the new instance that matches the old one at the cutover. Re-pointing it as it is would silently drop every write since the upgrade, which is what a point-in-time recovery to before the upgrade already gives, under a new project, without touching the live one. A safe re-point needs a reverse logical slot created at the cutover (or a full reverse move into the retained instance) and is left for later.

Resolved

The upgrade's target used to skip the capacity check and drop the PITR add-on. A node move builds its target through Validate, which checks that the size fits the node, and copies pitr_days; Upgrade did neither, so on a full node a second instance of the same size was created anyway on the node's one disk beside the source, and a project paying for 14 or 30 days of point-in-time recovery silently got 7, and was billed for 7. Now upgradeRoom runs the same fits check for the source's size on its node (and refuses a draining node): the preflight's target check is blocked when it fails, and insertUpgradeTarget checks again in the queueing transaction and refuses with the reason, telling the owner to move the project to a node with room first. The target takes the source's pitr_days, and a resized source's size is named custom rather than small (TestUpgradeTargetChecksRoomAndKeepsPITRDays).

Shared projects on an old major

A shared project lives on a cluster of its major, and nothing moves it off when the major is deprecated or retired. It keeps running there, and new shared clusters of a retired major may still be added for it. Its upgrade uses the same preflight and handler: the target is the least-loaded shared cluster of the newer major in its region that its organisation may use, the schema is tried in a scratch database there, and the move copies into that cluster (no new instance, so a rollback drops the partial copy instead). The old database is kept read-only (default_transaction_read_only) for 48 hours. A shared project needs such a cluster first: "no shared cluster runs Postgres 18 yet (Admin → Nodes → Add shared cluster)". V3 §2.4 asks for "one shared cluster per supported version in each region", and nothing creates one automatically.

See for what is archived before and after an upgrade, for switchovers, and for how the poolers hold clients during a freeze.

Failure handling

What failsWhat happens
A notice emailLogged, and its pg_version_notices row rolled back: the hourly sweep sends it again until it goes, or until a later step supersedes it. A deprecation withdrawn and made again sends no new first notice to organisations that had one, since their rows remain.
A retirement date passesNothing runs. Every read sees the major as retired from that moment.
A project on the instance is busyThe instance waits for a later sweep.
An HA instance has no announcementIt waits. A draft announcement is proposed for the first window far enough away.
Pausing the poolers failsEverything paused so far is resumed, the run is recorded as failed, and the instance is not touched.
The server stops during an upgradeThe operation's lease runs out and another worker runs it once more, resuming the poolers first; a last attempt that fails runs OnFail, which resumes them and records the failure.
The recreate failsThe agent starts the old container again. Recorded in minor_upgrades with the error, which says if even the old container would not start; an alert fires, and the sweep skips the instance until a newer release or Upgrade now.
An HA upgrade stops after the switchoverThe new leader runs the new release, so the instance no longer looks behind. The old leader stays a standby on the old release until something recreates it.
A major upgrade fails before the cutoverRetried once from a clean target database. Then failMove: the source serves again with no data lost, and the new instance is destroyed.
A major upgrade fails after the cutoverThe retry and OnFail both run only the finishing steps (route, resume, cleanup, stop the old instance, first backup).
The worker dies part-wayThe operation's lease runs out and another worker takes it up. See the operations queue.
