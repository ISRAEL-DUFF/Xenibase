Project auth is sign-in for the users of an app built on Xenibase, not for Xenibase's own operators (those are on ). It is served by xenibase-edge at /auth/v1/ and speaks the GoTrue dialect, so Supabase's client libraries work against it unchanged (V4 §4). Users live in the project's own database, in the xb_auth schema, so they move with it on promotion, branching and restore. xenibase-server keeps what must not reach the edge's request path in clear: email and SMS credentials, the queues that send codes, and the webhook hooks.

Who does what

projauth does every read and write of xb_auth, on the caller's transaction. The edge's routes (edge.auth and the files beside it) run each request as one transaction as the project's edge login (withAuth), the only login with rights on those tables. xenibase-server renders and queues messages and hooks (authmessage.go, authhook.go), and holds the settings, sealed secrets and signing keys (authconfig.go) that reach the edge on the signed feed ().

The xb_auth data

Schema versions 2 and 3 in services/schema.go create the tables; version 10 adds to them. Request roles see only xb_auth.user_profiles, with no hashes, tokens or factors: a user sees their own row, the service role and the owner every row, anon nothing.

Passwords

signup checks the address, passwordProblem (at least password_min_length characters, 8 by default, at most 256 bytes refused rather than cut, optionally letters and digits) and the redirect, and hashes before opening the transaction. Hashing is argon2id at OWASP's minimum (19 MiB, 2 passes, 1 lane), because one edge hashes for every project in its region. Hashes take one of as many slots as the edge has CPUs (hash).

  • Confirmation on (the default): a new user is created unconfirmed and sent a code and link. The answer is {"confirmation_sent": true} whether the address was new, unconfirmed or confirmed, so sign-up does not reveal who has an account (M31 #6).
  • Confirmation off: the user is signed in at once, and a taken address answers 422 user_already_exists, as Supabase does. The security review accepts this.

signinPassword locks the user's row, refuses a locked user, and checks the password with CheckPassword, which hashes against a fixed dummy hash when there is no user, so a missing user costs the same as a wrong password. A wrong password counts in RecordFailedSignIn: from the fifth in a row the user is locked for a minute, doubling with each further failure up to a day. A success clears the count. A bcrypt hash brought from Supabase is accepted and replaced with argon2id in the same transaction (Rehash, conditional on the old hash).

The lockout is per user, not per client, so anyone who knows an address can lock its owner out of password sign-in with about fifteen wrong guesses spread over a few minutes, for most of a day. Magic links and OAuth still work.

A squatter can sign up first with someone else's address and a password of their own. While the account is unconfirmed the squatter cannot sign in. A sign-up for an address whose row is still unconfirmed replaces the row's password with the new request's and ends its sessions. Each code records the password its request set (NewPasswordCode; a code sent again by /resend keeps the one it replaces). useVerified clears the password when a magic link or recovery code first proves the address (M31 #12), and when a signup or invite code does and the password is not the one its request set (KeepsPassword):

Resolved

A squatter used to keep their password through the owner's own sign-up: signup found the unconfirmed row and only sent a new code, dropping the owner's password, and useVerified cleared passwords only for magiclink and recovery. Admin-API invitations (linkFor reused the row) and phone sign-up (signupPhone) did the same. Now a sign-up again for an unconfirmed address or number, or a sign-up link from the admin API with a password, replaces the password and ends the row's sessions, and its code records that password. A signup, invite or phone_signup code that first proves the address or number clears any other password and ends the sessions (usePhoneVerified for numbers). A squatter who signs up again after the owner therefore leaves the owner's code with no password rather than theirs. TestSquatterLosesPasswordToOwnersSignup covers each path.

A new password through PUT /auth/v1/user (updateUser) ends every other session of the user (ASVS 3.3.3, V4.1-M11 #4). It does not ask for the current password. A user with a verified factor needs an aal2 session to change the password or email (MFA). A password set through the admin API or the dashboard ends no sessions.

Email links and codes

Every email carries a 6-digit code and a link token, made by NewCode from crypto/rand. Both last 10 minutes; an invitation lasts 24 hours. Only hashes are kept. The kinds are signup, magiclink, recovery, invite and email_change.

  • Code. POST /verify with email and token goes to VerifyCode. It takes the newest unexpired code of the allowed kinds for that target, under a row lock. A wrong code adds one to attempts. After five, the code is refused even when right, until it expires or a new code replaces it, which the one-a-minute rule holds back (V4.1-M11 #2).
  • Link. GET /verify?token=…&type=… needs no API key, since it is clicked from a mail client (keylessAuth). VerifyToken deletes the row by the token's hash. verifyLink redirects with the session in the URL fragment, never the query, with Referrer-Policy: no-referrer. Without a redirect it shows a plain page.
  • One a minute. tooSoon refuses a code for an address within 60 seconds of the last request for one of the same kinds, counting requests in code_requests (LastCodeRequest, under an advisory lock per address) whether or not the address has a user.

The edge asks xenibase-server for the email inside its transaction (sendEmail), so a refusal rolls the code back. queueEmail renders the project's template (the default if it fails on real data), seals and queues it. A worker sends through the project's SMTP, or the platform's at 30 an hour per project (PlatformEmailsPerHour), with five tries.

Redirects are checked by redirectAllowed: the site URL's scheme and host with its path or one below it, or an exact entry of redirect_urls, or, when allow_wildcard_redirects is on, a pattern. patternAllows matches a pattern against the parsed URL part by part: the scheme exactly, the host label by label with * inside one label (hostMatch), the port exactly or * for any, and the path with * matching anything but / and ** anything (globMatch). A query or fragment passes only a pattern with a matching one or a path ending in **. URLs with a user part are refused.

Resolved

Wildcard redirects used to match the whole URL as text, so they allowed other hosts: globMatch ran the pattern over the raw string, where * also matched ? and #, and with https://*.example.com/** the URLs https://evil.test?.example.com/ and https://evil.test#.example.com/x passed, sending a magic link's tokens to evil.test. Now the candidate is parsed first and patternAllows compares scheme, host, port and path separately, the host by its labels, so * stands for one label (or part of one) and never reaches the query or fragment. TestRedirectPatternsMatchHostAndPathApart covers these URLs and others.

recover and resend answer {"sent": true} whether or not the address has a user, as M31 #6 intends, and so does their rate check.

Resolved

The one-a-minute check used to reveal which addresses have users: tooSoon counted codes for the address, and only a real user gets a code, so two POST /recover calls answered 200 then 429 over_email_send_rate_limit for a known address and 200 twice for an unknown one, and signin/otp without user creation did the same for addresses and numbers. Now every request for a code is recorded in xb_auth.code_requests (schema version 10) before the user is looked up, and the rule counts requests, so both kinds of address get 200 then 429. TestCodeLimitsDontRevealUsers covers recovery, email and phone sign-in codes and /resend.

Anonymous sign-in (signinAnonymous, a sign-up with no credentials, off by default) makes a user with is_anonymous. Confirming an email or phone change, or linking a provider, makes it permanent. An email change sends a code to the new address only. The old address is not asked.

Phone codes by SMS and WhatsApp

messaging.Normalize makes E.164 (08031234567 becomes +2348031234567; other countries need + or 00), and Country maps the calling code to a country (the largest for shared codes such as +1). The edge (countryAllowed) and xenibase-server both check it against the project's list.

Phone codes are the same one_time_codes rows, with kinds phone (sign-in), phone_signup and phone_change, and the same five tries. signinPhoneOTP creates the user when sign-ups allow it and answers the same either way. The project's SMTP host and provider base URL used to bypass the outbound rules that hooks go through: mail.Config.Validate took any host and port, PhoneProvider.validate any https base_url, xenibase-server dialled them directly, and the SMTP test's 502 carried the dial error, so a project admin could map the control plane's network or have the worker POST to an internal service. TestAuthSMTP answers 400 for a refused address and a generic 502 for any other failure, whose detail goes only to the log. TestProjectSMTPAndProviderGoThroughOutbound and TestCheckAddr cover it.

OAuth providers

Each project uses its own app at Google, Apple, GitHub, Facebook or Microsoft (oauthProviders). Secrets travel sealed on the feed, and Apple's client secret is an ES256 JWT the edge signs (appleSecret).

  1. Authorize. oauthAuthorize (no API key, the sign-in rate) checks the redirect, takes the app's PKCE challenge (S256 by default, or plain, 43 to 128 characters), and stores a 10-minute flow_state row with the state's hash, the edge's own PKCE verifier to the provider, a nonce and the redirect.
  2. Callback. callback (GET, or Apple's form POST) uses the state once, by overwriting its hash, then exchanges the provider's code itself (providerUser). ID tokens from the token endpoint are trusted over TLS, as OIDC Core §3.1.3.7 allows, after idTokenClaims checks audience, expiry and nonce.
  3. Hand-off. With a challenge, the app gets a one-time code in the query (5 minutes), which exchangePKCE trades with the verifier at token?grant_type=pkce. The row is deleted before the verifier is compared, so a wrong verifier burns the code. Without a challenge, the session goes in the fragment (the implicit flow).

oauthUser picks the user in this order: the identity's owner; the signed-in user linking it (/user/identities/authorize, when manual_linking is on); a user with the same address if the provider says it is verified; or a new user. An email the provider does not mark verified never links. Microsoft's counts as unverified, which closes the nOAuth class of takeovers, and Facebook's counts as verified. Joining an unconfirmed user by a verified email clears its password and ends its sessions, as magic links do. UnlinkIdentity refuses a user's last identity. Unlinking the email or phone identity also clears that column.

Note

The state is tied to its flow_state row, not to a browser: the edge sets no cookies. With PKCE the app's verifier covers that. Without it (the implicit flow, or a link flow), a provider URL started by one person and finished by another completes the first person's flow.

MFA

Second factors are TOTP apps and, when mfa_phone is on, phone codes. The policy is off, optional (the default), required, or claim (required for users whose app_metadata.mfa_required is true). The gateway applies it to data and realtime requests:

  • Enrol. mfaEnroll adds an unverified factor (Enroll); TOTP returns a 160-bit secret and its otpauth:// URI once. A user who has a verified factor enrols another only from an aal2 session (belowMFA, which reads the session's aal from the database); below it the answer is 403 insufficient_aal.
  • Challenge. mfaChallenge makes a challenge good for 5 minutes. A phone factor is sent a 6-digit code, at most every 30 seconds per factor (challengeEvery), under the same server caps as sign-in codes. A TOTP challenge has no limit.
  • Verify. VerifyChallenge allows five wrong tries per challenge. Wrong codes also count on the factor across its challenges: from the fifth in a row (FactorLockoutAfter) the factor is locked for a minute, doubling with each further one up to a day, and both its challenges and its codes answer 429 mfa_factor_locked with Retry-After (factorLocked). A right code clears the count. A TOTP code is checked one 30-second step either side (totp.Verify), and its step must be later than the factor's last_used_step, so a code works once. An unverified factor can be verified only when the user has no verified one or the session is at aal2 already. A right code verifies the factor, and StepUp raises the session to aal2 and appends to amr. The session's refresh tokens are replaced and new tokens issued.
  • Remove. mfaUnenroll needs aal2 to remove a verified factor. When none is left, LowerSessions drops the user's sessions to aal1.
Resolved

A session at aal1 used to be able to enrol a new factor and so reach aal2: mfaEnroll checked only that the session was alive, and mfaVerify raised the session on any factor of the user, so a password or a recovery link was enough to pass mfa_required. updateUser likewise changed the password or email at aal1. Now, when the user has a verified factor and the session (as stored, not as the token says) is below aal2, enrolment answers 403 insufficient_aal, a password or email change 401 insufficient_aal, and so does verifying a factor enrolled before the user's first one was verified, as GoTrue does. A user's first factor still raises the session that verifies it. TestAAL1CannotChangeWhatProvesTheUser covers each.

Resolved

TOTP guesses used to be limited only by the project's request rate: five wrong tries used up a challenge, but a new one could be had at once, the /factors and /mfa/ routes had no auth rate group, and nothing counted failures per factor, so the gateway's 12,000 requests a minute per key found a code in under an hour. Now those routes are in the mfa group (30 a minute per IP), /user and sign-out in user (60), and five wrong codes in a row on a factor, across challenges, lock it for a minute, doubling up to a day, which leaves a few dozen guesses a day. TestTOTPGuessesLockTheFactor covers the lockout and both groups.

Sessions and refresh tokens

startSession is the one way in: the MAU check, other sessions ended under single_session, the session and its first refresh token (NewSession, not_after from session_max_seconds), the audit entry, the after-sign-in hook, the access token.

Row locks serialise two refreshes with one token, and the second ends the session: the theft detection (refresh_token_reused, audited). With no grace period, a client that refreshes twice at once, such as two tabs, signs itself out too. session_inactivity_seconds (0 by default, otherwise at least 600) ends a session not refreshed for that long. Sign-out (signout) deletes the session (local), all of them (global) or the others. A ban refuses sign-in and the next refresh but deletes no session (M31 #10). Admin sign-out ends them all.

Routes under /auth/v1/ that act for the user read the session first (liveUser), so an ended session's token fails there. The data API, storage and realtime only verify the token, so it works there until it expires.

Spec and code differ

docs/security-review.md (ASVS 3.3.1) says "ended sessions' access tokens are refused at once (the edge checks the session), not at expiry". That holds for /auth/v1 only. After sign-out, a password change, reuse detection or a ban, a stolen access token keeps reading and writing data until its exp: an hour by default, up to a day. V4 §4.8 says the same thing the code does ("a short access-token lifetime bounds the window").

Signing keys and tokens

Every project has its own P-256 key, made when backend services are turned on (ensureJWTKey). The private half is sealed under the master key with the row's id as associated data. A branch gets a new key, never its parent's (). The feed decrypts each live project's active key and sends it to the edges (feed), which sign tokens themselves (M31 #2). Every edge in a region therefore holds the private keys of every project there.

  • Lifetime. access_token_ttl, 3,600 seconds by default, 300 to 86,400. jwtes.Sign writes alg: ES256 and the key's kid.
  • Verifying. The gateway takes a Bearer token only with the publishable key (authorize). jwtes.Verify refuses any algorithm but ES256, finds the key by kid among this project's keys only, checks the signature, exp and nbf with a minute's leeway, and requires aud to be the project's ref. The gateway then requires role: user. A token from another project fails on both key and audience (FuzzGatewayIsolation).
  • JWKS. GET /auth/v1/.well-known/jwks.json (no key, cached 10 minutes, jwks) lists the active and verifying keys, so the project's own servers verify with no shared secret.
  • Rotation. RotateSigningKey (project admin) demotes the active key to verifying until 24 hours and 5 minutes from now, the longest possible lifetime plus skew, whatever the project's own TTL. It then inserts the new key. A trigger on project_jwt_keys puts the project back on the feed. The services loop retires lapsed keys (RetireJWTKeys), and they leave the JWKS and the edges.
Risk

A leaked signing key cannot be withdrawn at once (low). Rotation is the only control, and it keeps the old public key verifying for 24 hours and 5 minutes. There is no route to retire a key now. Every edge holds its region's private keys, so after an edge compromise forged tokens stay valid for a day after rotation. Not reproduced. Fix: a revoke action that retires the old key at once.

Risk

Email codes have no cap per address beyond one a minute (low). A code allows five guesses, and the next can be asked for a minute later, with no daily or hourly limit on an address when the project sends through its own SMTP. Phone numbers have the server's five an hour. A chosen address's sign-in code then takes 7,200 guesses a day, about 0.7% a day, with a sign-in email a minute as the only warning. Not reproduced. Fix: an hourly and daily cap per address, as for numbers.

Monthly active users

A user is active in a month when they sign in or refresh. The edge notes the pair (meter.activeUser) and sends it with its reports. recordActive inserts one auth_mau row per project, month and user, and adds one to the auth_mau usage metric only when the row is new, so MAU counts distinct users (M31 #9). The dashboard shows the month's count. Billing is on .

When the organisation's plan has a MAU limit and it is used up, the plan-limits sweep sets mau_blocked on the feed. It also sends a Bloom filter of the month's counted users at 1% false positives (bloom.New), about 12 KB for 10,000 users. mauAllowed lets in users the filter may hold (bloom.Has), or users this edge process let in this month (up to 50,000 per project), and refuses others with 429 mau_limit_reached and Retry-After at the next month. A false positive lets a new user in. The overshoot is bounded by one sweep of traffic (V4.1 §3.2).

Spec and code

Spec and code differ
  • V4 §4.1 allows "shared Xenibase dev credentials" for OAuth on Free. There are none: enabling a provider requires the project's own client id and secret (Validate).
  • V4 §4.8's leaked-password check and §4.5's bounce and complaint handling are not built. V4.1 §1.3 records both as deviations, and V4.1-M11 #9 accepts the password check as an ASVS gap.
  • V4 §4.6 puts captcha "on OTP requests". It covers signin/otp but not /resend, which also sends SMS and WhatsApp codes, nor phone MFA challenges.
