File storage is the third backend service (V4 §5). Buckets and objects are rows in the project's own database, in xb_storage, read and written as the caller's role, so the project's row-level security policies decide who may touch a file. The bytes are in the region's object store, under a key made from the object's version, which no caller chooses. xenibase-edge serves /storage/v1/ (storageRoute); xenibase-server runs the dashboard's storage, the sweep and the CDN purges.

An overwrite is a new key and a row update, and a reader streaming the old version finishes, since old bytes stay for the garbage grace (a minute). A move changes only the row; a copy copies the bytes to a new version (decisions V4-M33 #2). One trigger keeps the queue and the totals:

The trigger is SECURITY DEFINER and owned by the platform, so a policy or a request cannot forge the totals or the queue. A TRUNCATE by the owner fires no row trigger: the totals drift until the sweep recounts them, and the bytes are left to the reconciler (below). foldername, folder, filename and extension are helpers for policies, such as xb_storage.folder(path, 1) = xb_auth.uid()::text.

Rules the edge and the server share

internal/files is imported by both binaries, so a bucket, path or token the dashboard makes is one the edge accepts:

  • Buckets. BucketRe: 1 to 63 lowercase letters, digits, _, . or -. ValidBucket also refuses, for new buckets, the ten words the routes use after /object/ and anything shaped like a UUID, so /upload/{id} never collides with /upload/{bucket}/….
  • Paths (ValidPath, below) are never part of a store key, so no path can reach another key.
  • Keys. Prefix is files/<ref>/, ObjectKey adds objects/<version>. A version is a uuid column, so even a row an owner writes by hand names a key in its own project's prefix.
  • SQL. InsertSQL (an upsert is ON CONFLICT … DO UPDATE, so an overwrite needs the UPDATE policy), ListFolderSQL (one folder level after a keyset cursor) and LikePrefix; plus the MIME checks and URL tokens below.

TestPathsAndBuckets and the fuzz test in internal/files cover these; TestStorage sends %2e%2e, an empty segment and a NUL through the edge and gets 400 invalid_path.

Who may read and write

A keyed request passes the key and JWT check (Project auth) and MFA if required. The edge then runs the statement the request implies on xb_storage.objects as the caller (decisions V4-M33 #4), inside asRole, whose objectsGate refuses anon and user with 403 rls_required while row-level security is off: the owner owns the table and could turn it off. With no policy, anon and user (NOBYPASSRLS) reach nothing and only the secret key's service role, which bypasses policies, reaches files. The edge's own login passes its own policy, xenibase_edge … USING (true), where the decision was made elsewhere:

Anyone who can name an object in a public bucket can read it; listing still needs a policy. A private bucket answers 404 on the public routes. A policy's refusal is 403 not_allowed for a write and 404 for a read (storageError), so a reader cannot tell a hidden file from a missing one.

The dashboard and xenibase storage act as the platform through /api/v1/projects/{id}/files…, with no policies but the same rules and a 50 MB upload cap (UploadFile, decisions V4-M33 #14), and download as a sandboxed attachment from the control plane's origin (DownloadStorageObject).

Uploads

A direct upload (putObject) is POST (add X-Upsert: true to overwrite) or PUT (always upsert) to /object/{bucket}/{path}, with the bytes as the body or as the file part of a form, and optional metadata (a JSON object of at most 8 KB, plain or base64) in X-Metadata or a metadata part. In order:

  1. Bucket, read with the edge's login.
  2. Size. checkSize takes the smallest of 50 MB (directMax), the plan's largest upload and the bucket's file_size_limit. A known length over 50 MB but within the plan is told to use parts. With a quota, usage.bytes, the declared sizes of the large uploads in progress and the size must fit (413 quota_exceeded).
  3. Type. The first 512 bytes and the declared type go through DetectMIME, then the bucket's list (415 mime_not_allowed; entries are a type, type/* or */*).
  4. Policy, dry run. mayWrite runs the insert as the caller with a placeholder ETag and rolls it back, so no bytes are stored for a request the policies refuse.
  5. Bytes. A body of unknown length is first spooled to an unlinked temporary file, at most the limit plus one byte (spool). Then one PutObject of exactly that length, hashed with SHA-256 on the way.
  6. Row. commit inserts it as the caller, so the policies see the real size, type and metadata; on failure the new bytes are deleted.

Large uploads (startUpload, V4 §5.3) go straight to the store. POST /upload/{bucket}/{path} with the size, type, upsert flag and metadata runs the same checks, starts a multipart upload, records an uploads row for 24 hours and returns presigned URLs for every part (at least 16 MiB each, at most 10,000 parts), each signed for exactly its part's length. The quota check and the row's insert run in one transaction holding the usage row, so uploads started together count each other, and a project may have 100 open (429 too_many_uploads). GET /upload/{id} lists the parts the store has and gives fresh URLs for the rest, so a failed part is sent again alone. POST /upload/{id}/complete (completeUpload) lists the parts at the store rather than trusting the client's ETags, requires parts 1 to n with exactly the declared total, completes, sniffs the first 512 bytes (deleting the object on a mismatch), and commits the row as the role and claims saved at the start. DELETE /upload/{id} aborts. The upload id is the only credential for these three.

Resolved

Parts used to be neither bounded nor counted until an upload completed: PresignPart signed the part number and upload id but no length, so each part URL took up to the store's part limit (5 GiB on S3 and R2) for 24 hours, and open uploads were not in the quota check, so uploads started together each passed against the same total. Now PresignPart signs Content-Length into each part's URL (the fixed part size, the last part the remainder), so the parts can hold no more than the declared size; checkSize (and the dashboard's upload) counts the declared sizes of the uploads in progress; startUpload checks the quota and records the row in one transaction that holds the usage row, so concurrent starts take turns; and a project may have maxOpenUploads (100) open (TestPresignedPartSignsItsLength, TestMultipartUploadsAreBoundedAndCounted). In-flight parts are still not in storage_gb_hours, but they are bounded by the declared size and the 24-hour expiry.

Signed URLs

A signed URL lets someone without a key read one object, or upload to one path, until it expires (V4 §5.4, decisions V4-M33 #5). The token is a files.Token as base64url JSON (kind get or put, ref, bucket, path, expiry; optionally a download name, transform, upsert flag and owner, and for an upload the id of its upload_tokens row), a dot, and base64url of HMAC-SHA256 over "xenibase storage url\x00" and the payload. The key, storageSecret, is keyring.Derive("xenibase storage urls "+ref, 32), sent to the edge on the feed; it cannot be rotated per project, so only a new master key ends outstanding URLs.

Resolved

A signed thumbnail used to open the original: signDownload put the requested transform into an ordinary get token for a /render/sign/ URL, and neither Verify nor signedDownload looked at Transform, so the same token with render/sign changed to object/sign downloaded the full source. signedDownload now refuses a token that carries a transform (400 invalid_signature), as render already refused one without, so a signed preview serves only that render (TestSignedThumbnailDoesNotOpenTheOriginal).

Resolved

A signed upload URL used to skip the policies on what is written and could be spent many times: the policies saw only a placeholder row when it was made, signedUpload called putObject with no request so commit wrote the real row with the edge's login, which passes every policy, and nothing marked a token spent, so an upsert URL overwrote its path as often as its holder liked for up to 7 days. Now signUpload saves the caller's role and claims in a row of xb_storage.upload_tokens (schema version 8), named by the token's ID, and caps the URL at 2 hours. signedUpload uploads as that role and claims, so the dry run and the commit meet the policies with the real type, size and metadata (and an upsert asks UPDATE), and spendToken deletes the row in the edge's own transaction around the commit: only a write that commits spends the URL, and a second upload with it, on any edge, waits for the first and then finds it gone (400 invalid_signature). A token made before the upgrade has no row and is refused (TestSignedUploadIsTheSignersAndSingleUse).

Downloads, ranges and cache headers

Every download path ends in serveObject. It answers 429 storage_egress_limit while the organisation's monthly download allowance is used up, then sets the headers:

With nosniff also set, files are served from the project's API origin without running there: only PNG, JPEG, GIF, WebP, AVIF, BMP, video, audio, plain text and PDF are inline (inlineTypes); HTML, SVG and the rest are attachments. ?download forces an attachment, with that name unless it is 1 or true, percent-encoded into filename*. One range (bytes=a-b, a- or -n) is passed to the store and answered 206, or 416 outside the object; several or a malformed one get the whole object. If-None-Match on the store's ETag answers 304 before the store is asked. A served body counts as storage egress (meter.record).

The decoder is picked from the magic bytes, not the stored type; a GIF becomes a PNG of its first frame. A render is stored at transforms/<version>/<hash>.<format>, hashed from transformKey, and answered X-Cache: MISS; repeats are read from there (HIT) without a slot. Render workers (V4.1 §12.4, decisions V4.1-M11 #5). Unless XENIBASE_EDGE_RENDER_IN_PROCESS is set, each render runs in a child, xenibase-edge render-worker, one per slot, started on first use, with GOMEMLIMIT (XENIBASE_EDGE_RENDER_MEMORY_MB, 512 by default) and an RLIMIT_AS of 16 times that, since the WebAssembly runtimes reserve far more address space than they use (limitMemory). Requests and replies are length-prefixed frames on its stdin and stdout, a JSON header (at most 64 KiB) then the image (at most 26 MiB, readFrame).

A worker does not recover panics: a decoder that panics or runs out of memory ends it, and the slot starts a fresh one next time (renderPool.render). TestRenderPool and TestRenderWorkerCrash crash one with a test marker while other renders carry on.

A crash boundary, not a sandbox

Workers run as the edge's user, with its file system and network, and inherit its whole environment (start), XENIBASE_EDGE_SECRET included. The decoders are memory-safe Go and WebAssembly, so an escape needs a bug there first; a minimal environment and a seccomp profile would be the cheap next steps.

Where the bytes live

File storage has no target of its own. cmd/server sets services.Files to backup.FilesTarget, the region's backup target, or its in-country target for a data-residency project (decisions V4-M33 #1, Backups). Under it:

KeyWhat
files/<ref>/objects/<version>An object version's bytes, typed with its MIME type
files/<ref>/transforms/<version>/<hash>.<format>Cached renders of that version
projects/…, instances/…, metadata/…The same bucket's backups, WAL-G archives and metadata backups

The target's own Prefix, if any, comes first (Target.Key). The edge gets the target, the project's prefix, the signing secret and its limits in storageConfig, and keeps one client per project while the target is unchanged. The ref is the services ref (8 characters, unique), not the project ID, and a branch has its own.

Risk

Every edge holds the keys to the region's backups. The feed hands each edge the full storage.Target, access key and secret, of the bucket that also holds the region's encrypted backups, WAL-G archives and metadata backups; files and backups are kept apart only by the edge computing keys under files/<ref>/. The edge is the internet-facing process that parses uploads, forms and images, so code running in it, or a read of its memory, can delete every backup in the region, the copy meant to survive such an incident. A bucket of its own for files, or credentials scoped to files/, would keep a compromised edge away from the backups.

Risk

A region move leaves every file behind. Platform admins may move a non-residency project to another region's node (checkMoveRegion), and the move rewrites projects.region (moves.sql). The next feed points the edge at the new region's store, but nothing copies files/<ref>/ across: every object then answers "the object's data is missing", and the old bytes are never removed or billed, since neither the reconciler nor the deleted-project clean-up looks outside the current region. Decisions V4-M33 #13 records file moves as not built, but the move neither refuses nor warns. Refusing a region move while xb_storage.objects has rows, or copying the prefix as a step of it, would make it safe.

The CDN and purges

The operator puts a CDN in front of the edges (decisions V4-M33 #11). With XENIBASE_CDN_CLOUDFLARE_* set, the server purges through cdn.Cloudflare, 30 URL prefixes a request, 15 seconds each (TestCloudflarePurge). A purge is due whenever files leave a public bucket's URLs: the bucket goes private, is deleted or emptied, or one of its objects is deleted, replaced or moved away. The edge's handlers send these as storage events in the background (storageEvent, three tries), and the dashboard's UpdateBucket, DeleteBucket, DeleteFiles and UploadFile purge directly. An object purges each public route's prefix up to its path, which covers its renders; more than 20 objects at once purge the whole bucket.

Resolved

A purge used to be tried once, and only when a bucket went private: if Cloudflare was slow or refused, the caller logged a warning and nothing retried, so the CDN could serve the now-private files for up to cache_seconds (a year at most), and deleting, overwriting or moving a public bucket's object, or deleting the bucket, purged nothing. Now every purge is a row in the metadata database's cdn_purges (migration 00083), tried at once by purge; one the CDN refuses stays, and RetryCDNPurges, part of every sweep, claims the due ones and tries them again after a minute, doubling to an hour, until the CDN takes them (rows older than a year, the longest cache time, are dropped). The events above cover deleted, replaced and moved objects and deleted or emptied buckets (TestCDNPurgesAreQueuedAndRetried, TestPublicFilesLeavingTheirURLsArePurged). An edge that cannot reach the server after three tries still only logs the event.

The sweep, metering and clean-up

Deleted and replaced bytes go in two steps. The edge, a little after a write that queued garbage, removes queued versions older than the grace that no row names again, and their renders (collectSoon, collect). Anything it misses is left for xenibase-server, whose StorageSweep runs every 5 minutes on every server (services.Run) over the projects StorageProjects lists: services enabled, schema 4 or later, project active and not paused.

  1. Measure and meter (sweepProject): sum xb_storage.objects as the admin, correct usage, record project_storage, and set this hour's storage_gb_hours (a replace, so several servers meter once).
  2. Collect (collectGarbage): 200 queued versions at a time, FOR UPDATE SKIP LOCKED, deleting the bytes and renders of those no row names. Then abort uploads whose row has expired.
  3. Limits (storageLimits): each project's quota is the organisation's file_storage_mb less what its other projects hold, plus upload_max_mb and the month's egress and transform flags, written only when they change, which moves the feed.
  4. Abandoned uploads (abandonedUploads): abort any multipart upload under files/ older than 25 hours, in each region's store.
  5. Deleted projects (cleanupDeleted): delete files/<ref>/ 30 days after deletion, with the final backup (ScheduleStorageCleanups).
  6. CDN purges (RetryCDNPurges): try again the purges the CDN has not taken (above).

The reconciler, reconcileProject, lists the prefix before reading the rows, so an upload finishing in between is not an orphan. It deletes bytes that no row, upload or queued removal names once 7 days old, and records rows without bytes for the storage page (decisions V4-M33 #12). TestStorageSweep covers the sweep, the reconciler and the purge.

Risk

Some stored bytes are never metered. storage_gb_hours sums objects.size over the projects StorageProjects lists. Turning backend services off (Disable) keeps every file (V4 §2.4) but takes the project out of the sweep, so a paid organisation without a hard file quota can upload, turn services off and stop paying for the storage for as long as the project lives. Cached renders are not objects: each costs one transform, then is stored unmetered until its source version goes, and one image can be rendered at every size, fit, format and quality. Multipart parts in flight are the third gap (above). Metering projects with files whatever their services' state, and measuring transforms/ too, would cover them.

Risk

The reconciler runs only after a server has been up for a day. services.Run keeps its last run in a local variable that starts at zero, skips the first chance on purpose and waits 24 hours from start. A server deployed more often than daily never reconciles, and when every server is deployed together none does: orphaned bytes (a failed delete after a refused commit, a TRUNCATE) are never removed and rows without bytes never reported. Keeping the last run in the metadata database, as the backup scheduler keeps its window, would make it nightly as V4 §5.6 asks.

Backups hold rows, not bytes

A restore brings back xb_storage rows, never bytes: files deleted since come back as rows without bytes, and files uploaded since lose their rows and go with the reconciler (decisions V4-M33 #13). A restore cannot undo deleting a file.

Branches' files

A branch has its own ref, so its own prefix and signing secret, and its rows come with the data copy. With copy_files, copy_branch_files copies each version those rows name from the parent's prefix to the branch's inside the store; after a reset, strandedFiles first queues the branch's own bytes no refilled row names. Without it, the rows name bytes the branch lacks. Copies are the branch's objects, metered as such ().
