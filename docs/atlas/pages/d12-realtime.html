Realtime is the part of backend services that pushes to clients over a WebSocket: row changes from chosen tables, broadcasts between clients, and presence (V4 §6). There is no realtime package. xenibase-edge serves it from four files in internal/edge: the connection and its channels (realtime.go), the per-project hub and change feed (rthub.go), the wire format and filters (rtproto.go), and broadcast, presence and history (rtbroadcast.go). xenibase-server keeps the limits and clears what the edge leaves behind (internal/services/realtime.go). Everything realtime stores lives in the project's own database, in the xb_realtime schema. Delivery is at most once: a client that was away refetches.

Which tables send changes

A table sends changes once its owner or the dashboard turns realtime on for it. xb_realtime.enable(regclass), created by schema version 5 in schema.go, refuses anything that is not a table, tables in xb_*, pg_*, information_schema and xenibase, a caller who does not own the table, and a table without a primary key. It then installs one AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW trigger, xb_realtime_capture, with the primary key columns as its arguments, and records the table and its key in xb_realtime.tables. disable drops both. The dashboard calls them as the platform through SetRealtimeTable (PUT …/realtime/tables/{schema}/{table}, action project.realtime_manage, developer and above).

There is no publication, no replication slot and no logical decoding. The trigger writes to an outbox in the changing transaction, so a rolled-back change never appears:

  • What is stored. record is the whole new row. old_record holds only the primary key columns, so an update never carries the previous values out. xid defaults to pg_current_xact_id(), and at to now(), the transaction's start, which clients receive as commit_timestamp.
  • Who may write it. capture is SECURITY DEFINER, and only the edge login has SELECT on xb_realtime.outbox. No request role can read it or insert into it, so a client cannot forge a change.
  • The wake-up. Each captured row also runs pg_notify('xb_realtime', ''). Postgres folds identical notifications in one transaction into one, so a bulk insert wakes the edge once.
  • Clean-up. sweepRealtime deletes outbox rows older than 5 minutes, relayed messages older than 2 minutes and history older than 7 days, as the platform, on the 5-minute storage sweep, for every active project with schema version 5.

How the edge learns what is on: the edge feed (feed.go) carries the project, its keys, its exposed schemas and the realtime limits, but not the list of tables. The hub reads xb_realtime.tables itself (tableKeys) and caches it for 3 seconds. A join for a table not in the cached list reads it again at once, so a table just turned on can be subscribed to without waiting.

The hub and the listening connection

Each edge process has one rtHub per project, made on first use and kept for the life of the process. It holds the project's open connections, their joined channels (by topic) and the channels' subscriptions (by schema.table), the connection count and message counter for metering, the outbox cursor, and the broadcast and presence state. The first channel to join on a project starts listen, whatever the channel is for. It runs until the hub has had no channels for 30 seconds (rtLinger), so a reconnecting client finds it still there, or until the project leaves the feed (stop, below). A listener started after a stopped one waits for it to finish, since the cursor is the listener's own.

listen opens a session-mode connection (sessionConn) as the project's edge login, through the region's session pooler on :5432, whose address the feed carries (or SessionAddr overrides). A transaction-mode pooler cannot hold LISTEN. In session mode PgBouncer gives that client a server connection of its own for as long as it stays, so each project with realtime clients costs one backend connection per edge process, on the project's session pool. Without a session pooler in the feed the hub polls the outbox every second through the ordinary transaction-mode pool instead.

serve runs LISTEN xb_realtime; LISTEN xb_realtime_bc, sets the cursor, then loops: wait up to a second for a notification, read the outbox on a change notification or every second regardless, relay a broadcast notification from another edge process, and say hello to the others every 10 seconds.

Reading the outbox in transaction order

The cursor is a low-water transaction id and a map of the transactions at or above it already read, with the last row of each (decision M34 #3). initCursor starts it at the current snapshot's xmin. Each drain takes a new snapshot and reads rows whose transaction is visible in it and not yet read:

Everything below the new snapshot's xmin has finished, so the low-water mark moves up to it and older entries leave the map. A transaction still running at the snapshot is not visible yet and is read by a later drain. A long-running writer does not hold back later commits. The price is that delivery follows transaction ids, not strict commit order: two transactions that both commit between drains go out in the order they got their ids. When nobody on this edge subscribes to changes, drain just moves the mark to xmin and reads nothing.

Each batch also drops the data API's cached reads of the tables it touched on this edge (dropCached, V4.1 §10), so every edge listening to a project invalidates its cache whatever wrote the rows.

The WebSocket protocol

The wire format is the Phoenix channels protocol that Supabase's realtime clients speak, so they connect unchanged (decodeMsg, decision M34 #1). Version 1.0.0 sends each message as a JSON object and 2.0.0 (?vsn=2.0.0, or the first array a client sends) as [join_ref, ref, topic, event, payload]. A frame that is neither closes the connection.

A client upgrades at /realtime/v1/websocket?apikey=…. The request goes through the gateway first, like any other (): the hostname picks the project, the origin must be allowed, the key must be live, the per-IP and per-key rate limits apply, a suspended or paused project is refused, and so is a project whose organisation has used its month's API requests (planLimited) or that needs a second factor the token lacks. realtime then refuses the upgrade when the month's realtime messages are used up, when the organisation is at its spend cap, or past the connection limit. The connection's default identity is the key's role: service for the secret key, otherwise anon, or the user of a bearer token sent on the upgrade.

Subscriptions and filters

Each postgres_changes entry becomes a subscription through bindChanges, at most 20 on a channel (rtMaxSubs) and 100 on a connection (rtMaxConnSubs), refused before any is checked. The event is *, INSERT, UPDATE or DELETE; the schema defaults to public; a table is required, since all tables at once is not supported. The table must have realtime on, be in an exposed schema, and be readable by the channel's role (has_table_privilege, checked as that role). Anon and users also need row-level security on it, or the table listed as public:

A filter is column=op.value with eq, neq, lt, lte, gt, gte, or in.(a,b,…) up to 100 values (parseFilter), on a column the table has. It never reaches SQL: match compares it in Go against the row already read, numbers as numbers and anything else as text. There is no filter injection to have.

A join that binds changes answers only once the hub's listener has its cursor (waitReady), so no change committed after "subscribed" is missed. The reply lists each subscription's id, which every postgres_changes message then names.

Resolved

Row-level security is checked on every batch, not only when a subscription is made. The table's RLS flag used to be read in bindChanges only, so after ALTER TABLE … DISABLE ROW LEVEL SECURITY every existing anon or user subscription kept running its visibility query, which then returned every row, until it disconnected. visibleRows now applies the same rule for anon and users on a table not listed as public: it checks t.RLS from the catalogue it loads, then, since that is cached for up to 2 seconds, takes an ACCESS SHARE lock on the table and reads relrowsecurity itself, so the flag cannot change before the visibility query in the same transaction. When it is off, deliver drops that group's subscriptions (dropSubs) and sends each channel a system error naming the table; the channel stays joined for its broadcasts and presence, and the client subscribes again once security is back. TestRealtimeChangesStopWithoutRLS checks it against a project database.

Authorising each change for each subscriber

deliver handles one batch from the outbox. It collects the subscriptions of each table touched and the primary keys of the inserted and updated rows. It groups the subscribers by fingerprint: the role, and for users every claim except exp, iat, nbf, jti and session_id, which is never wrong, only less shared than V4 §6.3's "claims that policies reference" (decision M34 #5). Each group runs one transaction as its own role's login with its claims (WithRequest, as the data API does), reading every changed row of that table at once:

So yes, each row is checked as the subscriber's role, under the owner's policies and column grants, once per group per batch. What a subscriber receives as record is that query's row, the row as it is now, not the outbox copy. An insert followed quickly by a delete reaches nobody. An update that moves a row out of a subscriber's sight reaches them as nothing. columns carries the table's column types for the clients' conversions. Then, per change and per subscription: the event must match, the filter must pass on the visible row, and one message goes to each channel with the ids of its matching subscriptions.

Deletes cannot be checked: the row is gone. Each subscription keeps a set of the primary keys it was sent, up to 10,000, and a connection's subscriptions up to 20,000 between them, oldest out first (pkSet; a set that adds past the connection's bound lets its own oldest go), and a delete goes, as the primary key only, to subscriptions whose set holds the key (decision M34 #6). A subscriber who joined after the row was last sent never hears of its delete; TestRealtime checks that with a later subscriber.

Changes from another project cannot arrive: a hub reads only its own project's database, through that project's logins, and the token's audience must be the project's ref.

Limits keep the checks affordable. Past 100 groups on a table (MaxGroups; the groups are sorted by fingerprint, so always the same ones), and when a group's query fails or times out, those subscribers get a system message resync instead. Past 200 changes a second per project on this edge (allow), the rest of that second's batches are not delivered and each affected subscription is told to resync once. The groups' queries run one after another in the listener goroutine, so a slow policy delays every subscriber of the project on that edge, and the relay of broadcasts from other edges with them.

A user's token is checked for expiry in deliver, fanOut and presenceDiff before anything is sent, on every broadcast or presence update the channel sends, and every 10 seconds by the connection's own timer (recheck): a channel whose token has expired gets an error and is closed (expire). A client keeps a channel by sending access_token with a fresh token before then.

Broadcasts, private channels and presence

A broadcast from a client (broadcastFrom) needs an event. It is sent at once to this edge's channels on the same topic with the same privacy (self decides whether the sender hears its own), acknowledged when the channel asked for ack, relayed to the project's other edge processes, and kept as history if its topic is persisted. First it must fit the project's budget on this process (budget): at most 32 KB (rtMaxMessage), at most 1 MB a second of broadcasts and presence from all the project's clients (rtBytesPerSecond), and on a persisted topic at most 256 KB of history a minute (rtHistoryBytesPerMinute); otherwise the sender gets a too_large or rate_limited error reply and nobody gets the message. Servers broadcast over HTTP with the secret key: POST /realtime/v1/api/broadcast, 1 to 100 messages of at most 32 KB each, a body of at most 256 KB, under the same budget (429 with how many were sent).

A public channel is open to anyone with the publishable key, for reading and writing. A private channel (config.private) is decided by the owner's policies on xb_realtime.channel_access, a table the owner owns with row-level security on. channelAccess probes them as the channel's role in a transaction it rolls back, once for broadcast and once for presence: xb_realtime.probe (security definer) inserts a row for the topic, a SELECT as the caller decides whether they see it (may receive), and an INSERT as the caller decides whether their policies let them add one (may send). A user who may receive neither is refused the join. The secret key passes. The policies are asked again when the channel's token changes and, by recheck, every minute (rtRecheck): a user they now refuse is closed out, what they allow replaces the channel's flags (a user no longer allowed to track presence loses theirs), and while the database cannot be reached the flags stay as they were. A private and a public channel of the same name never hear each other: broadcasts and presence are keyed by topic and privacy (topicKey).

Presence (presenceFrom) keeps one entry per channel: track replaces the channel's earlier entry with the client's payload plus a new phx_ref, and untrack or leaving removes it. Every joiner gets presence_state, and the topic's channels get presence_diff for each change. The presence key is whatever the client says; on a public channel nothing stops two clients choosing the same one.

Resolved

Authorisation is no longer decided only at join, and token expiry holds for broadcast and presence too. channelAccess ran in join only, so a member removed from a room kept receiving its private broadcasts and presence until they left, and access_token swapped the identity without asking the policies; expiry was checked only in deliver, and a channel on a connection upgraded with a bearer token never expired at all, since setToken took exp only from a token it parsed. Now the expiry comes from the upgrade's claims too; fanOut and presenceDiff skip and close a channel whose token has expired, as does a broadcast or presence update it sends, and the connection's 10-second timer closes the rest; access_token asks a private channel's policies as the new user before switching to it; and every minute each private channel's policies are asked again. The flags are kept under the channel's lock with the identity they were asked for. TestRealtimeTokenExpiry and, against a project database, TestRealtimePrivateChannelsRechecked check it. Between checks a removed member still hears the room for up to a minute.

Persisted topics

The owner lists topics whose broadcasts are kept for 7 days in xb_realtime.persisted_topics, directly or through SetPersistedTopics (at most 100 topics). The edge caches the list for 10 seconds (persisted), and persist inserts each broadcast on a listed topic into broadcast_history as the edge login, with the sender's user id and whether it was sent on the private channel (private, schema version 9). Clients read it back with GET /realtime/v1/history/<topic>?after=&limit=, the public channel's, or with private=true the private channel's:

Resolved

A private topic's history is no longer readable with the publishable key. persist kept private and public broadcasts alike under the bare topic name, and history checked channel_access only when the query said private=true, then filtered by topic alone, so GET /realtime/v1/history/vip with just the publishable key returned every message members had sent on the private vip channel for 7 days, sender ids included. Schema version 9 adds private to broadcast_history; persist writes the sending channel's privacy, and the history query always filters by it, so the plain request reads only the public channel's history and private=true reads the private one's after the read policy (the secret key passes, which it did not before: channelAccess returned early for it without setting the flags, so the secret key's private history answered 403). Rows from before version 9, which do not say, became private, the column's default: their public broadcasts are readable only through the topic's read policy or the secret key until they expire. TestRealtimeHistoryKeepsPrivateApart checks each case against a project database. Anon may still read a public channel's history on any persisted topic.

Several edge processes, reconnects and missed messages

Every edge process listening to a project reads the whole outbox itself and delivers to its own clients, so row changes need no coordination between processes. Broadcasts and presence do, and go through the project's own database (decision M34 #8). relayOut sends pg_notify('xb_realtime_bc', …) through the transaction pool, but only while this process has a listening connection and has heard another process say hello in the last 35 seconds. A message over 7,800 bytes, which one NOTIFY cannot carry, is split into parts that each fit (splitRelay, base64 with the message's id and each part's number) and sent as the notifications of one statement, so nothing is written to a table or the WAL; relayIn holds parts for up to 10 seconds and 16 MB until the message is whole (joinPart). Only a message over 1,000 parts, about 5 MB (a large topic's presence state, which sendState now sends a topic at a time), is still written to xb_realtime.relay with only its id sent:

relayIn ignores its own messages, fans out broadcasts, applies presence diffs, answers a newcomer's hello with its own hello and full presence state (pst), and drops a process that says goodbye. A process not heard for 35 seconds is dropped with its clients' presence (expirePeers), which is how a crashed process's users leave. TestRealtimeNodeLoss kills one of two processes with SIGKILL and checks just that. Without a session pooler there is no listening connection, and broadcasts and presence stay within each process.

There is no replay. A client that disconnects misses what happened meanwhile and refetches when it rejoins; Xenibase's SDKs do this for live queries. When the hub's own listening connection drops, listen reconnects with a backoff from 1 to 30 seconds, sends every change subscriber resync (resyncAll) and starts a new cursor, so the changes in between are skipped rather than delivered late.

Resolved

The publishable key can no longer make the edge write large broadcasts into the project's database. A public channel needs no authorisation to send, a frame could be 256 KB and a connection could send 600 broadcasts a minute; once a second edge process listened to the project, every broadcast over 7,800 bytes became an xb_realtime.relay row, about 150 MB a minute per connection through the shared cluster's WAL, and on a persisted public topic a broadcast_history row for 7 days. Now a broadcast or presence message is at most 32 KB, the project's clients may send at most 1 MB a second of them through each edge process, and a persisted topic keeps at most 256 KB a minute per process; past these the sender gets an error reply and the message goes nowhere. A large message reaches the other processes as NOTIFY parts, which are not WAL-logged, so relay rows are left for messages over about 5 MB, which only a large presence state can reach. TestRealtimeBroadcastLimits and TestRealtimeRelayParts check the limits and the parts, and TestRealtimeBroadcastsSpareTheDatabase checks against a project database that no relay row is written and how much history is kept.

Heartbeats are no longer billed as messages. run counted every frame read and send every message queued, heartbeats and their phx_reply among them, so a connection that did nothing cost about 207,000 messages a month: five idle browser tabs used up a Personal organisation's 1,000,000. Resolved

The Personal plan's monthly message limit now stops connections already open. MessagesBlocked was read once, in realtime, before the upgrade, though the edgeapi field said it also stopped delivery, and the same held for an organisation that had used its month's API requests: a free project's clients that stayed connected kept sending and receiving for the rest of the month, metered on a plan with no overage to bill. Resolved

Memory per connection is bounded. A join could bind any number of postgres_changes entries and a connection hold 100 channels, each subscription's seen set growing to 10,000 keys (about 600 KB), so anyone with the publishable key on a table anon may read and insert into could make the edge hold gigabytes for one client; the send queue added up to 256 messages of up to 256 KB, and presence a 256 KB payload per channel on every process. Now a channel binds at most 20 subscriptions and a connection 100 (V4 §6.3's "subscribers per channel"), a connection's subscriptions remember at most 20,000 keys between them (about 1.2 MB), a frame is at most 64 KB and a broadcast or presence message 32 KB, and the send queue is bounded at 4 MB as well as 256 messages (a single larger change still goes when nothing else is waiting). TestRealtimeSubscriptionCaps, TestRealtimeSeenKeysBounded, TestRealtimeFrameLimit and TestRealtimeSendQueueBytes check each. The set also no longer lets a key go early when it was removed by a delete and sent again.

Spec and code differ

V4 §10.1 gives a plan's connections per project. The code enforces them per edge process (decision M34 #11), so a project gets the limit times the number of edge processes in its region. V4 §6.3 lists "subscribers per channel" and "groups checked per change (plan limit)" as limits; the code limits a channel's subscriptions (and a connection's), and the group limit is 100 on every plan.

When the project or its key changes

The gateway's checks run at the upgrade, and the connection remembers the key it was opened with. Whenever the feed brings a project's entry (a change, or the full resync every minute), apply hands its ref to feedChanged, which closes each open connection that refusal no longer allows: the project has left the feed (services off, deleted or moved), it is not active (its organisation suspended, or paused), its organisation has used the month's realtime messages (MessagesBlocked) or API requests (RequestsBlocked), or the connection's key is no longer one of the project's. Each channel gets a system error and the socket closes with 1008 and the reason; the client's reconnect then meets the gateway. When the project has left the feed the hub also closes its channels and stops the listener at once (stop), closing its session-pooler connection. Each connection's 10-second timer (recheck) applies the same refusal, as a backstop. A spend cap still leaves open connections alone (V4 §12).

Resolved

Open WebSockets no longer outlive a revoked key, a suspended organisation or services turned off. Nothing in the hub read the feed after the upgrade: a connection opened with a since-revoked secret key kept its service identity, every subscription and the right to join private channels for as long as it sent heartbeats; a suspended organisation's connections carried on; and when services were turned off, broadcasts and the session-pooler connection stayed until that connection happened to fail. Now apply tells the hub of every feed entry it takes, feedChanged closes the connections refusal no longer allows, and a project that has left the feed has its listener stopped at once; every connection also checks itself every 10 seconds. A failed serve no longer retries at once in a loop either: it waits a second (the poll without a session pooler failed fast against an unreachable database). TestRealtimeConnectionsFollowTheFeed checks the closes over real WebSockets, and TestRealtimeListenerStopsWithTheProject, against a project database, that the listener and its connection go and a listener starts again when the project returns.
