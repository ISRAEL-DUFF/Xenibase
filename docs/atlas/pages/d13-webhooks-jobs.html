A webhook POSTs the row changes of chosen tables to a URL; a scheduled job runs SQL or calls a URL on a cron schedule. Both are a tenant's way of making Xenibase send traffic, so both go through one hardened outbound client, and both pause while a project is not itself able to serve. The configuration and logs live in the metadata database; the webhook queue lives in the project's own database as a transactional outbox. Only xenibase-server delivers, under a fleet-wide lock, so plaintext secrets and tenant rows never leave the server that holds them.

The outbox in the project's database

Saving the first webhook installs a xenibase schema in the project's database: the webhook_outbox table and a trigger function, both owned by the superuser (outboxDDL). Each watched table gets a row trigger that writes every change to the outbox in the same transaction as the change, so a rolled-back change never produces an event and a committed one always does (V2 §9.1). An outbox row holds the webhook id, the qualified table name, the operation, and old_row and new_row as jsonb, plus the attempt count, next-attempt time and last error.

The schema belongs to Xenibase, not the tenant. REVOKE ALL takes the schema, the table and the function away from PUBLIC, so the project role cannot read the outbox, insert into it, or call the function. The function is SECURITY DEFINER with its search_path pinned to pg_catalog, pg_temp, and the triggers are created by the superuser, so the project role cannot attach the function to its own tables with a forged webhook id. The schema name is reserved: outboxDDL first drops any xenibase schema (or object in it) owned by anyone but the superuser, so a tenant's squat, or a copy a restore brought back as the project role, can never stand in for Xenibase's own (V2 §9.1, decision M15 #1).

Why the outbox is not a tamper vector

The delivery worker reads table_name and the row JSON straight from the outbox, but a tenant cannot write a row there, so it cannot make Xenibase send to an arbitrary address or carry another table's data: the destination is the webhook's stored URL (re-checked at delivery), and the only way into the outbox is the superuser-owned trigger on a table the tenant owns. The function builds the payload with to_jsonb(OLD/NEW); because to_jsonb on a composite recurses to built-in scalar types and ignores tenant-defined casts on composite or domain types (a base type's I/O needs the superuser), a column of a tenant type cannot smuggle a function that would run with the definer's rights.

Draining the outbox

Run takes one fleet-wide advisory lock (pg_try_advisory_lock), so exactly one xenibase-server is the deliverer; the others retry the lock every ten seconds. The holder runs one loop per project with webhooks (supervise), each on its own connection with LISTEN xenibase_webhooks to wake on commit, plus a five-second poll. A pass reads each webhook's head events in id order, LIMIT 100, and sends them one at a time; a head event that is waiting for its retry, or that fails, holds back the rest of that webhook's queue but not other webhooks. A delivered or dead-lettered row is deleted from the outbox and recorded in webhook_deliveries; a failed row keeps its place with a new next_attempt_at. Delivery is at-least-once (the send, the log row and the outbox delete are separate statements), so receivers de-duplicate on the stable Xenibase-Event-Id.

The event id is evt_<webhook>_<outbox id>, stable across retries and kept by a replay. committed_at is the change's transaction time. When old_row and new_row together exceed 256 KB the body carries no rows, only the primary key and "truncated": true (body).

Spec and code differ

V2 §9.1 step 6 says the worker reads outbox rows "with FOR UPDATE SKIP LOCKED". The code does not: head reads with a plain ORDER BY id LIMIT, and concurrency is prevented instead by the single fleet-wide delivery lock plus one loop per project. The effect the spec wants (no two workers sending the same event) holds; the mechanism is different, and the outbox connection is Xenibase's own, not the tenant's.

The outbound client: no SSRF, no rebinding

Every webhook delivery and HTTP job goes through internal/outbound, the only path by which a tenant makes Xenibase send a request. Check parses the URL (no userinfo, https:// only unless the host is allow-listed), resolves it once, and requires every resolved address to be public, so a name cannot mix a public address with an internal one.

Link-local and cloud-metadata ranges (169.254.0.0/16, fe80::/10, fd00:ec2::254) are refused even for an allow-listed host, and canon maps IPv4-mapped, NAT64 and 6to4 addresses to the IPv4 they embed so 64:ff9b::a9fe:a9fe is still caught as 169.254.169.254. The checked address is pinned: transport dials only that netip.AddrPort, with no proxy, so a second DNS lookup cannot rebind the name between the check and the connection. Send does not follow redirects (http.ErrUseLastResponse), bounds the call by a 10-second timeout, and keeps only the first 4 KB of the response as a snippet. A webhook batch is checked once by Prepare (gate, allow-list, DNS) and every event in the batch goes to that one checked address.

The allow-list is per organisation and set by the platform admin only. Each request is counted per organisation and destination host, host and counts only, written about once a second and swept after 30 days (SweepOutboundCounters). An organisation that is suspended or has outbound traffic turned off is refused by Gate; its deliveries then queue in the outbox.

Signatures, secrets and rotation

A webhook's signing secret (whsec_…) and any static headers are sealed with the master key (secretAAD, headersAAD) and shown once. Each request carries Xenibase-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body"> (signature.mac); the timestamp is the wall clock at send, and the receiver checks it against a tolerance to refuse replays. The signing package has no dependencies, so xenibase-status can verify the same scheme. Nothing in the delivery log keeps the secret: it records the URL, status, latency and the receiver's own response snippet.

RotateSecret replaces the secret and, with an overlap of up to 24 hours, keeps the previous one signing alongside the new one (two v1 values) until it expires, so a receiver can switch without failing events in flight. PreviousSecret drops the old secret the moment the overlap ends.

Retries, dead letters and failure emails

The outcome decides the row's fate. A 2xx succeeds. A 429, a 5xx or a network error retries; any other 4xx, a 3xx (redirects are not followed), and a destination refused at send time (its DNS changed to an internal address) dead-letter at once.

backoff doubles from 10 seconds to at most 2 hours with ±20% jitter, about 20 attempts over 24 hours; once a retry would land past 24 hours from the change the event is dead-lettered instead. A dead letter keeps its payload and is visible in the UI, replayable singly or in bulk by Replay, which re-queues it after the waiting events, keeping the original event id. Fifty consecutive failed deliveries pause the webhook, disable its triggers and email the project's admins and the organisation's owners (recordHealth). A minute's health check also marks a webhook broken if the tenant dropped or disabled its triggers (checkTriggers), rather than re-creating them silently.

The delivery log is swept after 7 days, dead letters not replayed after 30 (SweepDeliveries). The outbox lives in the project's own database and so counts against its storage quota; if it passes 100,000 rows the admins are emailed once (health). Because a paused webhook stops enqueuing, and because events older than 24 hours dead-letter fast and quickly trip the 50-failure pause, a down receiver bloats the outbox for at most about a day before the webhook auto-pauses.

Restore, branch, move and delete

Webhooks are configuration in the metadata database; the outbox is data in the project's database. What happens to the outbox on a lifecycle event is Reinstall and Strip, wired through provision.ResetWebhooks.

Scheduled jobs

internal/schedjobs runs a project's jobs on a 5-field cron schedule in an IANA time zone. Parse is Xenibase's own parser (ranges, lists, steps, day and month names, @daily and the other macros); it needs no dependency. Next walks forward in the schedule's location to the next matching minute, giving up after five years (so 30 February has no run). The plan's minimum interval is checked against MinGap, the shortest gap over the next 1,000 runs.

A SQL job runs its script as the project owner, in one transaction, through the console login, which holds no privileges of its own, so the script cannot RESET ROLE its way to the superuser (console.RunJob). Unlike an admin connection, the job keeps the database's read-only default, so a soft storage lock applies to it.

An HTTP job calls its URL through the same outbound client, signed with a per-job secret and a Xenibase-Job header (runHTTP). The schedule and request are validated at save time, and the request's headers may not set xenibase-*, host or content-length. Timeouts default to 5 minutes for SQL and 30 seconds for HTTP, capped at 1 hour.

Run holds its own fleet-wide advisory lock, so one server schedules; Tick picks the due jobs every five seconds, sets each next run from now (a run missed during downtime is not caught up; at most one late run fires, then the schedule continues), and starts each in a goroutine. dispatch records a run and enforces the overlap policy: a job whose previous run is still going is skipped or queued for when it ends. The check and the insert run in one transaction holding the job's row (LockJob, FOR UPDATE), as does starting a queued run when the one before it ends, and partial unique indexes allow one running and one queued run per job.

Runs that a stopped server left queued or running are failed on the next leader's start (FailInterruptedRuns). Three failures in a row email the admins. Run history is kept 30 days and at most 1,000 runs per job (SweepJobRuns).

Resolved

A daily job no longer runs twice, or never stops looking, at a DST change. Next stepped through wall-clock hours in the job's zone. When the clocks went back (America/New_York on 1 November 2026, when 01:00–02:00 occurs twice), a job at 30 1 * * * fired at 01:30 EDT and the next match was 01:30 EST an hour later, so it ran twice that day. When they went forward, a fixed time in the skipped hour was not merely missed: for 30 2 * * * in New York, time.Date normalised the missing 02:00 back to 01:00 EST, the walk went backwards, and Next looped for ever, hanging the scheduler's Tick and the save (whose MinGap looks a year ahead); in zones ahead of UTC the run was dropped for the day. Next now walks one zone period (from one offset change to the next, ZoneBounds) at a time, matching in plain UTC wall time inside it, where nothing repeats or is missing. A fixed-time schedule (minute and hour both given, not *) starts a period that follows a fall-back after the repeated stretch, so it fires at the first occurrence only; at a spring-forward it fires at the first minute after the gap if a time it matches fell in it (cronie's behaviour). Schedules with * in the minute or hour run by the clock through both. Every run is at least a minute after the one before. TestNextAcrossDST covers fixed-time, hourly and every-N-minute schedules across both 2026 changes in New York and London, and TestNextDSTYear a year of runs in five zones, including Lord Howe's half-hour shift and Santiago's at midnight.

Resolved

"Run now" no longer races the scheduler. dispatch used to read ActiveJobRuns and then insert a running row with nothing between the two, and RunJob calls RunNow on whichever API server serves the request, so a manual run that coincided with the scheduled one, or two manual runs on two servers, could both find no active run and both start: an overlap: skip job ran concurrently, and a queue job could start every request. A run queued just as the previous one finished could also be left waiting until the next leader failed it. The check and the insert now run in one transaction that first locks the job's row (LockJob), and the finishing run takes the same lock before it starts a queued one. Migration 00086 adds partial unique indexes on job_runs (job_id) for running and for queued rows, which both overlap policies allow at most one of, after failing any duplicates the race left. TestDispatchConcurrentSkip and TestDispatchConcurrentQueue dispatch each of many jobs from the scheduler and "Run now" at once and expect one run started (and, for queue, one queued) and the rest skipped; without the lock they start two or three.
