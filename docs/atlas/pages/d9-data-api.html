Backend services (V4) give a project an HTTP API at https://<ref>.<domain>: the data API, auth, storage and realtime. This page covers the data API and what it stands on. On the control plane, internal/services turns services on, makes the roles, schemas and keys, and feeds the edge. On the edge, data.go, datasql.go, datawrite.go and rpc.go turn each request into one parameterised statement. How the edge finds a project, checks keys and tokens and opens the transaction is on Connections, and is not repeated here.

Turning services on

POST /api/v1/projects/{id}/services needs project.services, the project admin role and the admin token scope (ServicesManage). Enable locks the project row, requires it active with no operation in flight, makes the project_services row with a new 8-character ref (NewRef: a letter, then seven of an alphabet without 0, o, 1 and l), and queues enable_services. If the project has no live key, the same transaction makes a publishable and a secret key and returns them once.

The operation, enableOn, runs four steps. Each can be repeated, so the three attempts the operation gets are safe:

  1. Roles. ensureRolesOn creates or repairs five roles on the instance, as the platform's admin.
  2. Schemas. applySchema brings xb_auth, xb_storage and xb_realtime to the newest version, each version in one transaction.
  3. Signing key. ensureJWTKey makes an ES256 key unless one is active. The private half is sealed with the master keyring, with the row's id as associated data (jwtAAD), so a sealed key copied to another row does not open.
  4. On. SetServicesEnabled, then SyncPooler so the poolers know the new logins. The feed then carries the project to the edges.

Names come from store/names.go. Every role is NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOINHERIT with a connection limit:

The xb_* schemas and the grants

schemaVersions is an ordered list of statement lists. The {{anon}}-style placeholders are filled in with quoted role names by expand. The schemas belong to the platform's admin, and PUBLIC has nothing on them.

VersionAdds
1The three schemas. xb_auth.claims(), claim(name), role() and uid(), which read current_setting('xb.claims'). The request roles' grants on public.
2Auth's tables (users, identities, sessions, refresh tokens, one-time codes, audit log). Only the edge login may use them. The user_profiles view lets a user see their own row, and the service role and the owner see every row.
3OAuth flow state, MFA factors and challenges, aal(), is_anonymous(), and the hook role's grants.
4Storage: buckets, objects (with row-level security, owned by the project's owner so the owner can write the policies), uploads, garbage and usage (Storage).
5Realtime: captured tables, the outbox, enable/disable, channel access and history (Realtime).

7Takes back the request roles' EXECUTE on extensions' functions. xb_auth.withheld, grant_targets and sync_grants, which only the edge login and the platform may run.

Version 1 grants table privileges to every role on every table in public, and the default privileges do the same for the owner's later tables. That is a deliberate choice (docs/decisions.md, V4-M28 #8): which rows a caller reaches is left to row-level security, with the edge's RLS gate in front. For anon and user, grantTablesStmt grants a relation only where the role holds nothing on it yet, so running version 1 again after a move or restore puts lost grants back without undoing the owner's own REVOKEs. Then xb_auth.sync_grants (version 7) takes back from anon and user every privilege on a relation that does not protect itself: a table or foreign table without row-level security, a materialized view, a view that runs as its owner. They keep SELECT on a public table. It records what it took in xb_auth.withheld and gives exactly that back once the table has row-level security (or, for SELECT, is listed public). The control plane runs it after every schema run and when the public tables change. The edge runs it as its own login, in a transaction of its own, whenever a project's catalog fingerprint changes (the catalog). So the usual order, a table, then row-level security and policies, works as before, and a table that loses row-level security loses its grants within the catalog's 2 seconds. Extensions' tables and the xb_* schemas are left alone. A schema exposed later gets the same statements, exposureStmts, run by applyExposure. Removing a schema from the list revokes nothing. The data API stops serving that schema, but the grants stay, so functions and views in a schema that is still exposed can go on reading it.

Resolved

The grants used to reach extension functions locked away from PUBLIC, and the API served them. GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public ran as the platform's admin, so it also covered what an extension installed there, and pg_stat_statements (on the shared tier's list, SharedExtensions) revokes pg_stat_statements_reset from PUBLIC because the statistics belong to the whole instance. <db>_anon held EXECUTE on it, datacat listed it, and POST /data/v1/rpc/pg_stat_statements_reset with the publishable key emptied every tenant's Query Insights on a shared cluster. Now version 1 and the exposure grants grant each function on its own (grantFunctionsStmt) and leave out any with an extension dependency (pg_depend, deptype e); the owner's later functions still get EXECUTE from the default privileges. Version 7 revokes EXECUTE on extensions' functions from the three request roles, so a project enabled before reaches the same state on its next reconcile. datacat leaves extensions' functions out, so the API answers 404 unknown_function for them and type generation and the advisor no longer list them. TestExtensionFunctionsStayLocked installs the extension, applies the versions, puts the old grant back and runs version 7, and calls the function through the edge.

API keys

GenerateKey makes xb_pub_ plus 32 characters or xb_sec_ plus 40, drawn with crypto/rand from 57 symbols (about 187 and 233 bits). Only the hex SHA-256 is stored (edgeapi.HashKey), with a prefix of the first six characters for lists. A publishable key is also kept in display, because it is meant to be shown. A secret key appears once, in the response that made it. A key this random needs no salt or slow hash. CreateKey adds a named key for rotation, and RevokeKey reaches the edges with the next feed change, which carries only live keys' hashes.

Turning services off

Disable sets enabled false and revokes every key in one transaction, so the edge stops at its next feed read. The queued disable_services takes the logins off the poolers, sets every role NOLOGIN and ends their sessions. The xb_* schemas and their data stay (V4 §2.4). Enabling again makes new keys and logs the roles back in.

Moves, restores and branches

Roles belong to an instance, but schemas and grants belong to the database. Three paths keep them together:

  • Promotion, demotion and moves copy grants to the target, and the grants fail if the roles are missing. The dedicated service first calls EnsureRolesOn (ServiceRoles in cmd/server), which creates the roles there without recording anything.
  • The reconciler. Reconcile runs every 15 seconds on ServicesToReconcile: enabled, active projects whose roles_instance is not their instance or whose schema version is behind. For a moved project it repairs the roles, takes the xb_* objects back from whoever restored them (reownSQL), and runs every version again, then the exposure grants.
  • A database made again (an in-place restore, a branch reset) calls MarkForReconcile through provision.DatabaseRecreated. It clears roles_instance, so the next pass does all of the above.

The ref, keys and signing key survive all of these, so URLs and apps' keys keep working. A branch instead gets an API of its own: a new ref, keys and signing key, without the parent's sessions (Database branches).

The catalog

datacat.Introspect reads what the API serves from the system catalogs. It reads relations in the exposed schemas (tables, partitioned tables, views, materialized views and foreign tables, but not partitions, at most 5,000), their columns with type, category, nullability, defaults, generated and enum labels, primary and foreign keys between exposed relations, and functions (prokind = 'f', not trigger functions or an extension's) with their arguments, defaults, volatility, SECURITY DEFINER and result columns. The edge, type generation, the API page (Describe) and the advisor all read it, so they describe the same API (V4-M30 #6).

  • Exposed schemas: public by default, 1 to 10, matching ^[a-z_][a-z0-9_]{0,62}$, never pg_*, xb_*, information_schema or xenibase (validExposure). applyExposure refuses a schema that does not exist. A name resolves as schema.table, or as a bare name in the first exposed schema that has it (Catalog.Find).
  • Public tables: up to 200 names (table in public, or schema.table) that anon and user may read without row-level security. They may never be written without it.

The edge keeps one catalog per project, shared by every role, because pg_catalog reads the same for all of them (catalog). A request uses the cached copy if it was checked less than 2 seconds ago. Otherwise it runs FingerprintSQL in the request's transaction. That query sums xmin and counts rows of pg_constraint and pg_proc in the exposed schemas, and of pg_class, pg_attribute and pg_policy in every schema of the project's, because privileges, row-level security and policies on a table outside the exposed schemas matter to the views and functions inside them, and to the cache. A changed result means the edge runs sync_grants (the grants), reads the catalog again, and records each request role's Reach for the gate. A 42P01 or 42703 from Postgres also drops it (pgAPIError). The catalog survives feed updates (apply carries it over).

Reads

data routes /data/v1/… by method and segment count. It decodes each segment on its own, so an escaped / stays inside its name.

RequestDoes

The rule (V4-M29 #2) is that names come only from the catalog and are quoted, and values only ever travel as parameters cast to the column's type. Request names must match identRe (no whitespace, quotes, backslashes, commas, parentheses, :, ! or >), but the SQL is built from the catalog's own *Column and *Table: builder.column looks each name up and qi quotes the catalog's spelling. Only JSON path keys reach the text from the request, through lit. Casts use format_type output from the catalog. FuzzReadSQL fuzzes the builder.

  • Select (ParseSelect): columns, alias:column, *, JSON paths (meta->plan, only on json and jsonb), and relations name(…) or name!hint(…) to 3 levels, 200 items per level. A row is row_to_json of a subselect.
  • Embedding (resolveEmbed) goes through a foreign key. The name can be the related table's name, or the column without _id. If two foreign keys fit, the request gets 400 ambiguous_relation rather than a guess. To-one becomes LIMIT 1 of a correlated subquery. To-many becomes json_agg of at most 1,000 rows, ordered by the target's key. Every embedded relation goes through the gate too.
  • Filters (where): eq neq lt lte gt gte compare as the column's type, in as = ANY($n::text[]::type[]), like and ilike on ::text, is null, true or false, contains and contained_by as @> and <@, and search with websearch_to_tsquery. A request may use at most 30 conditions. A JSON path compares as text.
  • Order and pages. orderKeys adds the primary key to the requested order, so pages are stable. A cursor is base64 JSON of the last row's key values as text plus a hash of the table and order (orderSig), so it cannot be replayed on another order. after builds the keyset condition with Postgres's default null placement. limit is 1 to 1,000 (default 100), and offset at most 10,000, not combined with a cursor.
  • Counts. exact runs count(*) under a savepoint with a 2-second timeout and answers null if that runs out (countExact). estimated is the planner's row estimate.

Postgres errors map to stable codes (pgErrors): 42501 becomes 403 permission_denied, a 22… becomes 400 invalid_value, 23505 becomes 409 unique_violation, 57014 becomes 504 statement_timeout, and so on. Unmapped errors become 400 database_error, or 503 for connection and resource classes.

The RLS gate

The edge refuses anon and user what row-level security cannot protect (V4 §3.6). It checks the relation the URL names, every relation embedded, what a view reads, and, for a function, what the caller's role can reach:

  • Views. datacat follows each security_invoker view's rule through pg_rewrite and pg_depend, and through the invoker views it reads, and records the relations nothing protects (Unprotected) and whether it calls one of the project's functions (CallsFunctions). viewGate refuses a view that reads such a relation, unless it is a public table and the request is a read, and a view that calls a function when functionGate would refuse it.
  • Functions. A SECURITY INVOKER function reaches whatever the caller's role may, and no catalog can say what a PL/pgSQL body reads. On each catalog refresh the edge records, per role, the relations it holds privileges on that nothing protects (ReachSQL, Catalog.Reach; SELECT on a public table does not count). functionGate refuses every such function to that role while the list is not empty, with 403 rls_required naming the first. sync_grants normally keeps the list empty, so this is the backstop for a project behind version 7 or a grant the owner made by hand. A SECURITY DEFINER function runs as its owner and passes (the advisor flags it).

writeGate is the same without the public-table exception, and a materialized view is never writable. The service role passes both. Column privileges are left to Postgres, and hiding a column takes the table-level SELECT away and grants the others. select=* expands to every column the catalog has, so a caller missing the privilege on one column gets 403 permission_denied for * and must name the columns it may read.

Resolved

The gate used to look only at the relation the URL named, while the grants reached every table. A table without row-level security answered 403 rls_required, and the advisor said "the publishable key can't reach this table", yet <db>_anon held SELECT, INSERT, UPDATE, DELETE on it, so a security_invoker view over it, or any SECURITY INVOKER function reading it (rpc applied no gate), published it to anyone with the publishable key. Now three things stand in the way. Postgres itself refuses: sync_grants takes anon's and user's privileges on such a table back as soon as an edge sees it, and gives them back once the table has row-level security, so existing projects' tables with policies, and the invoker views and functions over them, keep working, and an owner's own column grants survive. The view gate checks what a view reads, through pg_depend. The function gate refuses invoker functions to a role that still reaches an unprotected relation. The advisor's rls_disabled message now says that the table is out of reach directly and through views and functions, and view_reads_unprotected names an invoker view over such a table. TestRLSGateReachesViewsAndFunctions runs the payments example through the edge, with a public table, a table that gains and loses row-level security, and a database without sync_grants.

Resolved

The documented way to hide a column used to do nothing. docs/backend-services.md and the advisor's secret_column fix said REVOKE SELECT (email) ON profiles FROM "<db>_anon", which Postgres ignores while anon holds table-level SELECT, as it did from version 1; and a full re-run of version 1 after a move would have put the table-level grant back anyway. Now the guide gives REVOKE SELECT ON profiles FROM … followed by GRANT SELECT (id, name, …), and the advisor's fix (hideColumnFix) does the same with the table's other columns, or gives the column REVOKE when anon holds only column grants. grantTablesStmt skips a relation the role holds column privileges on, and sync_grants leaves a table with row-level security alone, so the hiding survives both. TestHiddenColumnStaysHidden shows the old statement leaving the column readable, runs the advisor's fix, reads through the edge, and runs every version and the sync again.

How a request runs

Every data API request is one call to WithRequest: one transaction through the transaction pooler, as the role's own login, with set_config('xb.claims', …, true) and set_config('statement_timeout', …, true) (Connections). For anon the claims are {"role":"anon"}, for the secret key {"role":"service"}, and for a user the verified token's claims. Policies read them through xb_auth.uid() and its siblings. Row-level security is Postgres's own, because the statement runs as <db>_anon or <db>_user, which are NOBYPASSRLS. GETs may go to read replicas (replicaRead).

The cost guard runs EXPLAIN on every read's statement before running it, as the caller and with the request's own values, and refuses it with 400 query_too_expensive above the limit. Nothing is cached: planning a typical 100-row read took about 57 µs against about 265 µs to run it in a local measurement, so a plan per request is cheap next to the round trip. An exact count is planned too, and over the limit it is not run and answers count: null, as when it times out. A set-returning function's call is planned with its select, filters and limit, which sees through a SQL function the planner inlines (a PL/pgSQL body is a fixed estimate to the planner). Writes and scalar functions are bounded by the statement timeout alone.

Resolved

The first values to arrive used to set the cost for all later ones. cost kept one estimate per SQL text, and filter values are parameters, so where=kind:eq:click&limit=1000 (a short walk of the key) admitted where=kind:eq:nothing (a scan of the whole table) at the first request's cost, about 100 times too low; the cache was shared between roles, so a plan made for the service role, without policy predicates, admitted anon too. Exact counts and set-returning functions were not checked at all. Now every request is planned with its own values as its own role, exact counts and set-returning function calls go through the guard, and the per-shape cache is gone. TestCostGuardPlansEachRequest sends the cheap value and then the expensive one as the service role and as anon, an exact count over the limit and under it, and an inlined SQL function called with both values.

The anonymous-read cache

A project can list tables (schema.table) and functions (rpc.name, rpc.schema.name) with a TTL of 1 to 3,600 seconds, at most 100 entries (cache_ttl_seconds, V4.1 §10). The edge then answers some GETs from an in-process LRU of 64 MB (respCache). A request is served from it only under all of these conditions:

Anon's claims are a constant, so one anonymous caller's answer is every anonymous caller's answer, and no user's rows can get in. The key (cacheKey) is the ref, the feed version, the catalog's fingerprint, the path and the sorted query without apikey. A lookup happens before any transaction (read, rpc), against the fingerprint the edge last read, and only while that was checked less than 2 seconds ago (fingerprint); otherwise the request goes to the database, whose catalog check runs. The fingerprint covers pg_policy, privileges and row-level security, and when it changes the edge drops all of the project's entries. A committed write drops the entries that read the written table, through the main table or an embed, and every function result. A function called with POST drops all of the project's entries (dropTables). Each drop increments a per-project generation, and a read that began before the drop does not store its rows. Realtime's hub drops the tables it sees change on that edge. Anything else, such as SQL, jobs or another edge, shows within the TTL. Stored answers carry Cache-Control: public with Vary: Authorization, Read-Replica.

Resolved

Taking access away used to miss the cache. The fingerprint did not cover pg_policy, and a hit never opened a transaction, so after a DROP POLICY, an ALTER POLICY or a REVOKE a popular URL kept serving the rows for the rest of its TTL, up to an hour. Now FingerprintSQL sums pg_policy too, with pg_class (privileges, row-level security) across the project's schemas; a hit is served only while the catalog was checked within its 2 seconds, so a steady stream of hits still reaches the database once per interval; and a changed fingerprint drops the project's entries, the read that saw the change not storing its answer either. TestCacheDropsWithAPolicy caches a read, drops the policy, lets the check fall due, and gets the empty answer, with the old entry gone.

Writes and functions

write and batch run in the caller's transaction (inTx), so policies' USING and WITH CHECK apply. An *apiError anywhere rolls the whole transaction back.

  • Insert: one row or up to 1,000, through json_populate_recordset(NULL::table, $1) naming only the columns sent, so defaults fill the rest and Postgres does the types (insert). on_conflict=cols makes it an upsert: DO UPDATE SET the sent columns, or DO NOTHING with resolution=ignore.
  • Update and delete need a key or a filter (400 filter_required, target). They run first and count afterwards. Above max_affected (1,000 by default, at most 100,000) the transaction rolls back with 400 too_many_rows.
  • Batch: up to 50 operations in one transaction. The first failure rolls back everything and names its index in details.operation.
  • Idempotency-Key (idempotencyOf): the key is claimed by xb_auth.idempotency_claim inside the write's own transaction, scoped to role:sub. A repeat within 24 hours gets the first answer, and the same key with a different request gets 422. Without a user or the secret key it is refused, because every anonymous caller would share one scope.
Resolved

return=minimal used to ask for the rows back anyway: every write's CTE ended RETURNING *, and Postgres applies the table's SELECT policies and column privileges to returned rows, so a table anon may insert into but not read (a contact form, a waitlist, an event log) refused every insert with 403 permission_denied. Now a minimal insert, update or delete runs without RETURNING (returning passes the statement through) and runWrite takes affected from the command tag, so max_affected still applies. An upsert still needs SELECT, because Postgres checks the SELECT policies of a row an ON CONFLICT insert writes. TestMinimalWritesNeedNoSelect inserts one row, two and a batch under an INSERT-only policy, and counts minimal updates and deletes.

Functions (rpc) take named arguments only. pickFunction chooses the overload whose names cover the arguments sent and that gets every argument without a default, and answers ambiguous_function rather than guess. Each argument is a parameter cast to its declared type (argValue; arrays come as JSON arrays). GET is allowed for STABLE and IMMUTABLE functions only (405 volatile_function), so a link or a prefetch never changes data, and only such calls are cached. Set-returning functions take select, where, order and limit on their output, by treating it as a view, and the whole call goes through the cost guard. The call runs with the caller's EXECUTE privilege, after the function gate for anon and user. A SECURITY DEFINER function runs as its owner, which the advisor flags.

The visual schema editor

The table editor's schema changes are built by schemaedit.Build, a pure function from a Change and a State to a Plan: statements, risk notes, a reverse migration, a slug and a hash. gatherState fills the state from the database, with parameters throughout: size and row estimate, the column's current type, nullability and default, whether a type change rewrites (rewrites: same type with a wider modifier, or a binary-coercible cast, does not), whether a default is volatile, and the definition of what is dropped.

  • Names are always quoted (Ident), at most 63 bytes. Types must match typeRe (identifiers, an optional schema, modifiers of digits, []) and exist (to_regtype). Expressions (defaults, checks, USING, index predicates) go in as written, which is the point. They run as the project's owner, who could run them in the SQL console anyway, and ApplySchema sends each statement with ExecParams, so one cannot carry a second.
  • Risk notes carry info, warning or danger, and rise to danger past 100 MB. They cover rewrites, volatile defaults, NOT NULL without a default on a table with rows, constraint checks under lock (offering NOT VALID), SET NOT NULL's scan, and drops. Indexes are built CONCURRENTLY by default.
  • Reverse migrations are written where they are unambiguous (a rename back, a drop of what was added, the old default or type, the old constraint or index definition), and as DownTODO notes where they are not (data that is gone, an enum value Postgres cannot remove). Render writes plain SQL, goose or dbmate, marking non-transactional plans.
  • A batch (the "Edit table" panel) is up to 100 transactional changes to one table, with a rename last.

Who may run what. Preview and migration export need project.console_read. Applying needs project.table_edit, developer and up, with token scope write, and the admin scope for a token whose plan drops something (ApplySchemaChange). ApplySchema refuses a project whose console is read-only, rebuilds the plan on the owner's session, and runs it only if its hash still matches the preview (ErrStalePlan). A drop also needs the dropped object's name typed. It runs with a 5-second lock timeout and a 10-minute statement timeout, and the audit log records the SQL.

Typed definitions

typegen.Generate renders the catalog, read as the platform (Service.Types, GET …/services/types, xenibase gen types), as TypeScript (a Database interface shaped like Supabase's, with Row, Insert and Update, views and functions), Dart (classes with fromJson and toJson) or Go (a struct per relation, plus Insert and Update structs with pointers where a field may be left out). A column is optional on insert when it is nullable or has a default. Generated columns are left out of inserts and updates.

Names are data, never source. They reach a file only as string literals, escaped for the language (strconv.Quote for Go, JSON's escaping for TypeScript, dartString for Dart, which also escapes $), or in comments, quoted when a character does not print. Identifiers are made by camel from letters and digits only (ASCII ones for Dart and TypeScript), start with a letter, and are numbered by a namer when two come out the same or meet a reserved word or a name the file uses (class_, List2). A Go JSON tag can hold only what encoding/json accepts, so a column with any other character is refused for Go with an error naming it, which the API answers as 400; TypeScript and Dart take any name.

Resolved

Generated code used to take database names as source text. Go field names only lost _ - . space, the update tag held the raw name in a backquoted string, and comments and Dart's json['…'] took names as they were, so a column named x⇥int⏎}⏎func⇥init()⇥{⇥panic("ran")⏎// (37 bytes) put init functions into every program built with the generated package, and a $ or ' broke the Dart file. Now names appear only escaped in strings and comments, identifiers are built from letters and digits, and a column Go cannot tag is refused. TestNamesAreNotCode uses the 37-byte name as a table and a column: Go refuses the column and, for the table, parses and type-checks with no function declared; the TypeScript and Dart files have the same lines as with a plain name, with the name only in escaped literals.

Spec and code differ

V4 §2.3 has the edge login SET ROLE to the three request roles. Each request role is now a login of its own, and the edge login holds no memberships (V4-M32 #18). §3.1 refreshes the catalog through an event trigger that bumps a schema version. The edge polls a fingerprint every 2 seconds instead, because only a superuser can create an event trigger and owner-run restores would fail on one (V4-M29 #1). §3.6 refuses queries above "the plan's limit", cached "per normalised query shape". The limit is a project setting, the same 1,000,000 on every plan, and nothing is cached: a plan kept per shape let one request's values vouch for another's (see How a request runs). §3.8 drops cached entries "via the same schema-version and change signals realtime uses". Writes through the same edge drop them, realtime does so only on edges with subscribers, and a schema, policy or privilege change drops all of them within 2 seconds. Other data changes show within the TTL. §3.6 says column privileges are respected: they are, but select=* then fails rather than leaving the column out, and hiding a column takes the table-level grant away first (the RLS gate). docs/backend-services.md says a write's select takes no relations, but returning passes them to the read builder, gated like reads.
