This page is about the people who use Xenibase itself: the platform admin, support staff, and the users who own and work in organisations. The users of an app built on Xenibase sign in through project auth, a different system in each project's own database (). The two share only internal/totp and internal/argonpw. Everything here lives in the metadata database and is served by xenibase-server's API, behind the guard described on .

Who is who

A user has one login and may belong to many organisations. Each organisation owns its projects, tokens, storage targets, usage and audit log. A user's power comes from three layers, each stored in its own column:

Accounts and signup

The first account is made by the setup wizard. BeginSetup needs the setup code xenibase-server prints to its log, checks the password, and seals the email, hash and a fresh TOTP secret into a 15-minute challenge. Nothing exists until CompleteSetup gets a valid code: then, under an advisory lock, it creates the platform admin as verified and approved, their personal organisation, and their first session. Five wrong codes delete the challenge.

After that, accounts come from signup or from invitations. The platform admin picks the signup mode (SetSignupPolicy, stored in settings under signup):

ModePOST /auth/signupA new account
invite_only (default)403 signup_closedOnly by accepting an invitation from the platform admin or from any organisation
approvalAcceptedUnverified and unapproved; signs in once verified and approved by the platform admin (ApproveUser, which emails them)
openAcceptedUnverified, approved at once

Signup checks, in order: the mode; the address (parsable, at most 254 bytes); the domain allow-list, an exact match on the part after the last @; the anti-bot challenge and the per-IP cap (SignupGuard, in approval and open mode alike); the password; and the current terms version. Turnstile runs when its keys are set, and any failure, Cloudflare being unreachable included, refuses the signup (Turnstile.Verify). The cap is 3 accounts per signup_ip a day by default (XENIBASE_SIGNUPS_PER_IP).

An address that already has an account gets an email saying so, and the request answers 202 as for a new one; the password is hashed first either way, so the two take as long. A new address gets a user row, a personal organisation (createPersonalOrg), a terms acceptance and a 48-hour verification link. emailToken retires earlier links of the same purpose, so only the newest works, and only once.

A password is at least 12 runes and at most 256 bytes (CheckPasswordPolicy), with no complexity rule and no breached-password check. defaultArgon is argon2id at 64 MiB, 3 passes and 2 lanes (RFC 9106's second recommendation) in PHC form. argonpw.Verify reads the parameters from the hash, so project users' cheaper hashes verify with the same code.

Signing in, TOTP and lockout

Sign-in is two calls. POST /auth/login runs Login. An unknown or disabled address verifies the password against a fixed dummy hash (dummyHash) and fails like a wrong password, counted and locked like one (addressFailure). Only the right password learns that the address is unverified or awaiting approval. A right password stores a 5-minute challenge, and then one of three things happens:

  • No second factor. An ordinary account without TOTP: the handler completes the challenge at once and the answer carries the session (loginResult).
  • TOTP. The answer carries a challenge id; POST /auth/totp sends it with a code to CompleteLogin.
  • Enrolment. Platform admins and support staff must have TOTP (totpRequired). Without one, the answer carries a new secret in a 15-minute enroll challenge, and the first valid code enrols it and returns the recovery codes.

Ordinary accounts turn TOTP on under Account → Security with the password and a first code (EnableTOTP), and off with the password and a code (DisableTOTP, refused to platform staff). Both changes are emailed.

Codes are RFC 6238 (HMAC-SHA1, 6 digits, 30 seconds, one step of drift; totp.Verify), and checkTOTP accepts only a step later than users.totp_last_step, so a code works once. Any 10-character input is taken as a recovery code, and useRecoveryCode removes it from the sealed list under a row lock. Regenerating the codes needs step-up.

Two limits stand in the way of guessing:

  • Per address. auth.Limiter is a sliding window in memory, per process: 10 attempts per 5 minutes for sign-in, TOTP, step-up, signup, reset requests and password changes, and 60 per 5 minutes for requests that present an emailed token, device starts and the OAuth endpoints (decision M8 #16). The address is the TCP peer, or the rightmost untrusted hop of X-Forwarded-For when the peer is in XENIBASE_TRUSTED_PROXIES (clientIP).
  • Per account. Every wrong password, TOTP code or recovery code, in sign-in, step-up, password change or TOTP setup, goes through recordFailure. The fifth in a row locks the account for 15 minutes, and each further one (after a lock ends) for twice as long as the last, up to a day; only a good sign-in or a new password starts the count again. While locked, every password, the right one included, answers 429 locked with Retry-After. The owner is emailed when a lock starts, at most once an hour (noticeLockout, in the background, so the answer takes no longer). An address with no enabled account is counted the same way in login_address_failures, so it locks after five failures as well, and the lock says nothing about which addresses are registered. A sign-in challenge is also deleted after three wrong codes.
Resolved

The lock used to say which addresses had accounts, never grew, and told nobody: five wrong passwords for a registered address answered 429 locked while an unknown one only ever answered 401, the lock was a fixed 15 minutes that reset the count (about 480 TOTP guesses a day for someone with the password), and signup answered an existing address in about 1 ms against 100 ms or more for a new one. Now an address without an enabled account is counted and locked exactly as an account is (login_address_failures, forgotten a day after its last failure), the lock doubles with each failure past the fifth up to a day, as project auth's does (), the owner is emailed when it starts (at most once an hour), and signup hashes the password and sends one email for an existing address as for a new one (TestLockoutDoublesAndSaysNothing, TestSignupTakesAsLongForAnExistingAddress). Anyone who knows an address can still keep it locked, now for up to a day at a time, within the per-address limit; the email tells the owner, and the right password works once the lock ends.

Sessions, CSRF and step-up

newSession makes 32 random bytes and stores only their SHA-256, with the IP and user agent. Every sign-in makes a new one, so a session cannot be fixed in advance. setSessionCookie sets __Host-xenibase_session with HttpOnly, Secure, SameSite=Strict, path / and a 7-day age. The __Host- prefix and Secure are dropped only when XENIBASE_COOKIE_SECURE is false, for plain-HTTP development.

Authenticate refuses and deletes a session idle for 12 hours, older than 7 days, or whose user is disabled, unapproved or unverified, and touches it at most once a minute (defaults in setDefaults, unchanged by cmd/server). Users list their sessions and revoke any of them. Disabling a user, changing their platform role, resetting their TOTP and resetting their password end all their sessions; changing the password ends all but the current one. Resetting the password or the TOTP also revokes every API token the user has, and changing the password does too unless the request sends revoke_tokens: false.

CSRF protection is double-submit (checkCSRF). GET /session issues __Host-xenibase_csrf, readable by script, and returns its value. Every mutating request from a cookie session, sign-in included, must echo it in X-CSRF-Token, and an Origin header, when sent, must name this host. Requests with a bearer token skip the check and ignore the cookie. Routes called by programs (the device start and poll, the OAuth token and revoke endpoints, webhooks, the edge) are in csrfExempt.

Step-up is a recent second check of the password and, when the account has TOTP, a code. Reauthenticate stamps sessions.reauth_at, and RecentlyReauthenticated accepts it for 10 minutes. A new session counts as freshly stepped up. Recovery codes do not work here. The guard requires it on the routes in reauthRequired: deleting a project or an organisation, transfers, regenerating recovery codes, break-glass, suspension, a TOTP reset, OAuth consent, creating an API token, backup keys, residency, role management, removing a node, and money. A platform role change (UpdateUser), approving a device login (ApproveDeviceLogin; denying one needs none) and an in-place restore check it in their handlers.

For tokens, tokenConfirmed asks instead for a confirm field equal to the target's name. A project transfer spans two organisations, so no token can make one.

Resets, roles and closing an account

RequestPasswordReset emails a one-hour link to an address with an enabled account and answers 202 whatever happens. ResetPassword consumes it, sets the password, marks the address verified, revokes every API token and ends every session, in one transaction; the email says so. TOTP stays, so a reset alone does not pass a second factor. xenibase-server admin can print a reset link when mail does not work (PasswordResetLink).

Someone who lost their authenticator and codes asks the platform admin, who checks who they are outside Xenibase and runs ResetTOTP: the secret and codes go, sessions end, API tokens are revoked, and the user is emailed.

SetPlatformRole makes or unmakes platform admins and support staff. From the UI the account must be enabled, approved, verified and have TOTP (ineligible); from the server those checks are skipped, for when nobody is left who can. The last active platform admin cannot be demoted. The change ends the user's sessions and emails them.

SetDisabled is the closest thing to deleting an account: sessions end at once, and the UserDisabled hook (revokeEverywhere) revokes every API token and drops the user's personal database logins in every organisation. Memberships stay. A platform admin cannot disable themselves.

Resolved

Recovering an account used to leave its API tokens, and a session minted them without step-up: ResetPassword, ChangePassword and ResetTOTP deleted only sessions, and neither POST /tokens nor POST /auth/device/approve needed step-up though OAuth consent did (decision OAuth #4), so a stolen cookie could create a 365-day admin token that outlived the owner's reset, and a /device?code=… link was one click from a 90-day token. Now a password reset and a two-factor reset revoke every token the user has, in the same transaction, and their emails say so; a password change does too unless the user unticks Also revoke my API tokens (revoke_tokens, on by default). POST /tokens is in reauthRequired, and approving a device login checks for a recent step-up in its handler; the web UI's step-up dialog answers both (TestRecoveryRevokesTokens, TestTokensNeedARecentStepUp).

Organisations, members and invitations

Every new user gets a personal organisation, "name's projects", on the Personal plan, or Unlimited for the platform admin. Its owner cannot leave it and it cannot be deleted; otherwise it is an ordinary organisation, and others can be invited to it. Any signed-in user can create more (orgs.Create), each on the Personal plan with them as owner, with no limit on how many.

Membership changes run under a lock on the organisation's members (withMembersLocked), so two requests cannot remove the last owner between them:

Remove (RemoveMember)Owners and adminsOnly owners remove owners; never the last. Project memberships and the user's tokens for the organisation go in the same transaction (deleteMembership), then their database logins.

Invite records an invitation (32 random bytes, SHA-256 at rest, 7 days, single use) and emails the link, which the inviter also sees once in case the email does not arrive. An organisation invitation names an organisation role and optional project roles; owners and admins send them (InviteOrgMember keeps owner and billing to owners), and a project admin adding an address that is not yet a member sends one as member with that project role. A platform invitation, the platform admin's, carries no roles and is refused for an address that has an account. Organisation invitations are capped a day per organisation and per inviter (below). Neither checks the signup mode or the domain allow-list: in every mode, an invitation is a way in.

accept takes a pending, unexpired, unrevoked invitation. An address that has an account must accept it signed in as that account, by link or from the in-app list. An address without one creates the account with the link (CreateVerifiedUser: verified and approved, since the link proves the address) and goes straight on to sign-in (AcceptInvitation). Marking it accepted and adding the memberships share one transaction, and a project that has left the organisation since is skipped.

Risk

An accepted invitation, or a project transfer, turns a billing member into a plain member. InsertOrgMember's ON CONFLICT keeps owner or admin and otherwise writes member, so billing is never kept. Invite refuses an existing member only when no projects are listed, so an admin who invites a billing member's address as member with one project takes away their billing access and gives them the project, which SetMemberRole forbids admins to do. Transfer adds every project member to the destination as member through the same query, with the same effect there. Reproduced with a scratch test. The CASE could keep billing unless the new role is higher, or Invite could refuse any existing member.

Resolved

Invitations used to be an unlimited mail relay with words the sender chose: nothing counted them, every user owns an organisation, and the organisation's and inviter's names went through linkify, so "Security team https://evil.test/reset" became a link beside the real button. Now checkInvitationLimits allows an organisation 100 invitations in any 24 hours and an inviter 50 across their organisations (XENIBASE_INVITES_PER_ORG_DAY, XENIBASE_INVITES_PER_USER_DAY; 0 turns a cap off), revoked ones included, and answers 429 rate_limited with Retry-After past them. Both names, and the first name in every greeting (mail.Hi), go through mail.Inert, which puts an invisible zero-width space after each ., :, / and @: they read the same but are not made links, here or by most mail clients (TestInvitationsAreCapped, TestInvitationNamesAreNotLinks). Platform invitations, the platform admin's, are not capped.

A project moves between organisations with POST /projects/{id}/transfer. TransferProject needs step-up and org.owner on both organisations; a destination the caller cannot see answers 404. Transfer refuses a project that is not active, a branch, a parent with live branches, and one with backups on the source's own storage targets. Its project members join the destination as members, every table carrying the project's org_id follows by ON UPDATE CASCADE, tokens of the old organisation lose the project, and tokens left with no projects are revoked. The destination's plan limits are not checked here.

An owner deletes an organisation by typing its name (RequestOrgDeletion, step-up). Personal organisations are refused. The organisation is deleting for 7 days, in which only reads and owner-only actions such as cancelling work, then each project gets a final backup and is deleted, and memberships and invitations end.

Resolved

A read-scoped token used to be able to make two changes: POST /orgs/{org}/leave is declared as org.view, so a read token could make its user leave, which revokes all their tokens there and drops their database logins; and DELETE /tokens/{token_id} took read, so it could revoke its user's admin tokens. A leaked read-only CI token or a read-only OAuth app could cut its user off. Now LeaveOrg needs the write scope from a token (the route stays org.view, so billing members can still leave), and RevokeMyToken needs it to revoke any token but the caller itself, which xenibase logout does with whatever scope it has (TestReadTokensChangeNothing).

Platform admins have no tenant role by being platform admins. platform.manage and support.console are session-only and answer 403, not 404. Support staff see the support console and organisations' metadata, never data. Backups and operations with no project are platform work and answer 404 to anyone else. To act inside an organisation they are not in, a platform admin opens a break-glass session (StartBreakGlass): step-up, a reason, 1 minute to 4 hours on the database clock, refused if they are already a member. Every owner is emailed, members see a banner, any owner can end it, and every audited request under it (every mutating one, and the audited reads) writes a row with break_glass set, in the organisation's log and the platform's. It hands out nothing that would outlive it: invitations, organisation and project role changes and ownership transfers answer 403 break_glass (refuseBreakGlass).

Resolved

Break-glass could be turned into permanent membership: under it the platform admin is an org admin, could invite their own address as admin, and accept, after which can found a real membership that outlived the session and an owner ending it, with nothing flagged break_glass. Now refuseBreakGlass answers 403 break_glass to invitations (organisation and project), organisation and project role changes, and ownership transfers made under break-glass, and everything else it allows is unchanged. Invite refuses anyone's own address, and accept refuses an invitation sent by the account accepting it, so one sent before the change cannot be used either (TestBreakGlassCannotGrantMembership). A membership already gained this way stays: the organisation's audit log shows the invitation with break_glass set.

API tokens and device login

A token is xb_ and 43 characters drawn uniformly from base62 (newSecret), shown once. Only its SHA-256 and its first 9 characters are kept, the latter for display; a slow hash would add nothing to 256 bits. It has a name, one organisation, scopes (NormalizeScopes: read, write includes read, admin requires write), an optional project list, and an expiry from 1 hour to the platform's maximum (365 days, lowered under Settings), 90 days by default. Creating one emails the user its name, prefix, scopes and expiry (notifyCreated); a week before expiry they are emailed again.

tokens.Authenticate refuses a token that is revoked, expired, or whose user is disabled, unapproved or unverified, answers 403 for a suspended organisation, and records the last use and IP at most once a minute. tokenSession then applies 600 requests a minute per token and 1,200 per organisation. Users revoke their own tokens (a token with write, or any token revoking itself); org owners and admins see and revoke every token in the organisation. Leaving or being removed revokes the user's tokens there, and disabling the user, resetting their password or their TOTP revokes all of them. A session creates a token only within 10 minutes of a step-up.

A token may create tokens, unless an OAuth app holds it. checkTokenGrant, used for every new token whatever its source, checks that the user can see the organisation and every listed project, and, when the caller is itself a token, that it was not issued to an app and that the new one has no scope, project or lifetime beyond it. The new token records its parent, and is revoked with it:

The CLI's login is RFC 8628's device flow (StartDevice). POST /auth/device, 60 per 5 minutes per address, returns a 32-byte device code (stored as its SHA-256) and an 8-letter user code from 20 consonants (newUserCode, about 2.6 × 1010 codes), both valid 10 minutes, with read and write requested unless the CLI asks otherwise. The user opens /device?code=… while signed in, sees the client's name and scopes, chooses the organisation, may narrow the scopes and restrict projects, and approves (ApproveDeviceLogin), confirming their password and code first unless they did in the last 10 minutes. ApproveDevice creates the token and seals its secret into the request, bound to the device code's hash, in one transaction. PollDevice answers authorization_pending, slow_down (polls closer than 2.5 seconds), access_denied or expired_token, and hands over the secret once, deleting the request. Looking a user code up needs a session, so codes cannot be tried from outside.

Third-party OAuth apps

An app such as Taskiem asks a user to connect an organisation through RFC 6749's authorization code grant with PKCE (the integrator's guide). What it receives is an ordinary API token, so everything in the section above applies to it.

  1. Register. The platform admin registers a client from a session (CreateClient): a name, 1 to 10 redirect URIs, absolute, https or loopback http, no fragment (ValidateRedirectURI), the most scopes it may ask for (read and write by default), and whether it is confidential. A confidential client gets an xbc_ secret, kept as its SHA-256; a public one relies on PKCE alone.
  2. Consent. The app sends the user to /oauth/authorize. ValidateAuthorize needs a live client, a redirect URI equal to a registered one, state of at most 512 characters, an S256 challenge (plain is refused), and scopes within the client's. A bad request is shown on the page and never redirected. The page needs a session and step-up. The user picks the organisation, scopes, projects and expiry, and DecideOAuthAuthorization runs checkTokenGrant, then IssueCode stores a 32-byte code (SHA-256, 10 minutes) with the user's choices and the challenge, and the browser is sent to the redirect URI with code and state. A denial is sent there with error=access_denied.
  3. Exchange. POST /oauth/token, form or JSON, client credentials in the body or HTTP Basic but not both, 60 per 5 minutes per address. Exchange authenticates the client (authenticateClient: a public client must send no secret), locks the code row, and checks that it was issued to this client, is unused and unexpired, has the same redirect URI, and that the verifier's SHA-256 matches the challenge. It creates the token and marks the code used in one transaction. A code presented a second time fails and revokes the token its first use issued. There is no refresh token.
  4. Revoke. The app revokes its own tokens with RFC 7009's endpoint (RevokeByClient), answering 200 for any token. The user disconnects the app from Account; org owners and admins revoke it with the organisation's tokens; the platform admin disabling the client revokes every token it was issued (DisableClient).
Resolved

Disconnecting or disabling an app used to leave the tokens it made for itself: an OAuth token with write could call POST /api/v1/tokens, and the child had no oauth_client_id, so DisableClient and Account's Disconnect left it working for up to a year. Now a token created by a token records it in api_tokens.parent_id (migration 00088), and a trigger on revoked_at revokes a token's children, and theirs, in the same statement, whichever path revokes it: Disconnect, the organisation's list, the app's own revocation, a reused code, or disabling the app. And checkTokenGrant refuses an OAuth-issued token any new token (403 token_not_allowed): the app holds exactly what the user consented to (TestRevokingATokenRevokesWhatItMade, TestTokenMadeByATokenGoesWithIt, TestOAuthFlowOverHTTP). Children made before the migration have no recorded parent.

Platform email

One SMTP configuration, set in the setup wizard and under Settings, sends all of Xenibase's own email (mail.Service). The password is sealed with the master key, and PutMailSettings saves a configuration only after a test message gets through. Validate takes STARTTLS on 587 (the default, refused if the server does not offer it), implicit TLS on 465, or none, meant for a relay on the same host but not limited to one; TLS is 1.2 or later. Unlike a project's own SMTP server, the platform's is not put through the outbound rules: the platform admin chooses it. A message is multipart/alternative, plain text first, then HTML in one branded layout (Render); header values have CR and LF replaced, and lines starting with . are dot-stuffed.

Spec and code

Spec and code differ

V1 §7.2 (V1 7.2), V2 §3.1 (V2 3.1) and V3 §7.4 make TOTP mandatory for every account, enrolled before first use, and V1 makes step-up "password + TOTP". Since the change recorded in the changelog ("Two-factor sign-in is off by default for ordinary accounts"), only platform admins and support staff must have it. Ordinary accounts sign in, and step up, with a password alone until they turn it on.

Spec and code differ

V2 §3.6 (V2 3.6) specifies account deletion by the user, blocked while they are the last owner of an organisation with projects, removing memberships, tokens, database logins and an empty personal organisation. There is no such route. Decision M9 #12 defers it, and the terms tell users to ask the platform admin, whose only tool is disabling the account, which keeps the row, the memberships and the personal organisation.

Spec and code differ

V3 §7.4 (V3 7.4) opens signup with "one Free org per user", and the acceptable use policy forbids getting around it. Nothing enforces it: orgs.Create makes any number of organisations for any user, each on the Personal quota plan, which is what the Free plan maps to, so the Free tier's limits multiply with the number of organisations a user creates.

Spec and code differ

OAuth consent narrows, never widens, the scopes the app asked for (decision OAuth #4). The server keeps nothing between the page's two calls, and DecideOAuthAuthorization checks the posted scopes only against the client's allowed ones, so the narrowing is the page's alone. Only the user can post a wider set.
