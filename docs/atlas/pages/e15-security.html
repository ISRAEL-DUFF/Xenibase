Xenibase runs other people's databases side by side. On the shared tier, many organisations' projects are databases in one Postgres cluster, behind one pair of poolers, reached from one set of servers. This page is the whole of how they are kept apart and how the platform's own secrets are kept: what each kind of attacker can reach, the master key, the isolation checklist and its live audit, the per-tenant limits in tenancy, outbound requests, and the tests. The pieces that belong to one service are on that service's page and are linked from here, not repeated.

Who the attackers are

V2 assumes any tenant may be careless or hostile (V2 §10.1). A malicious platform admin with root, timing and cache side channels between tenants on one cluster, and network-level denial of service are out of scope. Tenants who need more use a per-organisation shared cluster or a dedicated instance.

Secrets under the master key

Secrets the control plane must read back are sealed with one 32-byte master key (V1 §7.3). Which columns are sealed, hashed or kept in the clear is on . This section is how the sealing works and what depends on the key.

The keyring

loadMasterKey reads exactly one of XENIBASE_MASTER_KEY or XENIBASE_MASTER_KEY_FILE (for Docker and systemd secrets), as base64 in either alphabet, padded or not, and refuses anything that does not decode to 32 bytes (ParseKey). XENIBASE_MASTER_KEY_PREVIOUS holds old keys, comma-separated. NewKeyring makes the first the primary and indexes all of them by key id. A key id is the first 8 bytes of SHA-256 over a fixed label and the key, so it names the key without revealing it.

A ciphertext is version (1) | key id (8) | nonce (12) | AES-256-GCM. The version byte and key id are part of the associated data, and so is the caller's context, which names the column and the row ("nodes.pg_admin_secret:" + id). A sealed value copied into another row, or into another column, fails to open with ErrDecrypt. Decrypt picks the key by the id in the header and answers ErrUnknownKey when the keyring does not hold it. The nonce is random for every seal, and no key seals anywhere near 232 values, so nonce reuse is not a concern.

Values derived from the seed

Derive is HMAC-SHA256 over a label, keyed on the derive seed: 32 bytes sealed under the master key in the derive_seed settings row. The server loads it after migrating (rotate.LoadDeriveSeed) and sets it on the keyring before any service has it. The first server to start creates it (deriveSeed, under an advisory lock): on an install that already has projects the seed is the primary key, which is what Derive keyed on before the seed existed, so nothing changes on upgrade; a new install gets random bytes. A keyring without a seed (tests, tools that derive nothing) keys on its primary key. Derive gives values that must be stable and secret without storing them:

Rotation and verification

xenibase-server -rotate-master-key runs with the new key as primary and the old one in XENIBASE_MASTER_KEY_PREVIOUS, then exits (rotateMasterKey). It migrates the schema, then rotate.Run collects every sealed value under FOR UPDATE in one transaction: the 16 sealed columns, the seven blobs in settings rows (the derive seed among them), and the secrets in pending operations' parameters. Each one not already under the primary key is re-sealed with the same associated data. Sign-in challenges are deleted rather than re-sealed; their owners sign in again.

Before Run, PrepareDeriveSeed makes the derive seed if no server of this release has made it yet: from the old key, sealed under it, so the rotation re-seals it and a rotation that rolls back leaves a seed the old key opens. With more than one previous key it cannot tell which one the servers derived from, and refuses. A wrong old key, or a value sealed under a key the keyring does not hold, fails the transaction and nothing changes. After the commit, rotate.Verify opens every value again with a keyring that holds the new key alone, and fails if projects exist without a derive seed. TestEveryEncryptIsRotated reads every Encrypt call in the module and fails on associated data the column list does not cover, so a new sealed column cannot be forgotten silently ( has the earlier gap this closed).

Resolved

Rotating the master key used to take every project's backend services offline. Derive keyed on the primary key, so after a rotation edgePassword returned new passwords and the feed handed them to the edge, while the poolers (PoolerEdgeUsers) and the instances kept the verifiers stored at enable time, which ensureRolesOn reuses; every data API, auth, storage and realtime request failed SCRAM until the verifiers were cleared by hand, and signed file URLs stopped verifying. Derive now keys on the sealed derive seed, which a rotation re-seals and never replaces, so the edge and request roles' passwords, the console passwords, the file URL keys and the pooler admin's salt are the same before and after. TestMasterKeyRotation turns backend services on and checks that a keyring with the new key alone and the reloaded seed derives passwords that still match the stored verifiers; TestDerivedSurviveRotation compares the services' derived values across a rotation.

Running servers during a rotation

The operations guide stops the bundle's one server first. With several, one still running on the old key alone cannot open re-sealed values and keeps sealing new ones under the old key, which are lost once it is dropped. Stop every server, and keep the old key in XENIBASE_MASTER_KEY_PREVIOUS until a second rotation rewraps nothing.

What is lost with the key

Everything sealed: storage credentials, the agent and etcd CA keys, instance admin and Patroni passwords, projects' JWT signing keys and backup keys, webhook secrets, jobs, auth providers' settings, and the platform backup key. Project passwords are not affected, since only their verifiers exist. Backups survive only through the backup key the setup wizard makes the operator download (). The derive seed is sealed too, so the derived values go with the key, and a server without it does not start; a rotation keeps them.

The live two-tenant probes

After auditing every project, Instance drops any leftover probes, creates two throwaway tenants with the real create steps (NewProbe: role, database, hardening), audits their roles, and has A attack B (Probes). B creates a table and keeps a session open. A then tries to connect to B's database, postgres and template1, and runs each of these, every one of which must be refused:

Among them A tries to grant itself CONNECT on B's database. Then A must fail to read pg_stat_activity, pg_stat_get_activity, pg_stat_database(_conflicts) and the per-database and per-backend statistics functions, to raise its temp_file_limit or connection limit, and must not be a member of any predefined role. A success is a finding. An error counts as a refusal only if its SQLSTATE class is one Postgres uses for refusals (isRefusal); any other error fails the run, so a broken probe cannot pass for a refused one. The probes are dropped afterwards, even when the run fails.

How often, and the alert

Due runs every hour and queues an isolation_check operation for each running shared cluster whose latest check is older than Every (24 hours) and not queued or running. A check has two attempts and 30 minutes. Any finding fails it permanently, with the first three findings in the error and all of them in the step log. A failed check of a cluster that still exists raises the critical isolation_check_failed alert (alerts), which clears when a later check succeeds. Platform admins can run all checks at once from Settings → Tenant isolation (POST /api/v1/security/isolation-checks).

Resolved

The audit used to pass while the backend-service logins, or a cross-project grant, were wrong. Roles never looked at the five backend-service logins, which tenant SQL runs as on the shared tier, so a request role left with LOGIN while its organisation was suspended, without temp_file_limit or a connection limit, with an unexpected attribute or a predefined role passed; and the grants check asked only whether PUBLIC had CONNECT, so CONNECT on B's database granted to A's owner passed too. Now Roles checks the five logins' attributes (BYPASSRLS on _service alone), limits, NOLOGIN while suspended or hard-locked, and requires them to hold no role; and databaseGrants reads every grantee of CONNECT and TEMPORARY from aclexplode(datacl) and reports any that is not the project's own (or the owner, a superuser, or a move's login). TestRolesServiceLoginsAndGrants breaks each on the test cluster; TestLiveIsolationCheck turns a project's backend services on and breaks them through the operation, and the live probes try the grant.

Resolved

V2 §10.4's audit of forbidden capabilities includes "no SECURITY DEFINER functions owned by anything other than tenant roles or the fixed Xenibase webhook function" (V2 §10.4), and isocheck used to never read prosecdef. Database now reports a SECURITY DEFINER function owned by a superuser or a role not of that database, other than an extension's, unless it is one of Xenibase's own in an xb_* schema or xenibase (the backend services' functions, , and the webhook trigger) with its search_path set (TestSecurityDefiners).

Resolved

The package comment of isocheck, the doc comments of TestClusterConfiguration and TestLiveIsolationCheck, and the security review used to say the live check runs weekly (and nightly in places). They now say every 24 hours, which is Every, as V2 §10.4 asks; V1 §7.1 said weekly.

Extensions on the shared tier

The shared tier allows SharedExtensions: pgcrypto, uuid-ossp, citext, pg_trgm, hstore, unaccent, btree_gin, btree_gist, pg_stat_statements, vector and hypopg. Dedicated instances add postgis, pg_partman, timescaledb, postgres_fdw and pg_cron (V1 §7.4). The rule is that nothing on the shared tier reaches outside its database: no foreign-data wrappers or dblink (they connect from the cluster's own address, which pg_hba.conf trusts), no file access, no background workers running tenant SQL (pg_cron), and no preload library that is unsafe to share. hypopg serves query insights; pg_stat_statements is preloaded cluster-wide, its reset withheld from the request roles ().

EnableExtension refuses a name outside the tier's list or missing from the image, then creates it as the superuser WITH SCHEMA public. The image (deploy/images/postgres) has every contrib module and hypopg, but not vector.

The allow-list binds the API, not the tenant

The owner role owns its database, so it can CREATE EXTENSION any extension Postgres marks trusted without the API: tablefunc, ltree, intarray, fuzzystrmatch and the other trusted contrib modules (checked on Postgres 16). Trusted extensions are by definition ones a non-superuser may install, so none of them escapes the role, and the untrusted ones stay refused. The security review's "Enforced by POST /projects/{id}/extensions" is true of what Xenibase installs, not of what is installed.

Per-tenant controls

tenancy is V2 §10's hardening. Its loops run in every server: the reaper every 15 seconds, storage enforcement every minute, and a sweep every 5 minutes (opaque renames, usage, break-glass expiry, organisation deletion, retention). Each step is idempotent, so several servers converge.

Spec and code differ

V2 §10.3 says rate limits on console queries and operations are per-org token buckets in xenibase-server. Console queries are a concurrency count per process, so with N servers an organisation gets N times its limit; operations are a count of what is queued or running. Token limits are also per process.

Storage enforcement and locks

Postgres has no per-database disk quota, so EnforceStorage applies one from each shared project's latest measured size (sampled every 5 minutes, ignored if older than 30). The ratio is the larger of the project's size against its per-project limit and the organisation's total against its shared-storage limit.

applyStorageState moves a project between states and records the new state only after it took effect, so a crash part-way repeats the move instead of believing it done. Locks are re-applied every minute.

  • Soft lock. ALTER DATABASE … SET default_transaction_read_only = on, and idle sessions are ended so reconnecting clients pick it up (SetReadOnly). It is a default: a tenant can still open a read-write transaction to delete data, as V2 §10.4 intends, and the database's owner can reset it, which the next pass undoes.
  • Hard lock. Every login of the project becomes NOLOGIN, and their sessions end on the poolers and the server (SetLogins). The console logins are left out, so the team can still delete data and run Reclaim space.
  • Unlock. Under 100% the locks lift and the admins are emailed.
Risk

The hard limit is a sample and the soft lock is opt-out, so one tenant can still fill a shared node's disk. A tenant at 99% opens a read-write transaction (which the soft lock allows by design) and inserts at disk speed. Nothing stops it until the next size sample (up to 5 minutes) and enforcement pass (up to 1 more): temp_file_limit covers only temporary files, and the node-disk rule in StorageState applies only past 100%. At a few hundred MB a second that is tens of GB past a 512 MB limit, enough to fill a node and stop every project on it, which V2 §10.1 says no tenant may do. Measuring projects in warn or soft with pg_database_size on every pass would bound it. Not reproduced; read end to end.

Spec and code differ

V2 §10.4 and §10.8 say a hard lock and a suspension revoke CONNECT from the project's login roles. The code sets NOLOGIN on them instead, which also covers routes the poolers keep, and leaves the console logins able to connect.

The statement reaper

statement_timeout is user-settable, so it cannot be the guard. Every 15 seconds Reap connects to each shared cluster as its admin and looks at the client backends in its project databases, other than its own:

A long statement is cancelled with pg_cancel_backend; a session idle in a transaction is ended with pg_terminate_backend. A statement the reaper already cancelled that is still running, the same backend with the same query_start, caught the cancel, and is ended with its session (statement_terminated); the check reads reaped_sessions, which keeps each cancel's pid and started_at, so a pass on any server counts. Each one acted on is recorded in reaped_sessions with the first 1,000 characters of its query (kept 30 days, ) and shown in the project's activity view. Durations are measured against the service clock. Dedicated instances are exempt. The admin's own sessions are excluded; Xenibase's other logins in a project database (the console, restores, moves) are not.

Resolved

A statement that caught the cancel used to run for ever. PL/pgSQL can trap query_canceled, so a block such as DO $$ BEGIN LOOP BEGIN PERFORM pg_sleep(600); EXCEPTION WHEN query_canceled THEN NULL; END; END LOOP; END $$ resumed after the reaper's pg_cancel_backend with its query_start unchanged; every 15 seconds the reaper cancelled it again, recorded another row and reported success, and the session never ended. Now each cancel records the backend's pid and the statement's query_start (migration 00089), and reapInstance terminates a backend it finds still running a statement it cancelled (ReapedStatementCancelled), so such a statement lives one pass past the limit at most. TestReaperEndsStatementThatCatchesCancel runs that block on the test cluster and requires a cancel, then a termination.

Usage recording

RecordUsage records every completed hour since a watermark under an advisory lock, one server at a time, and redoes the last recorded hour because points can land late. Rows are upserted, so a repeated run changes nothing, and carry the organisation's plan at the time. Hourly rows roll up to daily after 90 days. The metrics and how they are priced are on .

Break-glass, dedicated allowances, deletion

  • Break-glass. StartBreakGlass lets a platform admin who is not a member act as an org admin for 1 minute to 4 hours, with a reason. The expiry is the database's clock, as the authorisation check reads it; every owner is emailed at once, any owner can end it, and actions are flagged in both audit logs.
  • Dedicated allowance. WithinAllowance and WithinAllowanceChange compare the organisation's instances, vCPU, memory and disk in use plus the request against its allowance; beyond it, a promotion becomes a request the platform admin approves (V2 §10.6). The Unlimited plan skips the check.
  • Organisation deletion. RequestOrgDeletion needs the name typed, refuses a personal organisation, switches logins off at once, and sets a 7-day grace period. FinishOrgDeletions then deletes each project (each with a final backup), and once none is left, in one transaction, keeps final backups for 30 days and removes invitations and memberships.

Webhooks, HTTP jobs, a project's own SMTP server and SMS provider, and import sources are the only ways a tenant makes Xenibase open a connection. All of them go through outbound. follows a delivery through it; the rules are these:

Every resolved address must pass, after canon maps IPv4-mapped, NAT64 and 6to4 addresses to the IPv4 they embed. The connection is pinned to the checked address, without proxies or redirects. Gate refuses a suspended organisation or one with outbound traffic off. Requests are counted per organisation, host and day, and the counts swept after 30 days (V2 §10.7).

The signature is signature: Xenibase-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "t.body">, one v1 per secret during a rotation's overlap. Verify refuses a timestamp outside the receiver's tolerance and compares in constant time. The package has no dependencies, so xenibase-status uses it for the server's pushes too. The edge's feed uses its own scheme over method, URI and body ().

The isolation tests and the security review
