This page is how Xenibase is installed, upgraded and watched once it runs: the Docker Compose bundle and its scripts, the images for the other machines, what an operator must keep off the server, the alerts and how they reach someone, the metrics, the logs, the separately hosted status page with its incidents, and the support desk. The services these watch are on their own pages and are linked, not repeated.

The compose bundle

A single-host install is deploy/compose/compose.yaml (V1 §11.1), project name xenibase. Everything is on one bridge network, 172.31.250.0/24, named after XENIBASE_NETWORK (default xenibase) so the agent can attach dedicated instances to it. The services that other configuration names by address have fixed ones below .20; Docker hands out the rest from .128/25.

Seven named volumes hold the state, among them pooler-config (written by the server, read-only in the poolers) and agent-state (the agent's identity and pinned CA). The server runs as uid 70, PgBouncer's user, so the poolers can read the 0640 files it writes. Secrets are environment variables from deploy/compose/.env; a required one is written ${NAME:?message}, so Compose refuses to start without it. Everything optional is passed through empty, which the server reads as off. Caddyfile serves the UI, imports caddy.d/*.caddy (empty until backend services are on), and on port 80 sends other hosts' /.well-known/acme-challenge/* to the server, which gets the database hostname's certificate itself ().

install.sh

install.sh installs and also upgrades in place. It runs from a git checkout, because the version it stamps comes from git describe. In order:

  1. Checks for Docker and Compose v2.
  2. If there is no .env: asks for the UI hostname and ACME email (or reads them from the environment), checks both by pattern, looks up the public IP from ipify, and under umask 077 writes .env with a fresh 32-byte master key and three 24-byte passwords. An existing .env is kept as it is.
  3. Appends what later releases added to old files: AGENT_BOOTSTRAP_TOKEN and XENIBASE_PUBLIC_URL.
  4. Builds the Postgres image for majors 17 and 18 (build.sh), then the server and the agent from the repository's Dockerfile with VERSION and COMMIT build arguments, and the edge too when COMPOSE_PROFILES includes services.
  5. docker compose up -d --no-build --wait, then recreates both poolers. A checkout replaces the bind-mounted .ini files with new inodes, and a running PgBouncer would keep reading the old one.
  6. Prints the URL and the first-run setup code, grepped from the server's log.

The Dockerfile builds the web app with Node 22 and both binaries with Go 1.26 without cgo, checks that the server embeds the real UI (-require-ui), and ships the server on distroless and the agent on postgres:18 with CA roots for S3.

upgrade.sh, and deploying from GitHub

upgrade.sh <tag> wraps install.sh with checks, a backup and a rollback. It first copies itself to a temporary file and re-executes from there, because git checkout replaces the script while the shell is still reading it. Exit status 0 is upgraded, 1 refused before any change, 2 failed and rolled back (or stopped with --no-rollback), 3 failed and the rollback failed too.

  1. Checks. A release tag that exists after git fetch --tags; unless --force, a clean tree and every service healthy; 10 GB free; and the tag's newest migration file not below the database's goose_db_version, so a downgrade is refused.
  2. Backup. pg_dump -Fc of the metadata database into upgrade-backups/, checked to be non-empty and to list goose_db_version, with a .meta file naming the release and schema it came from.
  3. Upgrade. git checkout the tag and run install.sh. The old containers serve while the images build.
  4. Gates. For up to UPGRADE_WAIT seconds (300), gates waits for every service to be running and healthy, xenibase-server -version to report the tag, and the schema to be at the tag's last migration. Operations that failed since the start are reported, not counted as a failure.
  5. Rollback, on any failure in steps 3 and 4:

Each migration runs in its own transaction, so one that fails leaves the schema at the last that succeeded, and the rollback sees the version moved and restores. Since 4.1 a server also refuses a schema newer than it knows (refuseNewerSchema). There are no previous-release images to switch back to: each build retags xenibase:local, so the rollback rebuilds the old checkout, normally from Docker's cache. Only the Postgres image keeps its predecessor, tagged by minor release (build.sh, ).

Risk

A rollback throws away more than the upgrade. The dump is taken before the image build; the old server keeps writing through the build (often minutes) and the new one through up to five minutes of gates. A rollback after a migration restores the dump, so that whole window goes, and the metadata is not the only state: a project created in it keeps its database and roles on the cluster with no row, a project deleted in it comes back as a row without a database, a password changed in it no longer matches the restored verifier, and a payment webhook processed in it is lost for good. docs/deploying.md's "project data is unaffected" undersells it. Dumping after the build, with the old server stopped, would shrink the window to the migration.

From GitHub. The Deploy workflow refuses a tag whose ci, e2e, docs-install and audit checks did not pass, waits for a reviewer of the production environment, and runs one deploy at a time (concurrency: deploy-production). Its key is restricted to the forced command deploy-ssh.sh, which accepts only upgrade <tag> [--dry-run], status and last, and runs an upgrade under nohup so a dropped connection cannot kill it half-way. make test-deploy runs both scripts against a fake docker through twelve scenarios, failed migration and failed rollback among them (upgrade_test.sh).

What the operator must keep off the server

Three things, and the server cannot recover any of them:

  • .env, for XENIBASE_MASTER_KEY. It seals every stored credential and the derive seed (). The generated file says so in its first line.
  • The backup key (Settings → Backup key). It decrypts every backup on platform targets, the metadata self-backups included, and never changes.
  • The bucket credentials of the default storage target, where metadata/ lives.

With those, docs/disaster-recovery.md rebuilds a lost control node from the newest nightly metadata backup (). The upgrade-backups/ dumps are a second, local copy taken before each upgrade. They are never pruned.

Firing, deduplication and clearing

A condition's key is kind:target_type:target_id. Evaluate upserts each holding condition against a unique index on the key WHERE status = 'firing', so it opens a row or refreshes the firing one (xmax = 0 tells which), and resolves every firing row whose key did not come up. A condition that returns opens a new row. The grace periods are kept in each process's memory (poolerFailing).

Risk
  • Nothing holds a resolved alert down. Thresholds have no hysteresis and one good evaluation resolves. A node's disk hovering at 85% as WAL is recycled, or a project at its disk warning, fires and resolves at each crossing, every 30 s at worst, each time a new row and two notifications. With several servers the grace clocks are per process, so one server resolves what another just fired. The alerts table is never pruned, so flapping also grows it. Resolving only after a few clear evaluations would cover all three.
  • A failed on-demand restore test of a deleted project never clears. FailedLatestOperations groups by project and keeps soft-deleted ones, and the restore_test case, unlike the backup one, does not check the project is live. Weekly tests run with no project and never replace that row. So "Restore test of failed" fires for good, and through States keeps the public page's Backups component degraded; for a live project, until someone tests it again. Alerts cannot be dismissed.
  • One failing source silences every alert. conditions returns nothing when any query fails, so Evaluate neither resolves nor fires. A query that keeps failing (a bug, a lock, a slow WALArchiveSamples over a large metric_points) leaves a log line every 30 s and no alert. Firing what was read while resolving nothing would keep decision M7 #1's protection.

Delivery

Channels are one webhook and one SMTP account, kept in the alerts settings row with the webhook secret and SMTP password sealed under the master key (Save). The API shows secrets only as present. DeliverPending claims up to 50 notifications at a time:

A failure sets the lock to 1 min × 2^attempts, capped at 30 min. With no channel configured, the notification is marked handled. Each event goes to every channel:

The webhook is a JSON POST with X-Xenibase-Event (alert.firing, alert.resolved, alert.test), 10 s to answer 2xx, and, with a secret, X-Xenibase-Signature: t=<unix>,v1=<HMAC-SHA256 of "t.body"> (alerts.Sign). The payload is the alert's id, kind, severity, summary, target, times and detail. It goes through a plain HTTP client, not the outbound one: the URL is the platform admin's. Email is plain text over STARTTLS (required when chosen), implicit TLS, or none for a local relay; a subject with anything outside printable ASCII is RFC 2047-encoded, so a name cannot add a header. Settings → Alerts → Test sends alert.test to each channel.

Risk
  • One broken channel resends to the working one. deliver joins both channels' errors and the whole notification is retried on both. With email misconfigured, the webhook gets each firing again every 30 minutes for 7 days, about 340 times; with the webhook down, the inbox does. A scratch test (webhook answering 200, SMTP on a closed port) saw one firing three times in three claims. Recording delivery per channel would fix it.
  • An alert that resolves before its first successful delivery is never sent. The claim takes a resolved alert only if its firing was notified, so while delivery fails any alert shorter than the backoff vanishes unannounced.

Metrics

Collect runs every XENIBASE_METRICS_INTERVAL (1 min) on every server. Per instance it opens one admin connection and reads each database's counters from pg_stat_database and client backends from pg_stat_activity, with pg_database_size every 5 min, and a dedicated instance's archiver (). TPS and cache hit ratio are deltas, skipped when a counter went backwards. The poolers' SHOW POOLS gives clients and waiting clients, and their transaction counters mark projects active for the Free tier (). Node metrics come from the agents' last health checks, when fresh.

Points go into metric_points, keyed by scope, id, metric, resolution and minute, with an upsert, so several servers or a restart do not duplicate a point. Hourly (and at start, for the last 25 hours) the collector averages completed hours into 1h points and prunes: 1m points after 24 hours, 1h after 30 days (PruneMetrics), over an index on (resolution, ts). The API serves 1 h and 24 h from minute points and 7 d from hourly ones, adding live averages for the hours not yet downsampled (Query). A project's metrics are ProjectView and add the top 10 statements from pg_stat_statements when the project enabled it; a node's are the platform admin's.

The Prometheus endpoint

GET /metrics serves the latest value of every series from the last max(3 × interval, 6 min) as gauges xenibase_project_* and xenibase_node_*, plus xenibase_up and the audit writer's own counters, which matter most when the database refuses writes. The route is public in the route table; the handler checks:

XENIBASE_METRICS_TOKEN must be at least 24 characters. Project series are labelled project_id, org_id, org and tier, never by project or database name, since a project's name is its tenant's; node series by node_id and node. Label values are escaped. Cardinality is bounded by the platform's own size: at most 11 series per live project (deleted ones drop out) and 8 per node, with nothing per request, user or query. Renaming an organisation changes its org label and so starts new series.

Logging

Every binary builds its logger with logging.New: log/slog to stderr, JSON unless the format is text. The server takes XENIBASE_LOG_FORMAT and XENIBASE_LOG_LEVEL; the agent, edge and status page take their own *_LOG_FORMAT and log at info. The API's requestLogger writes one line per request with method, path, status, bytes, duration and request id. The path has no query string, and no body or header is logged. Paths carry ids, and on two routes a billing contact's email or a support phone number, but no secret.

What is never logged: secrets (the import and Supabase helpers strip passwords from connection errors), and SQL. The console's audit entry has the statement count, the read-only flag and the error code, never the text (). The one secret logged on purpose is the first-run setup code, which works only until the first operator exists. Postgres itself logs any statement over 5 s (log_min_duration_statement) with its text, in the container's log; log_statement stays none, and the isolation check fails a cluster where it is not.

Risk
  • Container logs are never rotated. No service sets logging: and the install guide does not configure the daemon, whose default json-file driver keeps everything. A line per API request and every slow tenant statement's text pile up on the databases' disk until it fills. A max-size and max-file per service would bound it.
  • Secret files take the default umask. upgrade.sh creates its dump (password hashes, verifiers, every sealed secret) under the shell's umask, usually 0644, in a 0755 directory, and chmod 600s it only after pg_dump ends. An .env copied by hand from .env.example, as its first line suggests, keeps the copy's mode; install.sh never tightens it. It matters only with other local users, but umask 077 in both scripts costs nothing.

The status page: xenibase-status

xenibase-status is a separate pure-Go binary with one SQLite file (V3 §2.6), meant for another provider so an outage cannot take down the page that reports it, and it never touches Xenibase's database. LoadConfig refuses unknown keys in status.toml, reads *_file secrets, and requires a push secret of at least 32 characters if one is set.

Checks and automatic incidents

Every interval (1 min), Tick runs every component's probes at once from outside: http (a 2xx), postgres (a query through a DSN in a secret file) or tcp, 10 s each. Some failing is degraded, all failing is down. A heartbeat component takes xenibase-server's last report, or unknown after 5 min; with probes too, the worse wins.

An automatic incident is auto-<component>-<unix>, major when down and minor when degraded, backdated to the first failing check, quoting the probe errors; xenibase-server's pushes cannot overwrite it (409). A component shows the worse of its measured state and any open manual incident naming it, and a measurement older than three intervals as no data.

History

Each check records the worst state of the minute; each tick re-counts the last day into daily totals and drops minutes after 3 days and days after 90 (rollUp). The page draws 90 daily bars, with uptime counting degraded minutes as up and unknown ones as neither; /api/v1/status, /api/v1/incidents and /feed.rss serve the same. The HTML is html/template under a CSP of default-src 'none'.

Signed pushes

Five endpoints take xenibase-server's requests: PUT /api/v1/incidents/{id}, POST /api/v1/heartbeat, PUT /api/v1/sla/targets, POST /api/v1/sla/results and PUT /api/v1/subscribers/managed. Each needs Xenibase-Signature, the same scheme as webhooks (), checked by one wrapper:

Without a push secret every push is refused. A pushed incident must name its own id in the path and only known components; its updates are replaced as a set, and the ones with new ids are mailed. The heartbeat maps each state to the page's components of that heartbeat id, a region-specific state winning over a regionless one. The SLA endpoints are on .

Risk

A push's signature is not bound to its endpoint. The HMAC covers the timestamp and body only, and unknown JSON fields are ignored. A signed heartbeat body sent to PUT /api/v1/subscribers/managed decodes as an empty list and deletes every managed subscriber; sent to /api/v1/sla/targets it removes every SLA target. A scratch test did both (204 twice, the list emptied). A heartbeat replayed within five minutes also overwrites a newer one. It needs someone who sees a signed request, one a minute, and XENIBASE_STATUS_URL may be http://. Signing the method and path too, and refusing an older heartbeat, would close it.

Subscribers

With [smtp] set, anyone can subscribe (Subscribe): five requests an hour per client address, one confirmation mail per address per 10 minutes, the same answer whether or not the address is subscribed, a 48-hour link whose token is stored only as a SHA-256, and unconfirmed sign-ups dropped after 7 days. Links open a page whose button POSTs, so a mail scanner's prefetch changes nothing. Mail goes through an outbox, retried with backoff up to 10 times. Managed subscribers come from xenibase-server hourly (Subscribers): owners and billing contacts with status emails on, of active paying organisations, mailed without opt-in only for incidents on the components and regions their projects use. Unsubscribing removes the address from both lists and leaves a tombstone the syncs honour.

Incidents from Xenibase

Platform admins write incidents in Admin → Incidents (incidents.Create, Post, Edit), on the components in XENIBASE_STATUS_COMPONENTS. A change clears pushed_at; every 10 s Push sends each unpushed incident whole and marks it pushed only if it did not change meanwhile, so a status page that was down catches up. The same loop sends the heartbeat every minute (backups, dedicated, webhooks and jobs, billing, backend services per region: what is wrong, never how much or for whom), syncs subscribers hourly, and closes announced maintenance whose window ended. Organisations see open incidents covering their projects in a banner.

Risk

Without a status page, maintenance never ends. main starts incidents.Run only when XENIBASE_STATUS_URL is set (here), yet Run has a branch for no status page whose only job is EndMaintenance. On an install without one, an announced window is never resolved and an unconfirmed draft never lapses, so every covered organisation's dashboard shows the finished maintenance as in progress until an admin resolves it by hand. Starting Run unconditionally would fix it.

Note

An automatic incident and a degraded component's line show the probes' error text on the public page, cut at 200 characters. A postgres probe's error names the probe's user, database and the address it reached.

Support

internal/support keeps tickets in the metadata database (V3 §7.1), numbered T-n, each with a channel, status (open, pending, solved, closed), priority, the plan when it opened, an assignee and a response target. OpenTicket trims the subject to 200 characters, refuses a body over 20,000, inserts the ticket and its first message in one transaction, and acknowledges by the same channel.

Threading. Outbound mail carries [T-n] in the subject and a recorded Message-ID. An inbound email joins a ticket by that reference, or by an In-Reply-To or References id Xenibase recorded, but only from the requester or a member of the ticket's organisation; anything else opens a new ticket. Quoted history is stripped, and a message id seen before changes nothing. A WhatsApp message joins the open ticket from its number; media become a placeholder line. Attachments are not stored at all (every message's attachments is []), so there is nothing to serve or sanitise yet.

Response targets (TargetFor): Free is best effort with no target; Pro 8 business hours; Team 4; an urgent ticket on Pro or Team one hour of calendar time. Business hours are 09:00 to 17:00 WAT, Monday to Friday, without public holidays. A change of priority or organisation before the first response recomputes the target from the ticket's opening time.

Who sees what. In the dashboard, owners and admins see all of their organisation's tickets; other members see the ones they opened, by user id or email (seesTicket). A ticket of another organisation answers 404. Internal notes (direction = 'note') never leave the support console, by email or the org API. The console is for platform admins and the support role (SupportConsole), and its context panel shows the organisation's metadata, never data ().

Risk

Another organisation can claim a customer's tickets. Billing contacts and WhatsApp numbers are whatever an organisation's owners and admins type, unverified, and billing contacts rank first. If organisation A adds victim@b.example as a billing contact, every email the victim sends support opens a ticket in A: A's owners and admins read it and every staff reply in their dashboard, and A's members can reply into it by email, since the thread check accepts any member of the ticket's organisation. A scratch test reproduced both. A number registered by A does the same for WhatsApp (InboundWhatsApp), and B can no longer register it. Verifying an address or number by a code before it routes tickets would fix it.

Risk

An inbound email's sender is taken on trust. parseInboundEmail reads From and ignores the provider's SPF and DKIM verdicts; the inbound secret proves the provider called, not who wrote. Mail forged as an organisation's owner opens a ticket the console shows as the owner's, with the organisation's context, or, with the owner's sequential [T-n], joins the owner's thread. The forger reads no replies, but staff act on what tickets ask, and the acknowledgement from the genuine support address quotes the forged subject to the forged address. Flagging or refusing mail without a passing DMARC result would close it.

Version and build information

internal/version holds Version, Commit and BuildDate, set with -ldflags -X; a plain go build reports 0.0.0-dev. The bundle takes VERSION from git describe --tags --always, exactly the tag on a tagged checkout, which upgrade.sh's gate relies on. Only the main Dockerfile sets the build date. Every binary answers -version, the server serves GET /api/v1/version without authentication, and agents report theirs in health checks; the server sends no work to an agent of another major or an older minor ().

Spec and code

Spec and code differ
  • V1 §11.1 has a curl … | sh installer and a bare-metal systemd path beside Compose. There is only the Compose bundle, and install.sh needs a git checkout.
  • V1 §11.3 says the server refuses to start if the agent version is incompatible. It starts, and refuses work to that agent.
  • V1 §8.7 exposes /metrics "for anyone who wants it". It needs the metrics token or a platform admin's session (decision M6 #9).
  • V3 §2.6 wants the 90-day history to use "the same measurements as the SLA". The page's history comes from its component probes; the SLA counts separate per-project probes from both vantage points ().
  • V3 §7.1 gives the one-hour target to HA incidents. Any ticket the customer marks urgent on Pro or Team gets it.
  • docs/operations.md's alert table lists 12 of the 21 kinds, and calls the restore-test alert the weekly test's, though a test run on demand for one project raises its own.
