Xenibase is checked by one GitHub Actions workflow with nine jobs, built by one Makefile, and shipped as a GitHub release built from the tag once CI has passed on it. Most of the confidence comes from suites that run the real thing: a control plane in-process against real Postgres and PgBouncer, the install bundle in a browser, the install guide as a script. This page lists each check, what it proves and where it stops, and the CLI, SDKs, docs site and brand that the same system builds.

The ci job is one long sequence on one runner. Its order matters: the Postgres-backed unit tests run first against the service container on port 5432; the dev compose environment for the integration suite comes up last, on its own ports, so the two never meet. On failure it prints the dev environment's logs and the failing lines of the integration log. make test-go and make test-integration pipe go test -json through testsummary, which prints each package's result and the whole output of every failing test, then the counts and every skipped test grouped by reason, and exits 1 on any failure or when a test named in XENIBASE_TEST_MUST_RUN did not run. The recipes run under pipefail and the integration step pipes through tee under set -o pipefail, so neither pipe hides a failure.

ci.yml sets no concurrency and triggers on both push and pull_request, so a branch with an open pull request runs every job twice and a newer push does not cancel an older one: runner time, not correctness. There is no pull_request_target anywhere: pull requests from forks get a read-only token and no secrets.

Actions and pinning

The actions/* actions are pinned to major tags (@v4, @v5) everywhere except the atlas job, which pins checkout and setup-node to commit SHAs. Two third-party actions, golangci/golangci-lint-action@v8 (linter v2.14) and dart-lang/setup-dart@v1 (SDK 3.9.4), are pinned to major tags too; the third, aquasecurity/trivy-action in image-scan, is pinned to a commit (v0.36.0, with Trivy v0.76.1). dependabot.yml proposes updates to all of them, and to the Go modules, the npm trees, the Dockerfiles and the compose files' images, weekly and grouped.

They run in the ci job, which has a read-only token and no secrets, so a moved tag could break or falsify that job but could not publish or deploy. The release job, the only one that can write, uses only actions/*; the deploy job, which holds the SSH key, uses none and connects with StrictHostKeyChecking yes. The tag input reaches the shell only through an environment variable and is checked against ^v[0-9]+\.[0-9]+\.[0-9]+([.-][A-Za-z0-9.]+)?$ and then by git rev-parse, so it cannot carry shell syntax.

The Makefile

Makefile is the only entry point CI uses; every CI step is a make target, so a contributor can run the same thing locally. It runs recipes under bash -eu -o pipefail, and exports GOFLAGS += -tags=nodynamic (why: without it the image codecs load libwebp through purego and xenibase-server and xenibase-edge become dynamically linked).

How tests get a database

A package test that needs Postgres calls storetest.New. It connects to XENIBASE_TEST_DATABASE_URL, creates xenibase_test_ plus twelve random hex characters, runs every migration, and drops the database with WITH (FORCE) when the test ends. Without the variable the test skips. In CI the variable points at the job's postgres:18 service as its superuser, so these tests always run there.

The integration and isolation suites go further. testenv.Start builds a complete xenibase-server in-process (API, workers, provisioning and the services, with fakes for S3, SMTP, phone providers, Hetzner and the wallet provider) on a fresh metadata database, and registers the dev environment's shared cluster and test pooler pair. The suites share one pooler pair, which is why they run with -p 1. Each one checks its environment first:

The skip is what lets make test-go compile and pass over ./test/... without the dev environment, and it is also why a variable missing from test.env turns a suite off without failing it: the summary at the end of the run lists it, and CI's XENIBASE_TEST_MUST_RUN fails the run when one of the tests it names skipped.

Resolved

Some tests never ran in CI, and skips were silent: TestDumpRestoreCopy (the agent's real pg_dump and pg_restore) and docker.TestAgainstDaemon always skipped because nothing set XENIBASE_TEST_PG_BIN or XENIBASE_TEST_DOCKER, the second half of TestDedicatedResize (a size the node cannot hold moves the project) skipped on any runner with fewer than three CPUs, and nothing counted skips. Now the ci job installs the Postgres 18 client tools from PGDG and sets both variables, and TestAgainstDaemon fails rather than skips when it is asked to run without a daemon or its image. TestDedicatedResize fills the node by memory and asks for more memory, which Docker does not cap at the host's size as it does CPUs, so the move runs on any runner. testsummary lists every skip with its reason, and the ci job names the tests that must run in each step (TestDumpRestoreCopy and TestAgainstDaemon in test-go; TestDedicatedResize, TestMoveUnderLoad, TestTenantIsolation, TestSDKs and TestPoolerHostFailover in the integration step). Other skips are listed, not failed.

What the integration suite covers

The files are named for what they prove, from provisioning, backups, imports, promotion under a live writer, HA, moves (one under load, at 1 GB in CI) and branches to billing, regions, failure injection (failure_test.go, chaos_test.go), the backend services through a real edge, and the CLI. TestSDKs runs each SDK's live test against a project on a real edge (below). Waiting is done by polling with a deadline (waitFor) rather than by fixed sleeps, though fixed sleeps remain in places.

The isolation suite is the tenant-escape list from V1 §7.1. TestLiveIsolationCheck runs the same internal/isocheck that xenibase-server runs weekly per shared cluster, so CI and production share one implementation (decision M7 #5).

The browser journey and the install tests

make test-e2e builds the server, agent, Pebble and fake-S3 images and the Postgres images, starts the bundle from deploy/compose/compose.yaml with compose.e2e.yaml over it, and runs Playwright with Chromium mapping xenibase.test to the host. The first test goes from the setup wizard to a database a pg client reaches over TLS with a certificate issued by Pebble; it saves the session, and the rest reuse it in order (mode: "serial", one worker, no retries). Every screenshot point also runs axe in both themes, and a serious or critical WCAG 2.1 AA violation fails the run (a11y). On failure the job uploads Playwright traces.

test-docs clones the commit into a scratch directory, extracts the shell blocks that docs/install.md marks with <!-- docs-test -->, runs them as written, checks the installer printed a setup code and wrote .env at mode 600, then runs the first e2e test against what it installed. test-upgrade installs UPGRADE_FROM (by default the newest vX.Y.Z tag reachable from the commit and not on it, found when it runs; v4.1.0 without tags), commits a migration that cannot run and tags it, checks that upgrade.sh exits 2 with the old version, schema and a canary row intact, then upgrades to this commit under an annotated test tag and checks the reported version, the schema, the canary and the kept backup.

Resolved

The rehearsal used to install v4.1.0, which its comment called "the previous Xenibase release" four releases later. previous_release now picks the newest release tag reachable from the commit, skipping -rc, -test and -broken tags and a tag on the commit itself, so CI on a release tag rehearses the upgrade a real install makes next.

Lint and the race detector

.golangci.yml is golangci-lint v2: the standard set (errcheck, govet, ineffassign, staticcheck, unused) plus bodyclose, errorlint, gocritic, misspell, revive and unconvert, and the gofmt and goimports formatters with the module as the local import group. Generated files are excluded strictly, as are the comments and std-error-handling presets. There are 27 //nolint directives, each with a reason. Lint covers the main module only: sdk/go gets go vet in test-sdk, and test/acmedns gets nothing. The UI has no ESLint; tsc -b is its only static check.

The package tests, the integration and isolation suites and the Go SDK run under -race. test-acme, test-acmedns, the load test and the full move do not.

Versions and the release

Every binary carries its version, commit and build date in internal/version, set at link time by LDFLAGS. The Makefile takes the version from git describe --tags --always --dirty and the commit from git rev-parse --short HEAD; the release job passes the tag as VERSION. The Dockerfile takes VERSION and COMMIT as build arguments, which install.sh fills from the checkout, so a bundle install reports its tag too (the upgrade rehearsal checks it).

A pushed v* tag runs ci.yml, and its last job, release, waits for ci, e2e, docs-install, audit and upgrade to pass on the tag. It runs make release: the UI, then xenibase-server, -agent and -status for linux amd64 and arm64, the CLI for linux, darwin and windows on both architectures, a source tarball from git archive HEAD, and SHA256SUMS. It checks that the amd64 server embeds the real UI and that the server and CLI report the tag, extracts the tag's section from CHANGELOG.md (failing if it is empty), and publishes with gh release create --verify-tag. xenibase-edge is not among the binaries: the edge and every other image are built from source on the host by install.sh and enable-services.sh, and no image is pushed to a registry.

Resolved

A release used to be published whether or not CI passed on its commit: release.yml and ci.yml both started on the tag push and did not wait for each other, so a tag whose ci, e2e or upgrade job then failed still got a public release, usually before those jobs finished. Now the release is the release job of ci.yml with needs: [ci, e2e, docs-install, audit, upgrade], run only for a pushed v* tag, so it cannot race the tests; it alone has contents: write, and release.yml is gone. A tag whose jobs fail gets no release: re-running the failed jobs re-runs it once they pass, or the fix gets the next version. deploy.yml still checks the tag's check runs before Xenibase's own server.

The documentation site

docsite.Build renders every Markdown file under docs/ (including this atlas's README) with goldmark and GitHub-flavoured Markdown, wraps each in one template with the navigation from docs/site.json, and writes a search.json index (title, section, headings to level 3, and the first 4,000 characters of text). fixLink rewrites links: .md becomes .html, a directory becomes its README page, and anything that leaves docs/, or is a file under it that is not a page, becomes a link to the repository at blob/main. Every internal link must reach a page and its anchor a heading; cmd/docsite lists every broken one and exits 1, and TestDocs builds the real docs in make test-go as well.

Search is a small script with no dependencies. It loads search.json on the first keystroke, ranks title over heading over body matches (every word must match), and builds results with textContent, so a title cannot inject markup. The renderer passes raw HTML in Markdown through (html.WithUnsafe()); the input is the repository's own docs, so that is a choice, not an exposure. The site is uploaded as a CI artefact and published nowhere by the workflows.

What the link check does not see

Links rewritten to the repository are not checked: a guide that links ../deploy/compose/upgrade.sh keeps building after the file moves. At the verified commit all 75 such links resolve (checked by hand for this page). Links written in raw HTML are not checked either.

The SDKs

Three SDKs in sdk/ share one shape (decision V4-M36 #7): a client from the project URL and a key, with data, auth, storage and realtime; a refresh a minute before expiry, one at a time; reads by URL when the URL form can express them and by the JSON query form otherwise; live() queries that refetch on changes, on resync and after a reconnect; and realtime over the Phoenix protocol the edge serves.

The live tests need a project. TestSDKs enables backend services on one, starts an edge behind a proxy that supplies the project's host name, and runs all three (sign-in and refresh, reads and writes under row-level security, a realtime change, files, errors, sign-out). Each skips, or exits 0, without XENIBASE_SDK_URL, which is how make test-sdk runs them harmlessly.

A secret key (xb_sec_…) makes the JS client sessionless: no storage, no refresh, no reading of the URL (XenibaseClient). The SDK does not stop a secret key being used in a browser; the edge does, refusing a secret key on any request with an Origin header unless the project allows it (secret_key_in_browser). By then the key has been shipped in the app, so the guides tell developers to use the publishable key in apps.

Versions are set by hand in each package. A JS test keeps VERSION equal to package.json (the test); the Go and Dart constants have no such test. Nothing in CI publishes to npm or pub.dev, and the repository has no sdk/go/v* tags, so go get of the Go SDK resolves to a pseudo-version of the default branch.

The CLI

xenibase is cmd/cli calling cli.App.Run. It has commands that call the API, plus version, as a tree of names (xenibase backup restore, xenibase auth users ban), each over the generated client. Every command takes --json; destructive ones need --confirm <name>; exit codes are 0, 1, 2 for usage, 3 for a failed operation and 4 for 401 or 403. Global flags (--json, --context, --server, --no-wait) are taken from anywhere on the line.

Login. login takes an https:// server, or http:// only for localhost, 127.0.0.0/8 and ::1 (checkServerURL), and runs the device flow (print a code, open the browser, poll at the server's interval), and the user approves in the web app, choosing the organisation and scopes; --token - reads a token from standard input instead. It then stores a context named after the host and the organisation's slug. logout revokes the token on the server unless --keep-token.

Contexts and the config file. $XENIBASE_CONFIG_DIR, $XDG_CONFIG_HOME/xenibase or ~/.config/xenibase holds config.toml (contexts with server, organisation id, token or token_cmd, token id and CA file) and credentials.toml (personal database URLs, cached because the server shows a password once). Both are written at mode 600 in a directory created at 700; saveConfig writes a temporary file and renames it, and a unit test checks the mode. token_cmd runs through sh -c, so a token can live in a password manager. XENIBASE_CA_FILE or --ca-file adds a CA to the system roots for a server with a private certificate.

Which server and token. resolve starts from --context, XENIBASE_CONTEXT or the current context, then lets the environment and flags override parts of it. A context's token, token_cmd and CA file go only to its own server: when --server or XENIBASE_SERVER names a different one (normalServer compares scheme, host and port), they are dropped, and the token comes from XENIBASE_TOKEN or the one saved context for that server, or the command stops with exit 2. Every token, saved or from the environment, goes only to https:// or a loopback http://.

Resolved

--server or XENIBASE_SERVER used to send the current context's token to another host: resolve replaced only the context's server, so xenibase whoami --server https://staging.example, or a CI job setting XENIBASE_SERVER on a machine with a logged-in context, sent the production token there (reproduced with a context for https://prod.example, which delivered Bearer xb_prod_secret to a test server), and login accepted http:// for any host. Now a different server drops the context's token, token_cmd and CA file; XENIBASE_TOKEN or the single saved context for that server supplies the token, two such contexts or none stop the command with exit 2, and --context with a different --server is refused unless XENIBASE_TOKEN is set. http:// is accepted only for loopback, at login and for any token after it, and logout revokes only through the context it forgets (TestServerOverrideDoesNotSendTheContextsToken, TestPlainHTTPOnlyToLoopback). A context saved for a non-loopback http:// server stops working and needs a new login.

Integration tests build the real binary and run it against a real control plane: a CI-style job with a project-restricted write token that runs SQL on its project, gets not-found for another organisation's project and exit 4 deleting its own (M10's done-when); a device login approved as the user, whose saved context is then used; and policies lint exiting 1 while a table has no row-level security (cli_test.go). The e2e journey approves a CLI device login in the browser.

The brand in code

internal/brand holds the name, tagline, colours and logo paths for what the server renders itself: email (mail/layout.go) and documents. Email cannot use CSS variables, so the colours are literal #rrggbb strings. The web app's tokens live in web/src/styles.css, and TestThemeMatchesTheEmailPalette fails when --accent, --accent-strong or --accent-text stop matching Teal, TealDeep and TealLight, or when brand/mark.svg stops using Glow. The other four colours (mint, ink, muted, line) are not compared. brand/render.mjs renders the SVGs to the PNGs in web/public with Playwright's Chromium; it is run by hand and the PNGs are committed. The docs site has its own palette in siteCSS and is not checked against the brand.

Dependencies

One Go module for everything except sdk/go and test/acmedns, at Go , with go.sum committed and oapi-codegen pinned as a module tool. Three npm trees have committed lockfiles and are installed with npm ci: web, test/e2e and sdk/js. The audit job runs on every push (decision M7 #14), so a new advisory against any of them fails every branch until it is dealt with, related to the change or not. Dependabot proposes updates weekly, grouped by ecosystem, for the three Go modules, the three npm trees, the Dockerfiles, the compose files' images and the workflows' actions; a FROM built from a build argument (${REGISTRY}golang:…) may still need a hand.

Resolved

The audit stopped at Go modules and npm packages: the images that face the internet were never scanned, nothing proposed updates, and Caddy ran from the floating caddy:2, so two installs of one release could run different Caddy. Now Caddy is caddy:2.10.0 in the bundle, the status page and the DNS-plugin build (xcaddy build v2.10.0, the version test/acmedns checks), with each DNS plugin pinned to a version that needs no newer Caddy; the weekly image-scan job scans the images the install runs, Caddy and PgBouncer included, and fails on a fixed CRITICAL or HIGH vulnerability; and Dependabot proposes updates. The scan is weekly, not per push, so a new advisory fails one run rather than every branch, and an image whose vulnerability has no fix yet passes.

Where the specs and the code disagree

Spec and code differ
  • V1 §13 and §11.5 run the integration suites with testcontainers-go. They run against the dev compose environment (deploy/dev/compose.yaml, --profile test) started by the Makefile, with the variables in deploy/dev/test.env.
  • V1 §11.5 describes a single workflow: lint, tests, "frontend lint", the generated-code check, builds, integration, Playwright on tagged builds, and release artefacts on tags. There are three workflows; the release is the last job of ci.yml, after the tests; Playwright runs on every push, not only on tags; and the UI has no linter beyond tsc.
  • V1 §11.5's make release "builds the Postgres image, produces the Compose bundle". It builds neither: the bundle is a source tarball, and every image is built on the host at install time.
  • V1 §11.5's layout lists test/fixtures. There is none; the Supabase-shaped fixture is test/e2e/supabase-fixture.sql and the integration sources are containers in the dev environment.
  • V2 §7.1's config stores the organisation's slug as org; the code stores its id.
  • V4 §8.1's Go SDK is a separate xenibase-go repository; it is sdk/go in this one.
