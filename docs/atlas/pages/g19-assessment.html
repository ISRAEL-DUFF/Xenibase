This page is a judgement on the rest of the atlas, written for the people who decide what Xenibase's engineers do next. Every claim below was checked against the code at the commit in the header. Where a sentence is an opinion or an estimate rather than a fact read from the code, it says so. The detail lives on the pages it links to; this page collects it and ranks it.

In short: the control plane is in better shape than its speed of construction would suggest. Parts A to F found and fixed the defects behind 145 Resolved notes, and each fix came with a test. What is left falls into four groups. A few concentrations of trust carry most of the security risk (the shared client certificate that commanded every agent is now one per server, a day long and revocable): the edge's regional feed, the master key, and the shared clusters' private network. Nothing has been measured on real servers: every load figure comes from one 4-vCPU development container. Two tables in the metadata database grow with traffic rather than with customers, and the operations queue has no priorities. And the GA and launch gates are waiting on people: a penetration test, an accountant, a lawyer, a wallet sandbox and a facility in Lagos.

Scaling the metadata database and the poolers

Every server shares one metadata Postgres. It holds the platform's state and also two streams that grow with traffic. Every tenant connection goes through a pair of PgBouncers per pooler host, into shared clusters with a fixed max_connections. These are the numbers the code sets.

Connections

  • Each server has a metadata pool of 16 unless the URL says otherwise (defaultMaxConns). The operations notifier takes one connection out of the pool for its LISTEN. On the server holding the locks, the webhook lock, the job-scheduler lock and the HA watcher each hold a pooled connection for as long as they lead, leaving about 13 for 4 operation workers, the HTTP API and the loops.
  • PgBouncer runs two processes per pooler host, session and transaction, each with max_client_conn = 2000, default_pool_size = 5 and server_idle_timeout = 30 (transaction.ini). Each route gets the project's pool_size (5 on the shared tier, 20 dedicated) and max_db_connections equal to its connection limit (20 shared, 90 dedicated) (DefaultSharedSettings, Sync). Pools are per database and user, so a project with backend services has a pool per login.
  • A shared cluster in the bundle has max_connections=500 (compose.yaml). One project can hold up to 20 server connections through each PgBouncer, so a couple of dozen busy projects could in principle take the whole cluster (estimate). The role's own connection limit (20) stops any one login going further.
  • The edge keeps, per project and per login, a pool of up to 4 client connections to the transaction pooler (2 for the service and hook roles) (edge.go), idle for a minute at most.
  • Direct connections bypass the poolers: the metrics collector, reaper and insights per instance per server, backups, console sessions, and one LISTEN connection per project with webhooks, held by the delivering server (supervise).

What would break first

Ranked by how soon each would bite. The first comes from the measurements; the rest are estimates read from the code.

  1. Shared-cluster connections. Measured: about 300 projects in active use hold about 400 backends at any request rate, and 500 is the limit. Placement counts projects, not connections (drift row 4), so a node with many quiet projects and a node with a few busy ones look the same to it.
  2. api_request_logs. A row per request in the metadata database, with two indexes, written by COPY every 10 s and deleted continuously from the old end. At a few hundred requests a second sustained it becomes the metadata database's largest write load and the main source of its WAL and vacuum work (estimate). Partitioning by day and dropping partitions, or sampling, would remove the deletes.
  3. metric_points and the per-minute fan-out. Each server, every minute, opens a new admin connection to every instance and upserts about six rows per project. At 10,000 projects that is roughly 1,000 rows a second and 130 million rows kept (estimate), and with three servers the instance connections triple. One collector under a lock, and the same partitioning, would fix both.
  4. Webhook LISTEN connections. One direct connection per project with webhooks, all held by one server and outside the poolers' limits. On a 500-connection cluster a few hundred projects with webhooks would take a large share of it (estimate). Nothing counts them against the cluster.
  5. The operations queue. At a few hundred projects per server, the 02:00–04:00 backup window and any long move compete for 4 slots with whatever users ask for (risk 8).
  6. Pooler configuration. Every sync re-renders every route and reloads both PgBouncers. That took milliseconds at 150 projects. PgBouncer is single-threaded per process, so a pooler host's throughput is two cores' worth whatever its size (estimate).

What to measure, in order

  1. The six-server rig at the gate's 1,000 projects and 2,000 requests a second, recording metadata-database CPU, WAL rate, table sizes after a day, and pooler-host CPU per PgBouncer process.
  2. The number of server connections per active project on a shared node, by request rate and with webhooks on, to set where placement should stop.
  3. Operation queue age during the backup window with a few hundred projects and a large move running.
  4. Two and three servers against one metadata database, to see what the unlocked loops cost.

Judgement: one well-sized metadata database and a few shared nodes will carry a launch with hundreds of projects. Past that, connections per shared node are the measured limit and the request log the likely next one. No capacity figure should be quoted to a customer until the real-server run is recorded.
