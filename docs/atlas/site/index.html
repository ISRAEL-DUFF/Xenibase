    Engineering atlas

    How Xenibase is built, checked against its code.

    Xenibase runs Postgres for other people: hundreds of small databases on a shared cluster, dedicated instances with continuous backup and failover, and backend services (a data API, auth, file storage, realtime) in front of them. Every project keeps the same connection string for its whole life. This atlas explains how that is built, one feature and one component at a time. It is written for the engineers who maintain it.

    The system on one page#

    Clients reach a project in two ways: as Postgres, through the edge poolers, or over HTTPS, through xenibase-edge. Both are driven by xenibase-server, which keeps everything it knows in its own metadata database and does long work as queued operations. The databases themselves live on nodes, each with an agent. Select a box to read about it.

    Four ideas the rest depends on#

    The pooler is the address#

    A project's connection string names the pooler and an opaque database name, never a server. xenibase-server renders PgBouncer's routes and SCRAM verifiers from the metadata database (Manager.Sync), so a project can move, be promoted or fail over and its URL still works.

    Connections

    Long work is an operation#

    Creating, deleting, restoring, moving and upgrading are rows in operations. Workers claim them with FOR UPDATE SKIP LOCKED, write a step log the dashboard streams, retry with backoff, and run a compensating rollback when they give up.

    Follow one project

    Postgres enforces the tenancy#

    On the shared cluster each project is a database owned by its own role. CONNECT is revoked from PUBLIC, so a role can open only its own database, whatever the pooler routes it to. The control plane checks every API request against the organisation that owns the resource (authz.Can).

    Security and tenant isolation

    Passwords are never kept#

    A project's password is generated, shown once and forgotten. The metadata database holds only its SCRAM verifier, which is what PgBouncer authenticates with. The plaintext exists, sealed with the master key, only while the create operation needs it for its smoke test.

    What Xenibase is#

    Xenibase is a Postgres platform that one company runs for many customers. A customer signs up, gets an organisation, and creates projects. A project is a Postgres database with a stable connection string. On the shared tier it is one database among hundreds in a shared cluster. On the dedicated tier it is a Postgres container of its own on a node, archived continuously with WAL-G, optionally with a standby on another node and read replicas. Around the databases sit backups and restores, branches, a SQL console and table editor, database webhooks and scheduled jobs, and since V4 a set of backend services that make a project usable straight from an app: a data API, project auth, file storage and realtime, served by xenibase-edge.

    The product grew through five specifications, all at the repository root. V1 is the core: shared and dedicated tiers, the pooler, operations, backups and the operator UI. V2 added organisations, roles, API tokens, branches, webhooks and multi-tenant hardening. V3 and V3.1 added HA, the standby pooler, billing, the Free tier, regions and capacity automation. V4 and V4.1 added the backend services and the edge. docs/decisions.md records the choices made while building, milestone by milestone, and is the first place to look when the code and a spec disagree.

    The binaries#

    Every directory in cmd/ is one command (6 of them); five are released. The Makefile's build-go target builds them all with CGO_ENABLED=0, and release-check refuses a server or edge binary that links purego, so both stay static.

    BinaryWhere it runsWhat it does
    xenibase-serverThe control node, behind CaddyThe REST API and the embedded web UI, the operation workers, and about thirty background loops. It owns the metadata database (it runs the migrations at startup) and the pooler files. It also has offline modes: -gen-master-key, -rotate-master-key, admin and mail-preview.
    xenibase-agentEvery node, including pooler hostsregister once with a one-time token, then run: an HTTPS service behind mutual TLS with a fixed set of commands (health, host metrics, dump, restore, copy, dedicated instances through Docker, pooler files and keepalived on pooler hosts). decrypt opens a backup with an exported key.
    xenibase-edgeOne or more per regionThe backend services gateway at https://<ref>.<domain>.     xenibase-statusAnother provider, on purposeThe public status page. It probes Xenibase from outside and takes signed heartbeats and incidents, so an outage cannot take down the page that announces it.
    xenibaseDevelopers' machines and CIThe command-line tool: contexts, device login, and commands for organisations, projects, branches, SQL, backups and more, all through the public API with an API token.

    The sixth, cmd/docsite, builds the documentation site from docs/ and fails on a broken link. It is a build tool, not a release binary.

    What xenibase-server switches on#

    run in cmd/server/main.go builds each service in turn and hands them all to api.NewHandler. Much of it depends on configuration. Without XENIBASE_POOLER_CONFIG_DIR there is no pooler, and so no provisioning, backups, dedicated tier, branches, Free tier, backend services or webhooks; the server still serves accounts, organisations and billing.

    Background loops are goroutines on a context that is cancelled only after the HTTP server has drained, so open Server-Sent Event streams end before shutdown waits on them and interrupted operations are requeued.

    How they talk#

    FromToHow
    Browser, CLI, SDK scriptsxenibase-serverHTTPS through Caddy. Sessions in __Host- cookies with a double-submit CSRF token, or a bearer API token. Every route declares its authorization (routeRules), and the guard refuses a route that does not.
    xenibase-serverShared clusters, dedicated instancesDirect Postgres connections over the private network as an admin role whose credential is sealed in the metadata database. This is how roles, databases, grants and extensions are made.
    xenibase-serverAgentsHTTPS with mutual TLS. xenibase-server is a small CA (internal/agentca): it issues each agent a server certificate at registration, pinned by fingerprint, and presents a client certificate of its own (Nodes and agents).
    xenibase-serverPgBouncerFiles written atomically into the pooler directory (or pushed to pooler hosts through their agents), then RELOAD, PAUSE, RESUME, KILL on the admin console.
    App serversPgBouncerPostgres over TLS (client_tls_sslmode = require). :5432 is session mode, :6543 transaction mode. PgBouncer authenticates with the SCRAM verifier and passes SCRAM through to the backend.
    xenibase-edgexenibase-serverLong-polled configuration feed and reports, signed with the edge's own region-bound credential or the platform-wide edge secret (edgeapi.Signed: HMAC-SHA256 over the time, method, request URI and body, five minutes' tolerance).
    xenibase-edgePgBouncerTransaction-mode connections as the project's request roles, one transaction per request.
    xenibase-serverxenibase-statusSigned heartbeats and incidents (internal/statusapi).
    Resolved

    One edge secret for the whole platform used to authenticate every edge, and the feed returned every region's projects when the caller left region empty, so the secret of any one edge node read the database logins of every project in every region. An edge in a region with its own API domain now has its own credential, bound to that region on the server (VerifyEdge), and the platform-wide secret serves only the regions without their own domain (backend services guide).

    The fastest way to understand Xenibase is to follow one project from start to end. This page follows a developer who signs up on an install with open signup, creates a shared-tier project from the dashboard, connects an app server to it with a Postgres driver, and later turns on backend services and calls the data API from a browser. Each stage names the function that does the work and the rows it writes, so you can open the code beside it.

    Follow the project#

    Select a stage to light up its part of the sequence. Shaded bars are transactions: everything a stage writes there commits together or not at all.

    1. Sign-up makes a user and an organisation#

      POST /api/v1/auth/signup is a public route. auth.Signup reads the platform's signup policy (invite-only by default, or approval, or open, with an optional domain allow-list), checks the Turnstile challenge and the per-address limit of the signup guard, the password policy and that the terms version accepted is the current one. An address that already has an account gets a "you already have an account" email instead, so the response does not say which addresses are registered.

      Then one transaction inserts the user, runs the UserCreated hook, and records the accepted terms. The hook is createPersonalOrg: every user gets a personal organisation on the Personal plan and is its owner. The verification email goes last. Until the address is verified, and in approval mode until an admin approves, Login refuses to open a session, and only the right password learns why.

      usersorganizationsorg_membersterms_acceptancesemail_tokens

    2. The create request#

      POST /api/v1/projects passes the guard first: the session cookie (or bearer token), the double-submit CSRF token and the Origin check, outstanding terms. Its rule is scopeBody, so CreateProject names the organisation itself and calls authorizeOrg for org.create_project. With no org_id in the body that is the caller's personal organisation. Tenancy then checks the organisation's project quota.

      provision.Create validates the name, generates a 32-byte password and its SCRAM verifier, settles the Postgres major and the region, and picks the shared instance. It seals the password with the master key, bound to the new project id and the purpose, and in one transaction inserts the project (status provisioning), makes the creator a project member, and enqueues a create operation whose params.secrets holds the sealed password. The response is 202 with the operation, the connection strings and the password, which is never shown again.

      projectsproject_membersoperationsaudit_log

    3. A worker claims the operation#

      A trigger on operations sends pg_notify('xenibase_operations', …), and the notifier's LISTEN connection wakes the runner; polling every two seconds is the fallback. Runner.Run claims only while it has a free slot (four by default, XENIBASE_WORKERS). The claim takes the oldest runnable operation of a kind this process serves with FOR UPDATE SKIP LOCKED, sets it running, increments attempts and records the worker in locked_by.

      While the handler runs, a heartbeat refreshes locked_at every ten seconds. Another worker's reclaim loop puts back any operation whose heartbeat is more than thirty seconds old, and every write the old worker makes afterwards is refused because locked_by no longer matches.

    4. The database is built#

      runCreate opens the password, then runs steps that are each safe to repeat. EnsureInstance is a no-op on the shared tier. ensureRole creates (or alters) the owner role with every attribute spelled out: NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS, a connection limit, the verifier as its password, a temporary file limit, and the role's statement and idle-in-transaction timeouts. ensureDatabase creates the database from template0, owned by that role, revokes everything from PUBLIC and grants CONNECT, TEMPORARY to the owner. hardenDatabase revokes CREATE on public, gives the schema to the owner and, on the shared tier, hides pg_stat_activity.

      All of this is plain SQL from xenibase-server to the cluster as its admin role, over the private network. Identifiers go through pgx.Identifier.Sanitize, and the verifier is checked to be a SCRAM verifier without a quote before it is inlined.

    5. The poolers learn the route#

      Manager.Sync takes a cluster-wide advisory lock and rebuilds every region's pooler configuration from the metadata database: a route per project database, its owner's verifier, read-only _ro routes for projects with replicas, V1 aliases, personal logins, backend services' logins, probe logins and owner-created logins on dedicated projects. Render validates every name, host and verifier rather than escaping it, so nothing in the metadata database can inject pooler configuration. The files are written atomically in a safe order (users, then hba.conf, then routes), pushed to the pooler hosts through their agents, and every PgBouncer gets RELOAD.

      userlist.txthba.confdatabases.ini

    6. The smoke test, then active#

      smokeTest connects through both poolers as the owner with the real password and checks current_user and current_database(). That proves the route and the SCRAM passthrough end to end. The project is then set active, and when the runner marks the operation succeeded the same statement deletes params.secrets, so the sealed password is gone.

      projects.status = activeoperations.status = succeeded

    7. An app connects through the pooler#

      The app opens postgresql://p_…_owner:…@db.example.com:6543/p_…?sslmode=require. PgBouncer requires TLS, then applies hba.conf (auth_type = hba): a project with an IP allowlist takes its customer logins only from those networks. It authenticates the client with the verifier from userlist.txt, finds the route by database name, and logs in to the backend by passing the client's SCRAM proof through, so it never needs the password. Pools are per database and user, so connections are never shared between tenants.

      The last line of defence is Postgres itself. Every role is in one auth file per region, and a client can ask PgBouncer for any route. But CONNECT on each project database is granted only to its own roles, so a role routed to someone else's database is refused at login.

    8. Or through the edge#

      Turning on backend services (services.Enable) creates a publishable and a secret key and queues an operation that makes the project's request roles and xb_* schemas. The project then appears in the edge feed. A browser calls https://<ref>.<domain>/data/v1/… with the publishable key.

      Edge.ServeHTTP resolves exactly one project from the hostname, applies CORS, the project's state and plan limits, and authorize looks the key up by its SHA-256 among that project's keys only, rate-limits by address and key, and verifies a user's ES256 token against the project's own JWKs. WithRequest then runs the request in one transaction through the transaction-mode pooler, logged in as the anon, user or service role itself, with the claims and statement timeout set with set_config(…, true), so nothing outlives the transaction. Row-level security decides what the role sees.

    Names and credentials#

    A project's database name is p_ followed by ten random base32 letters, and its owner role is derived from it. Nothing in either says who the customer is or what the project is called, because both are visible to every tenant on a shared cluster in pg_database and pg_roles. A collision on insert is retried with fresh names, up to five times.

    Spec and code differ

    V1 gives names as <slug>_<4-char-random>, such as blog_k2f9 (V1 5.1). V2 §10.2 replaced them with opaque names, and a V1 project renamed since keeps its old name as a pooler alias (alias_db_name), so old connection strings still work. V1 also says the password is never stored reversibly (V1 5.3). The code keeps it, sealed, in the create operation until it finishes, because the smoke test needs it and may run in another process after a restart (decision M1 #3).

    Where the project lands#

    A shared project goes to a running shared instance in its region, on a healthy, active node, running the requested major. An organisation with shared clusters of its own uses only those; every other organisation uses only untagged ones. Among those, the instance with the fewest live projects wins.

    Spec and code differ

    V1's create flow picks "the shared node with the most free capacity" (V1 6.1). The query counts projects instead. Projects differ a lot in size, so a cluster with a few large databases keeps getting new ones; capacity automation (Part E) watches disk separately.

    A dedicated project goes through dedicated.Validate, which places it on the least loaded node in the region that fits its profile, or asks capacity automation for a new host.

    Resolved

    A tenant used to be able to choose the node for a dedicated project: CreateProject passed the request's node_id into CreateParams.NodeID for any caller allowed to create projects, and Validate then checked only that the node took dedicated instances, had an agent and was healthy, not that the instance fitted or that the node was active rather than draining. Now CreateProject refuses node_id with 403 unless the caller is a platform admin (the dashboard offers the choice only to them, and API tokens never are), and Validate runs placeDedicated's lifecycle and fits checks on a hand-picked node too, except for a detached replica, whose instance is already there (TestCreateProjectNodeIsForPlatformAdmins, TestValidateChecksAChosenNodeLikePlacement). Promote and move reach Validate too and get the same checks; who may name a node for a promote, HA standby, replica or demote is not changed here.

    How the operation is run#

    Every long action is the same shape: a row in operations, a handler that must be safe to run again, and optionally a compensating OnFail. The kind sets the attempts (create: three) and the time limit per attempt (create: 45 minutes, because a dedicated create may wait for a new host).

    When an attempt fails, the runner retries with exponential backoff (two seconds doubling to five minutes). A permanent error, or the last attempt, runs OnFail. For a create that is rollbackCreate: it soft-deletes the project as error, kills pooled connections, removes the route and drops the database and role, so a failed create leaves nothing behind. Every step log line is appended to the row and streamed to the dashboard over Server-Sent Events.

    Resolved

    The lease used to be fenced only by worker identity, and a failed heartbeat was logged and skipped, so a worker cut off from the metadata database for more than thirty seconds kept running an operation that another worker had reclaimed, and could even write its result over the new attempt's. Now heartbeat gives each heartbeat a third of the lease and cancels the attempt once heartbeats have failed for two thirds of it, before anyone can reclaim it, and every write to the row (heartbeat, step log, succeed, fail, retry) matches locked_by and attempts, so a stale attempt writes nothing even when the same process claimed the operation again. TestPartitionedAttemptStopsAndIsFenced cuts a worker off through a proxy and checks both.

    How cmd/server starts#

    The API and its guard#

    Routes are generated from api/openapi.yaml (415 operations on 325 paths) into a chi router. Every request under /api and /metrics first passes guard, which resolves the route pattern before routing so it can refuse early:

    1. Who. A bearer token becomes a token session, and the cookie is ignored. Otherwise the session cookie is looked up by its SHA-256.
    2. CSRF. A mutating request from a cookie session must carry the double-submit token, and its Origin, when sent, must name this host (checkCSRF). Program-to-program routes are listed in csrfExempt.
    3. A rule. The route must be in routeRules. A route with no rule is refused with 403, and TestEveryRouteDeclaresAnAction fails CI when the spec and the map disagree.
    4. Terms, then step-up. A browser session with new terms to accept gets terms_required, except on the few routes marked beforeTerms. Routes in reauthRequired (delete a project, turn on role management, transfer, refunds and others) need a password and code check in the last ten minutes. Tokens skip step-up and need the admin scope instead.
    5. Authorize. authorize finds the resource's organisation from the rule's scope, then asks authz.Can. A resource the caller may not know about answers 404, one they may see but not change answers 403. The resolved organisation, project and roles go into the request context for the handler.

    The operations queue#

    Every long action is a row in operations. A request inserts it, usually in the same transaction as the metadata change that needs it, and returns 202 with the operation. Workers claim it, run the kind's handler, and record the outcome. The dashboard follows it over Server-Sent Events.

    The claim takes the oldest due row of a kind this worker knows, with SKIP LOCKED, so workers never block each other or take the same row:

    A handler gets the operation and a StepLogger. Each log line is appended to the row only while this worker still holds it (locked_by, status = 'running'), and a line that matches no row returns ErrLeaseLost, so a handler that checks its log errors stops when it has lost the operation.     OnFail runs once, with its own two-minute budget, before the row is marked failed. Its error is logged and the operation fails either way.     The reclaim used to compare two clocks: locked_at is the database's now(), but the reclaim loop passed a cutoff from the worker's clock, so a server running more than 30 s ahead of the metadata database reclaimed every running operation on every pass. Now reclaimLoop passes only the lease length and the query computes locked_at < now() - make_interval(secs => @lease_seconds) (TestReclaimUsesDatabaseClock). The other lease weakness, a worker that could not reach the metadata database and kept running, is resolved too: see The life of a project.

    One operation per project#

    Rotate, delete, settings changes, reclaim space, and most flows in other packages go through withIdleProject: lock the live project row FOR UPDATE, check its status is one the action allows, check ProjectHasActiveOperation, then enqueue in the same transaction.     Resolved

    It used to be a convention, not a constraint: nothing in the schema stopped a second active operation, the nightly scheduler checked "no operation in flight" in ProjectsDueForBackup without locking the project (so a backup and a delete requested in the same instant could both be queued), and a kind that no running process registered stayed queued forever and blocked every exclusive action on its project. Now migration 00063 adds operations.exclusive and a partial unique index, operations_one_exclusive_per_project, so a second exclusive operation on a project is refused (jobs.ErrProjectBusy, a 409 through withIdleProject). Four kinds are queued as background (exclusive = false) because they legitimately sit beside one, some queued by it: drop_db_user (from RevokeCredentials), copy_branch_files (from the branch's own create), restore_test and drop_project_objects; they still make the project busy for the row-lock check. And each runner fails an operation of a kind it does not serve once it has waited, runnable, for a day (UnservedAfter), saying no worker runs that kind (TestOneExclusiveOperationPerProject, TestEnqueueIfIdleTx, TestUnservedOperationFails).

    Resolved

    A create whose rollback failed used to leave an orphaned database and roles: rollbackCreate soft-deleted the project, then ran teardown once, and if that failed (a pooler sync error, a cluster that stopped answering) the database, the owner, console and read-only roles stayed on the shared cluster with no project that could reach them. Now a failed teardown queues drop_project_objects, which retries it for about forty minutes and refuses a live project. Behind it, SweepOrphans runs hourly: it compares each running shared cluster's p_… databases and roles with the metadata and drops those of a project deleted more than a day ago on that cluster with nothing pending.     Resolved

    A delete that failed after teardown used to be unable to finish: runDelete started every attempt with the final backup, so after an attempt that had already dropped the database (and then failed on DropAutomation, SoftDeleteProject, a crash or a shutdown), every remaining attempt failed backing up a database that no longer existed, and the project was left in error. Now runDelete first checks whether the database is gone (the dedicated instance is deleted, or the shared database is not on its cluster) and if so logs that the backup is not needed and carries on (TestDeleteRetryAfterTeardownFinishes).

    Personal logins#

    Each project member can have their own database login, <db>_u_<random> (IssueCredentials). Revoking deletes the metadata row, syncs the pooler, kills the login's pooled clients and drops the role, queueing drop_db_user when the instance does not answer.

    Resolved

    IssueCredentials creates the role on the instance first and writes the metadata second. If that write failed after CREATE ROLE, the role used to stay on the instance with a password no one had, and teardown, which dropped only the logins in project_db_users, never removed it. Now a new login whose metadata write fails is dropped again at once, and dropMemberRoles also drops every <db>_u_… role it finds on the instance (TestIssueCredentialsLeavesNoRoleOnFailure, TestTeardownDropsUnrecordedPersonalLogins).

    Dedicated projects: role management and connection ceilings#

    Release 4.2.4 lets a dedicated project's owner create roles, so an application whose migrations run CREATE ROLE works unchanged. SetManageRoles (organisation owners, after step-up) refuses the shared tier and Postgres before 16, writes projects.manage_roles, and gives the owner CREATEROLE (OwnerCreateRole). Postgres 16 limits CREATEROLE to roles the creator holds ADMIN on and never lets it grant SUPERUSER, REPLICATION or BYPASSRLS.

    The poolers accept only logins Xenibase knows, so every 30 seconds SyncOwnedRoles reads the roles the owner administers, caps their connection limit at the project's, grants CONNECT, and records each syncable login and its verifier in project_owned_logins. A login is syncable when it is named <db>_… (each region's pooler auth file is one namespace), is not one of Xenibase's names, has no elevated attribute and has a SCRAM password. When the set changed it rewrites the rows in one transaction and syncs the poolers. Moves and major upgrades recreate the owner's roles on the target before the copy (restoreOwnedRoles).

    A dedicated instance's max_connections now grows with memory instead of being 100 for every size, and is stored per instance (migration 00060). A project's connection limit can go up to the instance's ceiling less ten reserved slots, and ensureRole clamps it again on every run so a move to a smaller size cannot leave it too high. A restore's instance never gets fewer than its source, because a standby will not replay WAL from a server that allowed more.

    Read replicas got per-replica standby settings (hot_standby_feedback, and one delay for both max_standby_*_delay settings). PATCH /projects/{id}/replicas/{replica_id} checks the replica belongs to the project, stores them, and on a streaming replica applies them with ALTER SYSTEM and a reload, recording when they were last confirmed (UpdateReplicaSettings).

    Resolved

    Role management used to be switched outside the project lock: SetManageRoles wrote the flag first and ran ALTER ROLE … CREATEROLE second, so a refused ALTER ROLE left metadata and instance disagreeing, and an apply_settings, move or restore that had loaded the project before the switch ran ensureRole with the old flag and undid it. Now it runs under WithIdleProject: it holds the project's row lock, refuses (409) while any operation is pending, alters the role inside that transaction and commits the flag only if the instance accepted, putting the role back if the commit fails (TestSetManageRolesRefusesBusyProject, TestSetManageRolesKeepsFlagWhenInstanceRefuses).

    The SQL console and query insights#

    Console sessions connect straight to the instance, not through the poolers, as <db>_console: a login with no privileges of its own, granted the owner role and <db>_ro WITH INHERIT FALSE, SET TRUE. Read-only sessions log in as <db>_console_ro, granted only <db>_ro. Each submission opens a session, runs SET ROLE to the owner (or, for a read-only member, to <db>_ro), sets the statement and lock timeouts, and closes afterwards (connect). Read-only mode runs one statement inside BEGIN READ ONLY; SELECT 1, so the snapshot is taken and the transaction cannot be switched back to read-write. Results are capped at 1,000 rows and cells at 64 KiB. The audit row records that the console ran and the error code, never the SQL.

    Resolved

    A read-only member could read as the owner: their session logged in as <db>_console, which may SET ROLE to the owner, so SELECT set_config('role', '<owner>', true), query_to_xml('SELECT * FROM t', true, false, '') returned rows RLS hid from <db>_ro and tables never granted to it, for a read-scope token and the table browser's raw filter too. Read-only sessions now log in as <db>_console_ro (ConsoleReadOnlyRole), granted only <db>_ro WITH INHERIT FALSE, SET TRUE, so there is no owner to switch to. It is created by ApplyConsoleRoles on first use, as the console login always was (the failed login is repaired and retried), so existing projects get it on their next read-only session. isocheck.Roles reports the login if it can become the owner, and TestReadOnlySessionCannotBecomeOwner and the isolation suite run the statement above.

    Query insights (insights) snapshot pg_stat_statements as the instance admin, keep each project's own rows as per-project deltas in query_stats and query_texts, and serve top queries, EXPLAIN, slow queries, index suggestions, bloat and locks. Tenants never query the view on a shared cluster, because the admin's copy is filtered by database before it is stored. Console sessions are tagged so their queries are not counted.

    GET /operations lists an organisation's operations, limited for members to the projects they belong to and for a project-restricted token to its projects (visibleProjects, which fails closed). ?platform=true lists platform work, for platform admins. GET /operations/{id} and its stream need project.view on the operation's project. The response carries the parameters, minus secrets, and the whole step log.

    Resolved

    A rotate's parameters used to include verifier and previous_verifier, the owner's new and old SCRAM verifiers, outside secrets, so they stayed in the row forever and were returned to anyone with project.view (a credential switch kept the new owner's the same way).     What a node is#

    A node is a machine that xenibase-server sends work to. Each runs xenibase-agent, which is the only thing on the machine the control plane talks to. The control plane never logs in over SSH and never runs a shell command it composed. It calls a fixed HTTPS API on the agent, and the agent turns each call into Docker API requests, pg_dump/pg_restore processes, or file writes.

    A node row has a role, set when an operator adds it (CreateNode):

    RoleWhat runs thereCan change to
    shared, dedicated, bothPostgres: a shared cluster, dedicated instance containers, or both. Which of these new projects may be placed on.Each other (SetRole)
    poolerThe two PgBouncers, keepalived, and the agent in pooler mode (pooler hosts)Nothing: remove it and add the machine again
    edgexenibase-edge beside the agent, never a database (V4.1 §11)Nothing

    A node also has a region (the home region when none is given) and an optional failure domain, which HA, etcd and pooler placement use to keep pairs apart.

    How a node joins#

    1. The operator adds the node. POST /api/v1/nodes (Admin → Nodes → Add node) inserts the row and returns a one-time registration token, xbreg_ and 24 random bytes. Only its SHA-256 is stored, with an expiry a day later (newToken). NewToken issues a fresh one for an existing node, replacing any earlier token.
    2. The agent registers. xenibase-agent register --server … --token …, or the first run when no state exists yet, which retries up to 30 times two seconds apart. agentsvc.Register makes a P-256 key and a certificate request (NewCSR) and posts it with the token and the address the server should dial (--advertise, default the hostname and port 7070) to POST /api/v1/agent/register. That route has no session. The token in the body authenticates, and the route is rate limited per IP (RegisterAgent). The agent checks the server's HTTPS certificate against the system roots or --server-ca.
    3. The server signs and pins. In one transaction, nodes.Register finds the node by the token's hash (unexpired, row locked), signs the CSR for that node, and records the certificate's SHA-256 fingerprint, the advertised host and port, and the agent version. The token is cleared in the same statement, so it works once.
    4. The agent saves its state: agent.key, agent.crt, the CA certificate and node.json, each 0600 in a 0700 directory (/var/lib/xenibase-agent). From then on run loads that state and listens.

    The bootstrap token#

    The install bundle's own agent registers the local node without an operator. XENIBASE_AGENT_BOOTSTRAP_TOKEN (at least 24 characters) is given to both the server and that agent, and the agent sends it with --node local. The server compares it in constant time, and accepts it only for the bundle's local node (XENIBASE_SHARED_NODE_NAME, default local), only while that node has never had an agent and is not removed, and only once: the registration records agent_bootstrap_used in settings, under an advisory lock. Re-registering needs a token from the UI.

    Resolved

    The bootstrap token never expires, and it used to claim any node without a pinned certificate by name: a machine just added whose own agent had not registered yet (so a hostile agent could take its identity and receive its instance specs and their passwords), or a removed node, which CompleteNodeRegistration brought back as healthy. It is now bound to the local node, refused for a removed node, and single use (TestBootstrapToken, TestBootstrapTokenBound).

    Machines Xenibase creates#

    Capacity automation (V3 §5.1) creates machines through cloud.Provider: Hetzner Cloud (hetzner.go), or manual, which has no API and returns ErrManual. The new server joins by itself with the same one-time token, carried in its cloud-init document (cloud.Bootstrap). That document installs Docker, turns off SSH passwords, sets ufw to deny incoming traffic except SSH and the private network, and starts the agent with the Docker socket mounted. On an edge node it also starts xenibase-edge and opens 8443. Every value that reaches a shell line is checked first by Validate: names, CIDRs and image references against patterns, and the token and edge secret refused if they hold spaces, quotes, $, backslashes or backticks. YAML strings are JSON-quoted.

    Note

    The cloud-init document is the server's user data, so the registration token and, on an edge node, its edge credential stay readable from the provider's metadata service by anything on that machine. The registration token is spent within minutes. An edge node's credential is not, but it unlocks only its own region's feed (see the edge).

    Both directions of the handshake#

    The server always dials the agent; the agent never calls the server after registering. When the server dials, dial trusts only the agent CA, requires TLS 1.3, and then checks two more things the CA alone would not give:

    The pin means a stolen copy of the CA key is not enough to stand in for a registered agent: the impostor would also need the node's own certificate. The subject check stops one node's genuine certificate being used at another node's address. Revocation is the pin: re-registering replaces the fingerprint, and RemoveNode (refused while any instance is live on the node) clears it. There is no CRL.

    On the agent, agentsvc.TLSConfig requires a client certificate from the pinned CA, TLS 1.3, and the subject xenibase-server. Go's own check also requires the client-auth key usage. Agent certificates are server-auth only, so one agent cannot call another even though the same CA signed both. An overlay test written for this page confirmed both refusals: a client certificate named xenibase-server with server-auth usage fails with "incompatible key usage", and a client-auth certificate with another name fails the subject check.

    Spec and code differ

    The V1 spec (§3.3) says the server "issues each agent a client certificate at registration". Agents get server certificates. The client certificate is the server's, and every agent accepts any unexpired one the CA signed with that subject. There is no per-server identity: a copy of any server's client certificate commands every agent until it expires.

    Resolved

    The server's client certificate used to be issued once, in nodes.NewService, and kept for the life of the process, so a xenibase-server that ran for more than 30 days without a restart lost every agent at once. Every handshake now asks clientCerts.get (through tls.Config.GetClientCertificate), which reissues it when 7 days or less are left and keeps the current one if that fails. The alerts loop asks too, so it renews on an idle server, and the agent_client_cert alert fires when under 3 days are left. TestClientCertRenewed reaches an agent with a certificate issued 40 days ago.

    Why a command cannot become a shell#

    The agent takes values, never command lines, and each value reaches a process as an argument or an environment variable:

    • Connections reach pg_dump and pg_restore as PGHOST, PGUSER, PGPASSWORD and the rest (pgEnv), so passwords never appear in ps. Schema filters are single --schema=… arguments (dumpArgs), so a value starting with - cannot become a flag. Child processes get SIGKILL if the agent dies (Pdeathsig).
    • Instance IDs must be UUIDs (instanceID). Container and volume names are made from them.
    • Postgres settings become -c name=value arguments to postgres, with names limited to [a-z_][a-z0-9_.]* and values without NUL or newline (settingName). The settings come from the server's size profiles and replica settings, never from a customer.
    • The few shell scripts are constants. Their variable parts come in through the exec environment: the move rules, the recovery settings, the backup name (checked against ^(LATEST|base_…)$). The one file a script sources, the recovery source's WAL-G settings, is written by shellExports with every value single-quoted.
    • etcd membership takes a peer URL that must start with https:// and a numeric member ID, sent as JSON to etcd's gateway.
    • Docker is reached through docker.New: the Engine API over the Unix socket (or tcp://, unencrypted), at API version 1.43 or the daemon's minimum if that is higher. It has no SDK dependencies.

    So what the control plane can do to a node is bounded by this API, not by what a shell could do. But that bound is wide. The agent runs as root with the Docker socket, and creates containers from whatever image and settings the server sends. Whoever holds the server's client certificate effectively has root on every node.

    Resolved

    An import's source address was not checked, which defeated IP allowlists: connectSource and the agent's /v1/copy connected to any host, from addresses every cluster's pg_hba.conf trusts, so a project's owner password got a full copy past its allowlist, and the path probed the private network. The source now goes through outbound.CheckSource: public addresses only unless the platform admin allow-listed the host for the organisation, and never loopback, link-local, a node's or instance's own address, XENIBASE_OUTBOUND_BLOCK or (with machines Xenibase creates) the cloud private network, allow-listed or not. pgsource.Config refuses a URL whose settings name another host (host=, several hosts, a socket directory) and pins the connection to the checked address: pgx resolves every name to it, and the agent's copy gets it as hostaddr. The import checks again just before the copy, and Supabase migrations take the same path.

    How commands are authenticated and authorised#

    Authentication is the TLS handshake and nothing else: no token, no request signature, no per-request check. Authorisation is all or nothing. Once a client presents a valid xenibase-server certificate, every path is open, and the agent does not know which project or operation a call is for. Each request is decided in the control plane. The operation that calls the agent has already been authorised against the caller's organisation role (see Security), and the agent trusts the server's decision.

    The server also refuses to send work to an agent it does not trust to understand it. agentFor checks the version the agent last reported against the server's (Compatible): the same major, and a minor no older than the server's. Development builds match anything. Health checks use dial without the version check, so an agent that needs upgrading still reports in.

    Pooler hosts add a second listener: an unauthenticated HTTP API on a loopback address for keepalived's check script and notify calls (LocalHandler). ServeLocal refuses any address that is not loopback. Any local process can mark the host MASTER and so make xenibase-server move the floating IP to it.

    Instances through Docker#

    instances.Create holds a per-instance lock and is idempotent. If the container exists it is started and waited for. Otherwise it pulls the image if missing. The image name is a template with {major}, default xenibase-postgres:{major}-walg3.0.9. It then creates the volume xenibase-<id>, optionally restores into it in a one-off container, and starts postgres with hard CPU and memory limits, shm sized from memory, SIGINT as the stop signal, and restart unless-stopped. It finally checks that the running major is the one asked for (postgres -V). PGDATA is always set inside the volume, because older images declare an anonymous volume that a recreate would lose.

    Network logins are limited at initdb to XENIBASE_AGENT_DB_ALLOW, which defaults to every private range and 127.0.0.1 (defaultDBAllow), with SCRAM. On every start the agent appends, once, rules that let only xenibase_move_<hex> logins in from XENIBASE_AGENT_MOVE_ALLOW for logical-replication moves, and reloads (ensureMoveHBA). Instances are reached by container name on the agent's Docker network, or on a port published on the node's private address.

    Note

    A project's IP allowlist is enforced at the poolers, not here. Anything that can reach a node's private address with a project's password connects to its instance directly. On the dedicated tier that includes another customer's postgres_fdw, which is allowed there.

    The path of a connection#

    Every client connection string names the region's database hostname, a port, and the project's database:

    postgresql://blog_k2f9_owner:…@db.example.com:6543/blog_k2f9?sslmode=require
    1. DNS and the floating IP. The hostname points at the region's floating IP. Hetzner routes that address to one of two pooler hosts. Without pooler hosts, the PgBouncers run beside xenibase-server, as in the compose bundle.
    2. PgBouncer. :5432 is session mode, for migrations, LISTEN and anything that needs a session. :6543 is transaction mode, for app traffic, with up to 200 prepared statements tracked per connection. Both run the same configuration (deploy/pgbouncer). TLS is required (client_tls_sslmode = require, TLS 1.2 or 1.3).
    3. Who may log in from where. auth_type = hba: PgBouncer reads the generated hba.conf, then checks the password against the SCRAM verifier in the generated userlist.txt. PgBouncer never sees a plaintext password.
    4. Routing by database name. The name in the startup packet picks a line of the generated databases.ini: the backend host and port, the backend database, and pool limits. PgBouncer connects to the backend as the same user and passes SCRAM through.
    5. The backend. One of three things: the shared cluster or dedicated instance that holds the database; the read replicas, for <db>_ro; or, for a paused or archived Free project, the waker.

    There is no SNI routing and no per-project hostname for Postgres. A region has one hostname and one certificate, and the database name alone picks the project. The data API, auth, storage and realtime go through xenibase-edge instead, which does route by hostname.

    The generated files#

    xenibase-server owns three files in the pooler directory (XENIBASE_POOLER_CONFIG_DIR, mounted read-only into each PgBouncer at /etc/pgbouncer/xenibase). Render produces them from a Config of routes, users and restrictions. Entries are sorted, so the same input gives byte-identical files. Names are validated, never escaped, so a bad name upstream cannot inject configuration:

    Manager.Sync builds one Config per region under a Postgres advisory lock, so two servers never interleave. It reads projects in a live status whose organisation is not suspended (PoolerRoutes; a suspended organisation simply loses its routes), their replicas, and every kind of login. A project is routed by its region's poolers, or by the home region's when its region has no pooler hosts. For 30 days after a move it is also routed by its old region's, so old connection strings keep working. A region's files go in the main directory for the home region, regions/<id>/ for the others. Files are written atomically (temp file, fsync, rename, directory fsync) in a fixed order: users, then hba.conf, then routes. A new route is never served before its user can log in, or wider than its allowlist. Then every pooler gets RELOAD (distribute).

    The admin console also carries PAUSE/RESUME around cutovers, KILL for deletes and password rotations, and RECONNECT. Freeze pauses the transaction pooler, falling back to KILL after a wait, and kills on the session pooler, whose clients would otherwise hold PAUSE open. Each command goes only to the poolers that route that database.

    One project's login on another's database#

    PgBouncer has no notion of which login belongs to which route. Any user in userlist.txt may ask for any database in databases.ini, and PgBouncer will open a backend connection as that user. Isolation is the backend's job: every project database has REVOKE ALL … FROM PUBLIC and CONNECT granted to its own roles only (ensureDatabase), so Postgres refuses the login. isocheck verifies that nightly on every cluster. The auth file is also one namespace per region, so login names must be unique across projects. Logins an owner creates must be named <db>_…, may not be one of the project's or Xenibase's own names (platformRole), and lose to a platform login of the same name.

    Pooler hosts, keepalived and the floating IP#

    With pooler hosts (V3 §2.1) each region has two machines. Each runs both PgBouncers and the agent in pooler mode in one container, and keepalived in another, the only one with NET_ADMIN (deploy/pooler-host).

    Getting the files there#

    After writing the files, pushHosts reads each region's bundle. That is its three files plus the TLS pair: the region's own if it has one, else the main directory's (readBundle). It hashes the bundle, advances the region's generation in the metadata database, and sends PUT /v1/pooler/config to each of the region's hosts over the agent's mutual TLS. Then it tells every host the generation, including any that just failed. A push fails only when every host refuses it. A host that missed it knows it is stale.

    The agent accepts only the five known file names, requires the routes and auth file, checks the hash against the content, and refuses an older generation with 409 (two servers raced). It writes users, rules, key, certificate, then routes, and sends SIGHUP to the PgBouncers (apply). The generation served and the generation expected are kept in a state file, so they survive a restart.

    Who holds the address#

    A host is ready when it has a configuration, serves the newest generation the server has announced, and both PgBouncers accept TCP connections (status). keepalived asks the agent's loopback /ready every second. Two failures drop the host out, and unicast VRRP with one-second adverts hands over in about 3 to 4 seconds. Both hosts start as BACKUP with nopreempt, so a host that comes back does not take the address back (keepalived.conf). keepalived's notify posts the new state to the agent, which reports it (setVRRP). The arbiter below moves the floating IP. Only an agent started with XENIBASE_AGENT_ASSIGN_FLOATING_IP=true and a Hetzner token also asks Hetzner itself on MASTER, retrying with backoff for up to two minutes, which keeps failover working while the control plane is down.

    xenibase-server's arbiter checks each region's pair every 3 seconds. It re-pushes to a stale host, at most every 15 seconds, and asks Hetzner where the IP points. Its rule is Decide:

    Following keepalived's MASTER happens at once: that is the failover. Moving the IP away from an unhealthy holder that keepalived has not replaced waits for two checks in a row. Each move, change of holder, split brain, host going stale and recovery is recorded as a pooler event and shown in Admin → Nodes.

    Split brain#

    If the two hosts lose sight of each other but not of Hetzner, both become MASTER. The arbiter reports split_brain and leaves a healthy holder alone, so nothing flaps. (Agents allowed to assign the IP each assign it once; Assign is a no-op when the IP already points at the caller, and the last assignment wins.) Both hosts are stateless and serve the same generation, so whichever receives the traffic routes it correctly. A host that missed a change cannot be ready, so cannot hold the address through keepalived. Two cases remain. If the control plane cannot reach the holder, the arbiter moves the address after six seconds even though clients could still reach it. That is a needless failover, not a wrong one. And while the control plane is down, nothing announces new generations, so a host that missed the last push before the outage still counts as ready.

    Resolved

    Each pooler host used to hold a Hetzner Cloud API token with read and write access (XENIBASE_AGENT_HETZNER_TOKEN), because the agent assigned the floating IP itself, and a Hetzner token cannot be narrowed to one IP: a compromise of an internet-facing pooler host handed over the whole Hetzner project. Now only xenibase-server assigns it, following keepalived's MASTER, and the agent only reports its VRRP state (floatingIP). The trade-off: while the control plane is down the address does not move. XENIBASE_AGENT_ASSIGN_FLOATING_IP=true with a token brings back agent-side assignment for those who prefer that.

    Spec and code differ

    V3 §2.1 says the server "verifies both hashes match". Staleness is decided by generation. The agent checks each bundle's hash against its content, and the server records each host's hash, but nothing compares the two hosts' hashes.

    The waker#

    A Free project that sits idle is paused, and later archived (V3 §4.2–§4.3). Its route then points at the waker instead of its cluster, with pool_size and max_db_connections of 1:

    The waker (internal/waker) runs inside xenibase-server on XENIBASE_WAKER_LISTEN. It speaks just enough of the protocol to answer. It declines TLS and GSS, reads the startup packet (at most 10,000 bytes, three tries), and asks freetier.Wake to queue a resume or an unarchive.     The waker does not authenticate: it relies on PgBouncer having checked the client's password first.     xenibase-edge#

    xenibase-edge (cmd/edge) serves each project's backend services at https://<ref>.<domain>. The data API, auth, storage and realtime are described in Part D. This section covers how it connects.

    The configuration feed#

    The edge keeps every project's configuration in memory and gets it from xenibase-server. It long-polls GET /api/v1/edge/config?since=…&wait=25 for changes and reads the whole feed again every minute as a backstop (apply ignores an older version that a resync brings back). An entry carries the pooler database and address, the edge login's and the request roles' passwords, the hashes of live API keys, the JWT verification keys, CORS, rate and cache settings, and the state. disabled removes the project. A project's database pools are kept while its connection details are unchanged, and closed when they change. Until the first full read the edge answers 503.

    Every call from the edge carries Xenibase-Signature, an HMAC-SHA256 over the time, method, request URI and body with the edge's credential or the platform-wide edge secret. The receiver accepts five minutes of clock difference (edgeapi.Verify).

    Resolved

    There used to be one edge secret for the whole platform (XENIBASE_EDGE_SECRET), and the region an edge served was a query parameter the edge chose, empty for all regions, so a regional edge and the cloud-init of every edge node held a key that read every project's service-role password in every region. An edge can now sign with its own credential, xbedge_<id>_<secret>, which names itself in Xenibase-Edge-Credential; the server keeps it sealed in edge_credentials with its region (edgecred.Issue, xenibase-server -issue-edge-credential, and capacity automation for the edge nodes it creates). The server fixes the region from the credential (EdgeScope.Feed): another region is refused, and wakes, auth messages and hooks, storage events and reports are limited to the credential's region. The platform-wide secret now serves only the regions without their own API domain, unless XENIBASE_EDGE_SECRET_ALL_REGIONS (deprecated) restores the old scope.

    From hostname to transaction#

    1. refFromHost takes the HTTP Host, lower-cased, without port or trailing dot. It must be exactly one label in front of XENIBASE_EDGE_DOMAIN. The edge serves a wildcard certificate whatever the SNI says, and the Host header alone picks the project.
    2. authorize looks the apikey up by its SHA-256 among that project's keys only. A key from another project is simply not found, so a Host header cannot be used to point one project's key at another. A secret key means the service role, and is refused from a browser unless the project allows it. A publishable key means anon, or user with a bearer token. The token must verify against that project's own ES256 keys with the project's ref as audience, and carry role: user. Per-IP and per-key limits apply. The client address is the RemoteAddr, or the last X-Forwarded-For entry when the peer is in XENIBASE_EDGE_TRUSTED_PROXIES (clientIP).
    3. WithRequest runs the whole request in one transaction through the transaction pooler, as the role's own login (<db>_anon, _user, _service), with the claims and statement timeout set with set_config(…, true). Nothing outlives the transaction, so transaction pooling is safe, and tenant SQL that resets the role stays that role. Only a feed from a server older than M32, which has no request-role passwords, makes the edge log in as the edge login and SET LOCAL ROLE.

    Pools are small: four connections per login, two for the service and hook roles. They use pgx's exec mode, with no server-side prepared statements kept between transactions (loginPool). GETs that may read from replicas use the <db>_ro route. These logins are the ones exempt from IP allowlists. The Bloom filter in internal/bloom sends a project's counted monthly users to the edge in a few kilobytes. A false positive lets an uncounted user in.

    How organisations are kept apart#

    There is no row-level security in the metadata database. The application connects as one role that owns every table, and tenancy is enforced by the API guard (The control plane) and by the queries. Tables that belong to an organisation carry org_id, including child tables where it could be derived (project_members, project_db_users, saved_queries, reaped_sessions, usage_records, audit_log), so a query can scope itself without a join.

    Queries live in internal/store/queries and sqlc turns them into typed Go in internal/store (sqlc.yaml; make generate, and CI fails on a diff). Each query either filters by org_id or says why it may not, in a comment the lint reads:

    TestTenantQueriesAreScoped splits every query file on -- name:, and for each query that reads or writes a tenant table requires either an org_id predicate or a -- tenant: system - <reason> line of more than ten characters. A tenant table is any table the migrations leave with an org_id or project_id column (migratedColumns replays them; TestTenantTablesMatchTheSchema checks the result against a migrated database). A predicate is org_id compared with a parameter, a list or NULL in a WHERE, ON or HAVING clause, or org_id among an INSERT's columns.

    Spec and code differ

    V2 says every sqlc query on a tenant table takes org_id and filters by it, as defence in depth even when the handler has checked (V2 2.6). In the code the opt-out is the common case: about 600 of the 850 queries carry tenant: system, most of them "a project the request already authorized". For those the only check is the guard and the handler.

    Resolved

    The lint was weaker than it read: its list of tenant tables was fixed in the test and predated backend services (project_api_keys, project_jwt_keys, project_services, read_replicas, auth_*, instance_members and others were missing), and any occurrence of org_id passed, including SELECT org_id, SET org_id = … or a join.     Resolved

    How migrations run#

    Migrations are plain SQL files embedded in the binary and applied by goose when the server starts, before it serves anything (store.MigrateTo). A Postgres session advisory lock serializes servers that start together. Each file runs in its own transaction, so a failed migration leaves the previous version. A server refuses to start on a schema newer than the newest migration it carries (refuseNewerSchema), because running there could write rows that break constraints it does not know, and checks again every 30 seconds while it runs. Each file has a Down section, used only by tests that load data at an older version. Rolling back in production means restoring the metadata backup taken before the upgrade.

    A few migrations change data as well as shape: 00010 turns operators into users and moves every V1 project into its owner's personal organisation, 00018 queues an apply_settings for every active shared project, and several add plan limits to quota_plans. sqlc expands SELECT * into named columns at generation time, so adding a column never breaks a running binary's queries.

    The recent migrations are safe to run on a live install. They add columns with constant defaults (no table rewrite) and small indexes, and the tables they touch have one row per project, instance or region. Adding a column with a CHECK still scans the table under an exclusive lock, which is fine at these sizes.

    Resolved

    The newer-schema check used to run only at start, so an older server already running when a newer one migrated kept working on a schema it didn't know, and some migrations removed what older binaries use (00038 renames auth_email_outbox, 00052 drops payment_methods and a billing_accounts column, 00025 drops a column). Now store.SchemaWatcher reads the version every 30 seconds; on a newer schema the server logs it, stops claiming operations (the runner's Paused) and answers /readyz with 503 until it is replaced. It still serves requests that reach it, so the migrations guide now sets the rule for future migrations: expand in one release, contract in the next.

    Part Z · About

    How the atlas is maintained

    Where the atlas's pages live, how the build reads the code, how to tell which pages the code has moved under, and how to update and publish it.

    What it is made of#

    The atlas lives in docs/atlas next to the code it describes, so a change to one can come with a change to the other in the same pull request.

    PathWhat it is
    pages/*.htmlOne file per page: a JSON header, then the page's HTML. The file name only sets the reading order on disk. The header's part and order set the order in the atlas.
    partials/*.htmlDiagrams used on more than one page or too long to keep inline. {{uid}} in a partial is replaced each time it is included, so marker ids never clash.
    src/The shell, the stylesheet and the page script that every page shares.
    atlas.jsonThe title, the repository URL that code links point to, the parts, where the packages live ("packages": {"root": "internal"}), and what each x-stat counts.
    atlas.mjsThe build. Node 22 and git, no packages.
    site/index.htmlThe built atlas: one self-contained file. Open it from disk or serve it anywhere. It is committed, so reading it never needs a build.

    A page's header#

    Every page starts with a comment holding JSON:

    • verified is the commit the page was last checked against, line by line. Set it only after reading the code at that commit.
    • sources are the files and directories the page describes. A commit that touches any of them after verified marks the page as moved.
    • status: "planned" with a scope list renders a placeholder that says what the page will cover.

    Elements that read the code#

    The build replaces these elements before writing the page. Anything that names code is resolved against the working tree, and links are pinned to the commit that was built.

    ElementBecomes
    <x-ref path="…" symbol="…">text</x-ref>A link to the first line in the file containing symbol. Without symbol, a link to the file. A path ending in / links to the directory.
    <x-code path="…" start="…" [end="…" | lines="n"] [doc] [max="n"] [caption="…"]/>An excerpt with highlighting and line numbers. It starts at the first line containing start and runs to the line containing end, or for n lines, or by default to the brace that closes the block. doc includes the comment above it.
    <x-packages names="a,b"/>, <x-packages rest/>Package cards with size and doc comment, read from the code. A bare name is looked up under the package root in atlas.json (internal/); a name with a slash is a path. rest lists every package under the root that no other x-packages mentions, and the build reports it.
    <x-stat name="…"/>A number counted from the repository, as atlas.json's stats defines it: go-lines-nontest, packages, migrations, migrations-latest, api-operations and others. Each definition names one of the kinds in statKinds (lines of tracked files, packages, files in a directory, the latest of them, pattern matches in a file, a captured value, the schema left by replaying migrations).
    <x-page id="page[--section]">text</x-page>A link to another page or section, with the page's title when there is no text.
    <x-include name="file.html"/>A partial.

    Attribute values are matched literally. Write &quot; for a quote inside one, as in start="if is(&quot;worker&quot;) {".

    The page script also understands a few classes: callout drift for spec and code that disagree, callout risk, callout note, evt for an event name, stepper with stage items whose data-lit lights the diagram groups marked data-stage, and data-go="page" on any diagram group to make it open that page.

    Keeping it current#

    Run these from the repository root:

    CommandWhat it does
    make atlasBuilds docs/atlas/site/index.html and docs/atlas/dist/artifact.html, and prints every reference that no longer resolves.
    make atlas-staleLists each written page and how many commits have touched its sources since it was checked, with the files.
    node docs/atlas/atlas.mjs checkBuilds in memory and fails if any reference is broken. Use it before committing.

    To bring a page up to date: run make atlas-stale, read the diff of the listed files since the page's verified commit, change what the page says, set verified to the commit you checked, then rebuild. Code excerpts and line links update themselves. Prose, tables and diagrams are what need a person.

    What the checks cannot see

    An excerpt anchored on a symbol keeps working when the code around it changes. A broken anchor is reported, but a change in meaning is not. And a later migration that changes what an earlier one created is not noticed while the excerpt points at the earlier one. That is why each page also lists its sources and turns amber when they change.

    Publishing#

    site/index.html is the atlas. Commit it with the change that updated a page. dist/artifact.html is the same atlas without the document wrapper, for hosts that add their own, such as a claude.ai artifact. It is not committed. CI's atlas job runs node docs/atlas/atlas.mjs check on every push, and on a pull request fails when pages, partials, the build or atlas.json changed without a rebuilt site/index.html.
