    Engineering atlas

    How Xenibase is built, checked against its code.

    Xenibase runs Postgres for other people: hundreds of small databases on a shared cluster, dedicated instances with continuous backup and failover, and backend services (a data API, auth, file storage, realtime) in front of them. Every project keeps the same connection string for its whole life. This atlas explains how that is built, one feature and one component at a time. It is written for the engineers who maintain it.

    The system on one page#

    Clients reach a project in two ways: as Postgres, through the edge poolers, or over HTTPS, through xenibase-edge. Both are driven by xenibase-server, which keeps everything it knows in its own metadata database and does long work as queued operations. The databases themselves live on nodes, each with an agent. Select a box to read about it.

    Four ideas the rest depends on#

    The pooler is the address#

    A project's connection string names the pooler and an opaque database name, never a server. xenibase-server renders PgBouncer's routes and SCRAM verifiers from the metadata database (Manager.Sync), so a project can move, be promoted or fail over and its URL still works.

    Connections

    Long work is an operation#

    Creating, deleting, restoring, moving and upgrading are rows in operations. Workers claim them with FOR UPDATE SKIP LOCKED, write a step log the dashboard streams, retry with backoff, and run a compensating rollback when they give up.

    Follow one project

    Postgres enforces the tenancy#

    On the shared cluster each project is a database owned by its own role. CONNECT is revoked from PUBLIC, so a role can open only its own database, whatever the pooler routes it to. The control plane checks every API request against the organisation that owns the resource (authz.Can).

    Security and tenant isolation

    Passwords are never kept#

    A project's password is generated, shown once and forgotten. The metadata database holds only its SCRAM verifier, which is what PgBouncer authenticates with. The plaintext exists, sealed with the master key, only while the create operation needs it for its smoke test.

    What Xenibase is#

    Xenibase is a Postgres platform that one company runs for many customers. A customer signs up, gets an organisation, and creates projects. A project is a Postgres database with a stable connection string. On the shared tier it is one database among hundreds in a shared cluster. On the dedicated tier it is a Postgres container of its own on a node, archived continuously with WAL-G, optionally with a standby on another node and read replicas. Around the databases sit backups and restores, branches, a SQL console and table editor, database webhooks and scheduled jobs, and since V4 a set of backend services that make a project usable straight from an app: a data API, project auth, file storage and realtime, served by xenibase-edge.

    The product grew through five specifications, all at the repository root. V1 is the core: shared and dedicated tiers, the pooler, operations, backups and the operator UI. V2 added organisations, roles, API tokens, branches, webhooks and multi-tenant hardening. V3 and V3.1 added HA, the standby pooler, billing, the Free tier, regions and capacity automation. V4 and V4.1 added the backend services and the edge. docs/decisions.md records the choices made while building, milestone by milestone, and is the first place to look when the code and a spec disagree.

    The binaries#

    Every directory in cmd/ is one command (6 of them); five are released. The Makefile's build-go target builds them all with CGO_ENABLED=0, and release-check refuses a server or edge binary that links purego, so both stay static.

    BinaryWhere it runsWhat it does
    xenibase-serverThe control node, behind CaddyThe REST API and the embedded web UI, the operation workers, and about thirty background loops. It owns the metadata database (it runs the migrations at startup) and the pooler files. It also has offline modes: -gen-master-key, -rotate-master-key, admin and mail-preview.
    xenibase-agentEvery node, including pooler hostsregister once with a one-time token, then run: an HTTPS service behind mutual TLS with a fixed set of commands (health, host metrics, dump, restore, copy, dedicated instances through Docker, pooler files and keepalived on pooler hosts). decrypt opens a backup with an exported key.
    xenibase-edgeOne or more per regionThe backend services gateway at https://<ref>.<domain>. It is stateless: it follows xenibase-server's configuration feed, serves data, auth, storage and realtime, and reports usage back.     xenibase-statusAnother provider, on purposeThe public status page. It probes Xenibase from outside and takes signed heartbeats and incidents, so an outage cannot take down the page that announces it.
    xenibaseDevelopers' machines and CIThe command-line tool: contexts, device login, and commands for organisations, projects, branches, SQL, backups and more, all through the public API with an API token.

    The sixth, cmd/docsite, builds the documentation site from docs/ and fails on a broken link. It is a build tool, not a release binary.

    What xenibase-server switches on#

    run in cmd/server/main.go builds each service in turn and hands them all to api.NewHandler. Much of it depends on configuration. Without XENIBASE_POOLER_CONFIG_DIR there is no pooler, and so no provisioning, backups, dedicated tier, branches, Free tier, backend services or webhooks; the server still serves accounts, organisations and billing.

    Each service that does long work contributes operation kinds to one map, and a single jobs.Runner serves all of them:

    Background loops are goroutines on a context that is cancelled only after the HTTP server has drained, so open Server-Sent Event streams end before shutdown waits on them and interrupted operations are requeued.

    How they talk#

    FromToHow
    Browser, CLI, SDK scriptsxenibase-serverHTTPS through Caddy. Sessions in __Host- cookies with a double-submit CSRF token, or a bearer API token. Every route declares its authorization (routeRules), and the guard refuses a route that does not.
    xenibase-serverShared clusters, dedicated instancesDirect Postgres connections over the private network as an admin role whose credential is sealed in the metadata database. This is how roles, databases, grants and extensions are made.
    xenibase-serverAgentsHTTPS with mutual TLS. xenibase-server is a small CA (internal/agentca): it issues each agent a server certificate at registration, pinned by fingerprint, and presents a client certificate of its own (Nodes and agents).
    xenibase-serverPgBouncerFiles written atomically into the pooler directory (or pushed to pooler hosts through their agents), then RELOAD, PAUSE, RESUME, KILL on the admin console.
    App serversPgBouncerPostgres over TLS (client_tls_sslmode = require). :5432 is session mode, :6543 transaction mode. PgBouncer authenticates with the SCRAM verifier and passes SCRAM through to the backend.
    xenibase-edgexenibase-serverLong-polled configuration feed and reports, signed with the edge's own region-bound credential or the platform-wide edge secret (edgeapi.Signed: HMAC-SHA256 over the time, method, request URI and body, five minutes' tolerance).
    xenibase-edgePgBouncerTransaction-mode connections as the project's request roles, one transaction per request.
    xenibase-serverxenibase-statusSigned heartbeats and incidents (internal/statusapi).
    Resolved

    One edge secret for the whole platform used to authenticate every edge, and the feed returned every region's projects when the caller left region empty, so the secret of any one edge node read the database logins of every project in every region. An edge in a region with its own API domain now has its own credential, bound to that region on the server (VerifyEdge), and the platform-wide secret serves only the regions without their own domain (backend services guide).

    The fastest way to understand Xenibase is to follow one project from start to end. This page follows a developer who signs up on an install with open signup, creates a shared-tier project from the dashboard, connects an app server to it with a Postgres driver, and later turns on backend services and calls the data API from a browser. Each stage names the function that does the work and the rows it writes, so you can open the code beside it.

    Follow the project#

    Select a stage to light up its part of the sequence. Shaded bars are transactions: everything a stage writes there commits together or not at all.

    1. Sign-up makes a user and an organisation#

      POST /api/v1/auth/signup is a public route. auth.Signup reads the platform's signup policy (invite-only by default, or approval, or open, with an optional domain allow-list), checks the Turnstile challenge and the per-address limit of the signup guard, the password policy and that the terms version accepted is the current one. An address that already has an account gets a "you already have an account" email instead, so the response does not say which addresses are registered.

      Then one transaction inserts the user, runs the UserCreated hook, and records the accepted terms. The hook is createPersonalOrg: every user gets a personal organisation on the Personal plan and is its owner. The verification email goes last. Until the address is verified, and in approval mode until an admin approves, Login refuses to open a session, and only the right password learns why.

      usersorganizationsorg_membersterms_acceptancesemail_tokens

    2. The create request#

      POST /api/v1/projects passes the guard first: the session cookie (or bearer token), the double-submit CSRF token and the Origin check, outstanding terms. Its rule is scopeBody, so CreateProject names the organisation itself and calls authorizeOrg for org.create_project. With no org_id in the body that is the caller's personal organisation. Tenancy then checks the organisation's project quota.

      provision.Create validates the name, generates a 32-byte password and its SCRAM verifier, settles the Postgres major and the region, and picks the shared instance. It seals the password with the master key, bound to the new project id and the purpose, and in one transaction inserts the project (status provisioning), makes the creator a project member, and enqueues a create operation whose params.secrets holds the sealed password. The response is 202 with the operation, the connection strings and the password, which is never shown again.

      projectsproject_membersoperationsaudit_log

    3. A worker claims the operation#

      A trigger on operations sends pg_notify('xenibase_operations', …), and the notifier's LISTEN connection wakes the runner; polling every two seconds is the fallback. Runner.Run claims only while it has a free slot (four by default, XENIBASE_WORKERS). The claim takes the oldest runnable operation of a kind this process serves with FOR UPDATE SKIP LOCKED, sets it running, increments attempts and records the worker in locked_by.

      While the handler runs, a heartbeat refreshes locked_at every ten seconds. Another worker's reclaim loop puts back any operation whose heartbeat is more than thirty seconds old, and every write the old worker makes afterwards is refused because locked_by no longer matches.

    4. The database is built#

      runCreate opens the password, then runs steps that are each safe to repeat. EnsureInstance is a no-op on the shared tier. ensureRole creates (or alters) the owner role with every attribute spelled out: NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS, a connection limit, the verifier as its password, a temporary file limit, and the role's statement and idle-in-transaction timeouts. ensureDatabase creates the database from template0, owned by that role, revokes everything from PUBLIC and grants CONNECT, TEMPORARY to the owner. hardenDatabase revokes CREATE on public, gives the schema to the owner and, on the shared tier, hides pg_stat_activity.

      All of this is plain SQL from xenibase-server to the cluster as its admin role, over the private network. Identifiers go through pgx.Identifier.Sanitize, and the verifier is checked to be a SCRAM verifier without a quote before it is inlined.

    5. The poolers learn the route#

      Manager.Sync takes a cluster-wide advisory lock and rebuilds every region's pooler configuration from the metadata database: a route per project database, its owner's verifier, read-only _ro routes for projects with replicas, V1 aliases, personal logins, backend services' logins, probe logins and owner-created logins on dedicated projects. Render validates every name, host and verifier rather than escaping it, so nothing in the metadata database can inject pooler configuration. The files are written atomically in a safe order (users, then hba.conf, then routes), pushed to the pooler hosts through their agents, and every PgBouncer gets RELOAD.

    6. The smoke test, then active#

      smokeTest connects through both poolers as the owner with the real password and checks current_user and current_database(). That proves the route and the SCRAM passthrough end to end. The project is then set active, and when the runner marks the operation succeeded the same statement deletes params.secrets, so the sealed password is gone.

      projects.status = activeoperations.status = succeeded

    7. An app connects through the pooler#

      The app opens postgresql://p_…_owner:…@db.example.com:6543/p_…?sslmode=require. PgBouncer requires TLS, then applies hba.conf (auth_type = hba): a project with an IP allowlist takes its customer logins only from those networks. It authenticates the client with the verifier from userlist.txt, finds the route by database name, and logs in to the backend by passing the client's SCRAM proof through, so it never needs the password. Pools are per database and user, so connections are never shared between tenants.

      The last line of defence is Postgres itself. Every role is in one auth file per region, and a client can ask PgBouncer for any route. But CONNECT on each project database is granted only to its own roles, so a role routed to someone else's database is refused at login.

    8. Or through the edge#

      Turning on backend services (services.Enable) creates a publishable and a secret key and queues an operation that makes the project's request roles and xb_* schemas. The project then appears in the edge feed. A browser calls https://<ref>.<domain>/data/v1/… with the publishable key.

WithRequest then runs the request in one transaction through the transaction-mode pooler, logged in as the anon, user or service role itself, with the claims and statement timeout set with set_config(…, true), so nothing outlives the transaction. Row-level security decides what the role sees.

    Names and credentials#

    A project's database name is p_ followed by ten random base32 letters, and its owner role is derived from it. Nothing in either says who the customer is or what the project is called, because both are visible to every tenant on a shared cluster in pg_database and pg_roles. A collision on insert is retried with fresh names, up to five times.

    Spec and code differ

    V1 gives names as <slug>_<4-char-random>, such as blog_k2f9 (V1 5.1). V2 §10.2 replaced them with opaque names, and a V1 project renamed since keeps its old name as a pooler alias (alias_db_name), so old connection strings still work. V1 also says the password is never stored reversibly (V1 5.3). The code keeps it, sealed, in the create operation until it finishes, because the smoke test needs it and may run in another process after a restart (decision M1 #3).

    Where the project lands#

    A shared project goes to a running shared instance in its region, on a healthy, active node, running the requested major. An organisation with shared clusters of its own uses only those; every other organisation uses only untagged ones. Among those, the instance with the fewest live projects wins.

    Spec and code differ

    V1's create flow picks "the shared node with the most free capacity" (V1 6.1). The query counts projects instead. Projects differ a lot in size, so a cluster with a few large databases keeps getting new ones; capacity automation (Part E) watches disk separately.

    A dedicated project goes through dedicated.Validate, which places it on the least loaded node in the region that fits its profile, or asks capacity automation for a new host.

    Resolved

    A tenant used to be able to choose the node for a dedicated project: CreateProject passed the request's node_id into CreateParams.NodeID for any caller allowed to create projects, and Validate then checked only that the node took dedicated instances, had an agent and was healthy, not that the instance fitted or that the node was active rather than draining. Now CreateProject refuses node_id with 403 unless the caller is a platform admin (the dashboard offers the choice only to them, and API tokens never are), and Validate runs placeDedicated's lifecycle and fits checks on a hand-picked node too, except for a detached replica, whose instance is already there (TestCreateProjectNodeIsForPlatformAdmins, TestValidateChecksAChosenNodeLikePlacement). Promote and move reach Validate too and get the same checks; who may name a node for a promote, HA standby, replica or demote is not changed here.

    How the operation is run#

    Every long action is the same shape: a row in operations, a handler that must be safe to run again, and optionally a compensating OnFail. The kind sets the attempts (create: three) and the time limit per attempt (create: 45 minutes, because a dedicated create may wait for a new host).

    When an attempt fails, the runner retries with exponential backoff (two seconds doubling to five minutes). A permanent error, or the last attempt, runs OnFail. For a create that is rollbackCreate: it soft-deletes the project as error, kills pooled connections, removes the route and drops the database and role, so a failed create leaves nothing behind. Every step log line is appended to the row and streamed to the dashboard over Server-Sent Events.

    Resolved

    The lease used to be fenced only by worker identity, and a failed heartbeat was logged and skipped, so a worker cut off from the metadata database for more than thirty seconds kept running an operation that another worker had reclaimed, and could even write its result over the new attempt's. Now heartbeat gives each heartbeat a third of the lease and cancels the attempt once heartbeats have failed for two thirds of it, before anyone can reclaim it, and every write to the row (heartbeat, step log, succeed, fail, retry) matches locked_by and attempts, so a stale attempt writes nothing even when the same process claimed the operation again. TestPartitionedAttemptStopsAndIsFenced cuts a worker off through a proxy and checks both.

    The API and its guard#

    Routes are generated from api/openapi.yaml (415 operations on 325 paths) into a chi router. Every request under /api and /metrics first passes guard, which resolves the route pattern before routing so it can refuse early:

    1. Who. A bearer token becomes a token session, and the cookie is ignored. Otherwise the session cookie is looked up by its SHA-256.
    2. CSRF. A mutating request from a cookie session must carry the double-submit token, and its Origin, when sent, must name this host (checkCSRF). Program-to-program routes are listed in csrfExempt.
    3. A rule. The route must be in routeRules. A route with no rule is refused with 403, and TestEveryRouteDeclaresAnAction fails CI when the spec and the map disagree.
    4. Terms, then step-up. A browser session with new terms to accept gets terms_required, except on the few routes marked beforeTerms. Routes in reauthRequired (delete a project, turn on role management, transfer, refunds and others) need a password and code check in the last ten minutes. Tokens skip step-up and need the admin scope instead.
    5. Authorize. authorize finds the resource's organisation from the rule's scope, then asks authz.Can. A resource the caller may not know about answers 404, one they may see but not change answers 403. The resolved organisation, project and roles go into the request context for the handler.

    The operations queue#

    Every long action is a row in operations. A request inserts it, usually in the same transaction as the metadata change that needs it, and returns 202 with the operation. Workers claim it, run the kind's handler, and record the outcome. The dashboard follows it over Server-Sent Events.

    The claim takes the oldest due row of a kind this worker knows, with SKIP LOCKED, so workers never block each other or take the same row:

    A handler gets the operation and a StepLogger. Each log line is appended to the row only while this worker still holds it (locked_by, status = 'running'), and a line that matches no row returns ErrLeaseLost, so a handler that checks its log errors stops when it has lost the operation.     Resolved

    It used to be a convention, not a constraint: nothing in the schema stopped a second active operation, the nightly scheduler checked "no operation in flight" in ProjectsDueForBackup without locking the project (so a backup and a delete requested in the same instant could both be queued), and a kind that no running process registered stayed queued forever and blocked every exclusive action on its project.     Resolved

    A create whose rollback failed used to leave an orphaned database and roles: rollbackCreate soft-deleted the project, then ran teardown once, and if that failed (a pooler sync error, a cluster that stopped answering) the database, the owner, console and read-only roles stayed on the shared cluster with no project that could reach them.     Resolved

    A delete that failed after teardown used to be unable to finish: runDelete started every attempt with the final backup, so after an attempt that had already dropped the database (and then failed on DropAutomation, SoftDeleteProject, a crash or a shutdown), every remaining attempt failed backing up a database that no longer existed, and the project was left in error.     Resolved

    IssueCredentials creates the role on the instance first and writes the metadata second. If that write failed after CREATE ROLE, the role used to stay on the instance with a password no one had, and teardown, which dropped only the logins in project_db_users, never removed it.     Dedicated projects: role management and connection ceilings#

    Release 4.2.4 lets a dedicated project's owner create roles, so an application whose migrations run CREATE ROLE works unchanged. SetManageRoles (organisation owners, after step-up) refuses the shared tier and Postgres before 16, writes projects.manage_roles, and gives the owner CREATEROLE (OwnerCreateRole).     The poolers accept only logins Xenibase knows, so every 30 seconds SyncOwnedRoles reads the roles the owner administers, caps their connection limit at the project's, grants CONNECT, and records each syncable login and its verifier in project_owned_logins. A login is syncable when it is named <db>_… (each region's pooler auth file is one namespace), is not one of Xenibase's names, has no elevated attribute and has a SCRAM password. When the set changed it rewrites the rows in one transaction and syncs the poolers. Moves and major upgrades recreate the owner's roles on the target before the copy (restoreOwnedRoles).

    A dedicated instance's max_connections now grows with memory instead of being 100 for every size, and is stored per instance (migration 00060). A project's connection limit can go up to the instance's ceiling less ten reserved slots, and ensureRole clamps it again on every run so a move to a smaller size cannot leave it too high. A restore's instance never gets fewer than its source, because a standby will not replay WAL from a server that allowed more.

    Resolved

    Role management used to be switched outside the project lock: SetManageRoles wrote the flag first and ran ALTER ROLE … CREATEROLE second, so a refused ALTER ROLE left metadata and instance disagreeing, and an apply_settings, move or restore that had loaded the project before the switch ran ensureRole with the old flag and undid it. Now it runs under WithIdleProject: it holds the project's row lock, refuses (409) while any operation is pending, alters the role inside that transaction and commits the flag only if the instance accepted, putting the role back if the commit fails (TestSetManageRolesRefusesBusyProject, TestSetManageRolesKeepsFlagWhenInstanceRefuses).

    The SQL console and query insights#

    Console sessions connect straight to the instance, not through the poolers, as <db>_console: a login with no privileges of its own, granted the owner role and <db>_ro WITH INHERIT FALSE, SET TRUE. Read-only sessions log in as <db>_console_ro, granted only <db>_ro. Each submission opens a session, runs SET ROLE to the owner (or, for a read-only member, to <db>_ro), sets the statement and lock timeouts, and closes afterwards (connect). Read-only mode runs one statement inside BEGIN READ ONLY; SELECT 1, so the snapshot is taken and the transaction cannot be switched back to read-write. Results are capped at 1,000 rows and cells at 64 KiB. The audit row records that the console ran and the error code, never the SQL.

    Resolved

    A read-only member could read as the owner: their session logged in as <db>_console, which may SET ROLE to the owner, so SELECT set_config('role', '<owner>', true), query_to_xml('SELECT * FROM t', true, false, '') returned rows RLS hid from <db>_ro and tables never granted to it, for a read-scope token and the table browser's raw filter too. Read-only sessions now log in as <db>_console_ro (ConsoleReadOnlyRole), granted only <db>_ro WITH INHERIT FALSE, SET TRUE, so there is no owner to switch to. It is created by ApplyConsoleRoles on first use, as the console login always was (the failed login is repaired and retried), so existing projects get it on their next read-only session. isocheck.Roles reports the login if it can become the owner, and TestReadOnlySessionCannotBecomeOwner and the isolation suite run the statement above.

    Query insights (insights) snapshot pg_stat_statements as the instance admin, keep each project's own rows as per-project deltas in query_stats and query_texts, and serve top queries, EXPLAIN, slow queries, index suggestions, bloat and locks. Tenants never query the view on a shared cluster, because the admin's copy is filtered by database before it is stored. Console sessions are tagged so their queries are not counted.

    What a node is#

    A node is a machine that xenibase-server sends work to. Each runs xenibase-agent, which is the only thing on the machine the control plane talks to. The control plane never logs in over SSH and never runs a shell command it composed. It calls a fixed HTTPS API on the agent, and the agent turns each call into Docker API requests, pg_dump/pg_restore processes, or file writes.

    A node row has a role, set when an operator adds it (CreateNode):

    RoleWhat runs thereCan change to
    shared, dedicated, bothPostgres: a shared cluster, dedicated instance containers, or both. Which of these new projects may be placed on.Each other (SetRole)
    poolerThe two PgBouncers, keepalived, and the agent in pooler mode (pooler hosts)Nothing: remove it and add the machine again
    edgexenibase-edge beside the agent, never a database (V4.1 §11)Nothing

    A node also has a region (the home region when none is given) and an optional failure domain, which HA, etcd and pooler placement use to keep pairs apart.

    How a node joins#

    1. The operator adds the node. POST /api/v1/nodes (Admin → Nodes → Add node) inserts the row and returns a one-time registration token, xbreg_ and 24 random bytes. Only its SHA-256 is stored, with an expiry a day later (newToken). NewToken issues a fresh one for an existing node, replacing any earlier token.
    2. The agent registers. xenibase-agent register --server … --token …, or the first run when no state exists yet, which retries up to 30 times two seconds apart. agentsvc.Register makes a P-256 key and a certificate request (NewCSR) and posts it with the token and the address the server should dial (--advertise, default the hostname and port 7070) to POST /api/v1/agent/register. That route has no session. The token in the body authenticates, and the route is rate limited per IP (RegisterAgent). The agent checks the server's HTTPS certificate against the system roots or --server-ca.
    3. The server signs and pins. In one transaction, nodes.Register finds the node by the token's hash (unexpired, row locked), signs the CSR for that node, and records the certificate's SHA-256 fingerprint, the advertised host and port, and the agent version. The token is cleared in the same statement, so it works once.
    4. The agent saves its state: agent.key, agent.crt, the CA certificate and node.json, each 0600 in a 0700 directory (/var/lib/xenibase-agent). From then on run loads that state and listens.

    The bootstrap token#

    The install bundle's own agent registers the local node without an operator. XENIBASE_AGENT_BOOTSTRAP_TOKEN (at least 24 characters) is given to both the server and that agent, and the agent sends it with --node local. The server compares it in constant time, and accepts it only for the bundle's local node (XENIBASE_SHARED_NODE_NAME, default local), only while that node has never had an agent and is not removed, and only once: the registration records agent_bootstrap_used in settings, under an advisory lock. Re-registering needs a token from the UI.

    Resolved

    The bootstrap token never expires, and it used to claim any node without a pinned certificate by name: a machine just added whose own agent had not registered yet (so a hostile agent could take its identity and receive its instance specs and their passwords), or a removed node, which CompleteNodeRegistration brought back as healthy. It is now bound to the local node, refused for a removed node, and single use (TestBootstrapToken, TestBootstrapTokenBound).

    Machines Xenibase creates#

    Capacity automation (V3 §5.1) creates machines through cloud.Provider: Hetzner Cloud (hetzner.go), or manual, which has no API and returns ErrManual. The new server joins by itself with the same one-time token, carried in its cloud-init document (cloud.Bootstrap). That document installs Docker, turns off SSH passwords, sets ufw to deny incoming traffic except SSH and the private network, and starts the agent with the Docker socket mounted. On an edge node it also starts xenibase-edge and opens 8443. Every value that reaches a shell line is checked first by Validate: names, CIDRs and image references against patterns, and the token and edge secret refused if they hold spaces, quotes, $, backslashes or backticks. YAML strings are JSON-quoted.

The registration token is spent within minutes. An edge node's credential is not, but it unlocks only its own region's feed (see the edge).

    Both directions of the handshake#

    The server always dials the agent; the agent never calls the server after registering. When the server dials, dial trusts only the agent CA, requires TLS 1.3, and then checks two more things the CA alone would not give:

    The pin means a stolen copy of the CA key is not enough to stand in for a registered agent: the impostor would also need the node's own certificate. The subject check stops one node's genuine certificate being used at another node's address. Revocation is the pin: re-registering replaces the fingerprint, and RemoveNode (refused while any instance is live on the node) clears it. There is no CRL.

    On the agent, agentsvc.TLSConfig requires a client certificate from the pinned CA, TLS 1.3, and the subject xenibase-server. Go's own check also requires the client-auth key usage. An overlay test written for this page confirmed both refusals: a client certificate named xenibase-server with server-auth usage fails with "incompatible key usage", and a client-auth certificate with another name fails the subject check.

    Spec and code differ

    The V1 spec (§3.3) says the server "issues each agent a client certificate at registration". Agents get server certificates. The client certificate is the server's, and every agent accepts any unexpired one the CA signed with that subject. There is no per-server identity: a copy of any server's client certificate commands every agent until it expires.

    Resolved

    The server's client certificate used to be issued once, in nodes.NewService, and kept for the life of the process, so a xenibase-server that ran for more than 30 days without a restart lost every agent at once. Every handshake now asks clientCerts.get (through tls.Config.GetClientCertificate), which reissues it when 7 days or less are left and keeps the current one if that fails.     Why a command cannot become a shell#

    The agent takes values, never command lines, and each value reaches a process as an argument or an environment variable:

    • Connections reach pg_dump and pg_restore as PGHOST, PGUSER, PGPASSWORD and the rest (pgEnv), so passwords never appear in ps. Schema filters are single --schema=… arguments (dumpArgs), so a value starting with - cannot become a flag. Child processes get SIGKILL if the agent dies (Pdeathsig).
    • Instance IDs must be UUIDs (instanceID). Container and volume names are made from them.
    • Postgres settings become -c name=value arguments to postgres, with names limited to [a-z_][a-z0-9_.]* and values without NUL or newline (settingName). The settings come from the server's size profiles and replica settings, never from a customer.
    • The few shell scripts are constants. Their variable parts come in through the exec environment: the move rules, the recovery settings, the backup name (checked against ^(LATEST|base_…)$). The one file a script sources, the recovery source's WAL-G settings, is written by shellExports with every value single-quoted.
    • etcd membership takes a peer URL that must start with https:// and a numeric member ID, sent as JSON to etcd's gateway.
    • Docker is reached through docker.New: the Engine API over the Unix socket (or tcp://, unencrypted), at API version 1.43 or the daemon's minimum if that is higher. It has no SDK dependencies.

    So what the control plane can do to a node is bounded by this API, not by what a shell could do. But that bound is wide. The agent runs as root with the Docker socket, and creates containers from whatever image and settings the server sends. Whoever holds the server's client certificate effectively has root on every node.

    Resolved

    An import's source address was not checked, which defeated IP allowlists: connectSource and the agent's /v1/copy connected to any host, from addresses every cluster's pg_hba.conf trusts, so a project's owner password got a full copy past its allowlist, and the path probed the private network. The source now goes through outbound.CheckSource: public addresses only unless the platform admin allow-listed the host for the organisation, and never loopback, link-local, a node's or instance's own address, XENIBASE_OUTBOUND_BLOCK or (with machines Xenibase creates) the cloud private network, allow-listed or not. pgsource.Config refuses a URL whose settings name another host (host=, several hosts, a socket directory) and pins the connection to the checked address: pgx resolves every name to it, and the agent's copy gets it as hostaddr. The import checks again just before the copy, and Supabase migrations take the same path.

    How commands are authenticated and authorised#

    Authentication is the TLS handshake and nothing else: no token, no request signature, no per-request check. Authorisation is all or nothing. Once a client presents a valid xenibase-server certificate, every path is open, and the agent does not know which project or operation a call is for. Each request is decided in the control plane. The operation that calls the agent has already been authorised against the caller's organisation role (see Security), and the agent trusts the server's decision.

    The server also refuses to send work to an agent it does not trust to understand it. agentFor checks the version the agent last reported against the server's (Compatible): the same major, and a minor no older than the server's. Development builds match anything. Health checks use dial without the version check, so an agent that needs upgrading still reports in.

    Pooler hosts add a second listener: an unauthenticated HTTP API on a loopback address for keepalived's check script and notify calls (LocalHandler). ServeLocal refuses any address that is not loopback. Any local process can mark the host MASTER and so make xenibase-server move the floating IP to it.

    Instances through Docker#

    instances.Create holds a per-instance lock and is idempotent. If the container exists it is started and waited for. Otherwise it pulls the image if missing. The image name is a template with {major}, default xenibase-postgres:{major}-walg3.0.9. It then creates the volume xenibase-<id>, optionally restores into it in a one-off container, and starts postgres with hard CPU and memory limits, shm sized from memory, SIGINT as the stop signal, and restart unless-stopped. It finally checks that the running major is the one asked for (postgres -V). PGDATA is always set inside the volume, because older images declare an anonymous volume that a recreate would lose.

    Network logins are limited at initdb to XENIBASE_AGENT_DB_ALLOW, which defaults to every private range and 127.0.0.1 (defaultDBAllow), with SCRAM. On every start the agent appends, once, rules that let only xenibase_move_<hex> logins in from XENIBASE_AGENT_MOVE_ALLOW for logical-replication moves, and reloads (ensureMoveHBA). Instances are reached by container name on the agent's Docker network, or on a port published on the node's private address.

    Note

    A project's IP allowlist is enforced at the poolers, not here. Anything that can reach a node's private address with a project's password connects to its instance directly. On the dedicated tier that includes another customer's postgres_fdw, which is allowed there.

    The path of a connection#

    Every client connection string names the region's database hostname, a port, and the project's database:

    postgresql://blog_k2f9_owner:…@db.example.com:6543/blog_k2f9?sslmode=require
    1. DNS and the floating IP. The hostname points at the region's floating IP. Hetzner routes that address to one of two pooler hosts. Without pooler hosts, the PgBouncers run beside xenibase-server, as in the compose bundle.
    2. PgBouncer. :5432 is session mode, for migrations, LISTEN and anything that needs a session. :6543 is transaction mode, for app traffic, with up to 200 prepared statements tracked per connection. Both run the same configuration (deploy/pgbouncer). TLS is required (client_tls_sslmode = require, TLS 1.2 or 1.3).
    3. Who may log in from where. auth_type = hba: PgBouncer reads the generated hba.conf, then checks the password against the SCRAM verifier in the generated userlist.txt. PgBouncer never sees a plaintext password.
    4. Routing by database name. The name in the startup packet picks a line of the generated databases.ini: the backend host and port, the backend database, and pool limits. PgBouncer connects to the backend as the same user and passes SCRAM through.
    5. The backend. One of three things: the shared cluster or dedicated instance that holds the database; the read replicas, for <db>_ro; or, for a paused or archived Free project, the waker.

    There is no SNI routing and no per-project hostname for Postgres. A region has one hostname and one certificate, and the database name alone picks the project. The data API, auth, storage and realtime go through xenibase-edge instead, which does route by hostname.

    The generated files#

    xenibase-server owns three files in the pooler directory (XENIBASE_POOLER_CONFIG_DIR, mounted read-only into each PgBouncer at /etc/pgbouncer/xenibase). Render produces them from a Config of routes, users and restrictions. Entries are sorted, so the same input gives byte-identical files. Names are validated, never escaped, so a bad name upstream cannot inject configuration:

    Manager.Sync builds one Config per region under a Postgres advisory lock, so two servers never interleave. It reads projects in a live status whose organisation is not suspended (PoolerRoutes; a suspended organisation simply loses its routes), their replicas, and every kind of login. A project is routed by its region's poolers, or by the home region's when its region has no pooler hosts. Files are written atomically (temp file, fsync, rename, directory fsync) in a fixed order: users, then hba.conf, then routes. A new route is never served before its user can log in, or wider than its allowlist. Then every pooler gets RELOAD (distribute).

    The admin console also carries PAUSE/RESUME around cutovers, KILL for deletes and password rotations, and RECONNECT. Freeze pauses the transaction pooler, falling back to KILL after a wait, and kills on the session pooler, whose clients would otherwise hold PAUSE open. Each command goes only to the poolers that route that database.

    One project's login on another's database#

    PgBouncer has no notion of which login belongs to which route. Any user in userlist.txt may ask for any database in databases.ini, and PgBouncer will open a backend connection as that user. Isolation is the backend's job: every project database has REVOKE ALL … FROM PUBLIC and CONNECT granted to its own roles only (ensureDatabase), so Postgres refuses the login. isocheck verifies that nightly on every cluster. The auth file is also one namespace per region, so login names must be unique across projects. Logins an owner creates must be named <db>_…, may not be one of the project's or Xenibase's own names (platformRole), and lose to a platform login of the same name.

    The poolers see the address a connection arrives from. PROXY protocol is not used anywhere: pooler hosts run with host networking behind a floating IP, which keeps the source address.     Pooler hosts, keepalived and the floating IP#

    With pooler hosts (V3 §2.1) each region has two machines. Each runs both PgBouncers and the agent in pooler mode in one container, and keepalived in another, the only one with NET_ADMIN (deploy/pooler-host).

    Getting the files there#

    After writing the files, pushHosts reads each region's bundle. That is its three files plus the TLS pair: the region's own if it has one, else the main directory's (readBundle). It hashes the bundle, advances the region's generation in the metadata database, and sends PUT /v1/pooler/config to each of the region's hosts over the agent's mutual TLS. Then it tells every host the generation, including any that just failed. A push fails only when every host refuses it. A host that missed it knows it is stale.

    The agent accepts only the five known file names, requires the routes and auth file, checks the hash against the content, and refuses an older generation with 409 (two servers raced). It writes users, rules, key, certificate, then routes, and sends SIGHUP to the PgBouncers (apply). The generation served and the generation expected are kept in a state file, so they survive a restart.

    Who holds the address#

    A host is ready when it has a configuration, serves the newest generation the server has announced, and both PgBouncers accept TCP connections (status). keepalived asks the agent's loopback /ready every second. Two failures drop the host out, and unicast VRRP with one-second adverts hands over in about 3 to 4 seconds. Both hosts start as BACKUP with nopreempt, so a host that comes back does not take the address back (keepalived.conf). keepalived's notify posts the new state to the agent, which reports it (setVRRP). The arbiter below moves the floating IP. Only an agent started with XENIBASE_AGENT_ASSIGN_FLOATING_IP=true and a Hetzner token also asks Hetzner itself on MASTER, retrying with backoff for up to two minutes, which keeps failover working while the control plane is down.

    xenibase-server's arbiter checks each region's pair every 3 seconds. It re-pushes to a stale host, at most every 15 seconds, and asks Hetzner where the IP points. Its rule is Decide:

    Following keepalived's MASTER happens at once: that is the failover. Moving the IP away from an unhealthy holder that keepalived has not replaced waits for two checks in a row. Each move, change of holder, split brain, host going stale and recovery is recorded as a pooler event and shown in Admin → Nodes.

    Split brain#

    If the two hosts lose sight of each other but not of Hetzner, both become MASTER. The arbiter reports split_brain and leaves a healthy holder alone, so nothing flaps. (Agents allowed to assign the IP each assign it once; Assign is a no-op when the IP already points at the caller, and the last assignment wins.) Both hosts are stateless and serve the same generation, so whichever receives the traffic routes it correctly. A host that missed a change cannot be ready, so cannot hold the address through keepalived. Two cases remain. If the control plane cannot reach the holder, the arbiter moves the address after six seconds even though clients could still reach it. That is a needless failover, not a wrong one. And while the control plane is down, nothing announces new generations, so a host that missed the last push before the outage still counts as ready.

    Resolved

    Each pooler host used to hold a Hetzner Cloud API token with read and write access (XENIBASE_AGENT_HETZNER_TOKEN), because the agent assigned the floating IP itself, and a Hetzner token cannot be narrowed to one IP: a compromise of an internet-facing pooler host handed over the whole Hetzner project. Now only xenibase-server assigns it, following keepalived's MASTER, and the agent only reports its VRRP state (floatingIP). The trade-off: while the control plane is down the address does not move. XENIBASE_AGENT_ASSIGN_FLOATING_IP=true with a token brings back agent-side assignment for those who prefer that.

    Spec and code differ

    V3 §2.1 says the server "verifies both hashes match". Staleness is decided by generation. The agent checks each bundle's hash against its content, and the server records each host's hash, but nothing compares the two hosts' hashes.

    What could be closed of the unverified hops.     Spec and code differ

    V1 §3.3 has the pooler certificate "obtained via DNS-01 or HTTP-01". The pooler certificate is HTTP-01 only (TLS-ALPN is turned off, and there is no DNS-01 solver in tlscert). DNS-01 exists for the edge's wildcard, outside this package.

    The waker#

    A Free project that sits idle is paused, and later archived (V3 §4.2–§4.3). Its route then points at the waker instead of its cluster, with pool_size and max_db_connections of 1:

    The waker does not authenticate: it relies on PgBouncer having checked the client's password first.     xenibase-edge#

    xenibase-edge (cmd/edge) serves each project's backend services at https://<ref>.<domain>. The data API, auth, storage and realtime are described in Part D. This section covers how it connects.

    The configuration feed#

    The edge keeps every project's configuration in memory and gets it from xenibase-server. It long-polls GET /api/v1/edge/config?since=…&wait=25 for changes and reads the whole feed again every minute as a backstop (apply ignores an older version that a resync brings back). An entry carries the pooler database and address, the edge login's and the request roles' passwords, the hashes of live API keys, the JWT verification keys, CORS, rate and cache settings, and the state. disabled removes the project. A project's database pools are kept while its connection details are unchanged, and closed when they change. Until the first full read the edge answers 503.

    Every call from the edge carries Xenibase-Signature, an HMAC-SHA256 over the time, method, request URI and body with the edge's credential or the platform-wide edge secret. The receiver accepts five minutes of clock difference (edgeapi.Verify).

    Resolved

    There used to be one edge secret for the whole platform (XENIBASE_EDGE_SECRET), and the region an edge served was a query parameter the edge chose, empty for all regions, so a regional edge and the cloud-init of every edge node held a key that read every project's service-role password in every region. An edge can now sign with its own credential, xbedge_<id>_<secret>, which names itself in Xenibase-Edge-Credential; the server keeps it sealed in edge_credentials with its region (edgecred.Issue, xenibase-server -issue-edge-credential, and capacity automation for the edge nodes it creates). The server fixes the region from the credential (EdgeScope.Feed): another region is refused, and wakes, auth messages and hooks, storage events and reports are limited to the credential's region. The platform-wide secret now serves only the regions without their own API domain, unless XENIBASE_EDGE_SECRET_ALL_REGIONS (deprecated) restores the old scope.

    From hostname to transaction#

    1. refFromHost takes the HTTP Host, lower-cased, without port or trailing dot. It must be exactly one label in front of XENIBASE_EDGE_DOMAIN. The edge serves a wildcard certificate whatever the SNI says, and the Host header alone picks the project.
    2. authorize looks the apikey up by its SHA-256 among that project's keys only. A key from another project is simply not found, so a Host header cannot be used to point one project's key at another. A secret key means the service role, and is refused from a browser unless the project allows it. A publishable key means anon, or user with a bearer token. The token must verify against that project's own ES256 keys with the project's ref as audience, and carry role: user. Per-IP and per-key limits apply. The client address is the RemoteAddr, or the last X-Forwarded-For entry when the peer is in XENIBASE_EDGE_TRUSTED_PROXIES (clientIP).
    3. WithRequest runs the whole request in one transaction through the transaction pooler, as the role's own login (<db>_anon, _user, _service), with the claims and statement timeout set with set_config(…, true). Nothing outlives the transaction, so transaction pooling is safe, and tenant SQL that resets the role stays that role. Only a feed from a server older than M32, which has no request-role passwords, makes the edge log in as the edge login and SET LOCAL ROLE.

    Pools are small: four connections per login, two for the service and hook roles. They use pgx's exec mode, with no server-side prepared statements kept between transactions (loginPool). GETs that may read from replicas use the <db>_ro route. These logins are the ones exempt from IP allowlists. The Bloom filter in internal/bloom sends a project's counted monthly users to the edge in a few kilobytes. A false positive lets an uncounted user in.

    How organisations are kept apart#

    There is no row-level security in the metadata database. The application connects as one role that owns every table, and tenancy is enforced by the API guard (The control plane) and by the queries. Tables that belong to an organisation carry org_id, including child tables where it could be derived (project_members, project_db_users, saved_queries, reaped_sessions, usage_records, audit_log), so a query can scope itself without a join.

    Queries live in internal/store/queries and sqlc turns them into typed Go in internal/store (sqlc.yaml; make generate, and CI fails on a diff). Each query either filters by org_id or says why it may not, in a comment the lint reads:

    TestTenantQueriesAreScoped splits every query file on -- name:, and for each query that reads or writes a tenant table requires either an org_id predicate or a -- tenant: system - <reason> line of more than ten characters. A tenant table is any table the migrations leave with an org_id or project_id column (migratedColumns replays them; TestTenantTablesMatchTheSchema checks the result against a migrated database). A predicate is org_id compared with a parameter, a list or NULL in a WHERE, ON or HAVING clause, or org_id among an INSERT's columns.

    Spec and code differ

    V2 says every sqlc query on a tenant table takes org_id and filters by it, as defence in depth even when the handler has checked (V2 2.6). In the code the opt-out is the common case: about 600 of the 850 queries carry tenant: system, most of them "a project the request already authorized". For those the only check is the guard and the handler.

    Resolved

    The lint was weaker than it read: its list of tenant tables was fixed in the test and predated backend services (project_api_keys, project_jwt_keys, project_services, read_replicas, auth_*, instance_members and others were missing), and any occurrence of org_id passed, including SELECT org_id, SET org_id = … or a join. It now reads the tables from the migrations and requires a real predicate. That caught 25 queries, all of them platform or worker queries on instances, storage_targets, region_early_access, device_auth_requests and the user's own memberships; each now says why in its tenant: system line, and the platform storage-target queries pass on org_id IS NULL.

    The schema ties a child's org_id to its project's. projects has UNIQUE (id, org_id), and the six tables that carry both (project_members, project_db_users, saved_queries, reaped_sessions, editor_preferences, dedicated_requests) have FOREIGN KEY (project_id, org_id) REFERENCES projects (id, org_id) ON UPDATE CASCADE (00068). Nothing checks that a project member belongs to the organisation; the handlers do. audit_log and usage_records keep the organisation of the time and have no key.

    Resolved

    Nothing used to tie a child's org_id to its project's, and orgs.Transfer moved members, logins and saved queries by hand, leaving reaped_sessions, editor_preferences and dedicated_requests under the old organisation.     How migrations run#

    Migrations are plain SQL files embedded in the binary and applied by goose when the server starts, before it serves anything (store.MigrateTo). A Postgres session advisory lock serializes servers that start together. Each file runs in its own transaction, so a failed migration leaves the previous version. A server refuses to start on a schema newer than the newest migration it carries (refuseNewerSchema), because running there could write rows that break constraints it does not know, and checks again every 30 seconds while it runs. Each file has a Down section, used only by tests that load data at an older version. Rolling back in production means restoring the metadata backup taken before the upgrade.

    A few migrations change data as well as shape: 00010 turns operators into users and moves every V1 project into its owner's personal organisation, 00018 queues an apply_settings for every active shared project, and several add plan limits to quota_plans. sqlc expands SELECT * into named columns at generation time, so adding a column never breaks a running binary's queries.

    The recent migrations are safe to run on a live install. They add columns with constant defaults (no table rewrite) and small indexes, and the tables they touch have one row per project, instance or region. Adding a column with a CHECK still scans the table under an exclusive lock, which is fine at these sizes.

    Resolved

    The newer-schema check used to run only at start, so an older server already running when a newer one migrated kept working on a schema it didn't know, and some migrations removed what older binaries use (00038 renames auth_email_outbox, 00052 drops payment_methods and a billing_accounts column, 00025 drops a column). Now store.SchemaWatcher reads the version every 30 seconds; on a newer schema the server logs it, stops claiming operations (the runner's Paused) and answers /readyz with 503 until it is replaced. It still serves requests that reach it, so the migrations guide now sets the rule for future migrations: expand in one release, contract in the next.

    What a backup is#

    Each backup is a backups row (target, operation, wrapped file key or project key, size, SHA-256 of the encrypted object) and, except for base backups, one object. objectKey names it projects/<id>/<kind>/<time>-<hex>.dump.enc, or .dump.gpg under a project's own key, relative to the target's prefix.

    KindTaken byKept

    finalA project delete (finalBackup)30 days
    safetyAn in-place restore, before it changes anything30 days

    A row goes running → succeeded or failed, then deleted. copied marks an original whose copy on another target was verified.

    Scheduling#

    backup.Service.Run ticks every minute on every server. Schedule:

    1. Returns at once without a default storage target or the platform backup key.
    2. Takes pg_try_advisory_xact_lock(hashtext('xenibase_backup_scheduler')), so several servers never queue twice.
    3. Lists due projects. The window opens at XENIBASE_BACKUP_HOUR UTC (default 2); each project is due at a stable offset into it, an FNV hash of its ID modulo XENIBASE_BACKUP_JITTER (default 2 h).
    4. Queues each through EnqueueIfIdleTx, which locks the project, rechecks it is active, and skips it if any operation is pending, so a backup never interleaves with a restore or delete. Shared projects get backup, dedicated ones base_backup.
    5. Queues a storage_switch for any dedicated project archiving somewhere other than where its backups now go, the metadata backup once per window, and the restore test once seven days have passed.

    "Already done" is any backup or base_backup operation since the window opened, whatever its outcome: a nightly backup that fails its three attempts waits for the next night, and the alerts report it. Hourly, Run also expires final and safety backups, fails rows whose operation ended while they were running (SweepStaleBackups) and deletes failed rows' leftover objects. Every five minutes it makes cross-region copies.

    Taking a logical backup#

    runBackup first looks for a backup an earlier attempt of the same operation finished (BackupForOperation), so a retry never takes a second one. dumpTo then resolves the target and sealing (sealing: a fresh file key wrapped by the platform key, or the project key's OpenPGP public key), fails rows an earlier attempt left running, inserts a new row and calls the agent. doDump pipes pg_dump --format=custom through the encrypter and a SHA-256 into a multipart upload, without touching the disk. Last, retention runs over the project's logical backups; its failure is only a warning.

    A failing pg_dump closes the upload's pipe with its error, so the multipart upload aborts; if it already looked complete, the agent deletes the object. An upload the bucket completes after the attempt gave up is caught by cleanFailed, which deletes failed rows' objects before every dump and hourly.

    BackupNow queues the same operation (a base backup on a dedicated project). On a platform target it counts against backup_storage_mb and is refused past it; nightly backups still run.

    Retention and expiry#

    Retention.Expired keeps the newest backup of each of the Daily most recent UTC days that have one, the newest of each of the next Weekly ISO weeks, and always the newest. Counting days that have a backup means failed nights never shorten the history. Policies are standard 7 + 4 (also the metadata backups), and the billed add-ons extended 30 + 12 and long 30 + 52 (V4.1 §4.2).

    applyRetention runs only after a successful backup of the project. deleteObject removes the object, its cross-region copy, and the original a switch copied it from. Final and safety backups carry an expires_at instead, and deleting an organisation re-dates its final backups to 30 days after (ExpireOrgFinalBackups).

    Risk

    A deleted project's nightly backups are never deleted. Retention runs only in the project's next runBackup, which a deleted project never gets, and its logical rows have no expires_at. runDelete and the organisation sweep touch only the final backup. So up to 11 copies of the database (82 with the long add-on) stay on platform storage for good, listed, downloadable and restorable; an archived Free project's earlier nightlies the same. V2 §10.10 and the terms template promise only final backups outlive a deletion, for 30 days. Fix: when soft-deleting a project, give its logical and archive rows the final backup's expiry, plus a migration for projects already deleted.

    Encryption and keys#

    GenerateKey refuses to replace the platform key, which would orphan every backup. ConfirmKey wants the whole key pasted back, compared in constant time. The control plane unwraps a file key and sends the agent only that.

    The writer holds a full buffer back until more data arrives, so the final chunk is always the one Close writes, and the reader reads a chunk ahead to know which one must carry the final flag (Reader.Read). A cut at a chunk boundary fails on the flag. Each chunk is authenticated before its plaintext is passed on.

    A project key lets an organisation restore with standard tools (V2 §6.3). pgpstream writes plain OpenPGP: SEIPD v1 with MDC, AES-256, no compression. Its integrity check comes at the end, so the agent's restore reports a decryption error even after pg_restore succeeded (doRestore), and the operation rolls back. The OpenPGP keys are never stored: deriveKey feeds 4 KiB of HKDF output as the random source to openpgp.NewEntity, with a fixed creation time, for PGPKey (WAL-G, from the platform key) and ProjectPGPKey. EnableProjectKey creates or rotates a project key (old backups keep theirs); ProjectKeyFile gives a README and the armored private key, behind re-authentication and the audit log.

    Risk

    Nothing pins the derived OpenPGP keys. The key is whatever go-crypto builds from the seeded reader. A version that reads its random source differently, or changes a default in the key packet, derives a different key from the same secret, and every WAL-G archive and .dump.gpg object becomes unreadable through Xenibase, unnoticed until a restore. TestPGPKeyDeterministicAndUsable only compares two derivations in one build. Fix: a golden test that derives from a fixed secret and checks the fingerprint against a constant.

    Where backups go#

    PlacementFor picks the project's chosen target (a platform target or its organisation's own bucket), else its region's, else the platform default; a data-residency project only targets marked as in its region. SaveTarget saves a target only after a live write, read, list and delete, and DeleteTarget refuses one in use, or holding backups unless the loss is accepted.

    • Cross-region copies (V3 §2.5): CopyRegionBackups copies logical backups on platform targets to the region's copy target under the same key, checking the SHA-256 while streaming and again by reading the copy back. Residency projects copy only within their region, and SetResidency deletes copies outside it.
    • Switching target (V2 §6.2): SwitchTarget is immediate on a shared project. A dedicated project gets a storage_switch that points WAL-G at a new prefix, restarts the instance and takes a base backup (reconfigureArchive). copy_existing copies logical backups as twin rows verified by checksum (copyBackup); delete_originals then removes the originals.
    Risk

    Two targets at one location turn "copy, then delete the original" into "delete the only copy". Only target names are unique; two rows may name the same endpoint, bucket and prefix (and backups and backups/ give the same keys, Target.Key). Copies keep the object key, so switching between two such targets with delete_originals overwrites each object with itself, passes the read-back, and deleteOriginal deletes it, while every row still says succeeded. Turning residency on does the same through deleteCopy when a region's copy target is its primary. Fix: refuse a target whose endpoint, bucket and normalised prefix match another's, and refuse a copy or copy deletion whose source and destination resolve to the same place.

    Restores#

    POST /backups/{id}/restore needs BackupCreate on the backup's organisation. backup.Restore accepts any succeeded project backup; a base backup becomes a recovery to the moment it finished. RestoreInto has the agent pipe the decrypted object into pg_restore --no-owner --no-acl --role=<owner> --single-transaction --exit-on-error as the project's console login, never the superuser, because a dump's functions run during a restore (restoreArgs). Webhook triggers are reset from Xenibase's configuration with an empty outbox (V2 §9.3).

    • Into a new project (the default): a project in the source's organisation, region and residency, created as a restore operation; the source may already be deleted. runRestore recreates the database empty on a retry, restores and publishes. Failure rolls the project back.
    • In place: the project admin role, re-authentication and the project's exact name. The project moves to restoring; a safety backup is taken (once per operation), the pooler KILLs clients while new ones wait, the database is recreated and restored, members' grants are re-applied (SyncMemberRoles), and the route resumes.

    GET /backups/{id}/download (ProjectExport, two at a time per organisation) streams a logical backup decrypted in xenibase-server as a plain pg_dump archive (Export).

    Risk

    A decryption that fails half-way can look like a complete file. Once DownloadBackup has written a byte, an error is only logged and the handler returns, so Go ends the chunked response cleanly and the client reports a good download of a truncated archive. The runbook's xenibase-agent decrypt … > metadata.dump has the same gap: it promises a damaged object "fails without writing a partial file", which holds only with --out (decrypt removes its own file), and the next line restores whatever was written. Fix: panic(http.ErrAbortHandler) on a mid-stream error, and use --out with && in the runbook.

    The weekly restore test#

    runRestoreTest picks a random active, unarchived project with a succeeded logical backup, and verifyRestore restores its newest logical, final or safety backup into xenibase_restore_test_<hex> on the project's own instance, owned by its owner and restored as its console login. It counts every table (TableCounts) and drops the database. Runs alternate between a backup's primary object and its cross-region copy. A platform admin can run one now; a failure raises the critical restore_test_failed alert.

    Spec and code differ

    V1 §6.5's weekly job restores "the latest backup of a random project"; it only ever restores logical backups, so dedicated projects' base backups and WAL are never restored by any check. §6.4's "WAL archive lag" is neither measured nor shown.

    Risk

    A dedicated project's archive can be broken for months unnoticed. Only the flush before a recovery reads pg_stat_archiver, and no alert covers archiving. If wal-push starts failing (rotated credentials, a full bucket), base backups may still succeed while WAL piles up in pg_wal until the volume fills and the instance stops, and recovery past the failure is impossible. The first test is the customer's restore. Fix: alert on a rising failed_count or a stale last_archived_time, and let the restore test run a point-in-time recovery of a random dedicated project into a scratch instance.

    WAL-G and point-in-time recovery#

    A dedicated instance runs with archive_command='wal-g wal-push %p' and archive_timeout=60; walg.Env supplies the prefix, credentials, zstd and the derived key.     Imports and Supabase migrations#

    An import (V1 §6.8) copies schemas from someone else's Postgres into a new shared project. The source is the tenant's, so Xenibase must neither change it nor trust it.

    1. Preflight. preflight reports the version (refusing 19 and later), size, schemas, extensions against the shared allow-list, and grants and policies naming anon, authenticated or service_role. On a Supabase source the managed schemas (SupabaseManagedSchemas) are left unselected.
    2. Create. Import repeats the preflight and creates the project. The URL is kept in memory for 12 hours under a random reference (Ephemeral); only the reference and a redacted URL reach the operation.
    3. Prepare. prepareImportTarget creates what pg_dump -n leaves out: the allowed extensions in their source schema, NOLOGIN stand-ins for the Supabase roles, and auth.uid(), auth.role() and auth.jwt() when auth is not imported.
    4. Copy. The agent pipes pg_dump --no-owner --no-acl --schema=… into pg_restore --role=<owner> as the console login, continuing past failing objects and listing up to 40 (agentsvc.copy).
    5. Verify. verifyImport compares row counts and sequences in the chosen schemas. A missing table fails and rolls back; a differing count is a warning, as the source may be live (decisions M3 #14).

    Every source connection goes through pgsource.Config, which refuses a URL naming any host but its authority (host=, several hosts, a socket directory) and pins Xenibase's connection and the agent's pg_dump to the address the guard approved:

    The guard is outbound.CheckSource: public addresses unless the platform admin allow-listed the host for the organisation; never loopback, link-local, metadata, or a node's or instance's address; and for imports never XENIBASE_OUTBOUND_BLOCK or the cloud private network, allow-listed or not (SourceInternal). The operation checks and pins again when it starts. Xenibase's own sessions run SET default_transaction_read_only = on (ReadOnly), a SET because PgBouncer refuses unknown startup parameters; pg_dump reads in its own read-only snapshot. The Supabase helper (V4 §9, MigrateSupabase) then rewrites policies, copies auth.users with their bcrypt hashes and copies storage, through the same pgsource path and the same in-memory credentials.

    Risk

    With more than one server, imports fail at random. The URL is only in the memory of the server that took the request, but any server may claim the operation. Elsewhere runImport fails permanently ("xenibase-server restarted?") and rolls back; with two servers about half of imports and Supabase steps end so. Decisions M3 #12 accepts only the restart case. Fix: keep the URL sealed in params.secrets until the operation ends, as rotations do, or claim import kinds only on the queuing server.

    Risk

    Verification reads every table in the source, not only the chosen schemas. verifyImport counts the whole source and filters afterwards, so a login that may read only the imported schema hits "permission denied" on another table and the import rolls back after an hours-long copy. pgverify.Compare has the same shape. Fix: filter by schema in TableCounts's catalogue query.

    Risk

    Supabase migrations get a weaker address check than imports. services.sourceGuard uses the general outbound service, built with no Internal ranges (main.go). A host allow-listed for an organisation, whose DNS the tenant controls, can then resolve into the cloud private network and reach platform services not registered as nodes, which an import refuses. Fix: give it the backup service's Internal list.

    Spec and code differ

    V1 §6.8 has the operator choose a tier for an import. ImportRequest has none: imports always create a shared project, to be promoted afterwards.

    Metadata self-backups and disaster recovery#

    runMetadataBackup has any agent dump XENIBASE_METADATA_BACKUP_URL (default XENIBASE_DATABASE_URL, off to disable) to metadata/ on the default target, in the Xenibase format, nightly at the window's start (V1 §11.6). A failure is a critical alert. docs/disaster-recovery.md rebuilds a lost control node from three things kept off it (the .env with the master key, the backup key file, the bucket credentials): start the metadata database, decrypt the newest metadata/ object with xenibase-agent decrypt, pg_restore --clean it, start everything (the pooler configuration is rendered again), re-register agents whose state was lost, and restore lost databases into new projects. Project-key backups also restore with gpg, pg_restore and wal-g alone.

    Note

    The metadata is as old as its last dump: projects, targets and project keys created since are gone from it, though their objects remain in the bucket. A project key exists only sealed in the metadata and in a download its admin may never have made, so such a key, or every project key once the master key is lost, leaves its .dump.gpg backups unreadable; the platform key file does not open them.

    Alerts#

    internal/alerts raises backup_failed (critical) when the latest backup, base backup or metadata backup failed, restore_test_failed (critical), and backup_overdue (warning) for an active project older than 26 hours with no backup in 26 hours (OverdueBackups). Any of them turns the public status page's Backups component to degraded (States).

    Risk

    "Backup overdue" fires for projects the scheduler skips on purpose.     Database branches

    Branches as shared-tier copies of a parent: from a backup or live, schema only, reset, detach and expiry.

    A branch is a project that starts as a copy of another project, its parent, and can be refilled from it later. Typical uses are a database per pull request in CI, trying a migration, or debugging against real data (V2 §8). internal/branching holds the whole lifecycle. It reuses provisioning and restores from the control plane and backups, and adds very little of its own.

    • branching579 linesCreates, resets, detaches, and expires database branches (V2 §8): shared-tier copies of a parent project, from its latest backup or live, that keep their URL and credentials across resets and delete themselves after a TTL.

    What a branch is#

    A branch is an ordinary row in projects with its own database, owner role, app password and pooler route. Seven columns, added by migration 00015, make it a branch:

    ColumnMeaning
    parent_project_idThe parent. Not null means "is a branch". A foreign key to projects(id) only, not to (id, org_id).
    branch_sourcebackup or live: where it was filled from, and the default for a reset.
    branch_schema_onlyWhether it holds the parent's schema without rows. Fixed at creation. A reset keeps it.
    expires_at, expiry_notified_atWhen the sweep deletes it (null: never), and whether the 24-hour warning was sent.
    branch_backupsWhether it takes nightly backups and a final backup on delete. Off by default.
    sensitive_data"Contains sensitive data" (V2 §8.5). Shared with ordinary projects. A branch copies its parent's.

    How a branch relates to its parent:

    • One level deep. Resolve refuses a parent that is itself a branch.
    • Same organisation, same region, always the shared tier, on the organisation's own shared cluster if it has one, even when the parent is dedicated. It runs the parent's Postgres major (Create reads the parent's instance).
    • Members are a snapshot. The transaction that inserts the branch copies the parent's project members and roles (CopyProjectMembers). Its creator becomes its admin, unless they are an organisation owner or admin, who are admins of every project anyway. Later changes to the parent's members do not reach the branch.
    • Its own credentials. The branch gets a new opaque database name, owner role and app password, shown once in the create response. A reset keeps all of them, and members' personal logins, so a DATABASE_URL in CI or a .env keeps working (TestBranchResetKeepsURL).
    • Not copied: webhooks and scheduled jobs. The xenibase schema that comes with the data is dropped or rebuilt by ResetWebhooks (see Life of a project).
    • Not promotable. Promotion refuses a branch (dedicated.Promote). Detach it first.

    Creating a branch#

    POST /api/v1/projects/{id}/branches (CreateBranch), or xenibase branch create, whose --replace deletes a branch of the same name first and whose --env prints DATABASE_URL lines for CI.

    1. Resolve. Resolve checks the request against the parent and fills the defaults. The parent must be active. A live copy needs a parent that is not asleep (a sleeping Free project refuses connections). A backup copy needs a succeeded logical backup. The TTL defaults to 7 days and must be 1 hour to 30 days, or 0 for none.
    2. Quotas. The handler checks CheckCreateBranch with the parent's latest measured size, then operations in flight (see limits).
    3. Insert and queue. Create calls provision.Create with a BranchSpec. One transaction inserts the project, sets the branch columns, copies the members, adds the creator and enqueues branch_create. The parent and options go into the operation's params as {"branch": {...}}, next to the sealed password.
    4. Backend services. If the parent has them, PrepareBranch makes the branch's API row, ref and keys now, so the response can return them once (below).
    5. Fill. The worker runs runCreate: Prepare (role, database, hardening). On a second attempt, RecreateDatabase first, to start from an empty database. Then fill, then Publish (member logins, pooler route, smoke test, active), then EnableBranch.

    fill first runs copyExtensions. It reads the parent's extensions, and creates those in public on the branch as the admin, because the restore runs as the owner, who may not. Extensions in a schema of their own come with the dump. Then it copies from one of two sources:

    SourceHowCost to the parent

    liveThe agent's /v1/copy: pg_dump of the parent as the instance admin, with --no-owner and --no-acl, piped into pg_restore as the owner on the branch (see agent commands).A full dump, now.

    Reset#

    POST /api/v1/projects/{id}/reset on the branch (ResetBranch). Reset queues branch_reset through EnqueueExclusiveTx: the branch must be active or error with nothing else in flight (one operation per project), and it moves to restoring. The source is the request's, or the branch's own. A backup source needs a backup of the parent. Schema only is always the branch's own.

    PgBouncer's KILL drops the branch's client and server connections, and new clients wait until RESUME instead of failing. RecreateDatabase drops the database WITH (FORCE) and makes it again with the same name and owner. The owner's SCRAM verifier lives on the role, which is not dropped, so the app password still works. SyncMemberRoles puts members' grants back. If both attempts fail, failReset resumes the route and leaves the branch in error, its data possibly partial. Another reset or a delete fixes it.

    Risk

    A reset re-reads the parent without asking whether the caller may still read it. The route checks project.branch on the branch only, and fill reads the parent by ID. Two ways this hands out data that was meant to be withdrawn. First, membership: removing someone from the parent (RemoveProjectMember) deletes only the parent's row, so a developer copied onto a branch, or its creator, can keep calling reset with "source": "live" and get a fresh dump of the parent's current data. Second, sensitivity: the full-data rule is checked only in Resolve. A full branch of a parent marked sensitive afterwards keeps refilling with every row, for any developer on the branch. Re-checking the caller's project.branch (and, for a full copy of a sensitive parent, the admin role) on the parent in Reset would close both.

    Detach, expiry and backups#

    • Detach (POST /api/v1/projects/{id}/detach, Detach) is one statement, DetachBranch: it clears the parent, the expiry, the warning and branch_backups. The project keeps its database, credentials, members and API. branch_source and branch_schema_only stay on the row as history.
    • Expiry moves with PATCH /api/v1/projects/{id}/settings (expires_at, or no_expiry), which needs project.settings, the admin role. SetExpiry accepts a time in the next 30 days and re-arms the warning. branch_backups goes through the same route (SetBackups).
    • The sweep, Sweep, deletes up to 100 expired branches per pass through the ordinary provision.Delete, with no final backup unless the branch takes backups. It then emails each creator once when less than 24 hours remain. Without SMTP the warning counts as sent. A conflict (another server got there first) is ignored, so several servers can sweep at once.
    Spec and code differ

    V2 §8.4 calls for "an hourly job". cmd/server runs the sweep every 10 minutes (branchSvc.Run), as docs/decisions.md (M13 #4) records, though the package and the comment above that line still say hourly.

    Risk

    Detach makes a standalone project without the checks a new project gets. Detach needs only project.branch, the developer role, and calls neither CheckCreateProject nor org.create_project. Branches don't count toward the projects quota (CountOrgProjects), and detaching frees the branch's slot, so create-then-detach repeats without limit. It gives an organisation as many permanent projects as it likes, and it lets a developer in an organisation whose members may not create projects own one as its admin. Restore-into-new-project, by contrast, checks CheckCreateProject. Detach also takes no lock and ignores the status, so a branch detached mid-reset is overwritten from its former parent once the reset continues. Running detach through EnqueueExclusive-style locking with CheckCreateProject would match the other paths.

    Risk

    The sweep deletes from a list it read earlier. ExpiredBranches runs once per pass, and provision.Delete locks the row but does not look at expires_at or parent_project_id again. A branch extended or detached between the query and its turn in the loop is deleted anyway, and without a final backup unless it took backups, because the sweep passes the skipFinalBackup it worked out from the row it read earlier. The window is short, a pass of up to 100 deletes, but it is exactly when a user acts to save a branch at the last minute. A check inside the delete transaction that the row is still an expired branch would close it.

    A transfer breaks the rule that a branch and its parent share an organisation. orgs.Transfer refuses neither a parent with live branches nor a branch, and the foreign key on parent_project_id does not include org_id.     Branches with backend services of their own#

    When the parent has backend services (V4.1 §9.5), the branch gets an API of its own, never the parent's, so neither's tokens work on the other. cmd/server sets branching.Service.API to the services service. The work is split in two because the keys must be in the create response but the API can only be turned on once the copy is in:

    1. PrepareBranch, in the request, in one transaction: the branch's services row and a new ref, the parent's settings (exposed schemas, public tables, CORS, auth configuration and templates) without their secrets (providers_enc: SMTP, SMS, OAuth, captcha and hook secrets), and a publishable and a secret key. A failure here is logged, and the branch is still made, without an API.
    2. EnableBranch, at the end of runCreate and of every reset: purgeSessions deletes the sessions, refresh tokens, flow states, one-time codes and MFA challenges that came with the data, so a parent's refresh token cannot be spent on the branch. Then the request roles, xb_* schemas and a new signing key. The parent's app users and their password hashes come with the data, so they sign in again on the branch with the same passwords.
    3. With copy_files on create only, EnableBranch queues copy_branch_files as a background operation. runCopyBranchFiles reads the object versions the branch's xb_storage.objects names, which came with the data copy, and copies each one from the parent's prefix to the branch's inside the store.

    TestBranchServices covers the keys, the separate signing key, the dropped sessions and the file copy.

    Risk

    Any copy error counts as "not found in the parent", and the operation succeeds. storage.Client.Copy returns ErrNotFound for a missing object and a wrapped error for anything else. The loop does not tell them apart. Throttling, a network error, an object over S3's 5 GB single-copy limit, or the operation's context ending each skip a file. The job then reports success with a "not found" count, and its three attempts are never used. The branch's rows point at files it does not have. Counting only ErrNotFound as missing and returning other errors would let the retry finish the copy.

    Risk

    A reset brings the parent's file rows but not their files, and strands the branch's own. runReset calls EnableBranch with copyFiles false. The refilled xb_storage.objects names the parent's current versions, so files the parent added since the branch was created are missing on the branch. The objects already under the branch's prefix, copies and the branch's own uploads, are no longer named by any row. The garbage list that would delete them lived in the dropped database, so the storage sweep, which meters rows, neither bills nor removes them until the branch is deleted. Copying files again after a reset, when the branch was created with them, would fix both.

    Resizing#

    PlanResize refuses a smaller disk and checks that the difference fits on every node holding a member. runResize writes the size onto the row and recreates. Without HA the poolers freeze the routes (Freeze: PAUSE on the transaction pooler, KILL on the session pooler) around one recreate, then replicas follow one at a time. With HA the standby and replicas go first, the project switches over, then the old primary is recreated, so writes pause only for the switchover. A disk change alone needs no restart. When the node cannot hold the new size, a project without HA or replicas is moved into an instance of the new size on another node; with them the resize is refused. failResize puts the old size back on the row and, without HA, recreates at it.

    Risk

    A resized instance cannot be restored or detached. A size that matches no profile is recorded as profile custom (profileName). A point-in-time restore and a replica detach copy the source's profile name into the new project, and Validate looks it up in Profiles, which has no custom. Every restore of a project resized to a non-profile size fails at once with unknown profile "custom" (confirmed with a scratch test), and restore is the path used in an incident. Pass the source's CPUs and memory as a size, as Move does.

    The maintenance window#

    Agents report each instance's running release and its image's, checked hourly. Every 5 minutes MaintenanceSweep, inside the window (default Sunday 02:00 to 06:00 UTC), upgrades at most one instance that is behind, dedicated first, skipping any with a project not active or with an operation pending (InstanceBusy). MinorUpgrade freezes the poolers for every project on it, recreates, resumes, and records the pause. An HA instance is switched over instead (minorUpgradeHA), and only inside maintenance announced to it 72 hours ahead; the sweep drafts that announcement for the first window at least 96 hours away, for an admin to confirm.

    Risk

    A maintenance restart is not an operation, so nothing keeps other work off the instance. The sweep checks InstanceBusy once and never takes the project's exclusive lock. For an HA instance minorUpgradeHA recreates the standby and waits for it to stream (up to an hour), and meanwhile the owner can queue ha_disable, which removes the standby it is about to switch to, or a resize, which runs its own minorUpgradeHA on the same members. The loop also runs on every xenibase-server without a lock, so two servers can restart instances at once, or the same one twice. Run minor upgrades through EnqueueExclusive as operations, or take a per-instance advisory lock.

    High availability#

    An HA project runs two Patroni members on nodes in different failure domains, with Patroni's state in its region's three-member etcd cluster. Patroni decides who leads; xenibase-server follows the leader and moves the pooler route.

    The etcd cluster and its CA#

    Each region has its own cluster, so its failover depends only on its own machines (V3.1 §3.1). ha.Setup takes three distinct healthy nodes of one region in three failure domains, refuses while any etcd setup or replacement is pending anywhere, and has each agent run etcd:v3.6.5 as a new cluster with a random token. Health is refreshed every 30 seconds; Ready, checked before HA or a replica is added, wants three members with a majority healthy.

    The etcd CA is separate from the agent CA, so neither's certificates pass for the other's. LoadCA creates it once under an advisory lock (P-256, 20 years, key sealed with the master key). Members get 5-year server-and-client certificates, and each HA instance a client certificate patroni:<instance>. Etcd checks client certificates on both ports but has no per-cluster authorisation: every Patroni scope sits under /xenibase/ and any certificate from the CA can write any key. Isolation between projects rests on tenants never getting a shell or superuser in a member container, whose environment holds the key.

    Replace swaps a member: a dead one is removed first so the other two keep a quorum, a live one (a drained node) only after the new one joins. MoveToRegionEtcd moves a project whose state is still in the home region's cluster: it removes the standby, restarts the leader on the new cluster under a pooler pause, and builds a new standby, so the project has none until the end.

    Patroni promotes the standby when the leader's 20-second lease expires and the standby is under 1 MB behind. The route is the server's job: RunHAWatcher polls every instance under Patroni once a second, and watchOne decides:

    Spec and code differ

    V3 §2.2 fences with "Patroni's watchdog plus the leader lease". The spec also puts etcd on the control node and moves archiving with Patroni callbacks; the code runs a cluster per region on tenant nodes and needs no callbacks, as Postgres archives only on a primary.

    Risk

    The watcher pauses a healthy project whenever the control plane loses sight of its primary. "No leader" includes the leader's REST API not answering xenibase-server within 2 seconds, twice (memberUp). A fault between the server and one node freezes every HA project led there, although Patroni, etcd and the poolers are fine, until the server sees the leader again or PgBouncer's wait timeout fails the clients. With two servers on one metadata database it is worse: the watcher has no lock and its paused flag and switchover mutex are per process, so one server's partial view pauses the poolers that only it will resume, and the other records a "failover" for the first's switchover. Pause only when Patroni agrees (the other members stop listing the leader too), and run the watcher on one server through an advisory lock.

    Switchover and synchronous replication#

    switchOver holds the instance's watcher lock, picks the least-lagging streaming standby that is not a replica (with synchronous replication, the synchronous standby, waiting up to 30 seconds for one), freezes the poolers, calls Patroni's /switchover, waits for the candidate to lead, routes and resumes. The old primary stops cleanly first, so nothing is lost; about 2 seconds of pause. Synchronous replication patches synchronous_mode in Patroni's configuration; without it a failover can lose up to 1 MB of acknowledged commits.

    The SLA probes#

    HA projects carry 99.9% monthly availability of the pooler endpoint. ensureProbe creates a login <db>_sla with only CONNECT and a limit of 5 connections. Every minute SLATick connects through each project's pooled URL and runs SELECT 1 within five seconds; with a status page it also pushes the targets to xenibase-status and pulls its per-minute results, both signed. A minute is unavailable when every vantage point that probed in it failed. Minutes while the project is not active or its organisation is suspended are excluded, as are minutes inside maintenance announced to the project 72 hours before them (ApplyMaintenanceExclusions, over the last six hours on every tick).

    Spec and code differ

    V3 §2.7 counts a minute unavailable "if the probe fails from two vantage points". The code needs only every vantage point that probed to fail, so without a status page one failed internal probe makes a minute unavailable (decision M19 #11).

    Failure domains and regions#

    A failure domain is what fails with a node: a rack, a host, a power feed. Separated decides whether two nodes can fail together. A recorded domain wins and a node without one counts as alone; otherwise two Hetzner servers are apart only inside the same spread placement group, and a node with neither is its own domain. The rule binds an HA pair (standbyNode refuses), a region's etcd members (setup and replacement refuse) and a region's pooler pair (a warning); read replicas never take over, so they are exempt. Changing a domain moves nothing: faildomain.Check lists the groups that now break it, for a banner and a failure_domain alert.

    A region groups nodes, a pooler pair with its own hostname (pooler hosts), a storage target and a copy target. Placement, standbys, promotions and demotions stay in the project's region. A hidden region's launch checks (Readiness) block opening it without a healthy node, with etcd that is not three members in three domains, or with a pair sharing a domain.

    Read replicas#

    A read replica is a member tagged nofailover and nosync: it streams from whichever member leads, is never promoted and never holds up a commit. A project may have two. runCreateReplica first puts a plain instance under Patroni (the same restart as HA), then builds the member from the newest base backup on a healthy node holding no member, in the project's region or, without data residency, another. Every replica of an instance publishes on one port, 20000 + fnv32(instance) % 10000, because PgBouncer takes one port for a host list. Moves, demotions, major upgrades and the regional etcd move are refused while a project has replicas.

    The pooler renders <db>_ro for such a project: the same logins, each server connection started with SET default_transaction_read_only = on, balanced across the replicas in rotation in the pooler's region, else all in rotation, else the primary (replicaHosts). Read-only is a session default the client can change, not a permission. On every watcher poll checkReplicas measures each replica's lag as how long ago the leader was first seen past the position the replica has not replayed, so a replica that stops replaying lags even while the leader is idle. Over 10 seconds, or not streaming, takes it out of rotation; under half that brings it back.

    Per-replica standby settings#

    Each replica has its own hot_standby_feedback and one delay for both max_standby_streaming_delay and max_standby_archive_delay; the primary and standbys keep Postgres's defaults.

    They reach the replica twice: in memberSpec's local parameters, so a recreated container starts with them, and through UpdateReplicaSettings, which stores them and, on a streaming replica, runs ALTER SYSTEM and a reload and reads back what the server runs with. The values can only be on, off or <n>s, checked before quoting. The watcher re-confirms them every 5 minutes (30 seconds after a failure), which also covers a replica rebuilt from a base backup with the primary's postgresql.auto.conf.

    Detaching a replica#

    DetachReplica turns a streaming replica into a new dedicated project while the source runs on. The new instance takes the member's ID, so container and volume keep their names. ensureDetached deletes the member row, recreates the container as a plain instance with the source's superuser, promotes it with pg_promote, resets primary_conninfo, the slot and the standby settings, and renames the database and owner as a restore does. A failure removes the new project and the replica.

    Moves#

    A node move (logical_move), a major upgrade (Postgres versions and upgrades), a promotion and a demotion all copy through one engine. A node move to another region's node is a region move. Each holds the project in a non-active status, which keeps other operations off it, for two attempts. Move refuses HA, replicas, the same node, and a region the project's data residency or a hidden region's early access forbids. A shared project goes into the target node's shared cluster of the same major; a dedicated one gets a new instance of the same size.

    The copy#

    runMove first checks where the project is: already on the target means the cutover committed and only finishMove is left. Otherwise it creates a new target instance, and prepareTarget creates the database and every login with the same SCRAM verifiers (owner, members, integrator roles, roles the owner made, NOLOGIN stand-ins for roles grants name); a second attempt first clears the first's replication objects and recreates the database. copyForMove then:

    1. Preflight (Preflight): wal_level=logical, a free slot and WAL sender, a target major no older, no large objects or unlogged tables, the extensions available on the target. Any blocker falls back to dump and restore inside the freeze, recorded as fallback_reason.
    2. Schema: pg_dump --schema-only | pg_restore through the target node's agent, owners kept.
    3. Replication (Setup): REPLICA IDENTITY FULL on tables without a primary key, a marker table on both sides, an event trigger refusing tenants' DDL, a REPLICATION login xenibase_move_<op> (agents admit it only from XENIBASE_AGENT_MOVE_ALLOW), a publication FOR ALL TABLES, and a subscription with disable_on_error and, at the same major, binary.
    4. Catch up (WaitCaughtUp): every table copied, then under 1 MB behind for 30 seconds.
    5. Freeze (freeze): owner and member logins NOLOGIN, the poolers frozen, those roles' and the console's sessions ended.
    6. Cutover, within 30 seconds: the marker below, then each used sequence set to the source's value plus 1,000 steps, then exact row counts on up to 20 tables of at most 16 MB.

    A dump-mode move copies with pg_dump | pg_restore inside the freeze and compares every table and sequence, so its pause grows with size. A logical move's does not: 115 ms at 1 GB and 135 ms at 3 GB under continuous commits, none lost (TestMoveUnderLoad).

    Spec and code differ

    Decision M18 #5 says missing extensions on the target block the move. In the code they are one more preflight blocker and every caller allows the dump fallback, so the move freezes writes, fails at CREATE EXTENSION and rolls back: a pause and a failed move instead of a refusal.

    The switch, and how the URL stays the same#

    MoveCutOver points the project at the target. Nothing in a connection string names an instance (the pooler host, database name, role and password all stay), so once finishMove re-renders the route and resumes, the held clients carry on against the target. A region move changes the hostname to the new region's, and keeps the old region in forward_region with forward_until 30 days ahead; while that is in the future the pooler sync also renders the project into the old region's configuration (served), so the old hostname reaches the new instance until the first sync after it.

    finishMove is idempotent and is also the rollback after the commit. It sets the project active, keeps the source for 48 hours (a shared copy read-only, a dedicated instance stopped) for DropRetired to remove, removes the replication objects on both sides in a deferred cleanupMove, and takes the target's first base backup, where its point-in-time window starts. Before the commit, failMove removes the replication objects, unfreezes the source, sets the project active, and destroys the new instance or drops the partial copy.

    Risk

    A retry after the freeze copies everything again with the source still frozen. Only the rollback, after the last attempt, unfreezes. A transient error between freeze and the cutover commit, or a crash, lost lease or deploy in that window, starts attempt two with the logins NOLOGIN and the poolers paused; it rebuilds the target and repeats the initial copy and catch-up before freezing again, and the project is unreachable throughout. In logical mode the window is seconds; in dump mode it is the whole copy, so a transient pgverify.Compare error or a deploy during a long promotion doubles the outage. Unfreeze at the start of an attempt that finds the project not yet cut over.

    Risk

    A rollback that cannot reach the source leaves the project frozen and stuck. unfreeze opens a connection to the source first; if that fails (often why the move failed) it returns before resuming the poolers, and failMove before setting the project active. Runner.fail logs "rollback incomplete", marks the operation failed and never retries. When the source returns the project is still moving (no operation can be queued), its logins NOLOGIN and PgBouncer still paused: down until someone repairs it by hand. Promotion and demotion share this. Resume the poolers regardless of the source connection, and retry incomplete rollbacks from a sweep.

    Risk

    Replication objects a rollback could not remove stay for ever. cleanupMove is best effort, logical.Cleanup skips the source when it cannot open it, and nothing else looks for xenibase_move_ objects. The orphaned slot has no consumer and no instance sets max_slot_wal_keep_size, so it keeps WAL until the disk fills, which on a shared cluster stops every tenant there; the event trigger keeps refusing the tenant's DDL. Sweep inactive xenibase_move_* slots, publications, triggers and logins with no running operation, and cap slot WAL.

    Risk

    A region move leaves the WAL archive in the old region. The target's archive is placed once, when it first runs, from the project as it is before the cutover, so regionTarget picks the old region's bucket, and the moved project's WAL and base backups stay there for the instance's life. Residency is not breached (residency projects cannot leave, and turning residency on is refused while the archive is elsewhere), but the archive outlives the move in a region the project left. Place the target's archive by its node's region, or queue a storage switch after a region move.

    Promotion and demotion#

    Promotion (runPromote) moves a shared project, not a branch, onto a new dedicated instance in its region. The wizard's estimate is 5 seconds for a logical copy, or 5 seconds plus the size at 40 MiB/s for dump and restore. The target is the project as it will be: the same role, verifier and database name, dedicated limits, timeouts kept, the console read-only. CutOverProject switches instance, tier and settings in one statement, the shared copy is kept read-only for 48 hours, and the instance takes its first base backup.

    Demotion refuses HA and replicas, and preflight runs seven checks: size against the shared storage limits, extensions outside the shared allow-list, roles beyond the project's own (integrator roles block), the allowance released, last week's peak connections (a warning), settings the copy drops (a warning), and a shared cluster of the same major in the region with room for the size plus 20%. They run at preflight, at queue time and again in runDemote. After the cutover finishDemotion takes a logical backup (point-in-time recovery ends) and stops the dedicated instance, destroyed 48 hours later; its WAL-G archive stays for the base backups still under it.

    Spec and code differ

    V1 §6.6 freezes with ALLOW_CONNECTIONS false and verifies every table's rows. The code uses NOLOGIN, which leaves pg_dump working (decision M5 #2), and a logical copy counts only small tables, trusting the marker (M18 #3). V3 §2.3 keeps every source read-only for 48 hours; a dedicated source is stopped instead.

    Postgres versions and upgrades

    Which Postgres majors are offered, their life from preview to retirement, minor releases in the maintenance window, and major upgrades.

    Checked against c67d14d · 2026-10-29No changes to its code since

    Xenibase runs more than one Postgres major at a time. Each major has a place in its life, kept in one table, and each instance runs an image built for its major. Minor releases are a restart on the same data, done by a background sweep in a weekly window. A major upgrade is a move: the project's database is copied by logical replication into a new instance (or a shared cluster) of the newer major, and the route is switched.

    Which majors are offered#

    Two things decide whether a major can be used. The server is configured with the majors it has images for, XENIBASE_PG_VERSIONS, default 17,18 (config). The pg_versions table says where each major is in its life (00046_pg_versions.sql). The first time the server looks, ensureVersions inserts every configured major as supported with ON CONFLICT DO NOTHING, so an operator's statuses are never overwritten. A major dropped from the setting keeps its row and is listed as not installed. Versions joins the two and counts the live projects on each.

    The image is a template. The agent's XENIBASE_AGENT_PG_IMAGE defaults to xenibase-postgres:{major}-walg3.0.9, and ImageFor replaces {major} with the instance spec's PGVersion (18 when it is 0). One Dockerfile builds every major: PG_MAJOR picks the official postgres base image, and WAL-G (a pinned commit), Patroni (a pinned version) and hypopg are added on top. Two checks keep an instance on the major it asked for:

    • After start, checkMajor runs postgres -V in the container and refuses a different major. An image name without {major} serves one version only, and this is where that shows.
    • PGDATA is set per major inside the instance's named volume, /var/lib/postgresql/{major}/docker (pgdataFor). The 17 image declares /var/lib/postgresql/data as an anonymous volume, and data there was lost on a recreate (decision M18 #9).

    The agent is built on postgres:18, so its pg_dump is 18. A newer major needs the agent image rebuilt before dumps of it work.

    The lifecycle#

    A major is preview, supported, deprecated or retired. The table's check constraint requires a retires_at on a deprecated row. No job ever flips a deprecated major to retired: EffectiveStatus reports a deprecated major as retired once retires_at has passed, everywhere the status is read (decision V4.1-M5 #3).

    The four columns are the four uses CheckVersion is called with: ForProject, ForPreviewProject, ForUpgrade and ForCluster. A major not in XENIBASE_PG_VERSIONS is refused for every use, whatever its row says.

    ForCluster's comment says "any major not retired", but the code allows a retired one on purpose: a cluster for the projects still on it.

    Changing a status#

    A platform admin changes a major with PATCH /api/v1/admin/pg-versions/{major} (UpdatePgVersion, Admin → Platform → Postgres versions). One endpoint covers every transition, and pgversions.Change enforces the rules:

    • Preview only stays preview: no major goes back to it.
    • Supported from anything: promoting a preview, or taking a deprecation or retirement back.
    • Deprecated needs retires_at at least 180 days ahead (MinNotice). Deprecating again keeps deprecated_at and may move the date. Only a fresh deprecation sends the first notice.
    • Retired is refused while a live project runs on the major, unless its date has passed. Projects are never upgraded automatically: an upgrade can break an app.

    Notices to organisations#

    On a deprecation, and again 90, 30 and 7 days before retirement (Reminders), the owners and admins of every organisation with a project on the major get one email listing those projects, each with a link to its Upgrade card. Sweep runs hourly (pgVersionSvc.Run(bgCtx, time.Hour) in cmd/server) and sends only the nearest step reached, so a server that was down past a step sends one mail, not several. notify inserts a pg_version_notices row keyed on major, organisation and step before sending, and skips the organisation when the insert finds a row already there. That makes the sweep safe to run on two servers at once, but also at most once: a send that fails is not retried. Projects on a deprecated or retired major show a banner (VersionBanner), red once it is retired: "keeps running but is unsupported".

    How new projects pick a major#

    provision.Create resolves the requested major with CheckVersion, as ForPreviewProject when the create form's preview box was ticked. A request without a major gets DefaultVersion: the newest installed supported major, else the newest installed deprecated one, else an error. A shared project then needs a running shared cluster of that major in its region (PickSharedInstance filters on pg_version), and otherwise fails with no_capacity. A dedicated project gets an instance of that major. Preview and retired majors are refused with a message saying what to choose instead. A deprecated major is still open: decision V4.1-M5 #2 keeps it so, to avoid surprising owners in the middle of a migration.

    Every other way of making a project goes through the same Create with the source's major and no preview flag: a branch (branching.Create), a point-in-time recovery (backup.PITR) and a detached read replica. Moves, promotions and demotions do not create a project and do not check the status.

    Risk

    A project on a retired or preview major cannot be recovered to a point in time, branched, or have a replica detached. All three call provision.Create with the source's major as ForProject, and CheckVersion refuses a retired major ("new projects can't use it") and a preview one ("choose it on the create form"). Point-in-time recovery only ever restores into a new project, so the owner of a retired-major project who drops a table has no way to get it back from the WAL archive. The decisions say retired projects "keep running", but their safety net has gone. The same happens to every preview project from the day it is made. Fix: pass a use such as ForDerived from these three callers that allows any installed major of the source.

    Minor releases#

    A minor release (18.1 to 18.2) changes binaries only, so an upgrade is a restart of the same volume on a newer image. The operator rebuilds or pulls the image tags on each node (make pg-image, install.sh, or docker pull; docs/upgrade.md). Nothing in Xenibase pulls a newer image: the agent pulls a tag only when it is missing.

    1. Releases are read. Every five minutes MaintenanceSweep first calls CheckReleases for running instances not checked in the last hour. The agent's info reads PG_VERSION from two images: the one the container was created from (pg_release) and the one its tag names now (pg_release_available). Clusters the server was configured with, which have no agent, are skipped.
    2. Inside the window (DefaultWindow: Sunday 02:00 to 06:00 UTC, one platform-wide setting), InstancesBehind lists instances whose two releases differ, dedicated before shared. NewerRelease keeps those where the tag is a later minor of the same major.
    3. One instance per sweep. An instance with a project that is not active or has an operation queued or running is skipped (InstanceBusy). An HA instance waits for maintenance announced to its project at least 72 hours before (announced), unless XENIBASE_MAINTENANCE_REQUIRE_ANNOUNCEMENT=false. proposeMaintenance drafts that announcement for the first window at least the draft lead away. The first instance that passes is upgraded, and the sweep returns, whether that worked or not.
    4. The restart (MinorUpgrade). It records a minor_upgrades row, then freezes every project database on the instance at the poolers (Freeze: PAUSE on the transaction pooler, falling back to KILL after 10 seconds; KILL on the session pooler). It calls Recreate and then RESUME. Read replicas of an instance without HA follow one at a time, each out of rotation meanwhile (recreateReplicas).
    5. HA instances are switched over, not restarted (minorUpgradeHA): each standby and read replica is recreated and waited for, the leader is switched over to a standby, and the old leader is recreated as a standby. Writes pause only for the switchover.

    On the agent, a recreate stops the container (60 seconds, then a kill), removes it, and creates a new one from the tag on the same volume:

    A shared cluster is upgraded the same way, after every dedicated instance, with all its projects frozen together. The bundle's own cluster from compose.yaml has no agent and is left to the operator. An admin can also upgrade one instance at once, outside the window and past the announcement gate (MinorUpgradeNow, POST /api/v1/admin/instances/{instance_id}/minor-upgrade).

    Risk

    A failed minor upgrade leaves the instance down, and the sweep then forgets it. The agent removes the old container before it creates the new one. If the new one cannot be created, started or made ready (an image whose Postgres will not start on this data, a setting the new build refuses, the 10-minute readiness limit, or the server's request being cancelled part-way), nothing puts the old container back. The old image is no longer tagged, the instance row still says running, and nothing reconciles a missing container on an instance without HA. Within the hour the sweep retries the same instance every 5 minutes, freezing its projects each time, and because it returns after one attempt, no other instance is upgraded meanwhile. Once CheckReleases runs again, a missing container reports no release (so the instance drops out of InstancesBehind), and a crash-looping one reports the new release (so it counts as upgraded). Either way an outage looks like a finished upgrade. Fix: on the agent, keep the old container (renamed, stopped) until the new one is ready and restart it otherwise; on the server, mark the instance error, alert, and move on to the next one.

    Risk

    The minor-upgrade sweep takes no lock and keeps no state that survives a crash. RunMaintenance runs on every xenibase-server with no advisory lock, unlike the backup scheduler or the scheduled jobs. Two servers on one metadata database pick the same first instance in the same window. The agent's per-instance lock runs their two recreates one after the other, so the instance restarts twice, and the first server's RESUME lets clients in while the second recreate has the instance down. The upgrade is not an operation either. If the server stops between Freeze and Resume (a deploy in the maintenance window is the obvious case), PgBouncer keeps the databases paused, and nothing at start-up or in the pooler sync sends RESUME. If the recreate finished, the instance is no longer behind and is never visited again. Its clients wait until PgBouncer restarts or someone resumes by hand. Fix: take pg_try_advisory_lock for the sweep, and run each minor upgrade as an operation whose OnFail resumes (or resume at start-up for any minor_upgrades row without finished_at).

    Risk

    The image tag does not pin the Postgres release. FROM ${REGISTRY}postgres:${PG_MAJOR} takes whatever minor the official tag held when that node built or pulled it, so xenibase-postgres:18-walg3.0.9 names different releases on different nodes. Any recreate outside the window (a resize, a restart from the Instance panel, a new HA standby, a new machine pulling XENIBASE_CLOUD_PG_IMAGE) lands on whatever the tag holds there. And because the previous release is no longer tagged, a regression in a minor release cannot be undone by pointing back at the old image. Fix: build from postgres:18.x or a digest, tag with the full release (xenibase-postgres:18.2-walg3.0.9), and let the server choose the release per instance.

    Spec and code differ

    V3 §2.4 asks for "a weekly maintenance window per region". There is one window for the platform, stored under the maintenance_window setting and read in UTC. Decision M18 #11 deferred per-region windows to M25 (regions), and they have not arrived.

    Major upgrades of dedicated projects#

    A major upgrade is not pg_upgrade. It is a move (decision M18 #10): a new instance of the target major, of the same size, on the project's own node, filled by logical replication while the old one keeps serving, then a cutover of a few seconds. pg_upgrade would need both majors' binaries in one container and a longer outage. Members with the ProjectPromote permission run it from the project's settings (POST /api/v1/projects/{id}/upgrade/preflight, then …/upgrade), and the deprecation emails link there.

    The preflight#

    UpgradePreflight changes nothing and returns a list of checks, each ok, warning or blocked:

    CheckBlocks when
    targetHA is on, or the project has read replicas (both must be removed first and set up again after), or a shared project has no shared cluster of the target major in its region open to its organisation.
    versionThe target is not supported (ForUpgrade), or is not newer than the current major.
    extensionsThe target cannot create an extension the project uses (logical.Preflight).
    replicationNever. A warning when logical replication is not possible (large objects, unlogged tables, no free slot or WAL sender): the copy is then a pg_dump piped into pg_restore during the freeze, and writes pause for its whole length, estimated at 40 MB/s plus 5 seconds.

    The schema check is a real restore. For a dedicated project, scratchTrial starts a temporary instance of the target major on the project's node: 0.5 CPU, 512 MB, profile scratch, no WAL-G. schemaTrial then creates a short-lived non-superuser login and database there, creates the project's extensions as the superuser, and restores a schema-only, owner-less dump as that login with errors allowed. Each error becomes a blocked line. The temporary instance is destroyed and marked deleted when the check ends, success or not, and if that destroy fails the orphan reaper removes it later. A shared project's check runs the same restore in a scratch database on the target cluster. Upgrade runs the whole preflight again and refuses if anything is blocked.

    The upgrade#

    1. Queued. In the transaction that sets the project to upgrading and queues a major_upgrade operation (EnqueueExclusiveTx), Upgrade inserts the target instance row: same node, the source's CPU, memory and volume, max_connections at least the source's, its own WAL-G prefix. It refuses if the project moved since the check.
    2. The target starts. The operation runs runMove, the node move's handler (Kinds: two attempts, 48 hours), which calls Ensure for the new instance.
    3. Roles are restored before any data (prepareTarget): the database and owner with the same SCRAM verifier (Prepare), member logins and the read-only role (SyncMemberRoles), integrator roles with the owner's admin option (restoreIntegratorRoles), the roles the owner created with role management, with attributes, password and memberships (restoreOwnedRoles), and NOLOGIN stand-ins for any other role that a grant, policy or owner in the database names (placeholderRoles). So existing passwords keep working on the new major.
    4. The copy (copyForMove). The schema goes first (copyKeepingOwners). Then a publication FOR ALL TABLES and a subscription copy the rows, not in binary mode, since the majors differ. Schema changes are paused on the project until the move finishes. The source keeps serving reads and writes.
    5. The freeze and cutover. When the subscription has caught up, freeze makes the owner and member logins NOLOGIN, pauses the poolers and ends remaining sessions. logical.Cutover waits up to 30 seconds for the last commits, copies sequences with a margin of 1,000 and compares sampled tables. One transaction then points the project at the new instance and records the old one in retired_databases for 48 hours (RetainSource). The old base backups get an expiry instead of being deleted.
    6. Finishing (finishMove, idempotent). It syncs and resumes the poolers, sets the project active, removes the replication objects (a slot left behind would keep WAL forever), stops the old instance (retireSource), and takes the first base backup on the new one. Clients reconnect to the same URL.

    Downtime is the freeze: the decisions record 115 ms for a 1 GB move and 135 ms for 3 GB under continuous writes (M18 #12). In dump mode it is the whole copy. Rollback covers only the time before the cutover: failMove removes the replication objects, makes the source's logins LOGIN again, resumes the poolers, sets the project active and destroys the new instance. After the cutover the only failure handling is to run the finishing steps again.

    Risk

    The orphan reaper destroys an upgrade's target after five minutes. ListOrphanedInstances treats any dedicated instance older than 5 minutes that no live project points at as left over by a failed create, and ReapOrphans, every minute, destroys its container, volume and WAL-G prefix. A major upgrade's target is inserted when the operation is queued, but the project points at it only at the cutover, so any upgrade whose queue wait, schema copy and initial sync take more than five minutes loses its target part-way. It then fails and rolls back, and its WAL-G prefix is deleted with it. No data is lost before the cutover, but a large database can never be upgraded. A reaper pass that lists the target just before a cutover commits would destroy the live instance. A scratch test written for this page confirmed it: a target 6 minutes old, with its project upgrading on the source, is listed as an orphan. Node moves, promotions and resizes that move make their targets the same way. Fix: exclude instances that a queued or running operation names as its target_instance, and re-check under a lock before destroying.

    Risk

    After the cutover there is no way back to the old major, and recovering to a time before the upgrade fails. The old instance is kept stopped for 48 hours, but no API, UI or command starts it again or points the project back at it. Point-in-time recovery offers the old base backups, because PITRWindow and BaseBackupBefore select by project, not by instance. But backup.PITR creates the new project with the current instance's major, so restoring a 17 base backup starts a Postgres 18 container on 17 data, which refuses to start ("database files are incompatible with server"). An owner whose app breaks on the new major cannot restore to yesterday. Fix: take the major from the base backup's instance in PITR (and allow it whatever its status), or trim the window to backups of the current major and say so. Also add an admin action that re-points a project at its retained instance within the 48 hours.

    Risk

    The upgrade's target skips the capacity check and drops the PITR add-on. A node move builds its target through Validate, which checks that the size fits the node, and copies pitr_days. Upgrade does neither. On a full node the second instance of the same size is created anyway, and it shares the node's one disk, which already holds the source (Docker volumes have no hard size), for the copy and the 48 hours the source is kept. A disk that fills stops every instance on the node. And InsertInstance leaves pitr_days at its default of 7, so a project paying for 14 or 30 days of point-in-time recovery silently gets 7, and billing follows it. Fix: run the target through the same fits check (or move to another node when it does not fit, as a resize does), and copy pitr_days as Move does.

    Shared projects on an old major#

    A shared project lives on a cluster of its major, and nothing moves it off when the major is deprecated or retired. It keeps running there, and new shared clusters of a retired major may still be added for it. Its upgrade uses the same preflight and handler: the target is the least-loaded shared cluster of the newer major in its region that its organisation may use, the schema is tried in a scratch database there, and the move copies into that cluster (no new instance, so a rollback drops the partial copy instead). The old database is kept read-only (default_transaction_read_only) for 48 hours. A shared project needs such a cluster first: "no shared cluster runs Postgres 18 yet (Admin → Nodes → Add shared cluster)". V3 §2.4 asks for "one shared cluster per supported version in each region", and nothing creates one automatically.

    See Backups, restores and imports for what is archived before and after an upgrade, Dedicated instances, HA and moves for switchovers, and Connections: poolers and the edge for how the poolers hold clients during a freeze.

    Failure handling#

    What failsWhat happens
    A notice emailLogged. The pg_version_notices row is already written, so it is not sent again. A deprecation withdrawn and made again sends no new first notice either, since its rows remain.
    A retirement date passesNothing runs. Every read sees the major as retired from that moment.
    A project on the instance is busyThe instance waits for a later sweep.
    An HA instance has no announcementIt waits. A draft announcement is proposed for the first window far enough away.
    Pausing the poolers failsEverything paused so far is resumed, the run is recorded as failed, and the instance is not touched.
    The recreate failsRecorded in minor_upgrades with the error. The instance may be down (see the risk above).
    An HA upgrade stops after the switchoverThe new leader runs the new release, so the instance no longer looks behind. The old leader stays a standby on the old release until something recreates it.
    A major upgrade fails before the cutoverRetried once from a clean target database. Then failMove: the source serves again with no data lost, and the new instance is destroyed.
    A major upgrade fails after the cutoverThe retry and OnFail both run only the finishing steps (route, resume, cleanup, stop the old instance, first backup).
    The worker dies part-wayThe operation's lease runs out and another worker takes it up. See the operations queue.

    Part Z · About

    How the atlas is maintained

    Where the atlas's pages live, how the build reads the code, how to tell which pages the code has moved under, and how to update and publish it.

    What it is made of#

    The atlas lives in docs/atlas next to the code it describes, so a change to one can come with a change to the other in the same pull request.

    PathWhat it is
    pages/*.htmlOne file per page: a JSON header, then the page's HTML. The file name only sets the reading order on disk. The header's part and order set the order in the atlas.
    partials/*.htmlDiagrams used on more than one page or too long to keep inline. {{uid}} in a partial is replaced each time it is included, so marker ids never clash.
    src/The shell, the stylesheet and the page script that every page shares.
    atlas.jsonThe title, the repository URL that code links point to, the parts, where the packages live ("packages": {"root": "internal"}), and what each x-stat counts.
    atlas.mjsThe build. Node 22 and git, no packages.
    site/index.htmlThe built atlas: one self-contained file. Open it from disk or serve it anywhere. It is committed, so reading it never needs a build.

    A page's header#

    Every page starts with a comment holding JSON:

    • verified is the commit the page was last checked against, line by line. Set it only after reading the code at that commit.
    • sources are the files and directories the page describes. A commit that touches any of them after verified marks the page as moved.
    • status: "planned" with a scope list renders a placeholder that says what the page will cover.

    Elements that read the code#

    The build replaces these elements before writing the page. Anything that names code is resolved against the working tree, and links are pinned to the commit that was built.

    ElementBecomes
    <x-ref path="…" symbol="…">text</x-ref>A link to the first line in the file containing symbol. Without symbol, a link to the file. A path ending in / links to the directory.
    <x-code path="…" start="…" [end="…" | lines="n"] [doc] [max="n"] [caption="…"]/>An excerpt with highlighting and line numbers. It starts at the first line containing start and runs to the line containing end, or for n lines, or by default to the brace that closes the block. doc includes the comment above it.
    <x-packages names="a,b"/>, <x-packages rest/>Package cards with size and doc comment, read from the code. A bare name is looked up under the package root in atlas.json (internal/); a name with a slash is a path. rest lists every package under the root that no other x-packages mentions, and the build reports it.
    <x-stat name="…"/>A number counted from the repository, as atlas.json's stats defines it: go-lines-nontest, packages, migrations, migrations-latest, api-operations and others. Each definition names one of the kinds in statKinds (lines of tracked files, packages, files in a directory, the latest of them, pattern matches in a file, a captured value, the schema left by replaying migrations).
    <x-page id="page[--section]">text</x-page>A link to another page or section, with the page's title when there is no text.
    <x-include name="file.html"/>A partial.

    Attribute values are matched literally. Write &quot; for a quote inside one, as in start="if is(&quot;worker&quot;) {".

    The page script also understands a few classes: callout drift for spec and code that disagree, callout risk, callout note, evt for an event name, stepper with stage items whose data-lit lights the diagram groups marked data-stage, and data-go="page" on any diagram group to make it open that page.

    Keeping it current#

    Run these from the repository root:

    CommandWhat it does
    make atlasBuilds docs/atlas/site/index.html and docs/atlas/dist/artifact.html, and prints every reference that no longer resolves.
    make atlas-staleLists each written page and how many commits have touched its sources since it was checked, with the files.
    node docs/atlas/atlas.mjs checkBuilds in memory and fails if any reference is broken. Use it before committing.

    To bring a page up to date: run make atlas-stale, read the diff of the listed files since the page's verified commit, change what the page says, set verified to the commit you checked, then rebuild. Code excerpts and line links update themselves. Prose, tables and diagrams are what need a person.

    What the checks cannot see

    An excerpt anchored on a symbol keeps working when the code around it changes. A broken anchor is reported, but a change in meaning is not. And a later migration that changes what an earlier one created is not noticed while the excerpt points at the earlier one. That is why each page also lists its sources and turns amber when they change.

    Publishing#

    site/index.html is the atlas. Commit it with the change that updated a page. dist/artifact.html is the same atlas without the document wrapper, for hosts that add their own, such as a claude.ai artifact. It is not committed. CI's atlas job runs node docs/atlas/atlas.mjs check on every push, and on a pull request fails when pages, partials, the build or atlas.json changed without a rebuilt site/index.html.
